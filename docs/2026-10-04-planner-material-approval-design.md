## §3 불변 원칙 (이 개편이 지켜야 할 것)

1. **미승인 = 미발송.** 승인 전에 나가는 돈은 담당자가 [만들기]에서 금액을 보고 누른 생성비뿐이다.
2. **승인한 것 = 나가는 것.** 승인 때 접점마다 지문을 각인하고, 발송 선점 직후와 커밋 직전에 다시 계산해 대조한다. 다르면 보내지 않는다(조회 게이트가 아니라 효과가 생기는 자리에서 막는다).
3. **생성은 사람 클릭으로만.** 워커는 AI 자동제작 엔진을 부르지 않는다(엔진의 금액 결박 `campaign-quick.ts:898`이 전제하는 "금액을 본 사람"을 지킨다).
4. **사람이 안 본 문안은 나가지 않는다.** 발송 경로에서 재생성 콜백을 없앤다. 스팸 실패는 재생성 후보 + 재확인 요청으로만 간다.
5. **혜택은 고객사 기입 verbatim.** 행사 행 원본(`benefit_text` · 기간 · 행사명)으로 서버가 카드1을 licensed 고정 조립한다.
6. **문자와 DM은 같은 날 같은 대상이면 1통**(기존 §3-20 캐리어 유지). 쌍 중 하나라도 지문이 어긋나면 **둘 다** 보내지 않는다.
7. **준비 판정은 한 곳.** 재료 창 · 승인 · 발송 당일이 같은 준비 판정 CT를 부른다(F2의 뿌리).
8. **돈은 기존 키 그대로.** 생성 `quick:{c}:{ch}:{token}:{지문}` · 대행 `planner:{회사}:{월}#회차` · 발행 `dm-publish:{id}` · 완성 `email-campaign-complete:{id}` · 문안 `planner-send:{캐리어}`.
9. **같은 효과는 같은 문으로.** 플래너 승인의 DM 발행·이메일 완성은 편집기 경로와 **같은 CT**를 지난다(차단 판정 · 단가 분기 · 경품 동기화 · 차감).
10. **사용자 범위 상시 원칙.** 회사 관리자는 그 회사 행사 전부를 보고 승인한다. 일반 사용자는 자기가 만든 행사만(메모리 상시 원칙 · 되묻지 않음).
11. **조용한 미발송 0.** 재료 없음 · 문안 준비 실패 · 미승인 · 스팸 실패 · 잔액 부족은 전부 사유와 함께 통지하고 화면에 남긴다.
12. **모델명 0 · native dialog 0 · 줄표 0 · 내부 오류문 노출 0**(F4).

- 이메일은 광고 표시를 서버가 강제한다.

### 6-3. 문자 문안 (워커 · Q3)
- 대조 워커가 "문안 없음 · 확인 대기 진입 가능" 접점에 문안을 만든다(`orchestrate` · 크레딧 묶음 · 원가 0) → `exec_meta.copy = { text, inputHash, spam }`.
- **입력 지문**(`inputHash` = 행사명 · 기간 · 혜택 · 상품 · DM 동반 여부 · 대상 축): 확인 대기 중 행사가 바뀌면 문안과 사전 스팸 결과를 무효로 하고 다시 만든다(회의론자 H6).
- 사전 스팸 = DM 링크 자리에 같은 단축 도메인 가짜 코드 · 이 단계 재생성 허용(사람이 보기 전) · 통과본만 확인 화면에 싣는다.

### 6-4. 확인 링크 (Q4 · Q5)
- 토큰 = DB 랜덤 · `meta.preview`에 sha256만 저장 · 주소 `#t=` fragment(`useApproveToken`) → 페이지 GET에 토큰 없음 · 화면이 API 본문으로 전달(접근 로그·Referer 유출 차단) · `Referrer-Policy: no-referrer` · 단축·추적 배관 미경유.
- **리비전당 1개만 유효**(새 링크 발급 · 지문 변경 · 승인 시 폐기) · 만료 = min(발급 + 7일, 첫 발송일 20시 승인 마감). 열람으로는 소비하지 않는다(문자앱 미리보기 · 새로고침 · 로그인 왕복). ⚠ Q4 "1회용"의 해석 = §12 D2.
- 발급 = 대조 워커: 확인 대기 + 첫 발송일 ≤ D+3(**"이하" 판정 + 조건부 스탬프** · 서버가 멈춘 날도 다음 주기가 집는다) · D-1 리마인드 1회 · D-3인데 재료·문안이 준비 안 됐으면 사유 통지(회의론자 M10).
- 수신자 = `notifyOperatorAdmins`(작성자 번호 → 없으면 회사 관리자 · 기존 폴백) · 통지 번호 0이면 캘린더 차단 상자 + 행사 등록 단계 경고.

### 6-5. 행사 승인 트랜잭션 (S3 · 회의론자 C1·C2·C3 반영)
`POST /marketing-planner/events/:id/approve`(로그인 · 화면이 본 지문 `seenHash` + 표시 금액 `shownTotal` 동봉): **월 행 `FOR UPDATE` 트랜잭션 하나**:
1. 월 행 upsert 후 `FOR UPDATE`(없으면 만들고 · cancelled면 새 회차로 approved). 월 status로 선점하지 않는다(C1: 기존 `claimApproval`은 pending만 선점 · 첫 승인 뒤 둘째 행사가 영원히 409). 같은 달 두 행사 동시 승인은 잠금 대기로 줄을 선다.
2. 권한: 관리자 = 회사 전체 · 사용자 = 자기 행사만(§3-10).
3. **지문 · 준비 판정은 언제나 다시 한다**(C2: 옛 "이미 낸 달 = 복구" 생략 분기를 옮기지 않는다). `seenHash ≠ 현재 지문`이면 409 → 화면 재조회.
4. 견적 = 미납 회차 대행 1,000 + DM 발행비(`dmPublishFeeSourceOf` 단가 · 인터랙션 120) + 이메일 완성 50. `shownTotal`보다 크면 409. 합계 `checkCredit`.
5. 대행료 `deductCredit`(엄격 · 실패 = 롤백 + 402) · 회차는 잠금 안에서 계산(§3-12 ABA 차단).
6. 이메일 완성 코어 CT(SMTP · 내용 차단 → `email-campaign-complete:{id}`).
7. DM 발행 코어 CT(**편집기 `POST /api/dm/:id/publish` 본문을 CT로 추출해 두 입구가 같은 문** = 첫 발행 차단 `dmPublishBlocker` → 단가 → `publishDm` → 경품 동기화 → `dm-publish:{id}` `deductCreditSafe` + [CREDIT][MISS]) · C3.
8. 접점마다 `exec_meta.approved = { hash, at, by }` 각인 · 접점 ready · 행사 approved · 확인 링크 폐기 · 커밋.
- 커밋 전 끊김 = 이미 일어난 차감·발행은 남고 다시 승인하면 같은 키로 이어받는다(재차감 0). 사람이 다시 누르지 않으면 대조 워커가 "대행료만 빠진 달 · 발행만 된 DM"을 통지.
- 승인 창 고지 = "DM 발행비 · 이메일 완성비는 승인 뒤 취소해도 돌려드리지 않습니다".
- **[승인 풀기]** = 월 행 잠금 · 접점 producing이거나 발송 시도 표식(`send_started_at`)이 있으면 거부 · approved → briefed · 환불·재차감 0 · 새 리비전.

### 6-6. 승인 직후 실주소 스팸 (회의론자 H7)
- 승인 요청 안에서 돌리지 않는다(수 분 · 504 재클릭). 커밋 뒤 표식(`exec_meta.post_approval_spam = 'pending'`)을 워커가 집어 DM 실주소가 붙은 최종 문안을 검사.
- 실패 = D-0 실패와 같은 규칙: 재생성 후보 1개 + 그 접점(쌍이면 둘 다)만 확인 대기 + 새 링크 · 재차감 0.

### 6-7. 실행부 (발송 당일)

  - 지난 달 미발송 행사 = cancelled · 접점 skipped(검사와 쓰기를 한 문장).

  - 옛 briefed(월 결재 올림) · producing · re_brief · 월 행 pending = 위 표로 옮긴다(9종 전부 · 회의론자 M9).

  - 캘린더에 1회 차단 상자 "결재가 행사별 확인으로 바뀌었습니다 · 확인할 행사 N [보기]".

## §11 회의 기록

**전원 합의**: 생성은 사람 클릭만 · 워커는 엔진 호출 0 · 재료 부품 = MakeInputs · DM·이메일 재료 1벌 · 혜택 카드 서버 licensed 고정 · 승인 지문 각인 + 효과 자리 대조 · 행사 수정 upsert · 확인 본문 1벌(공개·로그인 껍데기) · 로그인 뒤 복귀 장치 · 상태 사전 1벌 + 서버 displayState · 오른쪽 행사 목록 + 시간축 보강 · 폰 고치기는 문자 문안만 · 미승인 접점도 정리·통지 · F1~F10 함께 닫기 · 이관은 실측 뒤.

**갈린 지점과 선택**
- **S3 승인 뒤 비용 시점**: 승인 때(기획 · 회의론자) vs 발송 당일 선점 안(백엔드 · 프론트엔드 · 디자이너). **주재자 선택 = 승인 때.** 근거 = ①DM 실주소가 승인 때 정해져 링크까지 "승인한 문안 = 나가는 문안" ②승인 직후 실주소 스팸 검사로 발송일까지 재확인 여유(당일이면 하루뿐) ③사람이 화면 앞에 있을 때 돈이 확정돼 당일 잔액 부족 보류가 준다 ④"승인 = 실행 확정". 발송 당일 쪽의 장점(승인 때 나가는 돈 = 대행료뿐 · 취소 시 비환불 0)은 승인 창 고지로 대신한다. 회의론자 최종 검증이 이 선택을 받아들였다. **§12 D1에서 Harold 결정.**
- **S4 "1회용"**: 열람 POST 소비(기획 · 백엔드 혼합안) vs 리비전당 1개 + 만료(프론트 · 디자이너 · 회의론자 최종). 선택 = 리비전당 1개 + 만료 + 승인·변경 시 폐기 · 열람 소비 없음. **§12 D2.**
- **S7 결재 화면**: 삭제(기획 · 프론트) vs 결과 탭 유지(백엔드 · 디자이너 · 회의론자). 선택 = 결재 삭제 · "이달 결과"(결과 + 월 취소)만 유지 · 행사별 결과는 행사 상세.

**회의론자 최종 검증 반영**: C1 월 행 FOR UPDATE 트랜잭션(§6-5-1) · C2 지문·준비 판정 생략 분기 금지(§6-5-3) · C3 DM 발행·이메일 완성 코어 CT 추출(§6-5-6·7) · H4 옛 경로 소비처 같은 배포(§10) · H5 쌍 규칙(§6-7) · H6 문안 입력 지문(§6-3) · H7 승인 직후 스팸 워커화(§6-6) · M8 전환 = 멱등 부팅 패스(§8) · M9 9종 전환(§8) · M10 준비 실패 통지(§6-4) · 빠진 것 = 승인 권한(§3-10) · [승인 풀기] 잠금(§6-5) · 수신자 폴백(§6-4) · est_credits(§10) · 취소 집계 잔재(§6-9). 판정 = "C1·C2·C3·H5를 고치면 된다" → 전부 반영.
