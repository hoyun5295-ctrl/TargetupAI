## 0. 한 줄 요약

젬텍은 우리 계정으로 UTF-8을 받지 않는다(0910 실측 10건). 그래서 문자망 글자표(CP949)에 없는 글자(`–` `—` `•` `✓` `❤` 등)가 든 문자는
**가장 가까운 CP949 글자로 바꿔야만** 나간다. QTmsg는 이것을 몰래 하면서 `?`로 망가뜨리고, 비토는 반려하고 가둔다.
이 설계는 **몰래 바꾸지 않고(고객 클릭 또는 계정 동의), 가장 가까운 글자로, 전 경로에서** 내보낸다. 동의가 없으면 즉시 사유와 함께 끝낸다(갇힘 0).

### 0-1. ★0910 밤 결정 (Harold님) — 막고 계도한다
"못 나가는 걸 보내서 `?` 되게 하는 게 맞나? 안 나가는 게 맞고 계도하는 게 맞다."
→ 문자로 못 나가는 글자는 **바꿔 보내지도, `?`로 보내지도 않는다. 막고, 무엇이 왜 안 되는지와 한 번에 고치는 방법을 보여 준다.**
고객이 누른 순간 바꾸는 작성 화면(P2)은 그대로 둔다. **게이트웨이 계정 동의형 자동 대체(§4-3 b·c)와 그 DDL은 하지 않는다.**
대신 P3 = 사유가 보낸 쪽에 반드시 닿게 하는 일 + **나가야 할 것을 막는 결함 정정**(§4-3 e). QTmsg 보다 앞서는 지점 = 몰래 깨뜨려 보내지 않음 · 보내기 전 알림 · 한 번에 고침 · 사유 도달.

### 1-3. CP949 표

**정정(P2 착수 때 실측).** 처음 적은 "8,507자 표"는 WHATWG windows-949 표가 아니었다. Node `TextDecoder('euc-kr')`(ICU)로 만든 표였고,
ICU 는 한글을 KS X 1001 2,350자만 풀어 확장 한글(`똠` `햏` `뷁`)이 빠진다(Node 20.19.4 · ICU 77.1 실측 8,412자).

**기준 = 게이트웨이 Go `golang.org/x/text v0.41.0` `korean.EUCKR`.** 반려가 일어나는 곳이 여기라서다. U+0080~U+FFFF 를 한 글자씩 인코딩해 잰 결과:
ASCII 밖 **17,048자** = 한글 음절 U+AC00~U+D7A3 **11,172자 전부** + 기호·한자 등 5,876자. 집합 SHA-256 = `0a32f153acbbdf7385629ad3d0bfca54944a950d5eef68a265a3e16277d397c8`.
한줄로 표(`frontend/utils/cp949Chars.ts`)는 이 집합에서 만들었고, 계약 테스트가 같은 해시를 강제한다(§7). 브라우저·Node 디코더로 표를 만들지 않는다.
대체표 38행은 이 기준으로 다시 검증했다(실패 0). `–` 는 없고 `―` `·` `√` `♥` `★` `€` `®` 는 있다.
미검증: 확장 한글(`똠` 등)은 게이트웨이가 받지만, 젬텍·통신사를 거쳐 단말에 제대로 보이는지는 재 보지 않았다.

## 2. 불변 조건 (필독)

1. **몰래 바꾸기 0.** 대체는 ① 작성 화면에서 고객이 버튼을 눌렀을 때 ② 게이트웨이 계정에 동의가 켜져 있을 때만 일어난다. 발송 경로의 무동의 치환은 금지(B-0910-4).
2. **대체 대상 = CP949 에 없는 글자만.** CP949 에 있는 글자는 어떤 경로에서도 바꾸거나 지우지 않는다(§3-2 불변 목록).
3. **대체표에 없는 글자는 대체하지 않는다.** 그림 이모지처럼 가까운 글자가 없으면 작성 화면에서 고치게 하고, 게이트웨이에서는 사유와 함께 즉시 영구 실패로 끝낸다.
4. **갇힘 0.** 게이트웨이가 반려하는 모든 검증 오류는 `ErrorCode` + `Retryable=false` 로 돌려준다(작업 E).
5. **원문과 발송본을 함께 남긴다.** 게이트웨이가 대체했으면 원문·바뀐 글자 목록을 기록하고 콘솔·결과 화면에 "대체 발송"을 표시한다.
6. **대체표는 하나.** 한줄로·게이트웨이가 같은 표를 쓰고, 양쪽 계약 테스트가 표의 동일성과 §3 불변식을 강제한다.
7. 인코딩은 계속 0(EUC-KR). UTF-8 전환은 젬텍 회신 전까지 하지 않는다.

### 3-3. 표의 계약

- 원래 글자는 전부 CP949 에 **없어야** 하고, 대체 글자는 전부 CP949 에 **있어야** 한다(테스트로 고정).

- `engine/validator.go` 가 `fmt.Errorf` 대신 코드를 가진 오류를 낸다. 예: `VALIDATION_UNSUPPORTED_CHARS`(글자 목록 포함) · `VALIDATION_SIZE` · `VALIDATION_PHONE` · `VALIDATION_MSG_TYPE` · `VALIDATION_REQUIRED`.
- `session/grpc_server.go` `sendAckPolicyDetails` 가 검증 계열을 **분류 자체로** 영구 실패 처리한다(허용 목록에 한 줄씩 넣지 않는다. 0904 `URL_BLOCKED` 한 건만 넣고 구조를 안 고친 것이 같은 결함의 재발 원인).
- Agent 재배포 없음. API 경로는 기존 `engineRejectionResponse` 가 그 코드를 그대로 내보낸다.

> ⛔ **(b)·(c)는 0910 밤 결정(§0-1)으로 하지 않는다.** 기록으로만 남긴다. 실제 P3 범위 = 아래 (e).

**(b) 계정 동의형 자동 대체.** *(폐기)*
- 발신 계정 설정 `unsupported_char_policy` = `reject`(기본) | `substitute`.
- 인입 단계(검증 전), `encoding=0` 이고 규격 밖 글자가 있을 때:
  `substitute` 이고 모든 글자가 §3 표에 있으면 대체 후 검증을 계속한다. 하나라도 표에 없거나 `reject` 면 (a)의 `VALIDATION_UNSUPPORTED_CHARS` 로 끝낸다.

## 9. 범위 밖 기록 (이번 설계에서 고치지 않음)

- `journey-executor.ts:692-694` 여정 발송 직전 CT-46 치환 = 발송 경로 무동의 치환. BUGS 등재 후 별도 과제.
- CT-46 표가 CP949 에 있는 글자(`★ ♥ ☎ ▶ ※ “”`)를 바꾸거나 지운다. AI 생성 4곳(`journey-ai-generator` · `journey-ai-editor` · `variant-generator` · `operator-message-decorator`)이 쓴다.
- QTmsg(`.58`) 경로도 무동의 치환 중(`?` 로 망가짐). 우리 코드 밖.
- 게이트웨이 `GW_INTERNAL_API_KEY` 가 비어 내부 API(`127.0.0.1:9081`)가 무인증(`clientapi/server.go:649-651`).
- 젬텍 213 결과코드 미등록(정의 확인 뒤 등재. 추정 등재 금지).
- 멀티 텍스트 첨부 MMS/LMS 는 단말에 둘째 텍스트만 보인다(07·09 실측).
