## 1. 목적과 적용 범위

### 1-1. 목적

주식회사 인비토가 운영하는 기업 메시징 서비스 「한줄로」를 통해 **불법스팸이 발송되지 않도록** 사전·발송시점·사후 3단계로 통제하고, 그 통제가 실제로 작동했음을 기록으로 남기는 것을 목적으로 한다.

### 1-2. 적용 범위

| 서비스 유형 | 해당 | 통제 적용 |
|---|:--:|---|
| 웹페이지 발송 (hanjul.ai) | ○ | 이 계획서 전 항목 |
| API 발송 (SDK · 자사몰 연동) | ○ | 발송 시점 통제 전 항목 + 계정 통제(키 발급·출발지 등록) |
| 솔루션·모듈 (싱크에이전트 · 발송 에이전트) | ○ | 동일 |

**모든 발송 경로가 동일한 발송 시점 통제를 통과한다.** 화면마다 검사를 붙이지 않고, 발송이 시작되는 단일 길목(`bulkInsertSmsQueue`)에 통제를 둔 구조이기 때문이다. 발송 경로 17곳이 예외 없이 이 길목을 지난다.

### 1-3. 적용 대상자

- 당사 임직원 중 발송 시스템에 접근하는 자
- 계약을 통해 계정을 발급받은 고객사 및 그 사용자
- 당사 API·모듈을 통해 발송하는 연동 시스템

## 3. 방지 체계 개요 — 3단계

```
[1단계] 계정 통제          [2단계] 발송 시점 통제        [3단계] 사후 조치
누가 보낼 수 있는가         무엇을 보낼 수 있는가          보낸 뒤 무엇을 하는가
─────────────────         ─────────────────           ─────────────────
계약 기반 계정 발급          금칙어 조합 탐지              스팸 신고 접수
발신번호 회선 상한          통신사 스팸 사전 검사          조사·판정
다중 인증(MFA)             (광고) 표기 자동 부착          이용 정지·해지
국외 접근 통제              무료수신거부 번호 자동 부착      이용자 고지
부정사용 명의 대조          수신거부자 자동 제외           조치 이력 보관
계약 종료 즉시 차단         광고 발송 가능 시간 제한        재발 방지 점검

**설계 원칙 셋**

1. **통제는 발송이 시작되는 길목 하나에 둔다.** 화면마다 검사를 복사하면 반드시 빠진 경로가 생긴다.
2. **막는 장치가 고장 나면 무엇을 잃는지 먼저 적는다.** 필터 오류로 전 고객 발송이 멈추는 것이 오탐보다 큰 사고인 구간에서는 통과를 기본값으로 두고, 그 판단 근거를 코드에 남긴다.
3. **모든 조치는 기록을 남긴다.** 처리자·일시·사유·대상이 없는 조치는 조치로 보지 않는다.

## 4. 1단계 — 계정 통제 (누가 보낼 수 있는가)

### 4-1. 계약 기반 계정 발급 (본인확인)

- **공개 회원가입 경로가 없다.** 계정은 계약 체결 후 당사 관리자가 발급한다(코드 전수 확인 — `/signup`·`/register` 공개 라우트 0건).
- 계약 시 사업자등록증·담당자 신원을 확인하며, 계정은 **실제 발송 담당자 단위**로 발급한다.
- 공용 계정 사용은 통제 대상이다 — §4-6 참조.

### 4-2. 발신번호 회선 수 제한

가입자 유형별 상한을 등록 시점에 검사한다. **상한은 신규 등록에만 적용하고 기존 보유분은 변경하지 않는다.**

| 가입자 유형 | 무선 | 유선 |
|---|:--:|:--:|
| 개인 | 3 | 5 |
| 외국인 | 2 | 5 |
| 법인 | 4 | 종사자 수 기준(관리자 입력) |

개인·외국인은 고시 기준값이 자동 적용되며 회사 설정으로 상향할 수 없다. 등록 길목 3곳(관리자 직접 등록·고객사 등록·신청 승인)에 동일 게이트를 둔다.

> 구현 — `utils/sender-line-limit.ts` · `routes/manage-callbacks.ts` · `routes/sender-registration.ts` · `routes/admin.ts`

### 4-3. 다중 인증 (MFA)

- 계정별 **주 인증번호 1개**를 당사 관리자가 계약 담당자 기준으로 등록한다. 복수 번호 등록은 허용하지 않는다 — 다수가 공동으로 쓸 수 있는 인증수단은 기준에 부적합하다.
- 로그인 시 6자리 코드를 SMS로 발송하고, 통과하면 **해당 기기·IP 대역을 24시간 신뢰**한다. 접속 환경이 바뀌면 재인증한다.
- **5회 실패 시 계정을 잠근다.** 잠금 해제는 관리자 조치를 거친다.
- 인증번호 변경 시 그 계정의 신뢰 기기를 전량 해제하고 변경 이력을 남긴다.
- 시행일 이전에는 사전 고지 기간으로 운용한다(시행일 = `[확인 필요 — 확정 시행일]`).

> 구현 — `utils/mfa.ts` · `routes/auth.ts` / 테이블 `users.mfa_phone` · `mfa_challenges` · `mfa_trusted_devices`

### 4-4. 국외 접근 통제

- 국내 할당 IP 대역 목록을 보유하고, **그 대역에 들지 않는 접근을 국외로 판정**한다.
- 판정 지점은 **사람의 로그인**이다. API·모듈(SDK·싱크에이전트)은 별도 인증 체계를 쓰며, 국가가 아니라 **회사별로 사전 등록된 출발지 대역**으로 통제한다. 해외에 본사를 둔 고객사의 연동 서버는 그 대역을 등록해 사용한다.
- **예외는 사유 없이 등록되지 않는다.** 범위(계정·회사 API·회사 에이전트·전역)·대역·사유·승인자·승인일시를 함께 기록하며, 회수 시에도 삭제하지 않고 비활성 상태로 이력을 보존한다.
- 국외 접근은 차단 여부와 무관하게 전건 기록한다.

> 구현 — `utils/geo-access.ts` · `routes/auth.ts` · `routes/admin.ts` / 테이블 `geo_allow_cidrs` · `access_origin_allowlist`

### 4-5. 부정사용 차단 — 결제 명의 대조

- 무통장 입금 신청 시 **입금자명을 계정에 등록된 명의(법인명·회사명·대표자명)와 대조**한다.
- 불일치는 **자동 거절하지 않고 보류**한다. 배우자·경리·법인 담당자 명의 입금이 정상적으로 존재하기 때문이다.
- 보류 건은 고객사가 소명을 제출할 수 있고, **관리자가 소명을 확인했다는 표시 없이는 승인되지 않는다.**
- 승인·반려 결과를 처리자·사유와 함께 계정별로 기록한다.

> 구현 — `utils/fraud-review.ts` · `routes/balance.ts` · `routes/admin.ts`

### 4-6. 계약 종료·정지 즉시 차단

- 계약이 종료(`terminated`)되거나 정지(`suspended`)된 고객사는 **계정 상태와 무관하게 로그인이 차단**된다. 계정 단위 전파에 기대지 않고 회사 단위 게이트에서 판정한다.
- 해지 처리 시 소속 계정을 비활성화하고 **접속 중인 세션을 즉시 무효화**한다.
- 회수 이력(처리자·일시·잠근 계정 수·끊은 세션 수)을 남긴다.

> 구현 — `utils/company-access.ts` · `utils/session-manager.ts`

### 4-7. 공용 계정 통제

- 동일 계정으로 다른 위치에서 동시 접속을 시도하면 **접속 인계 안내**가 뜨고 그 시도가 기록된다. 이 기록이 공용 계정 탐지 지표로 쓰인다.
- 유휴 30분 경과 세션은 만료 처리한다.
- 접속 IP가 과다 분산된 계정은 정기 점검 대상으로 삼아 계정 분리를 안내한다.

> 구현 — `utils/session-manager.ts` / 감사 로그 `login_session_conflict`

### 4-8. 로그인 무차별 시도 차단

동일 (IP, 로그인ID) 조합으로 10분 내 5회 실패하면 30분간 자동 차단한다.

> 구현 — `utils/login-block.ts` / 테이블 `login_blocks`

## 5. 2단계 — 발송 시점 통제 (무엇을 보낼 수 있는가)

**아래 통제는 발송이 시작되는 단일 길목에서 적용되며, 웹·API·모듈 전 경로가 동일하게 통과한다.**

### 5-1. 금칙어 조합 탐지

- 차단정보 요소는 **키워드·URL·전화번호** 세 유형이며, **2~5개의 조합**으로만 규칙을 만든다.
- **단일 키워드 규칙은 만들 수 없다.** "대출" 한 단어로 막으면 금융 고객사의 정상 발송이 전부 막히기 때문이다. 요소가 **전부 일치할 때만** 탐지된다(예: `무직자` + `당일` + `bit.ly`).
- 같은 값을 중복 입력해 조합 하한을 우회할 수 없도록 중복을 접은 뒤 판정한다.
- 회사별 예외를 둘 수 있다 — 금융사에게 "대출"은 정상 업무 용어다.
- 규칙 등록 전 **실제 발송 문안에 돌려보는 오탐 시뮬레이션**을 제공한다.
- 탐지 이력(규칙·고객사·발송 경로·건수·문안 표본)을 보관한다. 문안 표본은 4자리 이상 숫자열을 마스킹해 저장한다.
- KISA 등 외부기관이 공유하는 차단정보를 규칙으로 반입할 수 있다.

> 구현 — `utils/spam-block.ts` · `utils/sms-queue.ts` · `routes/admin.ts` / 테이블 `spam_block_rules` · `spam_block_hits`

**현재 운용 단계** — 탐지 및 이력 확보 단계로 운영 중이다. 발송 차단으로의 승격은 실제 트래픽에서 오탐 여부를 확인한 뒤 시행한다. `[확인 필요 — 승격 예정 시점]`

### 5-2. 통신사 스팸 사전 검사

발송 전 통신사 스팸 판정을 사전에 확인하는 검사를 제공한다. 3개 통신사 테스트 회선으로 실제 판정 결과를 받아, 차단될 문안을 **보내기 전에** 확인한다.

> 구현 — `routes/spam-filter.ts`

### 5-3. 광고성 정보 표기 자동 부착

광고성 메시지에는 본문 앞에 `(광고)`를, 본문 끝에 무료수신거부 번호를 **시스템이 자동으로 부착**한다. 사용자가 지우거나 누락시킬 수 없다.

- SMS: `(광고)` + 본문 + 개행 + `무료거부{080번호}`
- LMS·MMS: `(광고) ` + 본문 + 개행 + `무료수신거부 {080-번호}`

> 구현 — `utils/messageUtils.ts` (CT-AD)

### 5-4. 무료수신거부(080) 연동

- 회사별 080 번호를 등록해 사용하며, 수신자가 080으로 거부 의사를 표시하면 **콜백으로 자동 수집**되어 수신거부 명단에 반영된다.
- 080 이용료는 회사별로 정산한다.

> 구현 — `utils/billing-080.ts` · 나래인터넷 콜백 연동

### 5-5. 수신거부자 자동 제외

- 수신거부 명단은 **계정 단위로 격리**되며, 발송 대상 산출 시 자동으로 제외된다.
- 시스템 이관·통합 시에도 수신거부 명단은 100% 보존한다.
- 엑셀 일괄 등록과 자동 동기화를 함께 제공한다.

### 5-6. 광고 발송 가능 시간 제한

광고성 자동 발송은 허용 시간대(한국 표준시 기준) 밖에서 실행되지 않는다. 예약 시각이 허용 시간대를 벗어나면 등록 단계에서 거부한다.

> 구현 — `utils/autosend-policy.ts` (`isSendableHourKst` · `validateScheduleTimeSendable`)

### 5-7. 발송 대상 0건 시 발송 차단

조건에 맞는 대상이 없을 때 시스템이 조건을 임의로 완화하지 않고 **발송을 차단**한다. 원하지 않은 수신자에게 광고가 도달하는 것을 구조적으로 막기 위한 장치다.

### 5-8. 발신번호 사전 등록 의무

등록·승인되지 않은 번호로는 발송할 수 없다. 발신번호는 증빙 서류 확인 후 승인 절차를 거쳐 등록된다.

② 조사           해당 계정의 발송 이력·문안·대상 규모 확인 (발송 원장 조회)
      ↓
③ 판정           불법스팸 해당 여부 판정. 판정자·근거를 기록
      ↓
④ 조치           경고 / 발송 제한 / 이용 정지 / 계약 해지
      ↓
⑤ 고지           조치 사유·근거·이의 제기 방법을 이용자에게 통지
      ↓
⑥ 이력 보관      ①~⑤ 전 과정을 계정별로 보관
```

### 6-3. 조치 단계 기준

| 단계 | 적용 상황 | 조치 내용 |
|---|---|---|
| 1차 경고 | 경미·최초 위반 | 서면 통지 + 시정 요구 |
| 발송 제한 | 시정되지 않음 / 반복 | 해당 계정 발송 기능 정지 |
| 이용 정지 | 중대 위반 / 반복 지속 | 계정 잠금 + 로그인 차단 |
| 계약 해지 | 고의·중대·시정 불응 | 회사 단위 차단 + 세션 무효화 + 회수 이력 |

### 6-4. 조치 시 이용자 고지

계정 상태를 제한하는 조치를 하면 **상태 변경·세션 무효화·문자 고지·이력 기록이 한 벌로** 처리된다. 고지 없이 상태만 바뀌는 경로를 두지 않는다.

> 구현 — `utils/account-action.ts`

### 6-5. 조치 이력 보관

모든 조치는 감사 로그에 처리자·일시·대상·사유·상세와 함께 기록된다. 보관 기간은 「로그 보관 정책」에 따른다.

## 7. 재이용·재인증 기준

| 상황 | 재개 조건 |
|---|---|
| 1차 경고 후 시정 | 시정 확인 후 즉시 정상화 |
| 발송 제한 해제 | 재발 방지 계획 제출 + 담당자 확인 |
| 이용 정지 해제 | 위반 원인 소명 + 책임자 승인 + 계정 재인증(MFA 재등록) |
| 계약 해지 후 재계약 | 신규 계약 절차 전부 재수행. 이전 위반 이력을 계약 심사에 반영 |

접속 환경이 변경된 경우(신뢰 기기 만료·IP 대역 변경) 다중 인증을 다시 수행한다.

## 9. 점검과 개선

| 주기 | 점검 항목 | 기록 |
|---|---|---|
| 월 1회 | 로그 점검(접속·인증·발송·과금·조치) | 「로그 보관 정책」의 점검 기록 양식 |
| 월 1회 | 금칙어 탐지 이력 확인 · 오탐 여부 확인 · 규칙 조정 | 점검 기록 |
| 월 1회 | 국외 접근 이력 확인 · 예외 승인 유효성 확인 | 점검 기록 |
| 분기 1회 | 계정 권한 점검(퇴사·이동자 회수 여부) | 접근권한 변경 이력 대장 |
| 분기 1회 | 공용 계정 의심 계정 확인 및 분리 안내 | 점검 기록 |
| 수시 | 신규 불법스팸 유형 확인 시 차단정보 규칙 추가 | 규칙 등록 이력 |
