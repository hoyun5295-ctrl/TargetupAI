4. **선불 5% 현재 충전 방식** — 게이트웨이 직접 / PAY 화면 병존 확인됨. PAY 폐기 후 게이트웨이 직접 경로만 유지해도 되는지(운영상) → **답변:**

### 4-1. 세 첨부 정독 검토 (2026-07-07 비토)

**업무절차 PPTX가 드러낸 양방향 구조 (조회 앱 아님 — 잔액 파이프라인의 한 축):**
- **정방향 (중계서버 → sales DB)**: "잔액/통계 DB 자동 push 엔진" — 1분 간격 RSRM_SalesStts(replace) + RSRM_SalesMst.RemAmt 잔액 동기화.
- **역방향 (sales DB → 중계서버)**: "충전금액 자동 수집 엔진" — 중계서버가 **RSRM_FillAmtHist(충전이력)를 읽어가** 자체 엔진 잔액에 반영 후 RsApplyFlag N→Y update. 즉 PAY의 선불 충전 입력이 중계서버 잔액을 올리는 유일 경로일 수 있음.
- 강문희 답변은 **정방향(통계/잔액 적재)만** 다룸. 역방향(충전 공급)을 한줄로가 이어받아야 하는지 미해결.

**흡수 방식 권장 (정답 1개):** 한줄로 측(PG서버 또는 별도 인스턴스)에 RSRM_SalesStts/Mst/FillAmtHist **동일 스키마 MariaDB 수신 테이블**을 만들고, 그 접속정보를 강문희에게 전달 → 게이트웨이는 접속 대상 DB만 교체(코드 최소변경). API안(1.5일 데몬)보다 DB직결이 replace 시맨틱·개발부담 면에서 유리하고, 강문희도 DB직결을 1순위로 답함. 이후 한줄로가 이 테이블을 읽어 Track D 화면 2종 + 슈퍼관리자 정산 합산.

**충전(역방향) 처리 분기:** 현재 활성 에이전트 업체가 후불(PayTp=1)이면 FillAmtHist는 사실상 死데이터 → 통계/잔액 정방향만 이관하면 끝. 선불(PayTp=2)이 있으면 한줄로가 FillAmtHist 상당 데이터를 새 DB에 써주고 중계서버 수집엔진이 그걸 읽게 목적지 변경 필요. → **RSRM_SalesMst.PayTp 분포부터 확인**(RSRM_SalesMst 재요청 시 동봉).

**강문희에게 넘길 것 (목적지 변경 발주 시):** ①수신 DB 종류(MariaDB 동일)·호스트·포트·DB명·계정/비번 ②54·57·58 인바운드 방화벽 open 확정 ③replace 기준키 = (DestDt, CustId, StoreId) 단위 삭제 후 유형별 재삽입 여부 확정 ④역방향 충전 수집을 유지할지(선불 존재 시).
