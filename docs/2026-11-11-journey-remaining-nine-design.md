## 4 처방

### 4-1 D1 — 멈춤은 진행 중인 실행에만 쓴다(뿌리 R93 새 「상태를 바꾸는 쓰기가 앞 상태를 조건으로 걸지 않아 종결을 비종결로 덮는다」)

1. `autoPauseExecution` 의 갱신 문장 = `UPDATE journey_executions SET status = 'paused' WHERE id = $1 AND status = 'active'`. 0행(이미 끝났거나 멈춘 실행)이면 상태는 그대로 둔다.
2. 멈춤 기록(`journey_step_pause_logs`)은 **상태를 바꾼 때만** 남긴다(0행 = 기록 0 · `console.warn` 한 줄 · 돌려주는 값 `'paused' | 'skipped'`). 옛: 끝난 실행에도 기록을 남겼다 → 기록 = 실제 멈춤과 1 대 1.
3. 이미 덮인 실행(운영 실측 = 켜진 여정의 멈춘 실행 0행 · K16) = 고칠 행 없음. 배포 전 P1 ① 로 「끝난 시각이 있는 멈춘 실행」을 다시 센다(0 이 아니면 그 행을 completed 로 되돌리는 한 줄을 그때 제시).

### 4-2 D2 — 여정 멈춤이 먼저 성공해야 나머지를 한다 · 실행 멈춤은 여정이 멈춘 상태일 때만(뿌리 R45 넓힘 「시스템이 멈췄는데 사람에게 안 닿는다」 · R12 「판정과 쓰기가 다른 잠금」)

4. `autoPauseExecution` 을 **계보 잠금 안의 조건부 멈춤**으로 바꾼다(같은 함수 · 같은 트랜잭션): `BEGIN` → `lockLineage(client, journeyId)`(다시 켜기 · 옵션 저장 · 감시와 같은 잠금) → `SELECT status FROM journeys WHERE id = …` → **여정이 `paused` 일 때만** 처방 1 의 갱신 + 기록 → `COMMIT`. 여정이 멈춰 있지 않으면(멈춤이 실패했거나 그 사이 담당자가 다시 켰다) 아무것도 쓰지 않고 `'skipped'`.
   - 다시 켜기는 계보 잠금을 쥔 한 트랜잭션에서 켜고 되살린다(K6) → 「여정 멈춤 → 다시 켜기 → 실행 멈춤」 순서에서 실행 멈춤은 켜진 여정을 보고 건너뛴다 = 켜진 여정 + 멈춘 실행 0. 「여정 멈춤 → 실행 멈춤 → 다시 켜기」 = 되살리기가 그 실행을 깨운다.
   - 잠금 순서 = 계보(advisory) → 실행 행. 여정 행은 잠그지 않고 읽는다(완료 처리의 「실행 → 여정 통계」 순서와 엇갈리는 행 잠금 0 · Codex 설계 1R #6 의 교착 사슬을 만들지 않는다).
5. 실행기의 여섯 자리 순서를 하나로: **① `pauseJourney`(실패 = 던진다 · 그 자리의 나머지를 하지 않는다) → ② 그 자리의 실패 기록 · 전진(있는 자리만) → ③ `autoPauseExecution`(실패 · 건너뜀 = 경고 한 줄)**.
   - ③ 적재 시도 상한 = 여정 멈춤 → 실패 기록 → 전진 → 실행 멈춤. 여정 멈춤이 던지면 전진하지 않는다 → 시도 기록이 그대로라 다음 회차가 다시 상한 갈래로 와 멈춤을 다시 시도한다(다시 보내기 = 표식 문장의 상한 조건이 막는다 · Codex 설계 1R #1).
   - ④ 안 들어감 재시도 소진 = **소진 판정을 그 칸의 시도 기록 수 한 기준으로 맞춘다**(`loadAttemptsSql(e, 칸) >= LOAD_ATTEMPT_MAX` · 옛 `error_count >= 1` 판정을 버린다 K7b · `error_count` · `last_error_at` 은 진단 칸으로 계속 쌓는다 · Codex 설계 2R). 첫 실패(시도 1) = 5분 뒤 재시도 · 둘째 실패(시도 2) = 소진 = 여정 멈춤 → 실패 기록 → 전진 → 실행 멈춤(옛: 멈춤 → 전진 = 마지막 칸이 완료되지 않아 되풀이 K7). 전진이 진행 중 상태에서 일어나 마지막 칸 = 완료(③ 과 같은 뜻 = 「다시 보내지 않고 실패로 넘김」).
     여정 멈춤이 던지면 전진하지 않는다 → 시도 기록이 2 그대로 → 다음 회차는 **표식 앞 상한 확인(③)** 이 그 실행을 잡아 다시 싣지 않고 같은 순서로 멈춤을 다시 시도한다(④ 와 ③ 이 같은 기준이라 그 사이에 적재가 끼지 않는다). 재시도 문장의 조건도 같은 기준(`< LOAD_ATTEMPT_MAX`).
     달라지는 것 = 앞 칸에서 한 번 실패했던 실행도 뒤 칸에서 「처음 + 다시 한 번」을 받는다(`LOAD_ATTEMPT_MAX` 주석의 뜻 그대로 · 옛: 뒤 칸 첫 실패에 바로 멈춤).
   - ① ② ⑤ ⑥ = 여정 멈춤 → (실패 기록) → 실행 멈춤(전진 없음 · 지금 뜻 그대로).
   - 전진으로 완료된 실행 = 처방 1 로 멈춤이 걸리지 않는다(완료 유지).
6. 호출 자리의 바깥 try / catch 는 그대로(실패를 삼키되 로그). 달라지는 것 = 삼켜도 남는 상태: 여정 멈춤 실패 = 「켜진 여정 + 진행 중 실행 + 시도 · 오류 횟수 그대로」(다음 회차 다시 시도) · 실행 멈춤 실패 = 「멈춘 여정 + 진행 중 실행」(다시 켜면 이어 간다).

### 4-3 D3 — 차감 실패 = 시도로 세지 않는다(뿌리 R8 넓힘 「시도 횟수가 하지 않은 시도를 센다」)

7. 차감 실패 갈래의 표식 삭제 문장을 한 문장으로 넓힌다: 표식을 지우면서 **그 실행의 그 칸 · 그 캠페인 시도 기록 가운데 맨 뒤 하나**를 같이 지운다(`WITH del AS (DELETE … RETURNING execution_id) UPDATE journey_executions e SET error_log = <맨 뒤 일치 항목을 뺀 배열> WHERE e.id IN (SELECT execution_id FROM del)`).
   - 시각 비교를 쓰지 않는다(시도 기록의 시각은 마이크로초 · 노드가 읽은 표식 시각은 밀리초). 맨 뒤 일치 항목 = 방금 표식 문장이 남긴 것: 실행기는 (여정 · 칸) 묶음을 한 번에 하나만 처리하고 그 실행의 시도 기록을 쓰는 자리는 표식 문장 하나다(지우는 자리 = 전진 문장 · 이 처방).
   - 표식이 지워진 실행에만 건다(`del` 이 돌려준 실행 = 표식이 아직 `sending` 이던 것 · 다른 자리가 이미 확정 · 정리한 표식은 건드리지 않는다).
   - 조각 = `dropLastLoadAttemptSql(실행 별칭, 칸 자리표, 캠페인 자리표)`(실행기 안 · `loadAttemptsSql` 옆).
8. 시도 기록을 미리 남기는 구조(표식과 한 문장)와 상한 판정은 그대로.

### 4-4 D4 — 월 예산 달 = KST(뿌리 R18 넓힘 「판정 시계」)

9. `l.sent_at >= date_trunc('month', NOW())` → `l.sent_at >= ${KST_MONTH_START_SQL}`(`stats-aggregation.ts` 조각 재사용 · 새 조각 0).
10. 계약 = 여정 유틸에서 `date_trunc('month', NOW())` 를 KST 변환 없이 쓰는 글자 0.

### 4-5 D5 — 여정 알림톡 줄도 행 단위 정책(뿌리 R1 넓힘 「같은 판정을 경로마다 다른 옵션으로 부른다」)

11. 실행기의 `resolveAlimtalkFallback(…)` 호출에 `{ emptyContentsPolicy: 'disableFallback' }` 를 넘긴다(직접발송 두 길과 같은 정책 = 그 고객만 대체 없음 · 알림톡 본 발송은 그대로).
12. 정책은 빈 문안에만 걸린다(CT 그대로) — 제목 없음 같은 설정 결함은 행 단위에서도 지금처럼 던진다.
13. 강등 수는 단위마다 한 줄로 센다(번호 원문을 로그에 쌓지 않는다 = 직접발송과 같은 꼴).

### 4-6 D6 — 칸 지우기 가드 = 미완료 실행(뿌리 R87 넓힘)

14. 가드 문장의 `status = 'active'` → `openExecutionSql('e')`(진행 중 + 멈춤 · 조각 재사용). 안내 문구는 그대로.
15. 그 자리 주석(「paused 를 넣지 않는 근거」)을 지금 사실로 고친다(되살리기가 있다 · 멈춘 실행도 번호를 다시 읽는다).
16. 영향 = 멈춘 실행이 그 칸 뒤에 걸려 있는 여정은 그 칸을 못 지운다(여정을 다시 켜 그 실행이 끝나거나 · 여정을 끝낸 뒤 = `endJourneyLineage` 가 멈춘 실행을 종결한다). 덜 지우는 쪽 · 지금 운영에 해당 실행 0(K16).

### 4-7 D7 — AI 수정은 알림톡 칸을 만들지도 바꾸지도 못한다 · 끝 칸은 글이 없다(뿌리 R91 넓힘)

17. 결과의 카카오 칸마다 **템플릿 코드로** 원래 패키지의 카카오 칸을 찾는다(배열 자리로 찾지 않는다 · Codex 설계 1R #4): 결과 칸의 템플릿 코드가 비어 있지 않고, 원래 패키지에 그 코드의 카카오 칸이 **정확히 하나**이고, 결과에도 그 코드의 카카오 칸이 **정확히 하나**일 때만 대응이 선다.
18. 대응이 선 칸 = 알림톡 설정 여섯(프로필 · 템플릿 코드 · 변수 맵 · 대체 종류 · 대체 문안 · 대체 제목)과 본문 · 제목 · 광고 여부를 **원래 칸 값으로 덮는다**(AI 답 무시 · 자리 · 대기 시간은 AI 답 = 순서 바꾸기 · 대기 조정은 된다).
19. 대응이 서지 않는 카카오 칸(코드 없음 · 원래에 없는 코드 = 새 알림톡 칸 · 같은 코드가 여럿) = **수정 전체를 적용하지 않는다**(「알림톡 칸은 AI 로 새로 만들거나 바꿀 수 없어요. 알림톡 칸은 직접 고쳐 주세요.」 · Codex 설계 1R #3 = 새 칸의 변수 맵 글자 값 · 대체 종류로 관문 밖 글이 나가는 길을 없앤다). 원래 카카오 칸을 결과에서 뺀 답(칸 삭제)은 그대로 된다.
20. 끝 칸(`end`) = 대기 · 조건 칸과 같이 본문 · 제목을 비운다.
21. 변수 꼴 관문(C126 `revisedGuarded`)은 그대로.

### 4-8 D8 — 붙이기 · 떼기 = 저장 대기일을 새 시작의 최솟값 이상으로(뿌리 R87 넓힘)

22. 두 UPDATE 에 `reentry_cooldown_days = CASE WHEN allow_reentry THEN GREATEST(COALESCE(reentry_cooldown_days, 0), CASE WHEN auto_reentry_enabled THEN $자동 ELSE $기본 END) ELSE reentry_cooldown_days END` 를 더한다. 값 = `reentryFloorDays(새 시작)` · `autoReentryFloorDays(새 시작)`(계약 CT · 숫자 바인드 둘) = 저장 검증(`journey-options-validator`)이 재진입 저장에 거는 최솟값과 같은 함수.
23. 줄이지 않는다(올리기만) · 재진입 허용 · 자동 스위치는 건드리지 않는다 · 재진입 불가 여정은 그대로.

### 4-9 D9 — 감시의 첫 칸 = 넣는 트랜잭션 안에서 읽는다(뿌리 R12 넓힘)

24. 두 넣기 길(`finishCursorBatch` · `enqueueCandidates`)에서 첫 발송 시각에 쓰는 첫 칸을 **계보 잠금 뒤 · 넣기 직전에 그 연결로 다시 읽는다**(자동 재진입 워커 C126 과 같은 자리). 잠금 앞의 읽기는 「칸이 없으면 넣지 않는다 · 커서 전진」 판단에만 남긴다.
   - 칸 편집은 계보 잠금을 쥐지 않는다(K15) → 넣기 직전에 읽은 값과 편집 커밋이 엇갈려도 「넣은 뒤 편집」과 같은 순서다(직렬 순서 하나가 선다). 없어지는 것 = 뽑기 · 상한 판정에 걸리는 시간만큼 벌어지던 창.
   - 잠금 안에서 첫 칸이 없어졌으면 넣지 않는다(되돌림 · 커서 그대로 = 지금의 「진입이 닫혔다」와 같은 갈래).
25. 행 잠금 · 지문 대조는 더하지 않는다(재진입 · 상한 · 하루 몫은 세대 K14 가 이미 막는다 · 감시가 여정 행을 잠그면 진입 교체 닫기와 완료 처리의 잠금 순서가 엇갈린다 · Codex 설계 1R #5 · #6).

```sql
-- P1 ① 끝난 시각이 있는데 멈춤으로 남은 실행(D1)
SELECT j.company_id, COUNT(*) AS paused_with_end FROM journey_executions e JOIN journeys j ON j.id = e.journey_id WHERE e.status = 'paused' AND e.completed_at IS NOT NULL GROUP BY 1 ORDER BY 2 DESC;
-- P1 ② 켜진 여정에 멈춘 실행(D2 흔적 · C126-P1 ② 와 같은 문장)
SELECT j.company_id, COUNT(DISTINCT j.id) AS journeys, COUNT(*) AS paused_executions FROM journey_executions e JOIN journeys j ON j.id = e.journey_id WHERE e.status = 'paused' AND j.status = 'active' GROUP BY 1 ORDER BY 3 DESC;
-- P1 ③ 재진입 허용 여정의 시작 사건별 저장 대기일(최솟값 아래인 줄을 계약 값과 대조: 휴면 7 · 그 밖 상태형 1)
```

    - **기록하는 회차** = 창을 다 본 회차(뽑은 수 < 회차 상한) 또는 하루 몫 여정의 회차(그날 몫 = 종전 뜻). **기록하지 않는 회차** = 회차 상한(JOURNEY_COUNT_CAP)으로 잘린 회차(다음 5분 회차가 같은 창으로 이어서 · 34 의 창 안 제외가 이미 넣은 고객을 뺀다) · 상한 초과로 멈춘 회차 · 넣기가 되돌려진 회차 · 예외.
    - **끝난 회차 = 이 회차가 기록 문장을 돌렸고 그 문장이 1행을 돌려준 회차 하나뿐**(★ Codex 설계 4R · 5R). 날짜형 시작(칸 있음)의 회차 결과에 `truncated`(= 1시간 쉼에 넣지 않는다 · 다음 5분 회차가 다시)를 「그렇지 않다」로 싣는다 — 회차 상한으로 잘려 기록 문장을 돌리지 않은 회차 · 넣기가 되돌려진 회차(세대 · 날짜 · 진입 닫힘) · 조건이 바뀌어 기록 문장이 0행인 회차 전부. 앞 회차가 올려 둔 기록은 이번 회차의 끝남을 대신하지 않는다(그날 22시에 끝난 뒤 23시 회차가 잘리면 23시 회차는 끝나지 않은 회차 = 5분 뒤 다시).
    - **회차를 여는 한 문장이 그날을 미완료로 먼저 내려 둔다**(★ Codex 구현 1R · 2R): `OPEN_STATE_SCAN_SQL` = 여정 행을 잠가 옛 기록을 읽고, 기록이 오늘 이상이면 어제로 내리고(더 옛날 · 없음은 그대로), 기준일과 간격(오늘 − 옛 기록)을 돌려준다. 끝났을 때만 기록 문장이 오늘로 올린다 → 회차가 잘리든 · 상한 초과로 멈추든 · 예외로 끊기든 · 프로세스가 죽든 그날은 미완료로 남고 다음 날 회차가 그날의 창을 다시 본다. 「끝난 뒤에 되돌리는 쓰기」를 두지 않는다(그 쓰기가 실패하면 되돌릴 길이 없다 — 구현 1R 에 넣었다가 2R 에 순서를 뒤집어 지웠다).
    - **한 여정의 날짜형 회차는 프로세스 사이에서도 하나씩**(★ Codex 구현 3R): 감싸는 함수 `runJourneyTriggerRound` 가 회차 전체(열기 → 뽑기 → 넣기 → 기록)를 여정마다 하나인 세션 잠금(`withJourneySessionLock('journey-date-scan', 여정)` · 잡기 시도) 안에서 돈다. 못 잡으면 열지도 않고 넘긴다(다음 5분 회차가 다시). 잠금의 꼴 = 한 번 보내기 잠금(`withOneShotLock`)과 같은 공용 함수 하나(그 함수는 같은 이름 · 같은 키로 이것을 부른다). 값을 비교해 겹친 회차를 가려내려던 장치(2R)는 같은 값으로 연 두 회차를 못 가려 지웠다.
    - 감싸는 함수는 끝나지 않은 회차(기록 문장 1행이 아님)를 truncated 로 돌려 1시간 쉼에 넣지 않는다 — 본문의 나가는 길마다 챙기지 않는다(설계 4R · 5R · 구현 1R 같은 부류).
    - 넣기 앞 기준일 확인과 기록 문장의 날짜 조건 = **지금 시각**(`clock_timestamp` · CT `KST_CLOCK_DATE_SQL`) — `NOW()` 는 BEGIN 때 굳어, 계보 잠금을 기다리다 자정을 넘긴 트랜잭션이 어제로 본다(★ Codex 구현 1R).
37. 다시 켜기 · 붙이기 · 떼기 · 새 판 = 수정 0. 멈춘 동안은 훑지 않으니 기록이 그대로 남고, 다시 켠 첫 회차가 간격으로 m 을 얻는다(사람 멈춤 · 시스템 멈춤 · 서버 정지 같은 규칙 — K27 의 사건 규칙과 다른 이유 = 사건은 지난 일이고 생일 · 소멸일은 앞날이다). 떼기로 시작이 생일로 돌아온 여정 = 오래 멈췄다 켠 것과 같은 뜻(지나지 않은 대상만).

- S1 추가: 날짜형 여정의 `last_state_cursor_on` 이 KST 오늘인지(배포 다음 날) · 선불 여정 알림톡 차감 행이 생기면 설명 꼬리 · 정산 로그.

```sql
-- P1 ④ 선불 회사의 켜진 여정 알림톡 칸(배포 뒤 차감 단가가 바뀌는 대상)
SELECT j.company_id, j.id AS journey_id, s.step_order, COALESCE(s.alimtalk_next_type, '(빈 값 = L)') AS next_type, c.cost_per_kakao, c.cost_per_sms, c.cost_per_lms FROM journeys j JOIN companies c ON c.id = j.company_id JOIN journey_steps s ON s.journey_id = j.id WHERE c.billing_type = 'prepaid' AND j.status = 'active' AND s.channel = 'kakao' ORDER BY 1, 2, 3;
-- P1 ⑤ 날짜형 시작 여정(생일 임박 · 연 단위 포인트 소멸)의 상태
SELECT j.status, j.trigger_event, COUNT(*) AS journeys FROM journeys j WHERE j.archived_at IS NULL AND j.status IN ('active', 'paused') AND (j.trigger_event = 'customer.birthday_approaching' OR (j.trigger_event = 'customer.points_expiring' AND j.trigger_filters->>'expiry_mode' = 'annual_date')) GROUP BY 1, 2 ORDER BY 1, 2;
```
