## §1 이 문서가 생긴 경위

2026-08-09, 게이트웨이 서버(58.227.193.65)가 UFW 설정으로 SSH 락아웃되어 해외 체류 중 접속 불가 상태가 됐다. 복구 과정에서 우리 자산 목록에 그 서버가 아예 없었고 콘솔 경로도 몰랐다는 사실이 드러났다. 같은 날 Harold님이 "형님(보안 실무자)이 5분이면 뚫는다고 한다"는 문제 제기와 함께 보안 체계 확립을 지시했다.

**목표를 정직하게 정의한다.** "절대 뚫을 수 없는 시스템"은 존재하지 않는다. 우리가 세울 수 있는 목표는 셋이다.
1. 공격 비용을 우리가 지키는 가치보다 비싸게 만든다 — 자동화 대량 공격은 시도할 자리조차 없게.
2. 뚫려도 가져갈 수 있는 것을 최소화한다 — 한 층이 무너져도 즉시 노출되지 않게.
3. 시도가 있으면 우리가 안다 — 몇 달 뒤에 알게 되는 상황을 없앤다.

## §3 현재 상태 (2026-08-09 실측)

### 3-1. 외부 노출 — 58.227.193.62 (메인)
**(측정 · 일본 노트북에서 외부 접속 테스트)** 인터넷에서 닿는 포트는 **22 · 80 · 443 셋뿐**이다.
차단 확인: 3000 · 3001 · 9001 · 9002 · 9010 · 23388 · 5432 · 3306 전부 불통.

### 3-2. 서비스 바인딩 (측정 · `ss -tuln`)
| 포트 | 바인딩 | 정체 | 외부 도달 |
|---|---|---|---|
| 22 · 80 · 443 | 0.0.0.0 | SSH · nginx | 도달 |
| **23388** | **0.0.0.0** | `pay-ingest-db` MariaDB (문서: OPS.md) | 차단됨(방화벽) |
| 3000 · 3001 | * (전 인터페이스) | 애플리케이션 (미확인) | 차단됨 |
| 9001~9011 (11개) | * (전 인터페이스) | **미확인** | 차단됨 |
| 로컬 전용 소켓 6개 | 127.0.0.1 | 정상 | — |

**판정:** 지금 안전한 이유는 서비스가 안전해서가 아니라 **방화벽 층이 가려주고 있어서다.** 방화벽 규칙 하나가 바뀌면 결제 데이터베이스가 즉시 인터넷에 노출된다. CLAUDE.md의 "Docker 포트 바인딩은 반드시 127.0.0.1, 0.0.0.0 절대 금지"(랜섬웨어 교훈)를 23388이 위반한 상태다.

### 3-3. 23388 실제 사용자 (측정)
현재 연결은 `127.0.0.1` 하나뿐. 컨테이너 로그의 접속원은 `172.17.0.1`(도커 내부 게이트웨이)뿐.
→ **강문희 쪽 PAY 데이터는 이 포트로 직접 들어오지 않는다.** 로컬 백엔드만 쓴다. 따라서 127.0.0.1 바인딩으로 내려도 수집이 끊기지 않는다. (PAY 데이터의 실제 유입 경로 = **미확인**, 확인 과제)

### 3-4. SSH (측정)
`PermitRootLogin no` · **fail2ban 활성** · 비밀번호 인증은 설정 미명시로 **기본값(허용)** 동작 · `auth.log` 비밀번호 실패 **513건**.
→ root 차단과 fail2ban은 제대로 되어 있다. 남은 위험은 비밀번호 인증이 켜져 있다는 것 하나.

### 3-5. 방화벽 3층 구조 (문서 + 측정)
1. **포티게이트** — 하나로호스팅에 요청으로 변경(패널 안내문 근거)
2. **브릿지 방화벽** — 하나로호스팅 웹 패널에서 셀프 관리. 현재 62 정책은 `ALL/TCP/출발지 ALL/허용` + PING 허용 + 기본 차단
3. **UFW** — 서버 OS 레벨

**중요:** 브릿지가 전 TCP 허용인데 외부에서 23388이 막힌다 → 실제 차단은 포티 또는 UFW가 하고 있다. **어느 층인지 미확인.** 패널 화면으로 노출을 판단하면 틀린다는 것이 오늘 실증됐다 — 노출은 반드시 밖에서 측정한다.

### 3-6. 계정·자격증명
- 슈퍼관리자: OTP + 백업코드 + 단일 세션 회전 + 로그인 실패 감사 + IP 차단 **(문서·코드 확인)**
- **하나로호스팅 패널: 2단계 인증 없음 (Harold 확인).** 이 계정이 방화벽의 열쇠이며 현재 단일 실패점이다. 재설정 경로인 **이메일 계정의 2FA 여부 = 미확인**
- 고객사 관리자 2FA 여부 = **미확인**

### 3-7. 코드·저장소 (내가 직접 확인)
- 정상: helmet · CORS 콜백 검증 · rate limit · 요청 본문 크기 제한 · `trust proxy 'loopback'`(X-Forwarded-For 위조로 IP 차단 우회 방지)
- 결함: `sync-agent/.env.bak`이 커밋 `c5f23938`(2026-04-18)부터 추적 중. 값은 테스트용으로 보이나 **재사용 여부는 Harold 확인 필요**
- 결함: `.gitignore`에 개인키 패턴(`*.pem`·`id_rsa`) 없음 → 키를 저장소에 떨어뜨리면 커밋된다. `.env`는 정상 작동(`git check-ignore` 확인)
- 위생: `.gitignore`에 NUL 바이트 70개 → 파일이 바이너리로 분류돼 검색 불능
- 검토 필요: 공개 뷰어 2개(모바일 DM · 거래내역서 확인)가 인라인 스크립트 때문에 helmet 앞에 마운트돼 보안 헤더 미적용. 의도된 선택이나 자체 CSP 필요

### 3-8. 자산 관리
`.65`가 우리 문서 어디에도 없었다. 서버별 **콘솔 경로(KVM 등)가 문서화돼 있지 않다.** 오늘 복구 지연의 직접 원인.

## §4 설계 원칙 (앞으로 어길 수 없는 것)

1. **모든 방어는 두 겹 이상.** 한 층이 무너져도 즉시 노출되지 않아야 한다. 방화벽이 유일한 방어인 자산(현재 23388)은 결함으로 본다.
2. **관리 평면과 서비스 평면을 분리한다.** 서비스는 80·443만 공개, 관리 접속(SSH 등)은 VPN 안으로.
3. **잠그기 전에 두 번째 문을 확인한다.** 방화벽·인증을 조이는 작업은 대체 경로(콘솔·예비 허용)를 실측으로 확인한 뒤에만. (오늘 .65 교훈)
4. **노출 판정은 패널이 아니라 외부 측정으로 한다.** (3-5 실증)
5. **비밀은 사람 기억이 아니라 도구에.** 재사용 금지, 매니저 생성, 대화·문서·메신저에 남기지 않는다.
6. **탐지 없는 방어는 절반이다.** 뚫린 것을 아는 장치가 없으면 몇 달간 모른다.
7. **되돌릴 수 있는 순서로만 조인다.** 각 단계에 롤백 방법을 미리 적는다.

## §5 단계별 실행 계획

### Phase 0 — 지금 즉시 (서비스 영향 0 · 롤백 불필요)
| 항목 | 내용 | 롤백 |
|---|---|---|
| 0-1 | **하나로호스팅 비밀번호 교체** — 매니저 생성 20자+ 무작위, 재사용 0 | — |
| 0-2 | **그 계정 이메일의 2FA 확인·활성화** — 재설정 경로가 실질 열쇠 | — |
| 0-3 | `.env.bak` git 추적 제거 + 값 재사용 여부 확인 | 커밋 되돌리기 |
| 0-4 | `.gitignore`에 개인키 패턴 추가 + NUL 바이트 제거 | 파일 복원 |

### Phase 1 — 자산·경로 확정 (측정만)
전 서버(.62 · .59 · .58 · .54 · .65)의 외부 노출 포트를 **밖에서** 측정하고, 서버별 **콘솔(KVM) 경로**를 확인해 OPS 문서에 등재한다. 콘솔 경로가 없는 서버는 그 사실 자체를 위험으로 기록한다. **이 단계가 끝나기 전에는 어떤 잠금 작업도 하지 않는다.**

### Phase 2 — WireGuard 구축 (추가만 · 아무것도 닫지 않음)
62에 WireGuard를 세우고 노트북에서 접속을 확인한다. UDP 포트 하나를 브릿지 방화벽에 여는 것 외에 변경 없음. 롤백 = 서비스 중지 + 포트 회수. **이 단계에서는 SSH를 그대로 둔다.**

### Phase 3 — 관리 평면 이전 (Phase 1·2 완료 후에만)
SSH 키를 만들고 키 접속을 확인한 뒤, 비밀번호 인증을 끄고 SSH를 VPN 대역에서만 받도록 좁힌다. 롤백 = 브릿지 방화벽 패널에서 현재 IP 임시 허용(웹에서 가능하므로 영구 락아웃 불가). **콘솔 경로가 확인되지 않은 서버는 이 단계를 하지 않는다.**

### Phase 4 — 호스트 심층 방어
23388을 `127.0.0.1` 바인딩으로 내린다(로컬 전용 사용 확인됨). 3000·3001·9001~9011의 정체를 확인해 외부 노출이 불필요한 것은 전부 로컬 바인딩으로. 자동 보안 업데이트 활성화 + 재시작 창 정례화(현재 62에 업데이트 46건·재시작 대기).

### Phase 5 — 애플리케이션 계층
노출면이 80·443로 좁혀지면 여기가 주 전선이 된다. 권한 검사(IDOR)·주입·업로드·외부 연동 콜백·의존성 취약점을 점검한다. 이미 Codex 적대검증으로 권한 구멍을 여러 번 잡아온 이력이 있으므로 새로 만들 것이 아니라 대상을 보안 축으로 넓힌다.

### Phase 6 — 탐지와 복구
고객 데이터 대량 조회·비정상 대량 발송에 알림. 백업 복구 훈련(백업은 돌고 있으나 복구 실측 = 미확인). 침해 대응 플레이북 1장(통지·신고 시한 포함).

### Phase 7 — 외부 검증
형님께 범위·기간을 서면으로 정해 침투 테스트 정식 의뢰. 보고서가 우리 우선순위표를 대체한다.
