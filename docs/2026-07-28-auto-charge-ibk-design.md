> **호출어**: "자동충전 개발재개"
> **상태**: 설계 확정 · **착수 대기** (기업은행 오픈API 이용 승인 대기 중)
> **작성**: 2026-07-28 · Harold 지시로 확정된 사항만 담는다. 추정은 "미검증"으로 표기했다.
> **연결**: 충전 요청·실행 축 = [docs/2026-07-24-agent-prepaid-charge-design.md](2026-07-24-agent-prepaid-charge-design.md) §5-3(실행)·§5-4(요청)

## 0. 무엇을 만드는가

지금은 고객사가 충전을 요청하면 **직원이 입금을 눈으로 확인하고 손으로 충전**한다.
이걸 **입금 감지부터 충전·완료 통지까지** 끊지 않고 잇는다.

```
고객사 충전 요청(금액·입금자명·충전대상)
  → 접수 즉시 안내 문자 (계좌·금액·입금자명·계정명)
  → 고객 입금
  → 기업은행 거래내역 조회로 감지
  → 금액·입금자명 매칭
  → 충전 실행
  → 완료 문자
```

**대상 지갑은 둘 다다** — 웹 선불과 게이트웨이(발송ID) 선불. 두 지갑은 별개이고 섞이면 안 된다
(0727에 `deposit_requests` 재사용을 폐기한 이유가 "그 승인은 웹 `balance`를 올린다 — 지갑이 다르다"였다).

**입금 계좌: 기업은행 585-028893-01-011**

## 1. 확정 사항

### 1-1. 문자 문안 2종 (확정 — 이대로 등록)

둘 다 **LMS**다(실측 334바이트 / 232바이트 — SMS 90바이트 초과). LMS는 제목이 필수다.
정보성 통지라 광고 표기·수신거부 문구는 넣지 않는다.

**① 충전 요청 접수** — 제목 `[한줄로] 충전 요청 접수 안내`

```
[한줄로 안내]

{업체명} 고객님,
{요청일시}에 {요청금액}원 충전 요청이 접수되었습니다.

아래 계좌로 입금해 주시면 자동으로 충전됩니다.

· 입금 계좌 : 기업은행 585-028893-01-011
· 입금 금액 : {요청금액}원
· 입금자명 : {입금자명}
· 충전 대상 : {충전대상}

입금 금액과 입금자명이 위와 다르면 자동 충전이 되지 않습니다.

감사합니다.
```

**② 충전 완료** — 제목 `[한줄로] 충전 완료 안내`

```
[한줄로 안내]

{업체명} 고객님,
{입금일시}에 입금이 확인되어 {충전금액}원이 충전되었습니다.

· 입금 계좌 : 기업은행 585-028893-01-011
· 입금자명 : {입금자명}
· 충전 대상 : {충전대상}
· 충전 후 잔액 : {잔액}원

감사합니다.
```

**정합성 규칙** — 머리(`[한줄로 안내]` + `{업체명} 고객님,`), 둘째 줄 "언제 + 무엇이" 한 문장,
불릿 `· 항목 : 값`(콜론 앞뒤 공백), 맺음 `감사합니다.`를 두 문안이 동일하게 쓴다.
계좌·입금자명·충전 대상이 두 문안에 모두 있어 고객이 나란히 놓고 대조할 수 있다.

`"입금 금액과 입금자명이 위와 다르면 자동 충전이 되지 않습니다."` — 이 문장은 빼지 않는다.
자동 매칭은 금액·이름이 정확히 맞아야 성립하는데, 이 말이 없으면 "왜 충전이 안 되냐"는 문의가 그대로 온다.

**채널**: 지금은 문자. 카카오 템플릿이 승인되면 **문안은 그대로 두고 채널만 알림톡으로 교체**한다.
그래서 문안과 발송 경로를 처음부터 분리해 만든다.

### 1-2. 변수 8개

| 변수 | 출처 |
|---|---|
| `{업체명}` | 회사 |
| `{요청일시}` | 충전 요청 레코드 생성 시각 |
| `{요청금액}` | 요청 폼 입력 |
| `{입금자명}` | 요청 폼 입력 (**신규 입력 항목**) |
| `{충전대상}` | 아래 1-3 |
| `{입금일시}` | IBK `trnYmd` + `inptHms` |
| `{충전금액}` | IBK `trnAmt` |
| `{잔액}` | 충전 후 잔액 |

### 1-3. 충전 대상 = 계정명 (구분 축)

같은 업체가 계정을 여러 개 갖는 게 이 설계의 함정이다(예: 런소프트 / 런소프트2 / 런소프트3).
**회사명으로 구분하면 안 된다.**

- **게이트웨이 선불** → `발송ID / 발급명` (예: `B0082 / 런소프트2`)
  0727에 발송ID 표시명을 게이트웨이 발급명(`RSRM_SalesMst.CustNm`) 하나로 통일하고 라벨을 이 형식으로 맞췄다.
  화면·문자·원장이 같은 이름을 쓰게 하려면 문자도 이 형식이어야 한다.
- **웹 선불** → **사용자명** (회사명 아님 — 웹은 사용자별로 따로 충전할 수 있다)

### 1-4. 인증 = 자체인증(2-legged) 방향

| | 자체인증 (2-legged) | IBK인증 (3-legged) |
|---|---|---|
| 절차 | Client Credentials — **사람 개입 없음** | 웹뷰 본인확인·동의(휴대폰·전자서명) |
| 토큰 | Access 90일 | Access 90일 + Refresh 1년 |
| 용도 | 이용기관 자신의 인증 | 제3자(고객) 금융정보 조회 |

우리는 **인비토 법인 명의 계좌를 우리가 조회**하는 것이고, 서버가 무인으로 돌아야 한다.
3-legged는 웹뷰 동의가 사람 손을 타서 무인 운영에 맞지 않는다.

### 1-5. 조회 방식 = 요청이 있을 때만

**상시 폴링을 두지 않는다.**

- 대기 중인 충전 요청이 **0건이면 API를 호출하지 않는다**
- 요청이 들어온 시점부터 **짧은 간격**으로 조회, 매칭되거나 요청이 만료되면 멈춘다
- 목표는 "입금하면 거의 바로" — 실제로 그렇게 운용하는 거래처 사례가 있다(Harold 확인)

간격은 **호출 단가·분당 호출 상한을 확인한 뒤 그 안에서 가장 짧게** 잡는다(§4).

### 1-6. 애매하면 멈춘다

자동 충전하지 않고 **보류함**으로 빼는 경우:

- 금액 불일치 (부분 입금·초과 입금)
- 입금자명 불일치
- 같은 입금자명 + 같은 금액의 대기 요청이 둘 이상이라 어느 건인지 특정 불가

**요청 단계에서 미리 막는다** — 같은 입금자명 + 같은 금액이 이미 대기 중이면 요청 접수 시 알리고
금액을 다르게 하거나 입금자명을 구분하도록 안내한다. 들어온 뒤에 푸는 것보다 확실하다.

은행이 주는 정보는 금액·입금자명·시각뿐이라, 같은 회사의 여러 발송ID가 같은 이름·같은 금액으로
요청하면 **은행 데이터만으로는 원리적으로 구분할 수 없다.** 그때는 사람이 처리한다.

## 2. 기업은행 API — 문서 실측

출처: IBK 오픈API 포털 문서 4건(2026-07-28 수집). 아래는 문서에 적힌 값 그대로다.

### 2-1. 거래내역 조회

- `POST /ibk/biz/bizAcntTrhsInq` (원화 예금계좌 거래내역 조회 v1.0.0)
- Server(개발): `https://devapiportal.ibk.co.kr:9443` — **운영 주소는 별도 확인 필요**
- 이용금액: **"별도협의"**
- 성공 200 / 실패 400

**Request Header**: `oapiUserSrn`(Number 10, Y) · `X-IBK-Client-Id`(String 32, Y) · `X-IBK-Client-Secret`(String 32, Y) · `Authorization: Bearer`(String 240, Y)

**Request Body 주요 항목**

| 필드 | 필수 | 내용 |
|---|---|---|
| `oapiClntId` | Y | 오픈API 클라이언트 ID |
| `oapiInofrTgtNo` | N | 실제 계좌번호(마스킹 미처리 대상 이용기관) |
| `oapiAcntAltrNo` | N | 계좌 대체번호(마스킹 처리 대상 이용기관) |
| `insgYmd` / `inqFnshYmd` | Y | 조회 시작·종료 `yyyyMMdd` (최대 5년, 1년 단위) |
| `inqDcd` | Y | `1` 입금 / `2` 출금 / `3` 입출금 → **우리는 `1`** |
| `otptTrtpDcd` | Y | `1` 순차 / `2` 역순 |
| `trnListNextkeyTrnYmd` · `trnListNextkeyFnshYmd` · `trnListNextkeyDepTrnSrn` | N | NEXT 페이지가 있을 때 셋팅 |

**Response `trnList[]` 주요 항목**

| 필드 | 내용 |
|---|---|
| `trnYmd` | 거래년월일 `YYYYMMDD` |
| `inptHms` | 입력시각 `HHMMSS` |
| `depTrnSrn` | **수신거래일련번호** (Number 7) |
| `trnAmt` | 거래금액 |
| `aftrBal` | 거래후잔액 |
| `dwmDcd` | `01` 입금 / `02` 출금 |
| `trnSmr` | 거래적요 (100) |
| `cnacDpsrNm` | **상대계좌예금주명** (50) |
| `trnDsncNm` | 거래구분명 (예: 'CC입금', '출금') |

**놓치면 안 되는 세 가지**

1. **한 번 호출에 최대 50건.** 그 이후는 NEXTKEY 3종으로 페이징해야 한다.
   끝까지 안 돌면 입금이 조용히 누락된다 — 2026-06-30 이새 전체동기화 조기 종료와 같은 계열이다.
2. **멱등키 = `depTrnSrn` + `trnYmd`.** 같은 입금이 두 번 충전되는 사고를 이걸로 막는다. 원장에 남긴다.
3. **입금자명 후보가 둘이다** — `cnacDpsrNm`(상대계좌예금주명)과 `trnSmr`(거래적요).
   문서 샘플은 둘 다 같은 값(`강삼BNB`)인데 **실계좌에서도 같은지는 미검증.**
   매칭 기준을 잘못 잡으면 전건 미매칭이 된다 — 실입금 1건으로 반드시 확인한다.

### 2-2. 토큰 (2-legged)

- 발급: `POST /ibk/biz/oauth/application/twoLeggedToken`
  `grant_type=client_credentials` · `scope=sa` · Basic auth로 `client_id:client_secret`
- 응답: `token_type` Bearer · `access_token` · `scope` sa · `expires_in` **7776000(90일)** · `consented_on`
- 폐기: `POST /ibk/biz/oauth/twoLeggedRevoke` (`token_type_hint=access_token`)

### 2-3. 토큰 (3-legged) — 채택하지 않지만 기록

- 웹뷰: `GET /ibk/biz/oauth/application/webview/authorize`
  (`response_type=code` · `redirect_uri` · `client_id` · `scope` 1 inquiry/2 transfer · `oap_cus_dcd` 1 개인/2 법인/3 중소개인 · `view_gubn` 1 최초동의/2 재동의/3 철회)
- → Authorization Code(465byte) + **`oapiUserSrn`** 수신
- 토큰: `POST /ibk/biz/oauth/application/threeLeggedToken` — Access 90일 / Refresh 1년
- `oapiUserSrn`은 "IBK의 모든 API 거래에서 유일한 고객의 KEY"

## 3. 재개 시 가장 먼저 확인할 것 두 가지

이 둘이 막히면 설계가 통째로 바뀐다. **코드를 쓰기 전에 확인한다.**

### 3-1. 2-legged에서 `oapiUserSrn`을 어떻게 얻는가 — 미검증

거래내역 조회는 `oapiUserSrn` 헤더를 요구하는데, 문서에는 그 값이 **3-legged 인증 완료 시 발급**된다고만 적혀 있다.
2-legged에서 얻는 경로가 수집한 문서 4건에 없다.

포털 좌측 메뉴의 **사용자등록 / 사용자관리 / 등록정보 조회** 문서를 받아 확인한다.
2-legged 이용기관은 그 API로 계좌를 등록하고 일련번호를 받는 구조로 **보이지만 추정이다.**

여기서 2-legged로 자기 계좌 조회가 안 되는 것으로 밝혀지면 인증 방향을 다시 잡아야 한다.

### 3-2. 웹 선불 잔액이 사용자 단위로 적재되는 구조인가 — 미확인

문자에 사용자명을 넣기로 했는데, 잔액이 회사 단위로만 쌓이는 구조라면 **사용자별 충전 자체가 성립하지 않는다.**
어느 테이블·어느 컬럼에 웹 선불 잔액이 있고 사용자 축이 있는지 실제로 확인한 뒤 설계를 확정한다.
(`information_schema`로 컬럼 실존까지 확인 — SCHEMA.md 기재만 믿지 않는다)

- **운영 서버 주소** (문서의 `devapiportal.ibk.co.kr:9443`은 개발용)

## 5. 안전 설계 (6원칙 정합)

**이중 진실 = 안전망 워커** (6원칙 ③)
은행 거래내역과 우리 충전 원장이 두 개의 진실이 된다. 자동 대조 워커를 **처음부터 같이** 만든다.
- 입금은 들어왔는데 충전이 안 된 건
- 충전은 됐는데 대응 입금이 없는 건
- **마지막 성공 조회 시각 감시** — 토큰 90일 만료나 API 장애로 조회가 멈추면
  고객은 입금했는데 충전이 안 되고 **아무도 모른다.** 폴링이라 에러가 화면에 뜨지 않는다.

**상태 변경 = 효과 검증 후 성공** (6원칙 ②)
게이트웨이 충전은 §5-3 경로 그대로 — `RsApplyFlag='Y'` 반영을 확인한 뒤에만 완료로 전이하고 완료 문자를 보낸다.
반영 전에 완료 문자를 보내면 시스템이 거짓말을 하게 된다.

**발송·돈 = 실측 1건 시나리오** (6원칙 ⑤)
배포 전 실입금 1건으로: 요청 → 안내 문자 → 실제 입금 → 감지 → 매칭 → 충전 → 잔액 증가 → 완료 문자까지 완주 확인.
이때 `cnacDpsrNm`과 `trnSmr`에 실제로 무엇이 들어오는지도 같이 본다(§2-1 3번).

**전수 grep** (6원칙 ①)
충전 경로는 웹·게이트웨이 둘이다. 한쪽만 고치고 끝내지 않는다.

## 6. 선행 조건 (이게 안 되면 자동충전도 안 돈다)

`billing_type='prepaid'` 지정이 **283행 전부 postpaid**라 지금은 충전 요청 탭도 충전 등록도 열리지 않는다.
컷오버 최소분 = 7월 실충전 4개(`B0082` · `D0078` · `D0079` · `C0112`).
자동충전을 만들어도 선불 지정이 먼저 되어야 동작한다.
