# 비토 게이트웨이 — 브랜드메시지 축 (GW-BRAND-MESSAGE)

> 허브 = [FEATURE-BITO-GATEWAY.md](../FEATURE-BITO-GATEWAY.md) · 수정 시 허브 §2-1 작업 규율 적용.
> **이 문서가 브랜드메시지 축의 확정 사실·결함·이력을 소유한다**(★2026-08-15 Harold 지시로 분리 — 허브 §4-6은 요약·포인터만).

## 1. 정체성

한줄로 → 게이트웨이 → 휴머스온(IMC) → 카카오로 나가는 **광고성 브랜드메시지**. 알림톡과 완전히 다른 축이다(알림톡 = 정보성·템플릿 검수 / 브랜드 = 광고성·발신프로필 기반). 2026-08-15 기준 **성공 발송 0건**.

```
한줄로 buildBrandMsgContents → MySQL SMSQ_SEND_1x(msg_type='F') → Bito Agent
  → 게이트웨이 kakao_brand_free/basic → humuson_imc BM_FREE_REQ/BM_BASIC_REQ → 카카오
```

**지원 범위** — 자유형(FREE) TEXT·IMAGE·WIDE만. 기본형(BASIC)은 게이트웨이·에이전트 준비 완료, 한줄로 적재 경로 미구현. 캐러셀류는 입구 차단.

## 3. 4101 — 확정된 것과 미확정인 것

**코드 의미(확정)** — IMC Developer Portal 응답코드 레퍼런스: **`4101 = SERIAL_NUMBER_PREFIX_DATE_EXCEPTION`**. 인접 = `4100 SERIAL_NUMBER_EXCEPTION` · `2006 시리얼넘버 형식 불일치` · `4103 허브파트너 없음` · `4104 발신프로필 없음`. 4100·4103·4104가 우리 결과코드표(`alimtalk-result-map.ts` IMC_REPORT_CODE_MAP)와 일치 — **브랜드 결과코드표가 맞음**을 교차 확인.

**배제 완료 6축**(각각 실측) — ①Agent 매핑(관통 확인) ②중계 프로토콜(접수 ACK) ③단가 ④채널 친구(I 타겟팅·본인 채널 친구) ⑤**발송 시간창**(08:37 주간 재발송도 4101) ⑥**계정·프로필**(같은 bind5/invito12·같은 프로필로 알림톡 `0000` 성공, 브랜드만 4101).

**시도했으나 실패한 형식 2종** — MSG_UID `00001707050`(순번 11자리) · `26081507051`(YYMMDD+순번). **인증 응답에도 시리얼 규칙 없음**(AUTH_KEY·ENC_METHOD·RS_LIST뿐, 전문 로그 확인).

⛔ **NGS 규격서를 근거로 쓰지 마라** — NGS는 GemTek 규격이고 휴머스온 IMC와 다른 프로토콜이다(0815 Harold 지적 — 그 근거로 만든 커밋 `9d1cda3`은 `64fc838`로 되돌림).
⛔ **형식을 추정해 넣지 마라** — 0815에 두 번 시도해 두 번 같은 코드였다. IMC 소켓 규격서를 받은 뒤에만 고친다.

**★0815(11) 규격서는 처음부터 있었다** — `Downloads/Humuson IMC 연동규약서_v20251031 (1).pdf`(91쪽, **BM 절 §2.19/§2.21 포함**) + `[휴머스온]브랜드메시지 Agent 사용 메뉴얼_20260209.pdf`(DB 테이블 규약) + `IMCAgent-2.3.1 결과코드 xlsx`. "소켓 규격서 미보유"는 오판이었다(Harold 지적으로 발견).
- 연동규약서 실측: BM 전문 MSG_UID = **"최대 11자리 유니크"가 전부**(날짜 접두 규칙 없음) / BM 전문 필드 집합에 **RESERVED_DATE·CONTENTS 없음** / RESEND_MT_TYPE=필수(M) / TARGETING에 F(전체 채널 친구) 존재.

### MSG_UID 축 종결 — 원인이 아니다 (★0815(11) 실측 3회)

| 시도 형식 | 결과 |
|---|---|
| `00001707050` (순번 11자리 = 알림톡과 동일) | 4101 |
| `26081507051` (YYMMDD+5) | 4101 |
| `20260815056` (yyyyMMdd+3) | 4101 |
| **`00001707058`** (`11f6287` 배포 후 — 알림톡과 동일 형식 환원) | **4101** |

**바꿔도 결과가 안 바뀌면 원인이 아니다.** 결정적 대조 = **11:28 알림톡 `00001707057` → `0000` / 11:29 브랜드 `00001707058` → `4101`**(30초 간격·같은 계정·같은 발신프로필·같은 세션·**MSG_UID 형식 동일**). 코드명 `SerialNumberPrefixDateException`만 보고 MSG_UID를 지목한 것이 오판이었다. → 브랜드 전용 규칙 **철회**(`11f6287`). RESERVED_DATE·CONTENTS 제거(`9a86918`)는 규약서 정합이라 유지하되 **4101 원인은 아니었다**.

**0815(12) 배포 후 브랜드 전송 프레임 실측**(규약서 §2.21 필드 집합과 일치 — 비규격 0):
`AD_FLAG:Y · BUSINESS_CODE · CHAT_BUBBLE_TYPE:TEXT · MESSAGE · MSG_UID · PHONE_NUMBER · PRIORITY:N · PUSH_ALARM:Y · RESEND_MT_TYPE:NO · TARGETING:I · UNSUBSCRIBE_PHONE_NUMBER · USER_MAP` + `REQ_UID · SENDER_KEY`.
한줄로 계약 정정분(§4-1)도 관통 확인 — `UNSUBSCRIBE_PHONE_NUMBER`가 k_etc_json 경유로 프레임까지 도달.

### ★★ 프로필·채널 자격 축 배제 — 검증된 타 프로필도 4101 (0815(13) 실측, Harold 설계)

**대조군을 만들어 닫았다.** 마코골프(`82b24d5f…`, 여미지)는 **타 중계 `.57`을 통해 브랜드메시지가 현재 정상 발송 중인 프로필**이다(0814 확인 = 중계 3대 중 `.57`만 F 지원). 그 프로필키를 `k_etc_json`에 넣어 비토 라인(SMSQ_SEND_14)에 직접 INSERT → 게이트웨이 관통 → **REPORT 4101 동일**(11:46:45, `MSG_UID=00001707059`).

| 프로필 | 자격 상태 | 비토 경로 결과 |
|---|---|---|
| `5dc46546…` (인비토) | `businessProfile:false` | 4101 |
| `82b24d5f…` (마코골프) | **`.57`로 실제 발송 중 = 자격 검증됨** | **4101** |

⇒ **`businessProfile: false`는 4101의 원인이 아니다**(그 가설 폐기). 발신프로필·채널 자격 축 전체가 닫혔다.
부수: 이 INSERT는 MySQL 클라이언트 인코딩으로 본문이 깨져 `MESSAGE` 키가 빠진 채 나갔다 — 단 11:29 건은 `MESSAGE`가 있었고 같은 4101이라 결론 무영향(본문보다 4101이 먼저 판정된다).

### ★★★★ 원인 최종 확정 — **우리 IMC 계정에 브랜드 발송 권한이 없다** (0815(15) · REST 실측)

**REST 발송 API가 원인을 한국어로 그대로 돌려줬다.**

| 경로 | 계정/키 | 결과 |
|---|---|---|
| 소켓 `BM_FREE_REQ`(252202) | `invito12` | `4101` = `SerialNumberPrefixDateException` |
| **REST** `POST /kakao-message/api/v1/brand/send/free` | `imc_q5WU…` | **`4005` "해당 채널 발송 사용 권한이 없습니다"** |
| REST — **프로필만 마코골프(`82b24d5f…`)로 교체** | 동일 키 | **`4005` 동일** |

마코골프는 `.54`에서 **실제로 브랜드가 나가는 검증된 프로필**인데 우리 키로 호출하면 같은 `4005`다. ⇒ **발신프로필·채널 축 완전 배제. 계정(API 키) 단위 권한 부재가 원인이다.**
**우리 전문은 처음부터 맞았다.** 소켓이 권한 부재를 시리얼 오류 코드로 돌려주는 바람에 MSG_UID를 4형식 바꿔가며 하루를 태웠다.

**남은 것 = 휴머스온에 브랜드 발송 권한 개방 요청**(문의문 = §6 원장 2번). 우리 쪽 코드 조치는 없다.

### ⛔ 왜 하루가 걸렸나 — REST를 한 번도 안 눌러봤다

`§3`에 "포털은 REST 전용"이라고 **적어두고도** 발송 경로 후보로 올리지 않았다. 게이트웨이가 소켓 커넥터를 가졌으니 소켓이 답이라고 전제했기 때문이다. REST 호출 1회면 오전에 끝났다.
**같은 기능에 접근 경로가 둘 이상이면, 막혔을 때 다른 경로로 한 번 찔러보는 것이 가장 싼 진단이다** — 경로마다 오류 메시지의 품질이 다르고, 그 차이가 원인을 드러낸다(소켓 `4101` vs REST `4005 한국어 사유`).

### (참고 — 위 확정으로 대체됨) `.54`는 BM_FREE_REQ를 쓰지 않는다 (0815(14))

**하루 종일 없어서 헤맨 성공 사례를 마침내 확보했다.** 마코골프 브랜드는 `.57`이 아니라 **`.54`(mmsr-qtmsg)** 에서 나가고 있었고, 그 발송 로그(`~/ngen/cms_mg2/logs/2026-0815/macawkko_m-deliver.txt`, 오늘 3,054건)의 실제 전문은 이렇다.

```
msgType[G]  etcjson[{"senderkey":"82b24d5f...","img_link":""}]  tmpl_code[]  next[N]
→ report result[1800]  (= 카카오 성공, sms-result-map.ts:27)
```

| | 마코골프 `.54` (성공 1800) | 우리 `.65` (4101) |
|---|---|---|
| msgType | **`G`** = 옛 친구톡(이미지) 코드 | `F` → `kakao_brand_free` |
| 전문 | 친구톡 계열 → **중계 엔진이 브랜드로 변환** | `BM_FREE_REQ`(252202) **직접** |
| 부가 필드 | `senderkey`·`img_link` **둘뿐** | CHAT_BUBBLE_TYPE·TARGETING·AD_FLAG·PUSH_ALARM… |

서수란 팀장 확인(0815) — **"기존 친구톡을 그대로 받고 엔진에서 브랜드메시지로 변환해서 처리"**. 즉 고객사는 옛 친구톡 코드로 넣고 브랜드 전용 필드는 **엔진이 채운다.**

⇒ **아무도 `BM_FREE_REQ`를 직접 쏘지 않는다.** 우리만 규약서를 근거로 그 경로를 두드렸고, 그 경로가 우리 계정에 열려 있지 않은 것이 4101의 정체로 보인다(최종 확정은 휴머스온 회신).

**⛔ 친구톡(G) 경로는 편법이다 — 기본 구조로 삼지 않는다**(0815 Harold 판단). 근거 셋 — ①폐지된 유형에 얹는 것이라 변환 장치가 걷히면 함께 죽는다 ②브랜드 고유 기능(M/N 타겟팅·AD_FLAG·HEADER·ATTACHMENT)을 못 쓴다(친구톡 전문에 그 필드가 없다) ③**우리는 신규 게이트웨이다** — 레거시 업체가 시스템을 못 고쳐서 쓰는 우회로를 신규 시스템의 표준으로 굳히면 안 된다. 정공 = `BM_FREE_REQ` 개방(문의 §6). 이관 일정이 급해 임시로 쓰게 되면 **"임시·제거 예정"을 문서에 못 박고 쓴다.**

### (참고) 한때 유일한 축으로 봤던 IMC 계정 `invito12` (0815(13))

전부 배제되고 남은 것: **계정 단위 브랜드 서비스 계약·권한**. 정합하는 그림 —
같은 계정·같은 세션에서 알림톡(`202002`)은 `0000` / 브랜드(`252202`)만 4101 · 프로필을 바꿔도 불변 · 마코골프가 `.57`로 성공할 때는 **다른 IMC 계정**을 쓴다.
⚠ **미검증** — 확정은 휴머스온 회신뿐. 문의 핵심 질문 = "**`invito12` 계정에 BM_FREE(252202) 발송 권한·계약이 설정돼 있는가**"(대조 근거 = `MSG_UID` 00001707058 / 00001707059 두 건).

### (폐기됨) 미충족 조건으로 의심했던 `businessProfile: false`

`getSender('5dc46546…')` 실측(0815):

| 필드 | 값 | 판정 |
|---|---|---|
| `brandMessage` | `true` | 브랜드 사용 신청 완료 |
| `unsubscribePhoneNumber` | `080-540-5648` | §2.1 충족 |
| `marketingAgreeFileUrl` | 등록됨 | §2.1 충족 |
| `status`·`profileStatus` | `A`·`A` | 정상 |
| **`businessProfile`** | **`false`** | **§2.2.1 I 타겟팅 조건 미충족** |

매뉴얼 §2.2.1 = "I 타겟팅 — **비즈니스 인증 채널일 경우 발송 가능**". 한때 유일한 미충족으로 보여 유력 원인으로 봤으나 **0815(13) 대조로 폐기됐다**(위 절 — 자격 검증된 타 프로필도 4101).
**단 프레임 축은 완전히 소진됐다**(0815(12) — MSG_UID 4형식·AD_FLAG·RESERVED_DATE·CONTENTS·본문 규약·UNSUBSCRIBE 전부 변경했고 4101 불변). 남은 것은 계정·채널 자격뿐이다.

**⛔ "QTmsg는 대기중인데 비토는 즉시 실패" = 원인 단서가 아니다**(0815(12) Harold 관찰 → 실측 정리).
두 경로 **모두 성공 0**이다 — QTmsg 쪽은 `.58` 중계에 브랜드가 적용돼 있지 않아(0814 확인) 접수 후 결과가 안 오는 **무응답으로 고인 것**이지 처리 중이 아니다(도착 0 실측). 표준 라인 `SMSQ_SEND`(1~11)에 F행 자체가 없다.
즉 **같은 뿌리가 경로마다 다른 모양**(무응답 / 7421 / 4101)이라는 0814 교훈의 재확인이고, **비토 경로만 IMC에서 구체 사유를 받아오는 유일한 진단 통로**다. 이 차이를 "비토만 문제"로 읽으면 자격 축을 잘못 배제하게 된다.
**처방(코드 아님)** = 채널관리자센터 > 관리 > 비즈니스 채널 신청 > 사업자정보 등록(§2.2.2 경로). `checkBrandTargeting`은 `509 신청 완료`만 답하고 `data:null`이라 발송 가부 판정에 쓸 수 없다.

## 4. 한줄로 측 확정 결함 4건 (★0815 — Harold 지시로 포괄 점검)

**"우리 문제"가 맞았다.** 매뉴얼이 요구하는 값이 게이트웨이까지 가지 못한다.

## 7. 이 축의 교훈

- ⛔ **막히면 다른 접근 경로로 한 번 찔러라 — 경로마다 오류 메시지의 품질이 다르다** (0815 최대 교훈). 같은 기능에 소켓과 REST 두 경로가 있었는데 소켓만 두드렸다. 소켓은 권한 부재를 `4101 SerialNumberPrefixDateException`으로 위장해 돌려줬고, REST는 `4005 "해당 채널 발송 사용 권한이 없습니다"`라고 한국어로 답했다. **REST 호출 1회면 오전에 끝났을 일에 하루를 썼다.** 더 나쁜 것은 REST의 존재를 §3에 적어두고도 후보로 올리지 않은 것 — "게이트웨이가 소켓을 가졌으니 소켓이 답"이라는 전제가 대안을 지웠다.
- ⛔ **문서에 있는 경로가 열려 있는 경로는 아니다** — 규약서에 `BM_FREE_REQ`가 정의돼 있다는 것과 우리 계정이 그것을 쓸 수 있다는 것은 별개다. 실무(`.54`)는 아예 다른 방식을 쓰고 있었다.
- ⛔ **에러 코드의 *이름*을 원인으로 읽지 마라** — `SerialNumberPrefixDateException`이라는 이름 때문에 0815에 MSG_UID를 세 번 바꿨고 세 번 다 4101이었다. 이름은 가설의 출처일 뿐 증거가 아니다. 0731의 "`7421 타임아웃` 라벨만 보고 우리 문제 아님으로 판정"과 **완전히 같은 실수의 2회째**다.
- ⛔ **대조군을 만드는 데 든 비용은 로그 3줄이었다** — 브랜드에만 진단 로그가 있어 비교 대상이 없었고, 그래서 반나절을 실패 행만 변형했다. 알림톡에 같은 로그를 넣자(`2f9c827`) **한 번의 발송 쌍으로 MSG_UID 축이 즉시 닫혔다**. 성공 사례 확보는 "구할 수 있으면 구한다"가 아니라 **먼저 만드는 것**이다.
- ⛔ **자격·설정 축을 프레임 축보다 먼저 물어라** — `getSender` 한 번이 `businessProfile:false`를 즉시 답했다. 프레임을 열 번 고치는 것보다 "이 계정이 이 기능을 쓸 자격이 있는가"를 한 번 묻는 것이 빨랐다(0814 브랜드 원인 확정 = 중계 능력 축과 같은 부류).
- ⛔ **성공 사례부터 확보하라** — 0815 하루 종일 실패 행만 변형하며 열 번 찔렀다(LESSONS_META 26 위반). 0731 12가설 헛돎과 같은 뿌리.
- ⛔ **다른 프로토콜 규격서로 메우지 마라** — IMC 규격이 없다고 NGS(GemTek)를 근거로 쓴 것이 0815의 오판.
- ⛔ **경계마다 규약이 다르면 그 자체가 결함이다** — 한쪽에서 싸매고 다른 쪽에서 푸는 구조는 반드시 누락을 만든다(§4-4).
- **접수 성공 ≠ 발송 성공** — `RETURN_CODE 1000`은 프레임 수락일 뿐, 판정은 REPORT다.
