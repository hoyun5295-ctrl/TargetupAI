> 허브 = [FEATURE-BITO-GATEWAY.md](../FEATURE-BITO-GATEWAY.md) · 수정 시 허브 §2-1 작업 규율 적용.

## 1. 정체성

한줄로 → 게이트웨이 → 휴머스온(IMC) → 카카오로 나가는 **광고성 브랜드메시지**. 알림톡과 완전히 다른 축이다(알림톡 = 정보성·템플릿 검수 / 브랜드 = 광고성·발신프로필 기반). 2026-08-15 기준 **성공 발송 0건**.

```
한줄로 buildBrandMsgContents → MySQL SMSQ_SEND_1x(msg_type='F') → Bito Agent
  → 게이트웨이 kakao_brand_free/basic → humuson_imc BM_FREE_REQ/BM_BASIC_REQ → 카카오
```

**지원 범위** — 자유형(FREE) TEXT·IMAGE·WIDE만. 기본형(BASIC)은 게이트웨이·에이전트 준비 완료, 한줄로 적재 경로 미구현. 캐러셀류는 입구 차단.

## 3. 4101 — **원인 확정·해소 완료** (★2026-08-18 18:35 실측)

> **원인 = MSG_UID 자릿수.** 우리가 11자리를 보냈고 카카오 브랜드 시리얼 조립이 그것을 감당하지 못했다. 9자리로 줄이자 즉시 `0000`.
> 아래 절들은 **그 결론에 이르기까지 배제한 축들의 기록**이다(같은 길을 다시 걷지 않기 위해 남긴다).

**종결 증거 — 게이트웨이 로그 원문 (배포 `def80be` 직후 첫 발송)**

```
18:35:00 카카오 전송 프레임  accountID=invito12 msgType=kakao_brand_free command=252202
         MSG_UID "001707071"  (9자리)  ngs_serial 00000000000001707071
18:35:00 카카오REPORT 원문   REPORT_TYPE "BF"  REPORT_CODE "0000"  FRIEND_YN "Y"  RESEND false
```

**같은 세션에서 바뀐 것은 자릿수 하나뿐이다** — 계정(`invito12`) · 발신프로필(`5dc46546…`) · 타겟팅(`I`) · 본문 · 명령(252202) 전부 4101 때와 동일하다.
바꿔서 결과가 바뀌었으므로 이것이 원인이다.

**부수 실측 — REPORT가 `USER_MAP`을 그대로 돌려준다**(`msg_uid`·`ngs_serial`·`trace_id`·`source_seq`).
`serialFromReport`는 USER_MAP을 1순위로 쓰므로, MSG_UID를 9자리로 줄이며 생긴 대조 키 충돌 우려는 이 경로에서 실질 위험이 없다.
(`msgMap[msgUID]` 폴백은 USER_MAP이 없을 때만 쓰인다.)

**왜 하루가 아니라 사흘이 걸렸나** — 0815에 MSG_UID를 3형식이나 바꿔 시험하고 "축 종결"이라고 적었는데 **그 3형식이 전부 11자리였다.**
내용만 바꾸고 길이는 한 번도 안 바꿨다. **바꾼 적이 없는 것을 배제했다고 적은 것**이 이 축에서 가장 비쌌던 오판이다.
⛔ **"바꿔도 안 바뀌면 원인이 아니다"는 참이지만, 그 전에 "내가 실제로 무엇을 바꿨는가"를 적어야 한다.**
그때 시험값 3개를 나란히 적어만 봤어도 전부 11자리라는 게 보였다.

## 3-0. (기록) 원인 확정 전까지 배제한 축들

**코드 의미(확정 · ★0818 결과코드표 xlsx 실측)** — `IMC-Agent 결과코드 v2.3.1.xlsx` **비즈메시지 시트**에 있다:
`4101 | SerialNumberPrefixDateException | 시리얼 넘버 Prefix 날짜 오류`.
⛔ **"4101은 코드표에 없다"는 오판이었다(0818)** — PDF 본문만 grep하고, 매뉴얼 §6.2가 "최종 참조"로 지목한 xlsx를 열지 않았다. 매뉴얼의 코드표는 스스로 **요약본(샘플)**이라고 적어 두었다. **요약본에 없다고 없는 것이 아니다.**

**★★ 시트 구조가 원인 축을 가른다** — 비즈메시지 시트는 세 구역이다.
① `휴머스온 메시지 접수 코드`(1000·2000·3000·8000~8004·9000·9999) — 우리 `RETURN_CODE 1000`이 여기
② **`카카오톡 메시지 발송 결과 코드 — 카카오까지 전달된 메시지`** — **`4101`이 여기다. 즉 카카오가 돌려준 코드다**(휴머스온 회신 "카카오 측에서 실패 코드가 반환되어"와 일치)
③ `휴머스온 추가 정의 — 카카오로 전달하지 않은 메시지`(8000~8006)

**권한·계약은 자기 코드가 따로 있고 우리는 그것을 받은 적이 없다.**

| 코드 | 뜻 |
|---|---|
| `811 NoPermission` | 요청 처리 권한 없음 — **"브랜드 메시지 API를 사용할 수 없는 허브파트너 등"** |
| `1009 SpecialVasIdNotRegistered` | 브랜드 발송용 특수 부가통신사업자 등록번호 미등록 |
| `1011`·`4105`·`4150` | 계약 정보 없음 |
| `4104` | 유효한 발신프로필 없음 |
| `2006 FailedToMatchSerialNumberPrefixPattern` | 시리얼넘버 **형식(패턴)** 불일치 |
| **`4101`** | **시리얼 넘버 Prefix 날짜 오류** ← 우리가 받는 것 |

⇒ **"소켓이 권한 부재를 4101로 위장했다"(0815 결론)는 폐기한다.** 카카오는 권한·계약에 전용 코드를 갖고 있고 그것을 쓰지 않았다. 형식 불일치(`2006`)도 아니다 — **패턴은 통과했고 그 안의 날짜가 틀렸다는 뜻**이다. REST `4005`(권한)와 소켓 `4101`(시리얼 날짜)은 **서로 다른 두 문제**다.

### ★★★ `.54`는 브랜드 경로를 아예 안 탄다 — 설정으로 확정 (0818 실측)

Harold 지시로 "성공하는 쪽 연동 설정"을 직접 열었다. `.54`의 휴머스온 카카오 모듈 = **`~/ngen/hmo/dpk.hm1/conf/dpp.xml`**(`hmo` = HuMusOn · 프로세스는 전부 `qtmss/*` 자체 스택 — **IMC-Agent는 설치돼 있지 않다**).

**결정적 증거 = 그 설정의 `CODE_CONV` 표.** 이 모듈이 처리하는 IMC 결과코드가 통째로 나열돼 있는데:

```
1001~1030 · 2003~2006 · 3000~3027 · 4000 · 4001 · 8000~8901 · 9000~9999 · 7101~7421
```

**`4100`·`4101`·`4103`·`4104`·`4105` — 브랜드 전용 41xx 코드군이 전부 없다.** `2006`(시리얼 형식 불일치)은 매핑돼 있는데 `4101`(시리얼 Prefix 날짜)은 없다. ⇒ **이 모듈은 그 코드를 받아본 적이 없다 = BM 경로를 안 탄다.**

| | `.54` `dpk.hm1` (마코골프 성공) | 우리 게이트웨이 (4101) |
|---|---|---|
| IMC 접속 | `119.207.76.100:32000` · `loginid invito` | 별도 계정(계정 차이는 당연 — 이건 원인이 아니다) |
| 카카오 명령 | 친구톡 계열 | **`BM_FREE_REQ`(252202) 직접** |

| 아는 41xx 코드 | **없음** | 받는 중 |

이것으로 세 근거가 한 점에 모인다 — 서수란 *"기존 친구톡을 그대로 받고 엔진에서 브랜드메시지로 변환해서 처리"*(0815) · 중계 3대 중 **`.57`만 F 지원**(0814) · 마코골프 로그 `msgType[G] → result[1800]`.

⇒ **아무도 `BM_FREE_REQ`를 직접 쏘지 않는다.** 우리만 규약서를 근거로 그 문을 두드리고 있고, **그래서 그 문에만 있는 시리얼 규칙을 우리만 마주친다.** 문서에 그 규칙이 없는 것도 같은 이유다.

⛔ **"계정이 다르다"는 원인이 아니다** — IMC 계정은 시스템마다 따로 발급된다. 0818에 그것을 차이로 보고한 것은 헛짚음이었다. 봐야 할 것은 **연동 방식**이다.

### ★ 시리얼 Prefix 날짜 규칙은 **어느 문서에도 없다** (0818 3종 전수 검색)

**왜 매뉴얼에 없는지에 구조적 이유가 있다** — Agent 매뉴얼은 DB 테이블 방식 전제이고, `REQUEST_UID`(발송 식별 UID)가 **"에이전트입력"** 으로 표시돼 있다(§4.4 No.26). **고객은 시리얼을 만들지 않는다. 에이전트가 만든다.** 그러니 규칙을 설명할 이유가 없다.

**우리는 에이전트를 쓰지 않는다** — 게이트웨이가 소켓을 직접 말하므로 MSG_UID를 우리가 만든다. 에이전트가 알아서 하던 규칙을 우리가 떠안았는데 그 규칙이 문서에 없다. ⇒ **추측 금지, 문의로만 푼다**(0815에 4형식 시험 = 4번 모두 4101).

**(구 기록)** IMC Developer Portal 응답코드 레퍼런스도 같은 값을 준다: `4101 = SERIAL_NUMBER_PREFIX_DATE_EXCEPTION`. 인접 = `4100 SERIAL_NUMBER_EXCEPTION` · `2006 시리얼넘버 형식 불일치` · `4103 허브파트너 없음` · `4104 발신프로필 없음`. 4100·4103·4104가 우리 결과코드표(`alimtalk-result-map.ts` IMC_REPORT_CODE_MAP)와 일치 — **브랜드 결과코드표가 맞음**을 교차 확인.

### MSG_UID 축 — 내용은 원인이 아니었고 **자릿수가 원인이다** (★0818 휴머스온 2차 회신)

**회신 원문 요지** — "내부 처리 과정에서 MSG_UID 자릿수 초과로 발송 실패. 기존 11자리가 아닌 **최대 9자리 이내**로 설정하여 재발송 요청.
(11자리로도 정상 처리되도록 내부 조치 예정)" + "요청 API KEY에 **브랜드메시지 사용 권한이 누락**되어 있어 적용함 — `4005`는 발신프로필이 아니라 **API KEY 단위** 오류" + "접수 `1000` → REPORT `4101` 구조는 정상이며 REPORT가 실제 카카오 처리 결과".

**왜 0815 실측이 이 축을 못 걸렀나** — 시험한 3형식이 **전부 11자리**였다(`00001707050` · `26081507051` · `20260815056` — 각 11자리).
**내용만 바꾸고 길이는 한 번도 안 바꿨다.** 바꾼 적이 없으니 배제된 적도 없다. 아래 "종결" 표는 **내용 축에 한해서만** 유효하다.
알림톡이 같은 11자리로 `0000` 성공하는 것도 반증이 아니다 — 자릿수 제한은 **카카오 브랜드 시리얼 조립 단계**이고 알림톡은 그 단계를 지나지 않는다.

**결과코드표가 이 설명을 보강한다**(0818 xlsx 실측) — 시리얼 축 코드가 `4100 SerialNumberException` · `4101 SerialNumberPrefixDateException` ·
`2006 FailedToMatchSerialNumberPrefixPattern` · `3012 SerialNumberDuplicatedException` **4개나 따로 있는데 자릿수 전용 코드는 없다.**

**매뉴얼 실측(0818 재확인)** — `REQUEST_UID = 발송 식별 UID`, **길이 규정 없음**. 에이전트가 만드는 값이라 규정할 이유가 없다.

**조치(코드 완료 · 배포 대기)** — `humuson_imc/payload.go` `makeMsgUID`를 유형별 자릿수로 분리. 브랜드 9자리 · 알림톡/친구톡 11자리 유지
(알림톡은 `0000` 성공 중이라 건드리지 않는다. 휴머스온 내부 조치가 끝나면 이 좁힘은 되돌릴 수 있다).
계약 3건 — 브랜드 9자리 · 브랜드 폴백 9자리 · 알림톡 11자리 회귀 방지. 11자리로 되돌리면 앞 2건이 실제로 깨지는 것을 확인했다.

## 4-1. 계약 정정 구현 (★0815(10) — 코드 완료 · 배포+실측 대기)

**신규약** — `msg_contents` = 내용물(자유형: 순수 본문 / 기본형: `TYPE_DEF`+변수 JSON — TYPE_DEF는 게이트웨이 absorb 하위호환 경계의 전문 식별 마커라 유지) / `k_etc_json` = 제어·부가 전부(`senderkey`·`CHAT_BUBBLE_TYPE`·`TARGETING`·`AD_FLAG`·`PUSH_ALARM`·`HEADER`·`ADDITIONAL_CONTENT`·`UNSUBSCRIBE_*`·`ATTACHMENT`). 알림톡과 같은 경계.

- **단일 조립기 `buildBrandQueuePayload`**(brand-message.ts)가 두 컬럼을 한 쌍으로만 산출 — 옛 `buildBrandMsgContents` 삭제. 두 컬럼을 따로 조립하는 구조 자체를 타입으로 봉쇄.

3. **이미지 경로 키** — §6.10.5는 카카오 업로드본은 `img_url`, 로컬·외부 경로는 `imc.img`(IMC가 대신 업로드)로 규정. 우리는 항상 `img_url`. 매뉴얼 자신도 §6.10.5 표는 `imc.img`, §5.4.1.2 예제는 `imc.img_url`로 표기가 갈린다.
4. **IMAGE 본문 길이** — §4.4.1 1,300자 / §5.4.1.2 예제 주석 400자 / §4.4 컬럼표 4000. 코드는 1,300 채택.

### ⛔ 이 정독에서 남는 것

- **규격 문서가 두 개면 둘이 다른 말을 한다** — Agent DB 매뉴얼과 소켓 연동규약서가 같은 필드를 다르게 규정한다. 어느 쪽을 따랐는지 **코드 주석에 절 번호로 남기지 않으면** 다음 사람이 되돌린다.
- **검사기를 조립기 밖에 두면 호출부 수만큼 구멍이 생긴다** — 6곳 중 1곳만 검사받던 구조가 결함 1~5의 공통 뿌리였다. 고친 뒤 `/brand-send`에 있던 별도 게이트 호출이 사라진 것이 구조 수정의 증거다.
- **매뉴얼에 없는 코드를 받았다는 사실 자체가 근거다** — 4101이 고객 배포 코드표에 없다는 것은 그것이 문서화된 고객 대상 사유가 아니라는 뜻이고, 권한 부재 가설과 일치한다.

## 4-3. Codex 적대 리뷰 2라운드 — 수용분과 **미해결 3건** (★0818)

1R = critical 1 · high 4 · medium 2 (전량 수용·정정) / 2R = critical 1 · high 5.

**2R에서 같은 부류가 두 번째로 나왔다** — ①환불 축 ②20:50 경계 ③검증 fail-open ④sendAt 파싱. 네 갈래가 전부 재출현이라 개별 수정을 멈추고 뿌리를 적는다.

### 왜 반복되는가 — 검증이 차감·적재 **뒤**에 있다

직접발송 순서가 `차감 → 문자 큐 INSERT → 브랜드 조립·검증 → 브랜드 큐 INSERT`다. 검증이 3단계라서, 거기서 실패하면 **돈은 이미 움직였고 문자는 이미 나갔다.** 그래서 검증을 고칠 때마다 "그럼 그 돈과 그 문자는 어떻게 되나"가 새로 생긴다 — 환불 축 지적도, 20:50 경계 지적도 전부 그 한 자리에서 나온다. 검증을 아무리 정교하게 만들어도 위치가 그대로면 같은 질문이 계속 나온다.

**구조 처방 = preflight.** 수신자별 브랜드 payload와 발송 시각을 **차감·첫 INSERT 전에 전량 조립·검증**하고, 검증된 canonical 값만 이후 단계가 쓴다. 그러면 규격 위반은 돈이 움직이기 전에 끝나고, 환불 축·부분발송·경계 문제가 함께 사라진다(덧댄 장치가 사라지는 것이 구조 수정의 신호). **Harold 승인 대기** — 직접발송 돈 경로의 순서 변경이라 별도 축이다.

## 7. 이 축의 교훈

- ⛔ **막히면 다른 접근 경로로 한 번 찔러라 — 경로마다 오류 메시지의 품질이 다르다** (0815 최대 교훈). 같은 기능에 소켓과 REST 두 경로가 있었는데 소켓만 두드렸다. 소켓은 권한 부재를 `4101 SerialNumberPrefixDateException`으로 위장해 돌려줬고, REST는 `4005 "해당 채널 발송 사용 권한이 없습니다"`라고 한국어로 답했다. **REST 호출 1회면 오전에 끝났을 일에 하루를 썼다.** 더 나쁜 것은 REST의 존재를 §3에 적어두고도 후보로 올리지 않은 것 — "게이트웨이가 소켓을 가졌으니 소켓이 답"이라는 전제가 대안을 지웠다.
- ⛔ **문서에 있는 경로가 열려 있는 경로는 아니다** — 규약서에 `BM_FREE_REQ`가 정의돼 있다는 것과 우리 계정이 그것을 쓸 수 있다는 것은 별개다. 실무(`.54`)는 아예 다른 방식을 쓰고 있었다.
- ⛔ **에러 코드의 *이름*을 원인으로 읽지 마라** — `SerialNumberPrefixDateException`이라는 이름 때문에 0815에 MSG_UID를 세 번 바꿨고 세 번 다 4101이었다. 이름은 가설의 출처일 뿐 증거가 아니다. 0731의 "`7421 타임아웃` 라벨만 보고 우리 문제 아님으로 판정"과 **완전히 같은 실수의 2회째**다.
- ⛔ **대조군을 만드는 데 든 비용은 로그 3줄이었다** — 브랜드에만 진단 로그가 있어 비교 대상이 없었고, 그래서 반나절을 실패 행만 변형했다. 알림톡에 같은 로그를 넣자(`2f9c827`) **한 번의 발송 쌍으로 MSG_UID 축이 즉시 닫혔다**. 성공 사례 확보는 "구할 수 있으면 구한다"가 아니라 **먼저 만드는 것**이다.
- ⛔ **자격·설정 축을 프레임 축보다 먼저 물어라** — `getSender` 한 번이 `businessProfile:false`를 즉시 답했다. 프레임을 열 번 고치는 것보다 "이 계정이 이 기능을 쓸 자격이 있는가"를 한 번 묻는 것이 빨랐다(0814 브랜드 원인 확정 = 중계 능력 축과 같은 부류).
