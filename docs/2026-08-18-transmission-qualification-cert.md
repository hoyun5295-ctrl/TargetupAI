## 4-A. ★착수 완료 — 계약 종료 계정 차단 3단 (2026-08-18 · 코드 완료·배포 대기)

§2-2의 결함을 닫았다. DDL 0.

| # | 무엇 | 어디 |
|---|---|---|
| ① | **로그인 게이트를 회사 축으로** — `terminated`·`suspended`면 계정 상태와 무관하게 403 + 감사 로그(`login_blocked` / `company_*`) | `utils/company-access.ts`(신규 CT) · `routes/auth.ts` |
| ② | **상태 변경이 세션까지 전파** — 해지 시 소속 계정 dormant + **접속 중 세션 무효화** | `utils/session-manager.ts` `invalidateCompanySessions` · `routes/admin.ts` |
| ③ | **회수 이력** — `audit_logs`에 `company_terminated`(처리자·일시·잠근 계정 수·끊은 세션 수) | `routes/admin.ts` |

**⛔ 이 축의 함정 2개**
1. **`SELECT u.*`에 `c.status`를 별칭 없이 넣으면 계정 상태가 회사 상태로 덮인다**(같은 컬럼명이 둘이면 뒤엣것이 이긴다) → 계정 상태 게이트가 통째로 오작동한다. `c.status AS company_status` 강제. 소스 불변식 테스트가 고정.
2. **`companies.status`의 NULL은 활성이다**(SCHEMA.md) → `!== 'active'` 부정 비교를 쓰면 상태 미설정 고객사가 **전부 로그인 불가**가 된다. 차단할 값만 열거하는 긍정 비교로만 판정.

검증 — backend tsc 0 · 전체 2,673건 통과 · 신규 계약 9건. 부정 비교 주입과 별칭 제거 주입 각각에서 기대한 테스트가 깨지는 것을 확인하고 원복했다.
⚠ **운영 계정 5개는 SQL로 직접 고치지 않는다.** 배포로 코드가 막은 뒤 슈퍼관리자 화면에서 상태를 정리하는 순서다.

**추가 과제(범위 밖 · 기록만)** — 회사 상태 `locked`·`dormant`는 이번 차단 열거에 넣지 않았다(현재 실측 0건). SDK·API 발송 경로가 해지 고객사를 막는지는 별도 인증 축이라 따로 봐야 한다(2.2가 "API·모듈 연동 서버 등 모든 접근 경로"를 요구한다).

## 4-B. 다중 인증(3.4) 설계 — Harold 원안 + 기준 대조

**Harold 원안 (0818)**
슈퍼관리자에서 계정별 **로그인 담당자 휴대폰번호 등록**(복수 가능) → 로그인 시 **인증받을 번호를 선택** →
그 번호로 **1800-8125 발신, 6자리 숫자 인증번호**를 알림톡(승인 후) 또는 문자로 발송 → 입력해 통과하면
**그 계정은 24시간 유효**, 그 안에 재로그인하면 인증 없이 통과. MOTP 앱은 쓰지 않는다.

**재사용 가능한 실물 (실측)**
- `1800-8125` = 이미 `SYSTEM_SMS_CALLBACK` 기본값으로 시스템 발신에 쓰인다(`routes/internal-alert.ts:19`)
- **인증 전용 발송 라인이 이미 있다** — `sms_line_groups.group_type='auth'` / `SMSQ_SEND_11`, `getAuthSmsTable()`을 여러 곳이 쓴다

**⚠ 기준과 부딪히는 지점 — 계정당 복수 번호**
가이드라인 3.4·3.5에 같은 문장이 두 번 나온다: *"다수의 이용자가 공동으로 사용할 수 있는 인증수단은 인증기준에 부적합합니다."*
2.1은 *"1인 1계정 원칙은 기업 1개당 1계정이 아니라 실제 발송자 1인당 1계정"*, *"공용 계정 사용… 운영이 불가"*.
⇒ **계정 하나에 번호 여럿 + 로그인 시 선택**은 "한 계정을 여러 사람이 각자 폰으로 쓰는 구조"로 읽힌다.

**★Harold 확정 (0818) — 주 번호 1개로 간다.**
계정당 유효한 인증번호는 **언제나 하나**다. 로그인 시 번호를 고르는 단계가 없다(고르는 순간 공동 사용 구조가 된다).
교체는 슈퍼관리자가 하고 이력을 남긴다. 담당자가 여럿이면 번호가 아니라 **계정을 나눈다**(2.1 1인 1계정과 함께 맞는다).
⇒ 등록 목록 테이블이 필요 없어졌다. `users`에 주 번호 컬럼 하나 + 변경 이력은 `audit_logs`.

**비토가 정한 부분 (원안에 없던 것)**
- **24시간 유효는 같은 기기·같은 IP 대역 조건**을 붙인다. 3.5가 "접속환경 변경 시 재인증"을 명시하고, 무조건 24시간을 믿으면 탈취 계정이 하루를 그냥 쓴다.
- 인증번호 발송분은 **고객사에 청구되지 않게 과금 제외**.
- 알림톡 템플릿 승인 전까지는 문자, 승인 후 알림톡 우선·실패 시 문자 폴백(발송 실패 = 로그인 불가라 단일 장애점을 만들지 않는다).
- 로그인 실패 초과 시 **계정 잠금 + 경고 안내**를 동반한다(현재는 (IP,ID) 30분 임시차단뿐이라 기준 ④를 못 채운다).

### ⛔ 왜 배포하면 안 되나 — Codex 적대 2라운드 `critical` 2건

**1. 동일 캠페인 재차단 시 실차감이 남는다 (critical)**
`prepaidDeduct` → 게이트 순서다. 차단되면 catch가 `campaign id + NOT_LOADED` 키로 환불하는데,
환불 멱등이 **캠페인 단위 누적**이라(`additionalRefund = requested - alreadyRefunded`) 같은 캠페인을 다시 보내
또 차단되면 **새 차감분이 이미 환불한 몫에 삼켜져 환불 0**이 된다. sweeper도 `processed > 0`일 때만 계산해 복구하지 않는다.
부수 — 무료 quota는 커밋 후 어떤 경로로도 복원하지 않는다(`prepaid.ts` 명시). 차단돼도 영구 소진.

**2. 2초 상한이 탐지 로그를 감싸지 않는다 (critical)**
`Promise.race`는 규칙 조회·판정까지만 감싼다. 그 뒤 문안마다 `await logSpamBlockHits()`가 hit당 PG INSERT를 **직렬 대기**한다.
detect 규칙 하나가 개인화 문안 10,000개에 걸리면 MySQL 적재 전에 최소 10,000회 직렬 INSERT가 돈다.

**그 밖 `high`** — matcher 동치 표현으로 하한 우회(`phone:"010-1234-5678"` vs `"01012345678"`, `keyword:"bit.ly"` vs `url:"BIT.LY"`) ·
`SpamBlockedError`를 분기하는 호출부가 없어 여정이 이를 통신사 장애로 오인해 5분 재시도 후 **여정 전체 일시정지** ·
1만 건 청크 경계에서 앞 청크만 적재된 채 뒤가 차단 · 시뮬레이션이 저장 문안을 보는데 실제는 변수 치환·(광고)·080 footer가 붙은 문안 ·
규칙 PUT의 `mode` lost-update · 자동마케팅 재활성화 시 미환불(현재 `AUTO_CAMPAIGN_RETIRED`로 봉인)

### ★ 뿌리 하나 — 게이트를 차감 뒤에 뒀다

행을 버리든 throw하든 정합이 깨진다. **돈이 이미 움직인 뒤**이기 때문이다.
1라운드에서 "행을 버린다"를 "throw"로 바꿨더니 문제가 환불 멱등으로 옮겨갔을 뿐이다.

⛔ **이 문제는 오늘 이미 한 번 푼 것이다.** 브랜드메시지에서 "조립·검증을 차감 앞으로" 옮겼고(0818(6)),

그 컬럼을 **읽지 않는다**(계약 테스트가 SQL 문자열을 검사한다). DB를 직접 `UPDATE ... mode='block'` 해도
아무 일도 일어나지 않는다. 차단을 여는 유일한 길은 재설계된 코드다.

**차단 승격은 §4-D 「남은 개발」 3번** — 판정을 차감 **앞** preflight로 옮긴다(브랜드메시지 0818(6)과 같은 자리).

### 0819 Codex 적대 2라운드 — `critical` 0 · `high` 2 · **전량 수용**

**둘이 같은 뿌리였다 — 탐지가 아직 발송 임계 경로에 얹혀 있었다.** 오전에 로그만 빼고 판정은 그대로 뒀다.

| 지적 | 판정 근거 |
|---|---|
| 2초 상한이 동기 판정을 제한하지 못한다 | 사실. `Promise.race` 타이머는 이벤트 루프가 돌아야 뜨는데 문안 순회·`evaluateContent`가 전부 동기라, 한번 시작하면 타이머가 뜨지 못한다. **상한이 상한이 아니었다** |
| 타임아웃된 규칙 조회가 취소되지 않고 PG 풀에 누적된다 | 사실. 캐시 미스가 겹치면 발송마다 별도 SELECT. 풀 고갈은 0814에 이미 겪은 축이다 |

**처방 — 탐지 전부를 임계 경로 밖으로.** 탐지는 발송에 아무 값을 주지 않는다.
그러자 `SPAM_GATE_TIMEOUT_MS`·`Promise.race`·타임아웃 분기가 **함께 사라졌다**(덧댄 장치가 사라지면 뿌리를 고친 것이다).

- `bulkInsertSmsQueue`는 문안 **스냅샷만 동기로** 뜨고(문자열 조립·Map 적재뿐 — 정규식·DB 없음) 판정을 `void`로 던진다.
  스냅샷이 필요한 이유 = 판정을 미루면 그 사이 호출부가 `rows`를 손댈 수 있고, 그러면 탐지 이력이 증거 노릇을 못 한다.
- **자르지 않고 늦춘다** — 200건마다 `setImmediate` 양보. 상한으로 잘라내면 조용한 누락이 되고, 임계 경로 밖이라 늦어져도 된다.
- `loadActiveRules` **single-flight** — 겹친 호출은 진행 중인 조회 하나를 함께 기다린다. 로드 중 무효화가 들어오면 `cacheGen` 불일치로 낡은 결과를 캐시에 쓰지 않는다.
- 본문 정규화를 **요소마다 → 본문당 1회**로 접었다(규칙 10개×요소 3개면 종전에는 본문을 30번 훑었다). 동작 무변경·순수 절감.

**검증** — BE·FE tsc 0 · vitest **182파일 2,776건 통과**(계약 +23) · `SPAM_GATE_TIMEOUT_MS`·`applySpamBlockGate`·`Promise.race` 전수 grep 잔존 0건.
계약에 고정한 것 = 로그 규칙별 접기 · 단일 INSERT · 실패 격리 · 마스킹 · 조회 SQL에 `mode` 없음 · **겹친 호출이 조회 1회** · **로드 중 무효화 시 캐시 미기입**.

⚠ 줄 수는 `spam-block.ts` 239→275(+36). 늘어난 것은 single-flight와 정규화 접기 두 **기능**이고,
없어진 것은 `sms-queue`의 상한·race·타임아웃 분기다. 땜질로 늘어난 줄은 없다.

### 0819 Codex 적대 3라운드(증분) — `critical` 0 · `high` 1 · `medium` 2 · **취사 3건**

| 지적 | 판정 | 처리 |
|---|---|---|
| [med] 무효화 뒤 호출도 **낡은 세대의 in-flight**를 공유한다 | **수용** | 정확하다. `cacheGen` 비교가 캐시 기입만 막고 호출자에게 돌아가는 목록은 안 막았다. `inFlight`에 세대를 함께 저장해 **같은 세대만 공유**하고, `finally`는 identity 확인 후에만 비운다 |

| └ `getAuthSmsTable` single-flight 미적용 | **불수용** | TTL 캐시가 이미 있고, 동시 탐지 상한 2가 그 조회의 동시성도 함께 묶는다 |

## 4-F. ★ 부정사용 보류·소명(2.3) — 완료 (2026-08-19)

기준 = "결제정보↔계정 연계 · 명의 불일치 **보류/소명** · 처리 결과를 **계정별로** 기록".

### ★ 설계 판단 — 보류를 상태가 아니라 **속성**으로 달았다

착수 전 `deposit_requests` 소비처를 전수로 봤더니, `held`를 새 status로 넣으면 **4곳이 조용히 깨진다**.

| 소비처 | `status='pending'`을 보는 이유 | `held` 신설 시 |
|---|---|---|
| `balance.ts:215` | 10분 내 중복 신청 판정 | 보류 중 같은 금액 재신청이 **통과** — 보류 우회 |
| `admin.ts` 승인·반려 게이트 | `status !== 'pending'` → 400 | 보류 건을 **승인도 반려도 못 함**(영구 정지) |
| `pending-badges.ts:44` | 대기 뱃지 카운트 | 보류 건이 **뱃지에서 사라짐** |
| `admin.ts` 목록 WHERE | 관리자 화면 | 목록에 안 뜸 |

그래서 `status`는 `pending` 그대로 두고 `held_reason IS NOT NULL`로 보류를 표시한다.
**수정 지점이 4곳에서 0곳이 됐고**, "대기 중이고 처리가 멈춰 있다"는 보류의 뜻과도 맞는다.

1. **자동 거절하지 않는다.** 판정은 보류까지다 — 입금자명이 배우자·경리·법인 담당자인 정상 사례가 흔하다.

3. **보류 사유 원문을 고객에게 내리지 않는다** — 판정 기준이 노출되면 우회를 돕는다. 화면 문구는 "확인이 필요하다"까지.

## 4-G. ★ 국외 접근 통제(2.2) — 완료 (2026-08-19)

기준 = "국외 IP 차단 · 화이트리스트 · VPN/프록시 통제 · 예외 승인 이력 · **모든 접근 경로**(웹·관리자·API·모듈)".

### ★ 설계 판단 1 — 사람은 국가로, 기계는 등록 출발지로

Harold 지적에서 나왔다 — **거래처 중 유한회사는 본사가 해외에 있다. 그 회사 SDK와 싱크에이전트는 어떻게 되나.**
실측하니 인증 경로가 코드에 이미 셋으로 갈려 있었다.

| 경로 | 인증 | 위치 | 국가 판정 |
|---|---|---|---|
| 사람 웹 로그인 | JWT(`userId`+`userType`) | `middlewares/auth.ts:37` | **한다** |
| SDK·자사몰 | `companies.cdp_api_key` | `routes/cdp.ts` `requireCdpApiKey` | **안 한다** |
| 싱크에이전트 | `companies.api_key` | `routes/sync.ts` `SyncAuthRequest` | **안 한다** |

`sync.ts`에는 `authenticate` import 자체가 없다. **게이트를 로그인에만 걸면 해외 본사 고객사는 영향이 0이다.**
기계 경로는 국가가 아니라 회사별 **등록 출발지 대역**(`scope=company_api`·`company_agent`)으로 통제하고,
그 등록 행위가 곧 기준이 요구하는 "예외 승인 이력"이 된다.

### ★ 설계 판단 2 — GeoIP 대신 국내 대역 화이트리스트

MaxMind 등 GeoIP 라이브러리를 넣으면 **새 npm 의존성**이 생긴다. 배포 스크립트는 `node_modules/typescript`가 있으면
`npm install`을 건너뛰므로 새 의존성은 서버에 설치되지 않고 **빌드 전체가 깨진다**(tailwindcss-animate 사고와 같은 축).
`login_blocks.ip_address`가 이미 `inet`이라 PG가 CIDR 포함 판정을 네이티브로 한다 — **의존성 0**으로 끝난다.

### 불변 원칙

1. **판정 지점은 로그인 하나.** `authenticate`(전 API)는 손대지 않는다 — 매 요청 판정은 비용·로그가 폭주하고 세션은 로그인에서 걸러진다. 세션 이후 축은 접속 인계·유휴 30분·MFA가 덮는다.
2. **모르는 것은 전부 통과.** 사설 IP · 대역 미적재 · 조회 실패 = `unknown` = 통과. 이 게이트는 전 고객 로그인을 막을 수 있어, "모른다"를 차단으로 접는 순간 전 고객이 막힌다.
3. **배포만으로는 아무도 안 막힌다.** `GEO_BLOCK_ENFORCE_FROM` 미설정 = 미시행. 국외를 만나도 `record`까지다. 값이 날짜가 아니어도 미시행(오타 방어). MFA와 같은 형태.
4. **화면에 켜는 스위치를 두지 않는다** — 시행은 서버 env가 소유한다. 관리자 화면은 상태만 보여준다.
5. **사유 없는 예외는 등록되지 않는다.** 회수는 DELETE가 아니라 `is_active=false` — 이력이 사라지면 심사에 낼 것이 없다.
6. **대역 교체는 트랜잭션.** DELETE와 INSERT 사이에서 끊기면 대역이 0건이 되고 통제가 조용히 사라진다. 2,000행 청크(PG 바인딩 상한 65535 회피).

### 0819 Codex 적대 2라운드(증분) — `critical` 2 · `high` 3 · `medium` 1 · **전량 수용**

### 0819 배포 직전 자체 점검 — 로그 폭주 1건 발견·정정

Codex 종료 후 "지금 배포하면 바로 문제될 게 있나"를 다시 훑다가 하나 찾았다.

**기계 경로 감사 로그 폭주** — CDP 13경로 + 싱크에이전트 13경로가 전부 `guardMachineOrigin`을 지나는데,
`access_origin_allowlist`가 **0건**이라 모든 호출이 `record`로 떨어져 **호출마다 예외 조회 SELECT + 감사 로그 INSERT**가 났다.
싱크에이전트 하트비트는 주기적이고 CDP 식별 호출은 고객 행동마다 온다 → 배포 즉시 로그가 쌓이고 PG 조회가 호출당 2회 늘어난다.

**정정** — 기록 단계는 **(회사·범위·IP) 조합당 1시간 1건**으로 축약했다(메모리 dedupe, 5,000키 상한).
등록할 대역을 걷어내는 데는 조합당 1건이면 충분하다. **차단은 여전히 매번 기록**한다.

⛔ 교훈 — **"미시행이니 안전하다"는 차단만 안 한다는 뜻이지 부하가 없다는 뜻이 아니다.**
탐지·기록 단계도 전 호출에 붙으면 그 자체가 부하다. 스위치를 끄고 배포할 때는 **꺼진 상태의 비용**을 따로 센다.

### ★ 배포 순서와 확인 (0819)

DDL은 **전부 실행 완료**다. 코드만 나가면 된다.

1. `.env`는 **건드리지 않는다** — `GEO_BLOCK_ENFORCE_FROM` · `ORIGIN_ALLOWLIST_ENFORCE_FROM` 둘 다 미설정이어야 한다(미시행 = 기록만).
2. 배포 후 **로그인 1건** — 게이트가 `rotateUserSession`(세션 생성 함수) 안으로 들어갔으므로 여기가 유일한 회귀 지점이다.
3. 배포 후 **싱크에이전트 하트비트** — `machine_origin_detected`가 조합당 1건만 뜨는지.
4. 그 뒤 순서 = 국내 대역 적재 → 탐지 기간 운영(정상인데 걸리는 대역 제거) → 해외 본사 고객사 예외 등록 → **그때** `GEO_BLOCK_ENFORCE_FROM` 투입.
5. MFA는 별개 축 — 9/1에 `MFA_ENFORCE_FROM` 투입.

## 4-H. ★ 5.2 차단 승격 — 설계안 (2026-08-20 작성 · 착수 대기)

> §4-E가 "왜 차단을 두 번 반려했는가"를 소유한다. 여기는 **그 뿌리를 어떻게 뒤집는가**만 적는다.
> 뿌리 = 게이트를 차감 뒤에 뒀다. 처방의 원칙 하나 — **발송 정책 판정은 차감 앞에**(브랜드메시지 0818(6) preflight와 같은 자리).

### ① 차단 판정 입력 = 원문 + 고정 부착물((광고)·080), **개인화 치환 전**

차감 앞에는 최종 개인화 문안이 아직 없는 경로가 있다. 원문 축이어야 조립 순서를 안 흔들고 전 경로에 성립한다.
판정 대상이 문안 원형 1~N개뿐이라 동기 비용이 유계 — 0819에 잡은 "개인화 1만 건 동기 판정"이 **구조적으로 재발 불가**가 된다.
치환으로 금칙어가 생기는 극단은 **탐지(현행 detect·최종 문안 축)가 계속 기록**한다 ⇒ **차단 = 원문 축 / 탐지 = 최종 문안 축**으로 이원화를 명시한다.
시뮬레이션도 차단과 **같은 입력**으로 맞춘다(0818 high — 시뮬레이션이 저장 문안을 보던 불일치가 함께 닫힌다).

### ② mode 2단 복원(detect/block) — hold는 만들지 않는다

`loadActiveRules`가 `mode`를 다시 읽고(계약 테스트 갱신) **block 규칙만** 차단한다. 규칙별 승격이 곧 시행이라 전역 ENV 스위치를 두지 않는다 —
운영 절차 = 오탐 시뮬레이션 확인 → 규칙 하나씩 승격. hold(보류 후 승인)는 발송 대기 상태 축을 전 경로에 신설하는 확장이라 **불채택**.

### ③ matcher 동치 정규화 (0818 high 잔여)

phone은 숫자만, url·keyword는 대소문자 무시로 비교. 하이픈·대문자 표기 우회를 닫는다.

### ④ 배선 — 차감 9곳·경로 5축, 각각 **차감(선불)·적재(후불) 중 앞선 것 앞**

| 경로 | 자리 | 차단 시 |
|---|---|---|
| `campaigns.ts` AI·direct(문자+BRAND 4곳) | 차감 직전 | 400 + 걸린 규칙 안내 |
| `direct-send-core` | 0818 preflight 자리 | 같음 |
| `brand-message` 2곳 | 기존 preflight 옆 | 같음 |
| `auto-campaign-worker` | 차감 전 | 회차 실패 기록(재시도 아님) |
| `journey-executor` | 실행 순서 실측 후 앞선 효과 앞 | **그 실행만 종결 + 사유 기록** — 여정 일시정지 금지(0818 high 재발 방지) |

`SpamBlockedError`를 복원하되 **경로별 catch를 같은 작업에서 배선**한다 — throw만 만들고 소비처를 안 만들면 0818 high가 그대로 재발한다

### 0827(2) 직원 계정 생성·초기 비밀번호 강제 변경 (Harold 지시)

**TOTP는 추가 개발 0.** 새 계정은 `totp_enabled`가 비어 있어 최초 로그인에서 QR·백업코드가 자동으로 뜬다(`auth.ts` enrollment 분기). 기존 흐름을 그대로 탄다.

**초기 비밀번호 강제 변경 — 게이트는 세션 발급 함수 안에 있다.**
JWT를 주고 화면에서 가리는 방식은 통제가 아니다(그 토큰으로 다른 API를 부를 수 있다).
`rotateUserSession`(세션을 만드는 유일한 함수)에 판정을 넣고 `RotateOutcome`에 `password_change_required`를 더했다.
**tsc가 호출부 3곳을 전부 적발**했다(0819 `geo_blocked`와 같은 패턴). 흐름은

```
로그인(비밀번호 확인) → TOTP 미등록이면 QR 등록 → TOTP 확정
  → must_change_password 확인 → true면 JWT 대신 변경 전용 단명 토큰(10분)
  → 비밀번호 변경 → 새 비밀번호로 다시 로그인
```

⛔ 불변 5개
1. 변경 토큰은 **`userId` 클레임을 담지 않는다**(`puid`) — 미들웨어 가드가 뚫려도 `req.user`가 안 채워진다. 인계 티켓과 같은 규율.
2. 토큰만으로 바꾸지 않는다. **현재 비밀번호를 다시 확인**한다 — 토큰이 새면 계정이 넘어간다.
3. 변경 후 세션을 발급하지 않는다. 다시 로그인한다(TOTP도 다시 지난다).
4. **컬럼이 없으면 강제하지 않는다.** 42703에 fail-closed면 전 슈퍼관리자가 로그인 불가가 된다. 통제를 위해 서비스를 세우지 않는다.
5. TOTP 확정 경로에서 막을 때도 **`totp_enrolled`는 기록한다** — 실제로 일어난 일을 안 남기면 감사 기록이 사실과 어긋난다.

**계정 생성·중지 화면** — 「직원 계정·권한」 탭에 추가. 생성은 `must_change_password=true`로만 만들어지고,
중지는 행을 지우지 않는다(지우면 그 계정이 남긴 기록의 주인이 사라져 심사에 낼 이력이 끊긴다).
비밀번호는 해시만 저장하고 **감사 로그 details에 어떤 형태로도 넣지 않는다**(감사 로그는 열람 대상이다).
