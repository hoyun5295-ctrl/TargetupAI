# [지시서] 자체게이트웨이 — 알림톡 템플릿·senderkey 처리 규약 사전 개발

> 발신: Harold / 작성: 비토 (한줄로 CTO 에이전트)
> 수신: 자비스 (자체게이트웨이 담당)
> 일자: 2026-07-14
> 배경 문서: `docs/레거시서버_폐기_플랜.md` §2-3 / QTmsg-사용자메뉴얼ver4.0 p.6~9

## 0. 배경 (왜 지금 만드는가)

레거시 템플릿관리자(event-admin)를 한줄로로 이관한다. 레거시 중계서버(54/58, 강문희 운영)는 "승인 템플릿 → 엔진 매핑 등록"을 API로 자동화하는 방식(구성안 1안)으로 마무리한다.

자체게이트웨이도 같은 규약을 지금 미리 갖춰라. 목적 2개:
1. 앞으로 업체들이 레거시 중계서버 → 자체게이트웨이로 옮겨올 때 무리 없이 수용한다.
2. 한줄로 쪽 연동 코드(매핑 등록 클라이언트)를 레거시/자체 양쪽에 동일 규약으로 재사용한다.

## 1. 대원칙

- **신규·이관 업체 온보딩 기본 스펙 = 발송 INSERT에 senderkey 동봉.** `k_etc_json = '{"senderkey":"..."}'`. 자체게이트웨이는 이것을 알림톡(msg_type K)의 공식 1급 경로로 지원한다. (QTmsg 매뉴얼은 이 방식을 친구톡 기준으로만 문서화했다 — 우리 게이트웨이는 알림톡에도 공식 지원으로 명문화한다.)
- **매핑 테이블은 보조·호환 장치다.** 발송 프로그램을 못 고치는 업체, 타사 템플릿코드를 그대로 쓰는 업체를 수용하는 용도. 레거시 엔진과 동일 시맨틱을 유지한다.
- **명칭 정본 준수.** 필드명은 QTmsg 매뉴얼 정본 그대로: `k_template_code`(varchar 30), `k_etc_json` 내 json 키 `senderkey`. (강문희 구성안 PPT의 `k_templ_code`/`senerkey` 표기는 오타 — 절대 스펙에 올리지 마라.)

## 2. senderkey 해석 우선순위 (알림톡 K)

레거시 엔진과 호환되게 아래 순서로 구현한다.

1. 매핑 테이블에 (bill_id, 외부템플릿코드) 행 존재 → 매핑의 senderkey·승인코드 사용 (최상위 — 레거시 매뉴얼 p.8 "우선순위 최상위" 동일)
2. 매핑 없음 + `k_etc_json.senderkey` 존재 → 그대로 통과 (동봉 방식)
3. 둘 다 없음 → 실패 처리. 결과코드는 QTmsg 체계의 7103(senderkey 유효하지 않음) 계열로 명확히 남긴다. 조용한 실패 금지.

## 3. 개발 항목

### 3-1. 템플릿 매핑 테이블
레거시 "카톡템플릿매핑관리"와 동일 기능 3개를 담는다:
- senderkey 세팅 (알림톡 발송 시 주입)
- 템플릿코드 치환 (외부템플릿코드 → 승인 템플릿코드. 타사 코드 쓰던 업체 수용용. 신규 업체는 두 값 동일)
- 라우팅 (출중계 모듈 구분이 필요해지면 확장)

키 = (bill_id, 외부템플릿코드) UNIQUE.

### 3-2. 매핑 관리 API 3종
한줄로가 호출한다. 레거시(강문희 측 API수신프로그램)와 규약을 맞춘다.

| API | 요건 |
|---|---|
| 등록(upsert) | **멱등.** 동일 키 존재 시 senderkey·승인코드 갱신 후 성공 응답. 재시도 안전이 목적 |
| 조회 | bill_id 단위 전량 반환. 한줄로 대조 워커·효과 검증이 사용 |
| 삭제 | 제공하되 한줄로는 자동 호출하지 않는다(수동 승인 시만) |

- payload: `bill_id`, `senderkey`, `approved_template_code`(승인 코드), `external_template_code`(업체 발송 코드), `route`(선택)
- 반영: 등록 즉시 발송에 반영(프로세스 재기동 불요)
- 인증: API 키 + IP 화이트리스트(한줄로 서버 IP만)

### 3-3. 결과코드
QTmsg 체계 유지. 최소 보장: 7103(senderkey 무효) / 7105·7106(발신프로필 없음·삭제) / 7204(템플릿 불일치) / 7315(템플릿 없음). 한줄로 대조 워커가 이 코드들을 감시 지표로 쓴다.

## 4. 검증 (완료 선언 전 의무)

실측 1건 시나리오를 통과시키고 로그를 증거로 남겨라:
1. 테스트 bill_id로 upsert 호출 → 조회로 행 실존 확인
2. 매핑 경유 알림톡 1건 실발송 → 성공 코드 확인
3. 매핑 없는 상태에서 `k_etc_json.senderkey` 동봉 알림톡 1건 실발송 → 성공 코드 확인
4. 둘 다 없는 발송 1건 → 7103 계열 실패 코드 확인 (조용한 실패 아님을 확인)

## 5. 참고

- 비토 라인(SMSQ_SEND_13)은 이미 `k_etc_json` senderkey 주입을 실전 사용 중(2026-07-07 강조표기형 종결 건) — 동봉 방식의 실전 선례.
- 레거시 매핑 목록(4,159건 엑셀)은 한줄로가 보관 — 업체가 자체게이트웨이로 이관될 때 해당 업체 분만 upsert API로 이식하면 된다.
