## §2 지켜야 할 성질(이 설계의 판정 기준)

원본 행 하나의 동의 표 = 수신 · 거부(미수신 또는 탈퇴) · 모름(값은 있는데 알아볼 수 없음) · 없음(빈칸 · 매핑 없음) 넷.

**P1 거부 우선.** 같은 회사 · 같은 번호의 원본 행 가운데 거부가 하나라도 있으면 거부. 아니면 수신이 하나라도 있으면 수신. 아니면 이미 있는 고객 = 옛 값 그대로(바꾸지 않음) · 신규 고객 = 모름이 하나라도 있으면 미동의 · 전부 없음이면 지금 기본값(동의).
**P2 순서 무관.** 원본이 같은 동안 결과(고객 행 수신동의 · 싱크 수신거부 원장)는 행 순서 · 요청 나뉨 · 묶음 경계 · 주기 · 에이전트 수와 무관하게 같다. 한 주기 안에서 왔다 갔다 하지 않는다(D3 · 그로 인한 감사 기록 0).
**P3 원본 변화는 반영된다.** 거부했던 행이 수신으로 바뀌거나 원본에서 지워지면 다음 세대 공개에서 반영된다(닫히지 않는 상태 0 · R6). 반영 실패(수신거부 해제 실패 등)는 다시 시도된다.
**P4 사람의 명시 거부는 건드리지 않는다.** 수신거부 화면 · 080 · 파일 거부(source manual · 080 · upload)는 싱크가 지우지 않는다(`sync.ts:305-306` 규칙 그대로).
**P5 기존 동작 보존.** 한 행뿐인 번호 · 자사몰 회원 · 한 명 추가 · 발송 자격 읽기(`consentSql` · 수신거부 읽기)는 바뀌지 않는다. 옛 에이전트(1.7.5 이하)의 고객 적재는 층 1 만 더해진다. **바뀌는 것(명시)** ① 1.7.6 에이전트 회사의 싱크 동의는 거부 = 적재에서 바로 · 수신으로 올리기 = 실행 끝(세대 공개) · 그 실행에 들어온 신규 고객은 거부가 아니면 실행 끝까지 대기(NULL · 발송 대상 아님 · 수신거부 등록 없음) · 세대를 모은 뒤 원본에 새로 생긴 수신 행은 다음 실행에 반영(§3-2 ⑤) · 섞인 회사의 옛 에이전트 고객 적재는 받지 않음(⑧) ② 공용 기본값은 새로 넣은 행에만 걸린다(이미 있는 NULL 행을 다른 문이 동의로 채우지 않음 · §3-2 ⑤).

### 3-2 층 2 — 세대 요약(싱크 · 에이전트 1.7.6 + 서버 · D2 · D3 · D5)

**왜.** 싱크 요청끼리는 서로 모르고, 요청 사이 · 주기 사이 · 증분에서 「같은 번호의 다른 원본 행이 무엇인가」는 원본에만 있다. 1판(원본 키 원장)은 모으는 도중에 공개해 반례가 났다(Codex 1R #1 · #2 · #6). 2판은 **원본 전체를 한 번 다 모은 뒤에만 공개**한다.
**LESSONS_BACKEND 「같은 사실을 두 번째 테이블에 복사하지 마라」 세 질문.** ① 멱등키 = (에이전트 · 번호) 요약 하나 · 세대 = 서버가 발급한 패스 번호 ② 재수렴 = 매 실행 원본 전체를 다시 모아 그 에이전트 확정 패스를 통째로 바꿈(상태 한 번) · 원본 키 이력 · 지우는 시각 규칙 없음 ③ 소비처 오염 = 세 표(패스 · 모은 행 · 기준)는 CT 한 파일만 읽고 쓴다(계약 시험) · 고객 수 · 활성 고객 · 통계 어디에서도 세지 않는다.

**① 표(DDL · §5).**
- `sync_consent_passes` = 세대(패스 번호 · 에이전트 · 회사 · 서버 시작 시각 · 상태 `collecting` → `collected` → `applying`(확정 · 고객 반영 중) → `done` / `abandoned` · 폐기 표식 `retiring` · 공개 진행 위치 · 근거를 커밋한 고객 적재 묶음 번호 `load_batches` · 바로 앞 확정 패스 `prev_pass_id` · 끝난 시각).
- `sync_consent_stage` = 패스마다의 (패스 · 번호) → 거부 있음 · 수신 있음 · 모름 있음 · **패스가 `applying` 으로 바뀌는 순간 그 행들이 그 에이전트의 확정 요약이다**(따로 옮겨 적지 않는다 · Codex 6R #1 · 요약 표 없음).
- `sync_consent_marks` = (회사 · 번호) → 마지막 거부 · 모름 관측 시각 · 처음 올리기를 미룬 시각 · 올리기 규칙 R\* 의 기준(④).
- 에이전트를 지우면 CASCADE · 단 지우기 전에 ⑥ 폐기를 먼저 돈다.

**3판 · 4판의 줄기(Codex 2R · 3R).** 1.7.6 에이전트가 있는 회사의 싱크 동의를 **올리는 곳은 세대 공개 하나**다(2판은 고객 적재 ⑤ 표도 올려 두 곳이 서로 다른 순간의 원본으로 정했다 = 2R #1). 고객 적재는 거부만 바로 쓰고 그 근거를 패스에 더하며(불변식 I1 · ⑤), 신규 고객은 거부가 아니면 대기(NULL)로 넣는다. 실행 순서 = 모으기 → 고객 적재 → 공개라 그 실행에 들어온 신규 고객도 같은 실행 끝에 정해진다.

**② 에이전트 1.7.6 — 고객 실행 한 번 = 세대 → 고객 적재.**
1. `POST /api/sync/consent-pass/start` → 서버가 패스 번호 · 시작 시각을 발급(그 에이전트의 `collecting` · `collected` 패스는 `abandoned` 로 닫고 그 모으던 행은 지운다 · `applying` 패스는 닫지 않는다 = 이미 확정된 요약이라 새 패스가 확정될 때까지 그대로 읽힌다 · 그 고객 반영이 덜 끝났으면 새 패스의 2단계가 어긋남 대조로 마저 맞춘다 · 폐기 중이면 409).
2. **원장 패스** = 원본 고객 표 **전체**의 가벼운 칸(번호 · 수신동의 · 탈퇴 칸)만 읽는다. 정규화는 지금 고객 적재와 같은 함수(설치별 값 분류 · 탈퇴 = 거부로 접음 · 모름 표시). 묶음마다 번호별로 미리 묶어 `POST /api/sync/consent-pass/stage`(패스 번호 · 최대 10,000번호).
   - **★ 1104 구현 확정(Harold 「전체 조회로 확정」)**: 어댑터 6종에 칸 골라 읽기 조회가 없어 원장 패스는 지금 고객 전량과 같은 조회(키셋 → 실패면 OFFSET) · 매핑 · 정규화로 행 전체를 읽고, 서버에는 번호 · 수신동의 · 모름 세 칸만 싣는다(`sync-agent/src/sync/engine.ts` stageConsentLedger · 묶음 = 행 그대로 · 서버가 번호별로 접는다 · Zod 검증을 거치지 않음 = 다른 칸이 틀린 행의 거부도 거부). 두 길이 같은 함수로 읽어 같은 번호를 다르게 읽는 틈이 없다. 비용 = 고객 실행마다 원본 전체 읽기 한 번 더(엠티 하루 1 → 2). 엠티 원장 패스 소요 시간 = VM 실측 때 잰다 · 문제가 되면 그때 칸 골라 읽기를 처방한다.
3. 끝까지 읽으면 `POST /api/sync/consent-pass/stage-done`(모으기 끝 표시 · 이 뒤 stage 0).
4. 고객 적재(지금 그대로 · 증분이면 증분) · 요청에 `agent_id` 와 패스 번호를 싣는다(서버는 이 요청의 동의 칸을 쓰지 않는다 · ⑤).
5. 고객 적재가 끝나면 `POST /api/sync/consent-pass/complete`(이번 패스에서 보낸 고객 적재 묶음 수를 싣는다)를 `done` 이 올 때까지 되풀이(한 번에 번호 5,000개 · 같은 요청 재전송 = 같은 결과). 고객 행만 실패한 묶음(200 · 행 실패)은 괜찮다 · **503 · 시간 초과 · 응답 없음으로 끝난 묶음이 하나라도 있으면 complete 하지 않고 그 패스를 버린다**(다음 실행에 처음부터 · Codex 5R #5).
6. 2 · 3 이 실패하면 그 실행의 고객 적재 · 공개를 하지 않는다(다음 주기에 1 부터).
세대 주기 = 고객 실행마다(엠티 = 하루 한 번 · 원본 가벼운 칸 전체 읽기 하루 한 번이 더해진다 · §4 ⑥).

**③ 서버 — 모으기.** `stage` = 패스가 그 회사 · 그 에이전트의 `collecting` 일 때만 · 번호 정규화 = `normalizePhone`(고객 행과 같은 값) · (패스 · 번호) 행에 셋 다 「또는」으로 더한다. 거부 있음 번호는 같은 트랜잭션에서 `sync_consent_marks.refusal_seen_at` 도 지금으로(더 늦은 값 · R\* 의 T(P) · 모름은 쓰지 않는다 · 5R #3). `stage-done` = `collecting` → `collected`(이 뒤 stage 주소는 409 · 고객 적재의 근거 더하기는 `collected` 패스에 계속). complete = `collected` · `applying` 일 때만. 모든 세대 주소는 회사 잠금 아래 상태를 보고 바꾼다(start 의 abandoned 처리와 같은 잠금 · Codex 2R 다음 단계). 고객 행 · 수신거부는 공개 전 건드리지 않는다(Codex 1R #1).

**④ 서버 — 공개(complete) = 두 단계(Codex 5R #2).** complete 는 회사 잠금 아래 상태를 보고 다음 한 묶음(번호 5,000)을 처리한다 · 같은 요청 재전송 = 진행 위치에서 이어가거나 `done` 을 그대로 돌려준다(멱등 · Codex 1R #3).
- **받는 조건(Codex 5R #5).** complete 는 에이전트가 보낸 「이번 패스에서 보낸 고객 적재 묶음 수」가 서버가 근거를 커밋한 묶음 수(`sync_consent_passes.load_batches` · ⑤)와 같을 때만 받는다 · 다르면 409 → 그 패스 `abandoned` · 다음 실행에 처음부터. 근거 커밋 뒤 고객 행만 실패한 묶음은 센 묶음이다(공개 허용) · 근거 커밋 전에 503 · 시간 초과 · 응답 없음으로 끝난 묶음은 세지 않는다(공개 거부).
- **1단계 확정**(`collected` → `applying` · 문장 하나 · 원자): 그 에이전트의 바로 앞 확정 패스(`applying` · `done` 중 시작이 가장 늦은 것)를 `prev_pass_id` 로 적고 상태를 바꾼다. 이 순간부터 회사 접기는 이 패스의 모은 행을 그 에이전트 요약으로 읽는다 · 그 전까지는 앞 확정 패스 행을 온전히 읽는다(덮어쓰기 0 · 교체 중 반쪽 요약 0 · Codex 6R #1). 고객 행 · 수신거부는 건드리지 않는다.
- **2단계는 최신 확정 패스만(Codex 7R #1).** complete 묶음마다 회사 잠금 안에서 그 패스가 그 에이전트의 확정 패스(`applying` · `done`) 중 시작이 가장 늦은 것인지 본다 · 아니면(더 새 패스가 이미 확정) 고객 행 · 수신거부 · `sync_consent_marks` 를 하나도 바꾸지 않고 409(`superseded`) · 그 패스 행은 새 패스의 「사라진 번호」 계산(`prev_pass_id`)과 정리에만 쓰인다. 그래서 회사 접기 · R\* 는 언제나 각 에이전트의 최신 확정 패스 집합 기준이다(처음 미룸 판정도 그 집합의 가장 늦은 시작 M · 8R). 폐기(⑥ 2)도 같은 확인(폐기 중 에이전트의 패스 complete = 409).
- **2단계 고객 반영**(`applying`): 대상 번호 = 이 패스의 모은 행 번호 ∪ `prev_pass_id` 에는 있고 이 패스에는 없는 번호(원본에서 사라짐) ∪ 그 회사 `sync_consent_marks.raise_since` 가 있는 번호 ∪ 그 회사 고객 행 · sync 수신거부가 접힌 판정과 어긋난 번호(묶음은 번호 글자 순 범위로 자르고 첫 묶음 = 처음부터 · 마지막 묶음 = 끝까지라 어긋남 대조가 그 회사 번호 전체를 한 번 덮는다). 번호 순 5,000개씩:
  - 회사 접기 = 확정 패스(`applying` · `done`) 중 에이전트마다 시작이 가장 늦은 것의 모은 행(폐기 중 제외)을 「또는」 → 판정 = 고객 행이 값 있음이면 `decideForExisting` · NULL(대기)이면 `decideForNew`(거부 · 수신 · 모름 = 미동의 · 전부 없음 = 기본 동의).
  - **낮추기**(판정이 미동의인데 고객 행이 동의 · NULL) = 바로.
  - **올리기**(판정이 동의인데 고객 행이 미동의 · NULL · 신규 빈칸 기본 동의 포함 · Codex 5R #4) = **규칙 R\***: 폐기 중 아닌 모든 에이전트의 「확정 패스(`applying` · `done`) 중 마지막 것」 시작 ≥ **T(P)** = max(`refusal_seen_at`(P), `raise_since`(P)). 이 패스도 1단계로 확정됐으므로 「확정 패스」에 든다(첫 실행 5,001번호도 같은 실행 안에서 정해진다 · 5R #2).
    - **처음 미룸 판정 = 회사 접기에 쓰는 확정 집합 기준(Codex 8R #1).** M = 폐기 중 아닌 모든 에이전트의 최신 확정 패스 시작 중 가장 늦은 것. P 의 `raise_since` 가 비어 있고 그 집합에 M 보다 먼저 시작한 확정 패스가 있으면(= 다른 에이전트 요약이 가장 새 요약보다 옛것) 올리지 않고 `raise_since` = M(처음 값 보존 · 그 뒤 재판단 때 다시 정하지 않는다 · 5R #1). 요청한 패스가 누구인지는 이 판정에 들어가지 않는다(다른 에이전트의 미완료 최신 패스가 재개돼도 같은 판정 · 8R). 그다음부터 T(P) 는 고정이다 → 에이전트들이 그 시각 뒤 한 번씩 더 마치면 지난다(A20 → B30 → A40 → B50 에서 B30 의 반영 때 raise_since = 30 · A40 의 반영 때 지남(A40 ≥ 30 · B30 ≥ 30) · 유한).
    - 지나면 올리고 `raise_since` 를 지운다 · 못 지나면 다음 공개(어느 에이전트든)의 2단계가 다시 본다.
    - 에이전트 하나인 회사 = 다른 에이전트 조건 없음 · T(P) = 마지막 거부 관측 → 거부를 본 패스 자신은 판정도 거부라 올릴 일이 없고, 다음 패스가 원본에서 거부가 사라진 것을 보면 올린다(재동의 · 지움 = 다음 실행 · P3).
  - 대조 = 고객 행이 바뀐 번호 + 어긋난 번호 → `reconcileSyncUnsubscribesFor`(같은 트랜잭션 · 실패면 그 묶음 전체 되돌림 · 진행 위치 그대로 → 다음 complete 가 같은 묶음 = 해제 실패 재시도 · 1R #6 · 고객 적재 끝 대조가 실패한 번호도 다음 세대에 고쳐진다 · 6원칙 ③).
  - 마지막 묶음 = `done` · 끝난 시각 · 그 에이전트의 이 패스보다 앞선 패스 행(확정 · 버림 모두) 삭제(지금 확정 하나만 남김).
- **막는 근거 = 실제 거부만(Codex 5R #3).** `refusal_seen_at` 은 거부(미수신 · 탈퇴)를 볼 때만 쓴다 · 모름은 모은 행(`any_unknown`)에만 남아 신규 판정에 쓰인다(기존 고객의 모름 = 바꾸지 않음 · 수신을 막지 않음).

**불변식 I1(Codex 3R #1 · 1R · 2R 과 같은 부류의 세 번째 = 「올리는 판정이 이미 본 거부를 못 본다」를 하나로 묶음).** 관측한 **낮추는 근거(거부 · 모름)** 는 어디서 왔든(모으기 · 고객 적재) 그 패스의 근거(`sync_consent_stage`)에 쌓이고 버려지지 않는다. **올리기**(수신 · 대기 → 동의)는 그 근거를 다 본 공개에서만 한다. 낮추기는 어디서든 바로 해도 된다(안전한 방향).

**⑤ 서버 — 고객 적재(1.7.6 요청 = `agent_id` 와 패스 번호가 실린 요청).** 그 에이전트 · 그 패스가 맞는지(패스 상태 `collected` · 폐기 중 아님) 회사 잠금 아래 확인 → 아니면 409.

- **근거 먼저 · 따로 커밋(Codex 4R #1).** 고객 행을 쓰기 **전에**, 따로 한 트랜잭션(회사 잠금)으로 그 요청의 낮추는 근거(거부 있음 · 모름 있음 번호)를 그 패스의 `sync_consent_stage` 에 「또는」으로 더하고, 거부 있음 번호만 `sync_consent_marks.refusal_seen_at` 을 지금으로(더 늦은 값) 쓰며, 같은 트랜잭션에서 그 요청의 묶음 번호를 `sync_consent_passes.load_batches` 에 더한다(중복 없이 · ④ complete 받는 조건) · 수신 근거는 더하지 않는다. 이 트랜잭션이 실패하면 요청 전체 503(고객 행 0 · 에이전트 재전송 · 근거 없이 쓰지 않음). 근거는 고객 행 청크 · 한 행 길이 나중에 실패해도 남는다(I1 · stage Y → 적재 N → 고객 행 실패 → 공개 = 거부 유지). 같은 요청 재전송 = 「또는」 · 더 늦은 시각이라 두 번 더해도 같다.
- 그다음 지금 청크 트랜잭션: **거부가 있는 번호 = 고객 행을 거부로 바로 쓴다**(신규면 거부로 넣음) · 그 밖(수신 · 빈칸 · 모름) = 업서트에 null(이미 있는 고객 = 그대로 · 신규 = NULL = 대기). 청크 실패 뒤 한 행씩 길도 같은 규칙(근거는 이미 커밋됨).

**⑧ 옛 에이전트 · 섞인 회사(Codex 3R #2).** 1.7.5 이하만 있는 회사 = 세대 없음 → 층 1 만(요청 사이는 1.7.6 으로 올려야 닫힘 · §4 ④). 한 회사에 옛 · 새 에이전트가 섞이면(그 회사에 패스가 있는 에이전트가 하나라도 있는데 `agent_id` 없는 고객 적재가 옴) **그 고객 적재를 409 로 받지 않는다**(「같은 회사의 다른 에이전트가 1.7.6 입니다. 이 에이전트도 1.7.6 으로 올리거나 슈퍼관리자에서 삭제해 주세요」 · 운영 경보 회사당 하루 한 통 · R14 공용 입구). **판정 자리 = 접수 때 한 번이 아니라 옛 요청의 청크마다 · 한 행 길마다 · 요청 끝 동의 대조 직전마다, 회사 잠금 아래**(Codex 4R #3): 첫 start 도 같은 회사 잠금을 잡으므로, 이미 접수돼 돌던 옛 요청은 첫 start 뒤의 첫 청크에서 멈춘다(그 앞 청크는 세대 전이라 지금 동작 그대로) · 요청 끝 동의 해제도 패스가 생겼으면 하지 않는다. 엠티 원격 교체 = 1.7.5 프로세스가 끝나고 1.7.6 이 첫 start 를 한다 · 그 사이 서버에 남은 1.7.5 요청도 위 판정으로 멈춘다. 옛 요청은 근거를 패스에 붙일 수 없고(에이전트 표시가 없다) 그 기본값 · 동의 해제가 공개된 거부를 비켜 간다 → 받는 길을 열어 두지 않는다. 섞이는 때 = 회사 지정 릴리스를 그 회사 에이전트 티어마다 같은 날 거는 것으로 막는다(⑩ · §8).

**⑨ 표가 없으면(DDL 전).** 세대 주소 · 1.7.6 고객 적재 = 503 `DB_MIGRATION_PENDING`(db_alter_safety_net · `isMissingSchemaError` 재사용) · 에이전트는 다음 주기에 처음부터. 옛 에이전트 적재는 표를 읽지 않는다(영향 0).

**⑩ 1.7.6 을 엠티에 원격으로(Harold 1103).** 자동 업데이트는 이미 있다(하트비트 → `GET /api/sync/version` → 내려받기 · 체크섬 · 교체 · 재시작 · `heartbeat/index.ts:185` · `updater/index.ts`). 그러나 릴리스는 빌드 티어(OS × DB) 단위라(`sync.ts:1528-1535` `tier = $1 OR tier IS NULL`) 그대로 올리면 같은 티어의 다른 고객사 에이전트도 전부 바뀐다(FEATURE-SYNC-AGENT §10 「고객사마다 출고」 위반). → `sync_releases` 에 회사 칸을 더해 **그 회사에만 거는 릴리스**를 만든다(회사 칸이 빈 지금 릴리스 = 지금 동작 그대로 · 고르는 순서 = 회사 지정 > 티어 > 전역). 원격 교체 경로(Windows · SYSTEM 예약 작업 재기동)는 VM 에서 1.7.5 → 1.7.6 으로 실측한 뒤에만 엠티 릴리스를 켠다.
**서버만으로(1.7.5 그대로) 닫을 수 없는 이유(1103 확인).** 1.7.5 는 요청마다 `mode` · `batchIndex` · `totalBatches` 를 싣지만, 묶음 전체가 무효 행이면 요청을 보내지 않고(`engine.ts:1249` `validData.length > 0`) `totalBatches` 는 시작 때 센 행 수라(`engine.ts:890`) 「전량이 끝까지 왔다」를 서버가 증명할 수 없다. 증명 없이 공개하면 못 받은 쪽에 있던 거부가 풀린다(1R #1 과 같은 꼴).

## §5 DDL(배포 앞 · 확인 출력 뒤 push)

먼저 없는지 확인(Harold 실행 · 결과 0행이어야 함):
`SELECT table_name FROM information_schema.tables WHERE table_name IN ('sync_consent_passes','sync_consent_stage','sync_consent_marks');`
FK 대상 확인: `SELECT column_name, data_type FROM information_schema.columns WHERE table_name='sync_agents' AND column_name IN ('id','company_id');`

```sql
CREATE TABLE sync_consent_passes (
  pass_id        uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  agent_id       uuid        NOT NULL REFERENCES sync_agents(id) ON DELETE CASCADE,
  company_id     uuid        NOT NULL,
  started_at     timestamptz NOT NULL DEFAULT now(),
  state          text        NOT NULL DEFAULT 'collecting' CHECK (state IN ('collecting','collected','applying','done','abandoned','retiring')),
  load_batches   integer[]   NOT NULL DEFAULT '{}',
  prev_pass_id   uuid,
  publish_cursor text,
  finished_at    timestamptz
);
CREATE INDEX sync_consent_passes_agent ON sync_consent_passes (agent_id, state);
CREATE INDEX sync_consent_passes_company ON sync_consent_passes (company_id, state, started_at);
CREATE TABLE sync_consent_stage (
  pass_id     uuid    NOT NULL REFERENCES sync_consent_passes(pass_id) ON DELETE CASCADE,
  phone       text    NOT NULL,
  any_false   boolean NOT NULL DEFAULT false,
  any_true    boolean NOT NULL DEFAULT false,
  any_unknown boolean NOT NULL DEFAULT false,
  PRIMARY KEY (pass_id, phone)
);
CREATE TABLE sync_consent_marks (
  company_id      uuid        NOT NULL,
  phone           text        NOT NULL,
  refusal_seen_at timestamptz,          -- 마지막 거부 · 모름 관측(서버 시각 · 더 늦은 값만)
  raise_since     timestamptz,          -- 처음 올리기를 미룬 패스 시작(처음 값 보존 · 올리면 지움)
  PRIMARY KEY (company_id, phone)
);
```
공용 기본값 바꿈(⑤) 앞 확인(Harold 실행 · 지금 운영에 이미 있는 대기 꼴 행 수): `SELECT COUNT(*) FROM customers WHERE sms_opt_in IS NULL;`
새 표라 운영 표 잠금 0 · 되돌리기 = DROP TABLE 세 줄.

회사 지정 릴리스(3-2 ⑩) · 먼저 확인: `SELECT column_name, data_type FROM information_schema.columns WHERE table_name='sync_releases' ORDER BY ordinal_position;`(칸 이름 · 지금 `company_id` 없음이어야 함)
```sql
ALTER TABLE sync_releases ADD COLUMN company_id uuid NULL;   -- NULL = 지금 릴리스 그대로(티어 · 전역)
```
