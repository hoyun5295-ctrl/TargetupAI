# 거래내역서 상세 구분 칸 — 처리 결과

## 접수 (서수란)

> 거래내역서 상세내역에 구분값에 웹의 경우 사용자명, Agent의 경우 계정, 대상 ID가 확인되어야 합니다. (통계처럼)
> ex. 라프레리의 경우 거래내역서에서 사용 지점을 확인하여 본사에서 청구하고 있습니다.

## 결론 — 요구 전부 처리됨 (2026-07-31, 배포 대기)

기준은 **"통계처럼"** 이다. 통계 화면이 보여주는 축이 곧 요구다.

| 통계 화면 | 거래내역서 | 상태 |
|---|---|---|
| 웹 = 사용자(계정) | 계정명 | 완료 |
| 에이전트 = `B0228 / 제이씨패밀리`, `B0229 / 제이씨패밀리_전산팀` | 같은 `발송ID / 발급명` | 완료 |

구현 = `utils/billing-scope-label.ts`(CT, 순수) — PDF·상세 모달·메일이 이 함수 하나를 쓴다.

- 웹 행: `billing_items.user_id`에 값이 이미 있었는데 읽는 쪽이 users를 안 붙이고 있었다 → `LEFT JOIN users` 추가.
- 에이전트 행: `발송ID / 발급명`. **화면에만 있고 PDF·메일에는 빠져 있던 것**을 공용 로더(`loadBillingStatementData`)로 옮겨 3면 동일.
- 동반 정정: 구분 칸 판정이 PDF 삼항식·화면 맵 두 벌이라 이미 갈려 있던 것을 CT로 통일 / 화면 라벨 맵에 `extra` 키가 없어 내부 코드가 그대로 노출되던 것 / PDF 62pt 칸에서 긴 이름이 두 줄로 흘러 다음 행과 겹치던 것(`fitToWidth` 실측 폭 말줄임).

### 배포 후 확인

거래내역서 상세(화면·PDF 둘 다)에서 에이전트 행이 `B0228 / 제이씨패밀리` 형태로, 웹 행이 계정명으로 찍히는지.

## 참고 — `StoreId`는 이 요구와 무관하다

게이트웨이 원장에 `StoreId`라는 별도 컬럼이 있고 정산 엑셀에 `대상ID` 열로 나간다. **접수의 "대상 ID"는 이것이 아니라 위 발송ID를 가리킨다**(통계 화면이 보여주는 값이 발송ID·발급명이므로).

`StoreId`는 우리가 발급하는 값이 아니라 고객사가 발송에 실어 보내는 값이라 회사마다 쓰임이 다르고(피케이포유 325 = 지점 코드 / 제이씨패밀리 B0229 2026-07 = 29,598개로 행 30,314과 거의 1:1 = 발송 건 식별자 — `send-usage-aggregation.ts:843`·`.test.ts:794` 실측), 그래서 2026-07-26에 청구 축에서 제외했다. **지금 요구에 필요 없으므로 이 문서에서 과제로 두지 않는다.** 나중에 지점별 청구가 실제로 필요해지면 그때 회사 목록을 받아 별도 내역으로 붙이면 된다.

## 다음 세션 과제 (오늘 조사에서 드러난 별건)

정산 축이 아니라 **발송 축** 문제 세 건과, 이번에 의도적으로 미룬 두 건.

1. **아이디룩 미발송 7,701건** — 2026-07-16 예약 2건(285 + 7,416). 캠페인 상태는 `completed`인데 발송 큐에 행이 0(라인 1~11 전 테이블 확인). 고객사는 발송된 것으로 알고 있을 수 있다. **우선순위 높음.**
2. **레거시 예약 직접발송 1,653건 전량 실패** — 아이디룩 565 · 인비토 186·901·1. 100% 실패라 수신자 사유가 아니라 경로 공통 원인 의심.
3. **여정(journey) 후불 미청구 통로** — `prepaidDeduct`가 후불에서 no-op이고 `campaign_runs`도 없어 월정산 두 축 어디에도 안 걸린다. 실데이터 0건이라 지금 새는 돈은 없다. 청구 축에 넣으면 선불 이중과금 위험이 있어 별도 설계 필요.
4. **대기(pending) 차단 게이트 완성** — 오늘 넣었다가 차단을 걷어내고 관측만 남겼다(미리보기 `billing_guard.pending_types`). 채널마다 "결과 확정"의 의미가 달라(큐 상태코드 / 스팸 테스트 상태+결과 / 에이전트 원장) 한 함수로 못 덮는다. 스팸 워커에는 결과를 확정하지 않은 채 테스트만 완료로 넘기는 경로가 있고, 최소과금 정액 발행은 게이트를 아예 안 지난다. 채널별 종결 판정 정규화가 선행 과제.
5. **미리보기 guard와 발행 차단 집합 불일치** — `BILLING_PERIOD_OVERLAP`·`BILLING_MANUAL_COMPLETED`·`BILLING_NOTHING_TO_ISSUE`가 미리보기에 없어 "미리보기 통과 → 발행 실패"가 난다. 기존 구조·UX 어긋남.
