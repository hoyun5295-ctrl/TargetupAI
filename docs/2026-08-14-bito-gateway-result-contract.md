# 비토 게이트웨이 → 한줄로 발송통계 적재 규격

> 수신: 자비스 (비토 게이트웨이 개발) · 발신: 한줄로(TargetUp) · 작성 2026-08-14
> 대상 = **에이전트만 쓰는 고객사**(한줄로 화면을 거치지 않고 게이트웨이로 직접 발송하는 업체)의 발송내역.
> 한줄로가 보낸 발송의 결과 회신은 이 문서 범위가 아니다(그건 SMSQ 큐 행 제자리 갱신으로 이미 동작 중).

---

## 0. 왜 필요한가

에이전트 전용 고객사의 발송은 한줄로 DB에 아무 기록도 남기지 않는다. 게이트웨이 안에서만 일어난다.

그런데 한줄로는 그 발송량을 알아야 한다.

- **발송통계 화면** — 고객사가 자기 발송량을 본다
- **청구서·거래내역서** — 유형별 성공 건수 × 단가가 청구 금액이다
- **선불 잔액 확인** — 선불 고객사의 잔액을 화면에 띄운다

QTmsg 쪽은 이미 이 구조로 돌고 있다. **비토도 같은 자리에 같은 형식으로 넣으면, 한줄로 코드를 한 줄도 안 고치고 그대로 합류한다.**

---

## 1. 이미 동작 중인 구조 (참고 모델)

```
[QTmsg 엔진]  ──수집엔진──▶  [한줄로 수집 DB · MariaDB]
                                RSRM_SalesStts   ← 일별 발송 집계
                                RSRM_SalesMst    ← 발송ID 원장(발급명)
                                RSRM_FillAmtHist ← 충전 이력
                                       │
                                       │  한줄로가 조회만 한다 (복제 안 함)
                                       ▼
                          발송통계 화면 · 청구서 · 선불 잔액
```

**회사 매칭 축** — 한줄로는 `발송ID(CustId)`로 어느 고객사 발송인지 판정한다. 한줄로 쪽 매핑 테이블(`company_agent_ids`)에 그 발송ID가 등록돼 있어야 귀속된다.

---

## 2. 비토가 할 일 — 한 문장

> **한줄로 수집 DB의 `RSRM_SalesStts` 테이블에, 일자 × 발송ID × 대상ID × 메시지유형 단위의 집계를 UPSERT 한다.**

건별 원문이 아니다. **일별 집계 숫자**만 넣으면 된다. 개인정보(수신번호·본문)는 오지 않는다.

---

## 3. 테이블 계약 — `RSRM_SalesStts`

| 컬럼 | 타입 | 넣을 값 | 필수 |
|---|---|---|---|
| `DestDt` | varchar(8) | 발송 일자 `YYYYMMDD` — **KST 기준** | **필수** |
| `CustId` | varchar | 발송ID (§5) | **필수** |
| `StoreId` | varchar | 대상ID(지점·브랜드 구분). 없으면 빈 값 | 선택 |
| `MsgType` | varchar | 메시지 유형 (§6) | **필수** |
| `TotCnt` | int | 총 발송 건수 | **필수** |
| `OkCnt` | int | 성공 건수 — **이 값이 청구 수량이다** | **필수** |
| `FailCnt` | int | 실패 건수 | **필수** |
| `ReadyCnt` | int | 결과 대기 건수 | **필수** |
| `RemAmt` | numeric | 그 시점 잔액 (§7) | 선불 고객사 필수 |
| `SysId` | varchar | 적재 출처 구분 — 비토 전용 값을 협의해 고정 | 권장 |
| `InsTm` | datetime | 최초 적재 시각 | 권장 |
| `UpdTm` | datetime | 마지막 갱신 시각 | 권장 |

`TotCnt = OkCnt + FailCnt + ReadyCnt`가 맞아야 한다. 어긋나면 화면과 청구서가 서로 다른 값을 보인다.

---

## 4. 집계 단위와 UPSERT 규칙 — 가장 중요한 항목

**키 = `DestDt` + `CustId` + `StoreId` + `MsgType`**

**한 키에 행은 하나다.** 그날 그 발송ID의 그 유형 발송이 늘어나면 **같은 행을 UPDATE** 한다. 새 행을 추가하지 않는다.

> ### 절대 금지 — 같은 키로 행을 여러 개 쌓는 것
>
> 한줄로는 이 테이블을 **`SUM()` + `GROUP BY`** 로 읽는다.
>
> ```sql
> SELECT DestDt, CustId, StoreId, MsgType,
>        SUM(TotCnt), SUM(OkCnt), SUM(FailCnt), SUM(ReadyCnt)
>   FROM RSRM_SalesStts
>  GROUP BY DestDt, CustId, StoreId, MsgType
> ```
>
> 같은 키로 **누적 스냅샷을 매번 새 행으로 쌓으면** 그 합이 실제 발송량의 몇 배가 된다.
> 그리고 **그 부풀린 숫자가 그대로 고객사 청구서에 찍힌다.** 화면에 에러가 안 나고 금액만 틀리기 때문에 발견이 늦다.
>
> 허용되는 방식은 둘 중 하나다:
> - **스냅샷 UPSERT (권장)** — 한 키 한 행, 그날의 현재 누적값으로 덮어쓴다
> - **증분 append** — 새로 발생한 건수만 더한 행을 넣는다 (합이 맞으므로 SUM이 정확하다)
>
> 섞으면 안 된다. **누적값을 append 하는 것이 유일한 사고 형태다.**

`InsTm`·`UpdTm` 두 컬럼이 있는 것이 UPSERT 구조를 전제한 설계다.

---

## 5. 발송ID(`CustId`) 발급 규칙

| 규칙 | 내용 |
|---|---|
| **전역 유일** | 한줄로 매핑 테이블에서 `agent_send_id`가 **UNIQUE**다. QTmsg가 이미 쓰는 ID와 겹치면 발송이 남의 회사에 귀속된다 |
| **접두 분리** | QTmsg는 `B`·`C`·`D` 접두를 쓰고 있다. **비토 = `V` 접두 확정(★2026-08-20 Harold) — `V0001`부터 연번.** 발급·소유 = 게이트웨이 `agent_account.pay_cust_id`(UNIQUE) |
| **불변** | 한번 발급한 `CustId`는 바꾸거나 재사용하지 않는다 — 과거 정산의 귀속 키다 |
| **신규 발급 = 통보 의무** | 한줄로에 등록되지 않은 `CustId`로 적재하면 **그 발송은 어느 회사에도 안 잡히고 청구에서 통째로 빠진다.** 새 발송ID를 발급하면 반드시 한줄로에 알린다 |

발송ID에 사람이 읽을 이름(발급명)이 있으면 함께 알려달라 — 화면에 `발송ID / 발급명`으로 표시한다. 내부 코드만으로는 고객사가 자기 것인지 모른다.

## 6. MsgType 코드

| 코드 | 유형 | | 코드 | 유형 |
|---|---|---|---|---|
| `S` | SMS | | `G` | 브랜드메시지 |
| `L` | LMS | | `KS` | 카카오 실패 → SMS 대체발송 |
| `M` | MMS | | `KL` | 카카오 실패 → LMS 대체발송 |
| `K` | 카카오 알림톡 | | `X` | 팩스 |

**여기 없는 코드를 보내면** 화면에 코드 문자가 그대로 노출되고, **청구 단가가 없어 0원으로 계산된다.** 새 유형이 필요하면 적재 전에 한줄로에 알려달라 — 매핑과 단가 항목을 먼저 만들어야 한다.

---

## 7. 선불 잔액 — `RemAmt`

선불 고객사의 **잔액 진실은 게이트웨이에 있다.** 한줄로는 그 값을 복제해 저장하지 않고, 가장 최근 `DestDt` 행의 `RemAmt`를 그때그때 조회한다.

그래서 **적재할 때마다 그 시점 잔액을 `RemAmt`에 함께 넣어줘야** 화면의 잔액이 최신이 된다. 비워두면 한줄로 화면에 잔액이 안 뜬다.

후불 고객사는 비워도 된다.

---

## 8. 적재 주기

- **당일 행은 계속 갱신한다** — 발송이 진행되면서 숫자가 늘어난다
- **지난 날짜 행도 갱신한다** — 통신사 결과가 늦게 오면 `ReadyCnt`가 `OkCnt`/`FailCnt`로 옮겨간다
- 실시간이 가장 좋지만, 최소한 **정산 마감 전까지는 확정값**이 들어와 있어야 한다

한줄로 정산은 매월 발행된다. 발행 시점에 `ReadyCnt`가 남아 있으면 그 건은 **성공으로 세지 않는다**(청구 수량 = `OkCnt`). 결과가 늦게 확정될수록 그 달 청구에서 빠질 위험이 있다.

---

## 9. 절대 금지 5가지

1. **같은 키로 누적 스냅샷을 여러 행 쌓지 않는다** — §4. 청구 금액이 부풀어 그대로 나간다.
2. **`CustId`를 바꾸거나 재사용하지 않는다** — 과거 발송의 귀속이 틀어진다.
3. **지난 날짜 행을 삭제하지 않는다** — 정산 재발행 시 그 기간 발송이 통째로 사라진다.
4. **`DestDt`를 KST가 아닌 기준으로 쓰지 않는다** — 월 경계에서 발송이 앞뒤 달로 새고, 그만큼 청구가 갈린다.
5. **미등록 `CustId`로 조용히 적재하지 않는다** — 그 고객사 발송이 영구 미청구로 남는다.

## 10. 검증 시나리오

| # | 시나리오 | 확인 |
|---|---|---|
| 1 | 테스트 발송ID로 SMS 10건 발송 | `RSRM_SalesStts`에 행 **1개**, `TotCnt=10` |
| 2 | 같은 날 같은 ID로 5건 더 발송 | 행이 **여전히 1개**, `TotCnt=15` (행 2개가 되면 §4 위반) |
| 3 | 결과 확정 (성공 14 · 실패 1) | 같은 행의 `OkCnt=14`·`FailCnt=1`·`ReadyCnt=0` |
| 4 | 한줄로 화면 확인 | 발송통계에 그 고객사 SMS 15건 · 성공 14건 |
| 5 | 선불 고객사 발송 | `RemAmt`가 차감된 잔액으로 갱신, 한줄로 화면 잔액 일치 |
| 6 | 유형별 (LMS·알림톡) 각 1건 | 유형별로 **행이 분리**되어 각각 잡힘 |

**1건씩 실측한 뒤 물량을 올린다.** 잘못된 적재가 한 달치 쌓이면 되돌리는 것이 훨씬 어렵다.

## 11. 한줄로 쪽 준비 사항 (우리가 한다)

| # | 항목 | 비고 |
|---|---|---|
| 1 | 수집 DB 접속 계정 발급 | **호스트 제한 계정**으로만 발급한다(현재 계정 전부 동일 정책). 접속 출처 IP를 알려달라 |
| 2 | `company_agent_ids`에 발송ID ↔ 고객사 매핑 등록 | 발송ID 목록을 받으면 등록한다 |
| 3 | 고객사별 유형 단가 설정 | 미설정이면 **0원 청구**가 되므로 발송 개시 전에 채운다 |
| 4 | 브랜드메시지(`G`) 단가 항목 | **준비 완료**(2026-08-14 실측 — 단가 5종 `sms`·`lms`·`mms`·`kakao`·`brand` 전부 존재). 비토가 `G`를 보내도 단가만 채우면 바로 청구에 붙는다 |

## 12. 회신 요청

1. **비토 발송ID 접두** — QTmsg의 `B`·`C`·`D`와 겹치지 않는 문자 하나를 정해 알려달라.
2. **적재 방식** — 스냅샷 UPSERT / 증분 append 중 어느 쪽으로 구현할 것인가(§4).
3. **적재 주기** — 실시간인가, 배치인가(배치면 주기).
4. **접속 출처 IP** — 계정 발급에 필요하다.
5. **보낼 유형 목록** — `S`·`L`·`M`·`K` 외에 `G`(브랜드메시지)가 포함되는가.
6. **선불 고객사 여부** — 있으면 `RemAmt` 갱신이 필수다.

## 부록 — 용어

| 용어 | 뜻 |
|---|---|
| 에이전트 전용 고객사 | 한줄로 화면을 쓰지 않고 게이트웨이로 직접 발송하는 업체 |
| 발송ID (`CustId`) | 게이트웨이가 고객사(계정)에 발급하는 식별자. 한줄로가 회사를 판정하는 유일한 키 |
| 대상ID (`StoreId`) | 한 발송ID 안에서 지점·브랜드를 구분하는 축. 청구서 구분 표기에 쓰인다 |
| 수집 DB | 한줄로 서버의 MariaDB. 게이트웨이 통계가 모이는 곳 |
