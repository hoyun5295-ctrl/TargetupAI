## §0 결론

MySQL 결과를 읽는 쪽이 행 일부를 못 보면(라인 재배정 · 0건 · 인덱스 어긋남) 한줄로는 그 숫자로 **PG 적재 수를 낮췄고**, 정산 스위퍼는 「차감 − 적재」를 미적재로 환불한다. 이번이 세 번째 같은 뿌리다(B-0914-1 0건 · F36 0926 테이블 해석 · B-1101-4 인덱스). 앞 두 번은 증상별(0건만 · 테이블만)로 막아 세 번째 모양을 못 막았다.

처방 = **규칙 하나: 실제로는 늘기만 하는 수(적재 행 · 성공 행 · 대체 행 · 알림톡 결과별 차액)는 정산이 읽기로 내리지 않는다.** 정산은 그 수마다 「본 적 있는 가장 큰 값」(기준)을 붙잡고 `max(기준, 이번 읽기)` 로 계산한다. 그러면 읽기가 아무리 줄어도 미적재 환불 · 실패 환불 목표 · 회수 한도가 환불 쪽으로 움직이지 않는다(§3-2 표). 읽기를 막거나 정산을 보류하지 않는다 — 보류는 정산 창(14 · 30일)이 닫히면 정당한 환불까지 묶는다(Codex 설계 1R #3 · #4).

- 전체 축 적재 기준 = `campaigns.sent_count`(적재 경로 기록 · 스위퍼가 읽은 합으로 올리기만). 이것을 읽기로 내리던 두 자리(재대조 · 예약 정리)를 `GREATEST` 로.
- 성공 기준 · 대체 행 기준 · 차액 기준 · 분리 축(문자 + 브랜드 `both`) 적재 · 성공 기준 = 새 기록 `send_config.readHigh`(스위퍼만 쓰고 읽는다 · 올리기만). 성공이 줄어 읽히면 회수 한도가 커져 행 기준 실패 환불의 넘친 몫을 못 거둔다(알림톡 대체 성공) · 대체 행이 줄면 여정 실패가 늘어난다(Codex 설계 2R #1) · 차액이 줄면 이미 정당하게 돌려준 차액을 회수한다(Codex 설계 3R #1) · 분리 축은 지금 적재 기준이 0이다(Codex 설계 1R #1).
- 읽기가 기준보다 적으면 불변식 경보 문구를 「미환불 의심(고객 손해)」 대신 「결과 행 일부가 안 읽힘(읽기 이상 · 돈 안 움직임)」으로(사람이 인덱스 · 라인을 본다).

## §2 뿌리 R37 — 읽기로 적재 기준을 내린다

- 적재 수는 **적재 경로가 큐에 넣은 행 수**다(`direct-send-worker.ts` 746 · `campaigns.ts` 1347~1354 · 3154 · 3266 · `auto-campaign-worker.ts` 1178 · 여정 `bumpStepCampaignCount`). 우리가 넣은 행은 우리가 지우지 않는 한 남는다.
- 결과 행을 지우는 한줄로 코드는 0이다. MySQL DELETE 는 전부 `status_code = 100`(대기) 행이고(`campaign-lifecycle.ts` 387 · `cancelled-queue-sweeper.ts` 39 · `direct-send-worker.ts` 768 · `campaigns.ts` 3582), 그 가운데 적재 수를 바꾸는 길은 수신자 삭제(`campaigns.ts` 3599 · 지운 수만큼 뺌)와 취소 정산(`cancel-settle.ts` 136~141 · §8 면제)뿐이다.
- 그러므로 **읽은 행 < 적재 기준 = 읽기가 틀렸다**(테이블을 덜 읽음 · 인덱스 어긋남 · 행 소실). 읽기로 기준을 내리면 그 차이가 미적재 환불이 된다.

## §3 규칙과 근거

### §3-1 규칙

1. **늘기만 하는 수** = 적재 행(우리가 넣은 행 · 지우는 것은 사건 길뿐) · 성공 행(성공 코드는 결과 테이블에만 쌓이고 실패 → 성공은 있어도 성공 → 실패는 없다 · 7305 = 실패로 세다가 성공으로) · 대체 행(재전송 엔진이 INSERT 만 · `bito-gateway/internal/agent/poller/resender.go`) · 알림톡 결과별 차액(성공이 늘거나 7305 → 성공일 때만 커진다 · 차감 단가 − 결과 단가의 합). 실패는 줄 수 있다(7305 → 성공) → 기준을 두지 않는다.
2. 기준 = 전체 적재 `sent_count` · 그 밖 `send_config.readHigh`: `success`(전체 성공) · `sub`(여정 알림톡 대체 행) · `unitDiff`(알림톡 결과별 차액 · 원 · 소수 둘째 자리) · `brandLoaded` · `brandSuccess` · `nonBrandLoaded` · `nonBrandSuccess`(분리 축). MySQL 읽기로 **올리기만** 한다(SQL 안에서 칸마다 `GREATEST`).
3. 정산 스위퍼 식: 처리 수 = `max(적재 기준, 읽은 성공 + 실패 + 대기)` · 회수 한도 · 불변식의 성공 = `max(성공 기준, 읽은 성공)` · 차액: **기록과 지급 허용을 나눈다**(Codex 설계 4R #1) — 차액 기준은 모호 판정(`ambiguous` · K행 대체 코드와 대체 행이 함께 보임 · `mysql-refund-sweeper.ts` 461~474)이 아닌 회차의 차액으로만 올리고, **지급(4-2-A)은 모호가 아닌 회차에만** 목표 `max(차액 기준, 이번 차액)` 으로 · 회수 한도 · 불변식의 차액 = `max(차액 기준, 이번 차액(모호면 0))`(정당한 차액은 받을 몫이라 한도에 넣는 것이 맞다 · 지급이 늦어도 순환불 합계 기준으로 맞다) · 여정 실패 = `읽은 실패 − max(대체 기준, 읽은 대체)` · 분리 축도 같은 식(지금 분리 축 적재 기준 = 0 · `mysql-refund-sweeper.ts` 391~392).
4. 읽은 처리 수 < 적재 기준 또는 읽은 성공 < 성공 기준이면 그 캠페인(축)의 불변식 경보 = 「결과 행 일부가 안 읽힘」 문구.

### §3-2 왜 이것만으로 돈이 안 움직이나 (스위퍼 · 동기화 전수)

| 돈 계산 | 읽기가 줄 때 | 근거 |
|---|---|---|
| 4-2 미적재 = 부담 − max(기준, 처리) | 기준이 그대로 → 0 | 규칙 1 · 2 |
| 4-2 실패 환불(FAIL 누적 목표) | 성공 · 대체 행이 안 읽혀도 실패는 늘지 않음(행 코드별 집계) · 목표가 작아질 뿐 · 누적이라 되돌리지 않음 | `prepaid.ts` 469(이미 충분 = 0) |
| 4-2-A 알림톡 차액(금액 목표) | **차액 기준**으로 목표를 잡음 → 줄지 않음 · 같은 키 누적이라 더 주지도 않음 · 모호 회차는 지금처럼 지급 0(기준이 있어도 새 지급 없음) | 규칙 3 · 같은 함수 |
| 4-3 회수 한도 = 부담 − 성공 − 대기 (+ 차액) | **성공 기준**으로 계산 → 성공이 안 읽혀도 한도가 커지지 않음 → 행 기준 실패 환불의 넘친 몫(알림톡 실패 + 대체 성공)을 그대로 거둠 · 더하는 차액 = **차액 기준** → 성공이 안 읽혀도 정당한 차액을 회수하지 않음(Codex 설계 3R #1) | 규칙 3 · `mysql-refund-sweeper.ts` 554~556 |

| 동기화 실패 환불(AI · 직접) | FAIL 누적 · 같음 | `campaign-lifecycle.ts` 652 · 778 |
| 적재 0 정산(`isZeroLoadShape`) | `sent_count > 0` 이면 들어가지 않음 | `refund-calc.ts` 103 |

### §3-3 기준 기록 `send_config.readHigh`

- 쓰는 곳 = 스위퍼 4-1 하나(집계를 이미 하는 자리) · 값이 커질 때만 한 문장 UPDATE(`jsonb_set` · 칸마다 `GREATEST(기존, 이번 값)` · 여러 프로세스가 겹쳐도 큰 값만 남음 · `updated_at` 은 건드리지 않음 = 적재 중 정리 판정에 영향 0).
- 적재 기준의 「합」은 `total`(이력 전체 + 라이브 대기 · 만료 실패) · 성공은 결과 테이블에서만 센다 — 옮기는 중인 행을 두 번 세지 않아 실제보다 커지지 않는다(커지면 환불이 모자란다 = 고객 손해). 옮기는 사이 잠깐 덜 셀 수는 있으나 기준은 올리기만 하므로 손해 없음.
- 읽는 곳 = 스위퍼 4-2 · 4-3 · 4-4 · 여정 목표뿐(화면 숫자 · 동기화 · 청구는 읽지 않는다).
- 지우는 곳 = 취소 정산이 적재 수를 낮출 때(대기 행을 지운 사건 · 다음 정산이 다시 쌓는다).
- 새 칼럼 없음(`send_config` jsonb 기존 칸 · DDL 0).

## §8 범위 밖 · 남은 위험

- **운영**: .62 `SMSQ_SEND_15` `idx_app_etc1_status` 재생성(발송 없는 시각 · Harold) · .62 불량 메모리 칸 제거(하드웨어 · 1026 결정 그대로). 근본은 하드웨어다 — 이 설계는 그 사이 돈이 움직이지 않게 하는 것.
- **손상 행 2건**(10-14 캠페인 두 개 각 1행 · 본체 값 변형) 원값 되돌리기 = 운영 판단.
- **취소 정산(면제 · Codex 설계 1R #2 불수용 · 추가 과제)**: 시작된 뒤 취소한 캠페인은 대기 행을 지운 뒤 남은 행 실측으로 적재 수를 정한다(`cancel-settle.ts` 128~142). 그 순간 읽기가 손상돼 있으면 남은 행을 덜 세어 과환불할 수 있다. 막으려면 지운 행 수(DELETE 영향 행 수)를 의무 기록에 쌓고 「적재 − 지운 수」로 정해야 하는데, 적재 중 취소(워커 경로)는 PG 에 적재 수가 아직 없어(`direct-send-worker.ts` 746 은 적재 끝에만 씀) 세 호출자(취소 CT · 워커 중단 · 재시도 워커)의 적재 기록부터 바꿔야 한다 — 취소 축 설계가 따로 필요하다. 이 묶음은 상시 정산 경로(스위퍼 · 재대조 · 예약 정리)를 닫는다.
- **적재 기준이 실제보다 큰 경합(Codex 설계 1R #3 · 이 묶음 전부터 있던 것 · 추가 과제)**: AI 발송이 `campaign_runs` 를 쓴 뒤 캠페인 `sent_count += n` 전에 동기화가 0 을 결과 수로 채우면 n + 결과 수가 된다(`campaigns.ts` 1334~1354 · `campaign-lifecycle.ts` 631~644). 보류를 버려 이 설계에서 영구 보류는 생기지 않지만, 미적재 환불이 그만큼 모자랄 수 있다 → 적재 경로의 쓰기 순서를 바꾸는 별도 과제.
- **기준 첫 기록 전**: `readHigh` 는 스위퍼가 처음 읽을 때부터 쌓인다 — 결과가 들어온 뒤 첫 정산 전에 손상되면 그 몫은 막지 못한다(전체 적재 축은 적재 경로 기록이라 처음부터 막힘 · 정산은 발송 48시간 안 30초마다 돈다).
- **행 값 변형**(손상이 행을 숨기지 않고 결과 코드를 바꿈 · 1000 → 다른 코드 = 실패로 셈): 원래 값을 알 길이 없어 이 규칙으로 막지 못한다 · 하드웨어 처방(§8 첫 줄)이 근본.
- **후불 청구 · 화면 · 통계**: MySQL 을 직접 세고 비교할 PG 기준이 없다. 같은 손상이면 덜 청구(회사 손해) · 덜 보임 → 추가 과제(Harold 판단) = 발행 전 PG 기준과 대조.
