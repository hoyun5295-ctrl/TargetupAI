### 3-1 `findAgencyBlanks(content): Blank[]` — `{ start, end, text, kind: 'mark' | 'bracket' }`
- **기호 꼴(mark)**: ○◯●ㅇ□■△▲ 2~4개 연속 · 라틴 O/o/X/x 2~4개 연속 · `*` `_` 2~4개 연속. 조건 = 바로 뒤가 한글이거나 「(공백 하나) 점 · 님 · 매장 · 지점」. 라틴은 앞뒤가 라틴 · 숫자면 제외(XXL · ZOOM · OOTD). 숫자 0 안 봄. 5개 이상 · 한 줄 통째 구분선 제외 · ★☆ · ㅋㅎ 안 봄.
  - 뒤에 「점」 「지점」 「매장」 이 바로 붙어 있으면 `text`·범위에 그 접미어를 **포함하지 않고** `suffix` 칸에 따로 싣는다(§4-3 채우기가 통째 · 앞부분만을 고른다).
- **괄호 꼴(bracket)**: `[ … ]` · `( … )` · `「 … 」` 안 글(공백 뺀 2~15자)이 ① 낱말 표와 정확히 같거나(매장명 · 지점명 · 점포명 · 고객명 · 이름 · 성함 · 매장이름 · 매장번호 · 매장전화번호 · 전화번호 · 연락처 · 날짜 · 금액 · 쿠폰번호 · 링크 · URL) ② 낱말 조각(고객 · 성함 · 이름 · 매장 · 지점 · 점포 · 전화 · 연락처 · 번호)을 품고 필드 끝말(명 · 이름 · 번호 · 성함 · 연락처 · 주소 · 전화)로 끝나며 **숫자(전각 · 원문자 ⑩ 포함 · 유니코드 숫자 `\p{N}`)가 없는** 것(`[소속매장명]` · `[소속매장전화번호]` · `[회원번호]` 예 · `[매장 안내]` · `[번호표 이벤트]` · `[매장 선착순 100명]` 아님 · Codex 설계 2R). **문안만으로 판정**한다(명단 열이 저장되지 않는 승인 단계에서도 같은 결과 · Codex 설계 1R). 명단 열은 후보 제안(§3-2)에만 쓴다.

## §4 고치는 길

### 4-1 원스텝 확인 화면 — `slotFills` (명단이 손에 있음)
- 조정값 `slotFills: [{ start, end, before, column?, text? }]`(column = 명단 열 · text = 직접 적은 이름). `parseOneStepOverrides` 가 varMapping 처럼 걸러 받는다(712 주석에 「문안은 요청서가 진실 · slotFills 예외」 한 줄).
- 글 차례(analyzeOneStep · Codex 설계 1R): 요청서 글 → 문자 정리(`prepareAgencyCopy` · intake 785) → 괄호 변수 바꾸기(§8-3) = **`baseContent`**(미리보기 응답에 실음) → slotFills 적용 → **문자 정리 한 번 더**(직접 적은 이름의 보낼 수 없는 글자도 같은 규칙) = 분석 글 → 항목 뽑기(864) · 바이트 재기(990) · 미리보기 · 확정이 모두 이 글.
- 위치 기준 = `baseContent`. 서버가 `baseContent` 에서 빈 자리를 다시 판정하고, **채우기 범위는 그 빈 자리 범위(기호 꼴은 접미어 포함 · 뺀 두 범위 중 하나)와 정확히 같아야** 한다(일반 문구 바꾸기 0 · Codex 설계 2R). 큰 start 부터 · 겹치면 반려 · 그 자리 글 ≠ before = 반려(다른 값으로 대신 0).
- 변수 이름 충돌 대조(Codex 설계 2R · 3R): ① column 채우기끼리 한 이름에 다른 열 = 반려(「소속 매장」 · 「소속매장」 두 열을 두 자리에) ② 조정값 varMapping 이 그 이름을 다른 열에 잇고 있으면 반려 ③ **`baseContent` 에 이미 있던 같은 이름 변수**만 그 연결 열(조정값 > 같은 이름)과 대조해 다르면 반려(새로 생기는 변수는 자동 연결과 대조하지 않는다 = 공백만 다른 둘째 열을 고른 선택 보존) · 통과하면 varMapping 에 명시로 얹는다.
- column 이면 `%열이름(공백 뺌)%` 로 바꾸고 **서버가 varMapping[이름] = 고른 원본 열을 명시로 얹는다**(같은 이름 자동 연결에 기대지 않는다 · 공백만 다른 두 열에서도 고른 열). 조정값 varMapping 이 같은 이름을 다른 열에 이미 잇고 있으면 반려(충돌 표시). 미리보기 예시는 실제 연결 결과(첫 수신자 값)로 그린다. `%이름%` 이 조각 하나로 안 읽히면 그 채우기만 반려 · 항목 4개 상한이면 단추 잠금.
- 미리보기와 확정이 같은 파일 + 같은 조정값 = 같은 글.

- ★ 같은 뜻 이름의 열(Harold 1125 「이름 고객명정도는 붙여줘도 되는거아니냐? 원하는게 사람이 하는것과 같은 대행인데」): 문안 항목(「%고객명%」 · 괄호 자리 「[고객명]」)에 저절로 이을 열 = 같은 이름 → 없으면 **같은 뜻 이름**. 기준 = 표준 필드 표(standard-field-map)의 고객 이름 항목 한 벌(「고객명」 = 「이름」 = 「성함」) · 여기서 새 낱말을 적지 않는다 · 지금은 그 항목만(등급 · 포인트 · 받는 사람 번호 묶음은 안 씀).
  - 잇는 조건 = 같은 뜻 이름의 열이 정확히 하나 + 값 모양이 사람 이름일 수 있음(명단 전체에서 비어 있지 않은 값 가운데 이름일 수 없는 값 = 칸 전체가 휴대폰 번호 + 「점 · 지점 · 매장 · 점포」로 끝나는 값이 절반을 넘으면 안 이음 · Codex 같은 뜻 2R ~ 6R). 둘이면 안 잇고 화면 후보에는 둘 다 나온다.
  - 알림 줄 규칙 하나 = 항목 이름과 다른 이름의 열로 채우는 항목은 전부 적는다(최종 연결값 · 「문안의 [고객명] 자리는 명단 「이름」 열 값으로 고객마다 채웁니다.」).
  - 서버가 분석하는 입구(메일 · 원스텝)에 적용 · 화면 접수(직접 작성)는 사용자가 연결 표에서 고른다(그대로).
  - 실물: 팀장 시험 파일을 메일 한 통으로 = 5건 접수 · 건마다 그 알림 줄(발송 ID · 발신번호 등록은 시험에서 맞춰 둠 = 운영 미검증).
- 함께 고친 다른 카드 시험 둘(push 관문을 막음 · 서버 코드 무변경): journey-recheck-1111 T5(파일을 네 번 읽던 것 → 한 번) · c145-session-visits 「25초 이하」 고정 → 그 행에서 서버 계약대로 계산한 상한(last_seen_at − started_at 내림 + 5초 · 신호 360번에 1초가 넘으면 26이 정상이라 단독 3회 중 1회 실패하던 것).
- 범위 밖(기록만 · Codex 짝 2R 불수용): 메일 두 파일에서 요청서 파일에 이름이 요청서인 시트가 둘(「요청서」 + 「내용2」)이고 명단이 별도 파일이면 첫 요청서만 접수된다 — 이번 변경 전부터의 두 파일 동작이고(판정 single · 오늘 분기), 막으면 오늘 접수되던 메일(안 쓰는 양식 탭이 남은 요청서 파일)이 반려로 바뀐다.
- 같은 뜻 이름 Codex 리뷰 = 7R approve · 8R approve(단위 전체에서 나온 실패 다섯 = 시트 못 찾음 내부 오류 문장을 영문으로(root-ledger R10 · 호출부 셋 모두 catch 로 받아 화면에 안 나감) · 옛 시험 둘의 「안 맞는 이름」 예시가 이름 ↔ 고객명이라 같은 뜻 이름 밖의 열로 옮김).
- 미검증(기록만): 24시트 원본 파일 미확보(이름이 무엇이든 인접 + 휴대폰 열이면 짝이 되게 했으나 그 실물로는 미검증).

### 6-2 메일
- `buildIntakeUnits`: 표 파일마다 plan. 모든 파일이 single 이면 **오늘 분기(1개 · 2개 · 자립형 여럿) 그대로**. 하나라도 pairs 면 모든 파일이 pairs 이거나 자립형 single 이어야 하고(별도 명단 두 파일 꼴과 섞이면 반려) 단위 = 짝마다 + 자립형마다. invalid 가 있으면 그 사유로 반려. ~~단위 합 상한 MAX_FORMS(5)~~ → ★1125 따로 첨부한 요청서 파일만 5개까지 · 한 파일 안 짝은 상한 없음(§13).

### 6-3 원스텝 화면
- 화면의 고른 건 = **화면에 보이는 분석의 건(`analysis.pairIndex`)** · 따로 상태를 두지 않는다(건 바꾸기 분석이 실패하면 지금 건 그대로 · 올린 이미지는 바꾸기가 성공한 뒤에만 비움 · 이미 접수한 건은 다시 접수 0 · Codex 설계 7R).
- **미리보기 응답 `pairs: [{ index, label }]`(2 이상일 때만) · 조정값 `pairIndex` · 미리보기는 없으면 0 · **확정은 짝이 2 이상이면 pairIndex 필수**(없으면 반려 「이 파일에는 요청서가 N건 들어 있습니다. 접수할 건을 골라 주세요.」 · 옛 화면이 첫 건만 접수하고 성공으로 끝나는 것을 막는다 · Codex 설계 1R).
- 화면: 짝 칩 줄(「5건이 들어 있어요」) · 확정 성공 뒤 [다음 건 확인](같은 파일 · 다음 index · 확정한 짝은 표시 · 다시 확정 단추 안 그림).

## §7 이미지 맞추기 (메일 · 다건)

- 요청서 「이미지 파일명」 칸 = ① 줄 값 + 그 아래 ② ③ 줄(첫 비지 않은 칸이 ②③④⑤ 로 시작) → `imageFileNames[]`(번호표 · 앞뒤 공백 뺌 · 순서 = ①②③).
- 이름 대조 규칙 = **양쪽 같은 함수**(Codex 설계 1R): 앞의 ①~⑤ 번호표 뺌 · 끝의 이미지 확장자(.jpg .jpeg .png .gif .bmp) 뺌 · 공백 전부 뺌 · 소문자. 첨부끼리 대조 이름이 겹치면 반려. 이미지 자리(단위 · 순번) 하나 = 첨부 정확히 하나 · 첨부 하나 = 자리 정확히 하나(같은 단위의 ① ② 가 같은 첨부를 가리켜도 반려)여야 접수. 아니면 반려 · 시트마다 사유(「정기문자(생일_GOLD) 시트의 이미지 GD 에 맞는 첨부가 없습니다」 · 「첨부 abc.jpg 는 어느 시트의 이미지 파일명과도 맞지 않습니다」).
- 단위 하나 · 단건 메일 = 오늘 규칙 그대로(첨부 순서 · 칸 무시 · 불변 23).
- 상한: 단위마다 이미지 ≤ 3(LIMITS.mmsImageCount) · 다건 메일 이미지 합 ≤ 3 × 단위 수 · 첨부 수 상한 MAX_ATTACH_FILES 5 → 20(= 표 5 + 이미지 15) · 용량 50MB 그대로. 이미지 맞추기 검사(`prepareMailMmsImages`)의 장수 검사는 단위가 정해진 뒤로 옮긴다(단건 = 3장 그대로).
- 저장 = 단위별 계정 확정 뒤 · 반려 = `dropSavedImages`(오늘 그대로).
- 중복 판정 지문(Codex 설계 6R · 7R): 메일 안 형제 대조 · 이미 접수된 건 대조 둘 다 **제목 + 붙는 이미지 바이트 지문(sha256 · 첨부 차례)**. 이미지 파일 이름은 지문이 아니다. 이미 접수된 건은 SQL 로 제목까지 거른 뒤 저장 파일(`mms_image_paths`)을 읽어 지문 대조 · 파일을 못 읽는 옛 행만 원본 이름 차례로 보수 대조(두 번 발송 · 청구보다 건너뜀이 안전). 단건 메일도 같은 지문.
- ① 칸이 비고 ②③ 줄에만 이미지 이름을 적어도 이미지 지정이다(첨부 0장이면 반려 · Codex 설계 7R).

## §8 같은 실물에서 걸리는 셋 (요청서 해석 · 원스텝 · 메일 공통)

### 8-1 테스트 명단 표
- 「담당자 번호」 별칭에 「테스트번호」 · 「테스트 번호」 · 「테스트 수신번호」 더함.
- 그 칸에서 번호가 0개면(「(오른쪽 테스트 명단 참고) →」 · 빈칸) 시트에서 「테스트 명단」(공백 뺌 `테스트명단`) 칸을 찾아, 그 아래 머리줄에서 휴대폰 · 핸드폰 · 전화 · 연락처 열을 고르고 아래로 빈칸 전까지 휴대폰 값을 담당자 번호로(최대 10 · 오늘 정규화).

### 8-2 빈 발신번호 = 명단 매장번호 열
- 요청서 해석기는 빈 회신번호를 오류로 내지 않는다(명단을 모름) → analyzeOneStep 이 판정. 확인 화면 회신번호 조정값이 있으면 그것이 먼저(오늘 그대로). 칸이 비었고 조정값이 없을 때만: 명단 열 가운데 매장 전화 열(이름 공백 뺌이 (매장|지점|점포|가맹점) 과 (번호|전화|연락처) 를 함께 품음)이 정확히 하나이고, **그 열이 수신자 열이 아니며 휴대폰 값 비율이 0.5 미만**(`scorePhoneColumns` · 매장 전화 = 유선)이면 열 방식 `{ mode: 'column', column }`(Codex 설계 1R · 수신자 열과 겹쳐 매장 번호로 보내는 일 0). 그 밖 = 최종 회신번호 없음 = 반려 「회신번호 칸이 비어 있습니다」 + 후보 열 이름.
- 그 뒤는 오늘 그대로: 등록 안 된 번호 = 반려(intake 962-968) · 종류 상한 500.
- 화면 접수(Composer) = 해석기를 안 타므로 무관.

### 8-3 명단 열과 같은 이름의 `[ ]` = 변수
- analyzeOneStep 문안 정리 직후: `[X]` 의 X(공백 뺌)가 명단 열과 같은 이름(`sameNameColumn`)이면 `%X(공백 뺌)%` 로 바꾼다. 아니면 그대로(`[시세이도]` 같은 머리말).
- 바꾼 것은 확인 화면 · 메일 회신에 한 줄(「문안의 [고객명]을 명단 고객명 열로 채웁니다」).
- 이름이 다른 필드 괄호(`[소속매장명]` ↔ 열 「소속 매장」)는 §3-1 괄호 꼴로 잡힌다. **메일 접수에서 괄호 꼴이 남으면 그 건은 반려**(사유 = 「문안의 [소속매장명]에 맞는 명단 열이 없습니다. 고객리스트 열 이름을 소속매장명으로 맞춰 다시 보내 주세요. 가까운 열: 소속 매장」). 이유: 괄호 꼴은 필드 이름 꼴이라 채울 자리일 것이 거의 확실하고, 접수 뒤에는 그 열 값이 저장되지 않아 고칠 길이 없다(§2). 기호 꼴(OOO)은 메일도 알림만(회의 합의 · 오탐 탈출구).
