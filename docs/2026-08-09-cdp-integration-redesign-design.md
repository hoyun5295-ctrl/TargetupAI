## §1 왜 고치나 (Harold 지시 2026-08-09)

자사몰 연동은 이 서비스에서 **가장 핵심적인 진입점**인데 초기 모델에 멈춰 있다. 화면(`CdpSettingsPage.tsx` 2,616줄)이 어지럽고 시인성이 떨어진다. 사용자는 마케팅 담당자인데 화면은 개발자용이다.

**핵심 진단 — 병목은 "예쁨"이 아니라 세 가지 구조 문제다.**
1. **독자 불일치** — 담당자가 보는데 내용(웹훅 시크릿·SDK 스크립트·REST 계약)이 전부 개발자용이고, **그걸 개발자에게 전달하는 장치가 없다.** 담당자는 "이걸 누구한테 어떻게 주지"에서 멈춘다.
2. **탭이 우리 시스템 기준(연결·웹·앱·검증)** — 고객이 밟는 순서가 아니다. 특히 **검증이 별도 탭**이라 "설치했는데 되는지 모른다"가 생긴다.
3. **좋은 신호가 숨어 있다** — 실시간 수신 진단(§2-2)이 이미 있는데 웹 탭 안쪽에서만 보인다.

## §3 설계 원칙

1. **독자는 마케팅 담당자다.** 개발자용 내용은 "개발자에게 보내기"로 위임하고, 담당자 화면에는 상태와 다음 할 일만 남긴다.
2. **설정 화면이 아니라 상태 화면.** 열자마자 각 몰이 연결됨/설치 대기/수신 중 어디인지 실측으로 보인다.
3. **검증을 단계에 녹인다.** 별도 탭을 없애고 각 단계가 자동 완료 판정된다 — 특히 "첫 데이터 수신"이 초록으로 바뀌는 순간이 핵심.
4. **몰이 달라도 흐름은 같다.** 연결 → 설치 → 확인 3단계는 전 몰 공통. 몰별 차이는 그 안의 입력 항목뿐.
5. **1클릭 UX(marketing_user_ux_priority).** 개발자에게 보내기·재검증·복사는 클릭 1회, 추가 입력 없음.
6. **Journey Builder 동급 품질(design_quality_minimum).** sticky 헤더·다크 톤·상태 카드·ConfirmModal+useToast·모바일 반응형.
7. **내부 용어를 독자 언어로.** 화면 문구·caption에 테이블/컬럼명(`cdp_allowed_origins` 등) 노출 재검토. (단 `Data source —` 캡션은 전 화면 하우스 컨벤션이라 이 트랙 단독 변경 대상이 아님 — §8 별건)

## §5 화면 흐름 (재설계)

> **★Harold 확정 판정 기준(2026-08-10): ①깔끔하고 ②보기 쉽고 ③스텝 바이 스텝.**
> §5의 모든 요소는 이 셋으로 판정한다. **하나라도 해치면 그 요소는 뺀다.** 지금 화면이 어지러운 이유는 기능이 부족해서가 아니라 **한 화면이 여섯 몰 × 네 탭 × 개발자 문서를 동시에 이고 있어서다.**

### 5-0. 깔끔함의 정의 — 화면을 세 층으로 쪼갠다

한 화면에 다 담지 않는다. **한 번에 하나의 질문에만 답한다.**

| 층 | 답하는 질문 | 담기는 것 | 담지 않는 것 |
|---|---|---|---|
| **1층 · 현황판** | "우리 연동은 지금 어떤 상태인가" | 몰 카드 6장 + 요약 지표 3개 | 입력 폼·스크립트·개발자 문서 |
| **2층 · 진행 패널** | "이 몰을 붙이려면 지금 뭘 해야 하나" | 그 몰의 3단계 + 지금 단계의 액션 1개 | 다른 몰 이야기·완료된 단계의 상세 |
| **3층 · 개발자 자료** | "개발자에게 뭘 넘기나" | 스크립트·웹훅 규격·체크리스트 | 담당자용 안내(여긴 개발자만 본다) |

**1층에서 2층은 카드 클릭, 2층에서 3층은 "개발자에게 보내기".** 뒤로 가기는 항상 한 단계. 옛 4탭(연결·웹·앱·검증)은 이 3층에 흡수돼 사라진다.

### 5-1. 1층 — 연동 현황판

- 상단 sticky 헤더(그라데이션 아이콘) + 한 줄 설명 + 우측 새로고침.
- **요약 지표 3개** — `수신 중 N · 준비 중 N · 조치 필요 N`. 숫자만 크게, 설명은 작게.
- **몰 카드 6장**(모바일 1열 / md 2열 / lg 3열). **카드는 4줄을 넘지 않는다** — 로고+이름 / 상태 배지 / 한 줄 요약 / 버튼 1개. 그 이상은 2층으로 민다.
- **버튼은 카드마다 하나뿐이고 상태가 문구를 정한다** — `연결하기` · `이어서 설정` · `상태 보기` · `조치하기`. 무엇을 눌러야 할지 고민하는 순간이 없어야 한다.

### 5-1-1. 상태 배지 5종 — 색과 말이 1:1

색만 다르고 말이 모호하면 보기 쉬워지지 않는다. **각 배지는 "지금 누가 무엇을 해야 하는가"를 문장으로 말한다.**

| 배지 | 색 | 화면 문구 | 다음 행동 주체 |
|---|---|---|---|
| 수신 중 | emerald | `데이터 수신 중 · 24시간 N건` | 없음(정상) |
| 설치 대기 | amber | `설치만 남았어요` | 고객사 개발자 |
| 준비 중 | violet | `연결 완료 · 데이터 연동 준비 중` | 한줄로(우리) |
| 조치 필요 | rose | `인증이 끊겼어요 · 재연결 필요` | 고객사 담당자 |
| 연결 안 됨 | white/40 | `아직 연결 전` | 고객사 담당자 |

**`준비 중`(violet)은 이번에 신설한다** — 네이버·메이크샵처럼 연결은 됐지만 우리 쪽 매핑이 남은 상태다(§2-3·§8-1). 지금은 이 상태를 표시할 방법이 없어 다른 몰과 똑같이 보이고, 그래서 고객이 "연동했는데 왜 고객이 0명이냐"고 묻게 된다. **모르는 것을 초록으로 칠하지 않는다는 §6 원칙의 화면 판이다.**

### 5-2. 2층 — 3단계 진행 패널 (몰 공통)

```
 ①  연결 ─────── ②  설치 ─────── ③  첫 데이터 확인
   자격·OAuth      스크립트·웹훅      수신 대기 → 수신됨
```

**스텝 바이 스텝의 규칙 다섯.**
1. **한 화면에 활성 단계는 하나.** 완료된 단계는 초록 체크 + 한 줄로 접고, 미래 단계는 흐리게 잠근다. 펼쳐진 상세는 언제나 하나뿐이다.
2. **각 단계에 액션은 하나.** `연결하기` / `스크립트 복사` / `기다리는 중`. 부가 동작(개발자에게 보내기·다시 검증)은 보조 위치에 작게.
3. **단계 완료는 시스템이 판정한다.** 사용자가 "다음" 버튼으로 넘기지 않는다 — 연결되면 ①이 닫히고, 첫 이벤트가 오면 ③이 초록이 된다. **사용자가 자기 진도를 스스로 신고하는 화면은 만들지 않는다.**
4. **③은 기다림을 보여준다.** "첫 이벤트를 기다리는 중"이 살아 있는 상태로 보이고(폴링), 수신되면 신호 4종(페이지뷰·회원식별·동의·클릭)이 하나씩 켜진다. 옛 검증 탭은 여기 흡수돼 사라진다.
5. **막힌 단계에는 빠져나갈 길을 준다.** 10분 넘게 ③이 안 켜지면 "안 들어오나요?" 안내가 나타나 원인 3가지와 개발자 재전달 버튼을 연다.

**몰이 달라도 이 3단계는 같다.** 다른 것은 ①의 입력 항목과 ②의 안내 내용뿐이다. 매핑 보류 몰(네이버·메이크샵)은 ②·③ 대신 **`준비 중` 안내 한 장**을 보여준다 — "연결이 끝났습니다. 한줄로가 데이터 연동을 준비 중이며 영업일 1일 내 완료됩니다." 거짓 진행바를 돌리지 않는다.

### 5-3. 개발자에게 보내기 (신규 · ★0810 방향 정정)

> **정정 요지 — 공개 링크도 메일도 만들지 않는다. 클립보드 복사 하나로 간다.**
> **왜 링크를 접었나(Harold 지적 수용):** 자체호스팅 웹훅은 규격과 **시크릿**이 함께 가야 완성인데, 시크릿은 링크에 담을 수 없다(아래 비밀 등급). 그러면 담당자가 어차피 시크릿을 사적 경로로 넘겨야 하고 **그 경로로 규격도 같이 보내면 된다.** 링크는 문제를 반만 풀면서 **웹훅 규격(엔드포인트·헤더·서명 방식 = 정찰 가치)만 새로 공개**한다. 같은 날 오전 보안 설계서에서 노출면을 줄이기로 해놓고 오후에 공개 경로를 여는 모순이기도 했다.
> **왜 메일도 접었나:** 담당자는 이미 메일·메신저·이슈트래커를 쓴다. 우리가 보내면 발송 경로가 하나 늘어 승인·도달률·실패 처리가 따라붙는데 그만한 값을 못 한다. 필요해지면 나중에 더하는 additive 작업이다.
> **결과 — 구조를 고쳤더니 코드가 줄었다:** 공개 엔드포인트 0 · 토큰 0 · 만료 관리 0 · DDL 0. (착수 중 만들었던 서명 토큰 CT는 삭제했다. 덧댄 장치가 남으면 그게 땜질이다.)

- 담당자가 클릭 1회 → 그 몰의 설치 안내(스크립트 · 수집 허용 도메인 · 웹훅 규격 · 확인 방법)가 평문으로 **클립보드에 복사**된다. 담당자가 자기 채널로 붙여 넣고, 무엇을 어디로 보낼지 직접 통제한다.
- 조립 = `frontend/utils/cdp-install-guide.ts`(CT). 마크다운 기호를 최소로 써서 메일·메신저 어디에 붙여도 읽히게 한다.
- **값이 없으면 가짜로 채우지 않는다** — SDK 키가 없으면 스크립트 절 자체를 넣지 않는다.
- **비밀 등급을 나눈다(재검토 정정 — 옛 초안은 "키를 담지 않는다"고 써서 스크립트 전달 자체가 불가능했다).**
  - **SDK 공개키(`data-hjl-key`) = 안내에 포함한다.** 몰 페이지 HTML에 그대로 실려 브라우저에 노출되는 값이라 본래 공개다. 이것 없이는 전달의 의미가 없다.
  - **`webhook_secret` = 안내에 절대 담지 않는다.** 서명 검증용 진짜 비밀이라 화면에서만 확인하고 담당자가 별도 안전 경로로 전달한다. **함수가 시크릿 인자를 아예 받지 않는다** — 받는 순간 담을 수 있게 되므로 구조로 막는다. 안내에는 "보안상 포함하지 않았습니다, 담당자에게 별도로 받아주세요" 문구만 들어간다.
  - **⛔ 서버 egress IP를 담지 않는다.** 네이버 커머스 연동은 우리 서버 IP를 고객 앱에 등록해야 하는데, 코드 주석이 "서버 IP는 코드·화면 비노출 — 실제 연동 업체만 담당자에게 개별 안내(공개 시 전 고객사가 우리 IP를 알게 됨 = 공격 표면)"로 못 박아 뒀다. 복사본은 담당자 손을 떠나 어디로든 갈 수 있으므로 링크가 아니어도 원칙은 같다. **네이버 안내는 IP 자리를 비우고 "담당자에게 개별 안내"로 대체한다.**
- **계약 고정** = `cdp-provider-keys.contract.test.ts` — 토큰 CT·공개 엔드포인트 부재 / 시크릿 인자 부재 / IP 패턴 부재(주석 제외 후 검사) / 값 없으면 절 자체 생략. 시크릿·IP를 심어 실제로 검출되는지 확인 후 원복했다.

### 5-4. 스크립트 블록 통합 ✔**구현완료(0810)**
- 웹/앱 웹뷰 2블록 → **토글 1개**(`components/cdp/CdpSnippetBox.tsx`). 차이는 속성 한 줄(`data-hjl-platform="app"`)뿐인데 화면 높이를 두 배로 먹고, 담당자가 둘 중 무엇을 줘야 할지 매번 고민하게 만들었다.
- 복사 버튼도 하나 — 활성 변형만 복사한다. 붙여넣은 뒤 무엇이 일어나는지("페이지를 한 번 열면 첫 데이터 확인이 켜집니다")를 그 자리에서 알린다.
- **같은 정리에서 설치 진단 블록을 제거했다** — 스테퍼 ③이 같은 일을 하고 있어 중복이었다. 옛 검증 탭의 마지막 잔재다.
- 계약 = `pre`가 목록 순회 안에 있으면 여러 코드 블록이 동시에 뜨므로 테스트로 금지(§5-5 "코드 블록 동시 노출 1개").

### 5-5. 시인성 규격 — 구현 시 지켜야 할 수치·문구 규율

**분량 상한(넘으면 다음 층으로 민다).**
| 요소 | 상한 |
|---|---|
| 카드 1장 | 4줄 · 버튼 1개 |
| 한 화면의 펼쳐진 상세 | 1개 |
| 한 단계의 주 액션 | 1개 |
| 코드 블록 동시 노출 | 1개(토글로 전환) |
| 1층에 보이는 코드 블록 | **0개** |

**문구 규율 — 화면은 고객 언어로만 말한다.**
- 내부 용어 금지: 테이블·컬럼명, `webhook_secret`, `cdp_events`, provider 키 원문. `Data source —` 캡션은 하우스 컨벤션이라 유지하되 **1층 카드에는 달지 않는다**(현황판은 지표만).
- 상태는 형용사가 아니라 **문장**으로. "정상"이 아니라 "데이터 수신 중 · 24시간 128건".
- 실패는 원인과 다음 행동을 함께. "연동 실패"가 아니라 "인증이 만료됐어요 · 재연결하면 이어집니다".
- 시간이 걸리는 일은 **예상 시간을 밝힌다**("영업일 1일 내", "설치 후 5분 내 첫 데이터").

**★0810 추가 — 개발자 자료는 화면에 펼쳐두지 않는다(Harold 지적).** 앱 탭이 인앱 계약 문서를 **전부 펼친 채** 쏟아내고 있었다(포스터형 필드 규격·캐러셀 계약·Swift/Kotlin 예제). 모든 블록이 같은 무게라 훑을 수 없고, 담당자에게는 한 줄도 필요 없는 내용이다. §5-0의 3층 원칙을 여기에도 적용한다 — **한 줄 요약 + "개발자에게 보낼 내용 복사" 하나 + 기본 접힌 아코디언**(단일 열림). 구현 = `components/cdp/CdpDeveloperDoc.tsx`, 계약 데이터(`APP_INAPP_CONTRACT_SECTIONS`)는 무수정 재사용. **페이지가 계약 항목을 직접 순회해 그리면 옛 벽이 돌아오므로 테스트로 금지한다.**

**Journey Builder 동급 요소(design_quality_minimum 필수 항목).** sticky 헤더 + 그라데이션 아이콘 · 다크 톤(`bg-slate-950` + `border-white/10`) · violet 액센트 · 모바일 1열 반응형 · ConfirmModal + useToast(native dialog 0) · 모달은 `rounded-2xl`+`shadow-2xl`.

**접근성 최소선.** 상태를 색으로만 구분하지 않는다(배지에 아이콘+문구 동반) · 진행 단계는 `aria-current` · 폴링 중 상태 변화는 `aria-live`로 알린다.

## §6 상태 판정 규칙 (실측 기준)

**⛔ 전제 — 몰마다 살아있음의 신호가 다르다(§2-3).** 하나의 규칙을 전 몰에 적용하면 메이크샵이 항상 거짓 상태가 된다. **모르는 것은 초록으로 칠하지 않고, 틀린 배지를 만드느니 배지를 달지 않는다.**

### 6-1. 이벤트를 남기는 몰 (자체호스팅 · 카페24 · 아임웹 · 고도몰)
| 상태 | 판정 |
|---|---|
| 수신 중 | 그 `source`의 `count24h > 0` |
| 설치 대기 | 연결됨 AND 그 source의 `firstEventAt == null` |
| 수신 끊김 | `firstEventAt != null` AND 임계 기간 0건 |
| 연결 안 됨 | 위 모두 아님 |

### 6-2. 매핑 보류 몰 (네이버 · 메이크샵) + 싱크에이전트
이벤트 축으로 판정하지 않는다. **`준비 중`(violet) 배지 하나로 표시**하고 수신 배지를 달지 않는다(§5-1-1). 매핑이 붙는 순간 6-1로 옮긴다 — 그때 배지 규칙도 함께 바뀐다.
싱크에이전트는 이 화면의 provider 카드에 없지만 출처 라벨에는 있다 — **대시보드에 넣을지 자체가 결정 사항**(§9-8). 넣는다면 상태 근거는 `FEATURE-SYNC-AGENT.md`의 하트비트 축이지 `cdp_events`가 아니다.

### 6-3. 인증 만료 (전 OAuth 몰 — 카페24·네이버·아임웹)
토큰 만료·권한 철회는 흔한 운영 사고이고, 이때 "수신 끊김"으로만 보이면 원인을 못 찾는다. **`인증 만료` 상태를 별도로 두고 재연결 버튼을 붙인다.** 판정 근거(각 client의 토큰 상태 컬럼)는 §9-6 확인 후 확정.

### 6-4. 오탐 방지
저트래픽 몰은 정상인데도 24시간 0건일 수 있다. **임계값은 몰별 평소 수신 주기를 실측한 뒤 정한다**(§9-3). 확정 전에는 "수신 끊김" 배지를 켜지 않는다 — 잘못된 경보가 무배지보다 나쁘다.

### 8-1. 매핑 보류 2종 — 네이버 · 메이크샵 (결함 아님 · 화면 표시가 문제)

**남는 진짜 문제는 화면이다.** 두 몰은 다른 몰과 똑같이 표시되고 어댑터도 `available: true`다. 실제 업체가 연결하면 "연동됨"으로 보이는데 고객 수는 0으로 남는다. **상태를 정직하게 말할 배지가 없다는 것**이 이 재설계가 풀 몫이고, 그것이 §5-1-1의 `준비 중`(violet)이다.

**남은 판단(Harold):** 매핑을 첫 업체 때 붙일 것인가(현행 계획·런북 §7-1), 아니면 그 전에 미리 구현할 것인가. 어느 쪽이든 **화면은 지금 당장 정직해져야 한다.**
**근거(코드 판정 — 운영 데이터 불요):** ①내보내는 함수가 조회 3종뿐, 매핑·적재 없음 ②`routes/makeshop.ts` 130줄에 connect·status·preview·disconnect만, 동기화 엔드포인트 없음 ③폴링 워커 없음 ④`/preview` 주석이 "구조 확인 후 CDP 매핑 확정"으로 미구현임을 자인 ⑤대조군 고도몰은 `parse`→`syncOrder` 경로가 실존

## §10 이 설계서가 네 번 틀린 이유 (재발 방지)

같은 표(§2-3)가 네 번 연속 틀렸다. **네 번째는 Codex 적대검증이 잡았다(high 1건, 내가 근거 4개를 직접 확인 후 수용).**

| 회차 | 무엇이 틀렸나 | 왜 |
|---|---|---|
| 1차 초안 | 상태 판정을 `install-status` 하나에 걸었다 | **한 곳에서 확인한 것을 전체로 확장 해석**했다(메이크샵 누락) |
| 2차 | 고도몰·싱크에이전트가 표에서 빠졌다 | **목록의 단일 출처를 대조하지 않고** 검색에 걸린 것만 모았다 |
| 3차 | 고도몰을 "적재 안 함"으로 오판했다 | **직접 호출만 보고 공통 경로를 안 따라갔다**(`syncOrder` 안의 `trackEvent`) |
| 4차 | 네이버를 "적재 함"으로 오판했다 | **호출문 존재를 도달 가능으로 착각했다.** 시크릿이 없어 그 자리에 영영 못 간다 |

3차와 4차는 정반대 방향의 오류인데 뿌리가 같다 — **`trackEvent`라는 문자열이 파일에 있는지 없는지로 판정했다.** 3차는 문자열이 없어서 "안 함", 4차는 있어서 "함"이라 했고 둘 다 틀렸다. 진짜 질문은 **"실행이 그 줄에 닿는가"**였다.

전체를 관통하는 것은 하나다 — **판정을 내리기 전에 "이 결론을 뒤집을 경로가 남아 있는가"를 묻지 않았다.**

**규칙 (이 문서와 앞으로의 설계서에 적용)**
1. **실측 표는 그 도메인의 단일 출처를 기준으로 전수 대조한다.** 여기서는 `PROVIDER_CARDS`. 검색 결과는 출처 대조 뒤의 보조 근거일 뿐이다.
2. **적재 여부는 문자열 검색이 아니라 도달 가능성으로 판정한다.** 양방향으로 확인한다 — "호출문이 없다"면 그 파일이 부르는 공통 경로(CT)를 한 단계 이상 따라가고, **"호출문이 있다"면 그 줄까지 실행이 닿는 조건(시크릿·설정·스케줄러)이 실제로 채워지는지** 확인한다. 둘 중 하나만 하면 3차·4차 오류가 반복된다.
3. **한 사례로 확인한 것을 전체로 확장하지 않는다.** 표의 각 행은 각각의 근거를 갖는다.
4. 표를 고칠 때마다 **어느 출처와 대조했는지 문서에 남긴다.**
