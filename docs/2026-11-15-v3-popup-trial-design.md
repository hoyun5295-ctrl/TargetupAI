## §2 로그인 전 팝업 = `components/v3/V3LoginIntroModal.tsx`

### 2-1 띄우는 자리와 스위치

- 자리 = `pages/LoginPage.tsx` 의 `showPolicyNotice`(점검 안내 창이 먼저 · 슈퍼관리자 화면 제외 · 「오늘 하루 보지 않기」 = `LoginPolicyNoticeModal` 의 같은 저장 열쇠). 판정 함수는 지금 그대로 `shouldShowLoginPolicyNotice()`.
- **스위치 ENV `V3_LOGIN_INTRO`**(값 `on` 일 때만 V3 팝업 · 비면 종전 인증 안내 창). 이유 = 팝업의 장면 2 ~ 4(상품 반응 · 기본 여정 한 번에 · 업종 평균)는 단계 개방 ENV(`V3_STAGE_*`)가 닫힌 동안 고객이 못 쓰는 기능이다. 로그인 전에는 회사를 모르므로 회사별로 가릴 수 없다 → 열지 않은 기능을 약속하지 않도록 Harold 가 V3 를 연 뒤 한 번 켠다.
- 화면이 스위치를 아는 길 = 공개 주소 `GET /api/public/intro/v3-login`(로그인 없음 · 응답 `{ on: boolean }` · 판정 CT `utils/v3-login-intro.ts`). 응답을 못 받거나 늦으면(1.5초) 종전 인증 안내 창. **★1115 배포 직후 고침(§12-5)** = 창은 첫 그림부터 뜬다. 무엇을 띄울지는 이 브라우저가 지난번에 받은 답(`localStorage` `v3LoginIntroOn`)으로 정하고(받은 적 없으면 종전 인증 안내 창), 서버 답은 기억을 고치며 첫 그림과 다를 때만 창을 바꾼다. 못 받은 답은 모름 = 띄워 둔 창과 기억 그대로.
- 인증 안내는 사라지지 않는다 = 다섯째 장면이 요약(제목 세 줄 = `LoginPolicyNoticeModal` 의 `CHANGES` 를 그대로 읽는다) + 「인증 안내 전체 보기」를 누르면 종전 `LoginPolicyNoticeModal` 이 그대로 뜬다.

## §5 무료체험 3회 = CT `utils/studio-trial.ts` + 표 `image_studio_trials`

### 5-1 자격과 신청

- **체험 자격 한 곳** `utils/plan-guard.ts studioTrialEligible(plan, user)`(요금제 판정의 주인 파일 · 뿌리 대장 R2 = `isAiOperatorAllowed` 를 그 파일 밖에서 따로 부르지 않는다) = `!isAiOperatorAllowed(plan, user)` ∧ `isUnsubscribed(plan)` ∧ `!isSubscriptionBlocked(plan).blocked`.
  = 지금 판정이 AI 기능을 막는 **미가입** 회사뿐. 30일 AI 체험 중 · 허용 명단 · 슈퍼관리자 · 유료 = 자격 없음(지금 길이 이미 열려 있다) · 만료 · 정지 = 자격 없음(미가입이 아니다).
  이 함수를 신청 · 생성 문 · 소개 창 갈래 · 화면 입구가 모두 부른다(판정 사본 0).
- 주소 `POST /api/image-studio/trial/request`(로그인 필수 · 고객사 사용자).
  - 자격 있음 → `INSERT … ON CONFLICT (company_id) DO NOTHING` 뒤 그 회사 행을 읽어 `{ requested: true, granted, used, remaining }`(두 번 눌러도 같은 답 · 3회가 다시 차지 않는다).
  - 자격 없음 → 409 `TRIAL_NOT_ELIGIBLE` · 요금제 조회 실패 = 503 · 표 없음 = 503 `DB_MIGRATION_PENDING`.
- 상태 `GET /api/image-studio/trial` = `{ eligible, requested, granted, used, remaining }`(신청 전 = requested false · 표 없음 = 503).

### 5-2 생성 문(`routes/image-studio.ts` `/generate` 한 곳)

지금 순서 = 준비 확인 → **요금제 문**(`aiZonePlanBlocked`) → 시도 키 → 잠금 → 같은 시도 기억 → 납부 확인 → 입력 검사 → **크레딧 사전 확인** → 생성 → **성공 뒤 차감** → 기억 → 응답.

**체험의 원칙 = 생성 전에 한 칸을 먼저 잡고(선점), 실패하면 되돌린다. 이미 쓴 키로는 새 그림을 만들지 않는다.** (크레딧은 「성공 뒤 차감」이지만 체험은 「잡은 칸 수 = 만든 포스터 수의 상한」이 불변식이어야 한다 → 모자라게 줄 수는 있어도 넘치게 줄 수는 없다.)

바꾸는 것(체험 모드일 때만 · 그 밖은 한 글자도 같은 길):

1. 요금제 문 자리에서 요금제 문맥을 한 번 읽어(`loadPlanContext`) `resolveStudioTrial(companyId, user, plan)` 과 종전 요금제 문(`aiZonePlanBlocked` 의 `ctx`)에 같이 쓴다.
   - 지금 판정이 허용(`isAiOperatorAllowed`) → `none` = 종전 길 그대로(체험 행이 있어도 보지 않는다 = 권한이 줄지 않는다).
   - 자격 있음(§5-1) ∧ 신청 행 있음 → `trial`(그 행의 `granted` · `used_keys` 를 싣는다).
   - 그 밖 = `none` → 지금 그대로 `aiZonePlanBlocked`(미가입 + 미신청 = 종전 403).
   - 표 없음(42P01) = `none`. 요금제 조회 실패 = 종전 문이 내는 503 그대로.
2. 체험 모드에서는 납부 확인(`isChargedByKey`) · 크레딧 사전 확인(`checkCredit`) · 성공 뒤 차감(`settleOrUndo`)을 부르지 않는다.
3. 키 = 시도 키(`attemptKey`)가 있으면 그것 · 없으면 이 요청에서 만든 `image-studio:{새 id}`(지금 차감 멱등키와 같은 꼴 · 키 없는 요청은 매번 새 칸).
4. 같은 시도 기억(`recallStudioResult`)이 있으면 지금처럼 그 결과를 준다(소모 0 · 새 생성 0).
5. **「이미 쓴 키인가 · 남은 칸이 있는가」의 판정 자리는 선점 한 곳뿐이다**(요금제 문 자리에서 읽어 둔 `used_keys` 로 미리 가르지 않는다 = 두 프로세스가 같은 사전 상태를 읽고 같은 키로 겹쳐도 판정이 갈리지 않는다).
6. 입력 검사(템플릿 · 제품 · 예시 문구) · 임시 용량 검사를 다 지난 뒤, 생성 직전에 **선점** `reserveStudioTrial(companyId, key)`:

```sql
UPDATE image_studio_trials
   SET used_keys = array_append(used_keys, $2)
 WHERE company_id = $1::uuid
   AND NOT ($2 = ANY(used_keys))
   AND cardinality(used_keys) < granted
RETURNING cardinality(used_keys) AS used, granted
```

   - 1행 = `ok`(한 칸을 잡았다 → 만든다).
   - 0행 = 만들지 않는다. 두 뜻을 **뒤이은 읽기 한 번**으로 가른다(`reserveStudioTrial` 이 `state` 로 돌려준다):
     - **남은 칸이 있다**(쓴 칸 < 받은 칸) = `spent` → 409 `TRIAL_ATTEMPT_SPENT`(「이 요청은 이미 처리됐어요. 다시 만들려면 만들기를 한 번 더 눌러 주세요.」 · 남은 횟수는 그대로다). 칸이 남았는데 0행 = 이 키가 이미 쓰였다는 뜻이다: 같은 키의 겹친 요청 · 재기동이나 다른 프로세스로 기억이 사라진 다시 요청 · 그 키가 방금 되돌려진 틈. 어느 쪽이든 화면이 만들기를 다시 누르면 새 시도 키로 한 칸을 새로 쓴다.
     - **남은 칸이 없다**(행 없음 포함) = `used_up` → 403 `TRIAL_USED_UP`(「무료체험 3회를 모두 쓰셨어요.」).
     - 읽은 행에 「이 키가 있는가」로 가르지 않는다 = 선점과 읽기 사이에 그 키가 되돌려지면(겹친 첫 요청의 생성 실패) 「칸이 남았는데 다 썼다」로 답하게 되기 때문이다.
7. 생성 · 임시 저장이 실패하면 **되돌림** `releaseStudioTrial(companyId, key)`(`array_remove`) 뒤 지금의 오류 응답. 되돌림이 실패하면 로그 한 줄 + 경보(칸 하나가 쓰인 채 남는다 = 모자라게 주는 쪽 · 넘치지 않는다).
8. 성공 = 결과를 기억하고 응답에 `trial: { used, granted, remaining }` 을 싣는다.

이 순서라 「만들었는데 소모 문장이 실패」하는 길이 없다(소모가 생성보다 앞) → 임시 그림을 거둘 일도 생기지 않는다. 회사당 동시 생성은 지금도 한 건(프로세스 잠금)이고, 선점은 DB 한 문장이라 두 프로세스가 겹쳐도 3칸을 넘지 않는다.
