## 1. ★ config 스키마 변경 — live config 마이그레이션 정확한 diff 요청

v1.0.10 예제 config를 보니, 강조표기 attachment 매핑 방식이 v1.0.8과 **달라졌습니다**:

- **v1.0.8(현재 live)**: `field_map.kakao_payload: "k_etc_json"`
- **v1.0.10(예제)**: 전용 섹션 신설 —
  ```yaml
  kakao_payload_map:
    attachment: "attachment_json"   # 예제는 placeholder 컬럼명
    carousel: "…"
    business_code: "…"
    user_map: "…"
    ft_type: "…"
    chat_bubble_type: "…"
  ```

설치 스크립트는 live config를 덮지 않으므로, **바이너리만 v1.0.10로 바꾸면 live는 여전히 옛 `field_map.kakao_payload`** 입니다. v1.0.10이 이 옛 키를 무시하면 강조표기 매핑이 조용히 죽습니다.

**확인/회신 부탁:**
1. v1.0.10에서 강조표기(대표링크)는 `field_map.kakao_payload`가 아니라 **`kakao_payload_map.attachment`**로 매핑하는 게 맞습니까? (옛 `field_map.kakao_payload` 하위호환 지원 여부도)
2. 우리 실제 컬럼은 `k_etc_json` 입니다. 그러면 live config는 아래가 맞습니까?
   ```yaml
   # field_map 에서 제거
   #   kakao_payload: "k_etc_json"   ← 삭제
   # 신설
   kakao_payload_map:
     attachment: "k_etc_json"
   ```
3. **v1.0.10 엔진이 `k_etc_json` 안의 `attachment_link`(snake, url_mobile/url_pc/scheme_ios/scheme_android) 객체를 꺼내 IMC ATTACHMENT.link(urlMobile/urlPc)로 변환**합니까? (7300의 실제 관문. `link` 키가 아니라 `attachment_link`임에 유의)

## 2. 대체발송(kakao_failover / kakao_alt_msg) 매핑

v1.0.10 field_map에 신규로 `kakao_failover`·`kakao_alt_msg`가 있습니다. 우리 컬럼은 알림톡 실패 시 대체발송용 `k_next_type`(S/L) / `k_next_contents`(본문)입니다.

**확인 부탁:** 알림톡 실패→SMS/LMS 대체발송을 쓰려면 live config에 아래를 추가하는 게 맞습니까?
```yaml
field_map:
  kakao_failover: "k_next_type"
  kakao_alt_msg: "k_next_contents"
```
(안 쓰면 생략 가능한지도. `kakao_failover.enabled`는 false 유지 예정 — Agent가 고객사 DB에 재전송 row 만드는 건 원치 않음.)

## 3. 유지해야 할 live 설정 (마이그레이션 시 실수 방지)

예제 기본값과 우리 운영값이 다른 항목 — 마이그레이션 때 **아래는 우리 값 그대로 유지** 부탁:
- `state_policy.mode: "final_result_only"` (예제 기본은 `transition_column`). 우리는 최종 REPORT 전 고객사 상태 보존이 필요합니다.
- `table: "SMSQ_SEND_13"`, `agent_id: "hanjul01"`, gateway/source 접속정보, `msg_type_values.kakao_alim: "K"` 등 현행값.

## 4. reportDBFailures 원인 (교체 시 함께 확인)

현재 v1.0.8 로그에 `reportDBFailures:2502` + 대기 1건(07-05 이후 정지)이 있습니다. 교체 스크립트의 `doctor --check-runtime-write`(트랜잭션 롤백 probe)로 **SMSQ_SEND_13 UPDATE 권한**을 검사하니, 그 결과를 회신 부탁합니다.
- runtime-write가 FAIL이면 = 리포트 write-back 실패의 원인(DB 계정 UPDATE 권한). 이 경우 한줄로가 계정 권한을 손보겠습니다.
- PASS면 = 그 07-05 대기 1건은 별도 원인(그 시점 이슈)이라 무시 가능한지 판단.
