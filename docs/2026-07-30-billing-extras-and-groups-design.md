>

## §0 문제 — 특례가 시스템 밖에 있다

일괄발급·컨펌·세금계산서 체계(0728)를 세웠는데도 서 팀장은 매달 전 업체를 손으로 보정하고 있었다.
청구 규칙 상당수가 **머릿속과 종이(KT 명세서 손글씨)에만** 있기 때문이다. 사람이 바뀌면 청구가 틀어진다.

접수 항목을 성격으로 가르면 셋이다. 한 덩어리로 보면 설계가 안 나온다.

| 부류 | 성격 | 해법 축 |
|---|---|---|
| ① 반복 금액 규칙 | 매달 같은 값(최소과금·080 관리비·정액 특례) | **축 A** — 회사 규칙·월별 항목 |
| ② 발행 분할 | 누구 앞으로 몇 장을 끊는가(지점·대상ID·계정 묶음·모듈/웹) | **축 B** — 발행 그룹 |
| ③ 수기 종량 | 매달 값이 바뀌고 사람 판단이 끼는 것(통화료·URL 제작·대행 문안) | **축 A** — 월별 항목 수기 입력 |

## §2 축 A — 080 청구 (구현 완료)

### 2-1. 실체 (KT 명세서 실측)

인비토 명의로 **월 1장**이 온다. 일반전화 1대 + **080 서비스번호 18대**. 번호마다 `부가서비스이용료(고정) + 이동전화에 건 통화료(변동) + VAT`.
2026-07 청구분 실측: 총 155,930원 / 080 소계 147,462원 / 부가서비스 전 번호 4,000원 / 통화료 0~27,790원 / **VAT = floor((통화료+부가서비스) × 10%)**(18행 전수 확인).
번호↔업체는 명세서 여백의 손글씨가 유일한 근거였다. `080-566-3330`에 "7월부터 리스킨 사용" 메모가 있어 **번호는 업체 간 재배정된다**는 것도 확인된다.

이용료 9,900원(부가세 포함)은 KT 청구서에 없다 — **인비토가 붙이는 080 관리 서비스료**(Harold 확정).

### 2-2. 구조

```
번호 매핑(1회 등록) → 매달 KT PDF 업로드 → vision 판독 → 코드 검산 → 사람 확인 → [반영] → 발행이 항목으로 인쇄
```

- **매핑** `billing_080_numbers` — 번호(숫자만·전사 유일)·회사·라벨(부서/브랜드)·이용료 공급가(기본 9,000)·KT 부가서비스 공급가(기본 4,000)·통화료 청구 여부·활성. 금액은 전부 **공급가 저장**(VAT는 청구서가 파생 — 0726 원칙).
  - 기존 `users/companies.opt_out_080_number`(수신거부 콜백 축)는 **재사용 불가** — 회사당 1개뿐이고 의미가 다르다(실측 확인).
- **판독** `utils/billing-080.ts extractKtStatement` — 0728 사업자등록증 판독(`biz-registration-extract`) 미러. PDF/이미지·10MB·매직바이트 스니핑·크레딧 0.
- **검산은 AI가 아니라 코드**(`validateKtStatement`, 전부 fail-closed):
  ① 행 내부합 `call+svc+vat = subtotal` ② `VAT = floor((call+svc)×10%) ±1` ③ 부가서비스 0 행 거부 + 3행 이상일 때 최빈값 이탈 거부 ④ `Σsubtotal = total_080` **및** 행 수 = `count_080`(둘 다 필수 — 0이면 판독 실패로 본다) ⑤ 번호 중복 ⑥ **3행 미만 = 자동 반영 불가**(통계 축이 성립하지 않는 표본).
- **결속** — /parse가 정규형(번호 정렬·정수 고정)에 **HMAC 서명**(TTL 6시간)을 발급하고, /apply는 서명이 유효한 전문만 받아 **검산을 서버에서 다시 실행**한다. 판독을 거치지 않은 금액은 반영될 수 없다.
- **반영** → `billing_extra_items`에 **번호당 1행**(`kind='080_call'`, 그 달 그 번호의 통화료). 회사 단위 독립 트랜잭션. 발행된 달은 건너뛰고, 이미 반영된 번호는 `ON CONFLICT DO NOTHING`으로 **그 번호만** 건너뛴다. 미매핑 번호는 "보류"로 표시만.
- **발행 통합** — `channel='extra'` 신설. 발행 코어가 **미소비 항목만** FOR UPDATE로 싣고, 그 항목이 실린 장의 커밋 트랜잭션에서 `billed_billing_id`를 마킹한다. 항목줄·금액 항등식·장 분배·절사 계약은 기존 그대로(공급가 정수라 절사 멱등).
- **파생** — 스냅샷 1행 × 매핑 원장 → 이용료·KT 부가서비스·통화료 최대 3줄(`buildExtraBillingItems`). 금액 0은 줄을 만들지 않는다. §2-4.

### 2-3. 왜 이렇게 했나 (Codex 적대검증 5R에서 굳은 것)

| 결정 | 이유 |
|---|---|
| `billed_billing_id` 소비 마커 | 없으면 7/1~15 + 7/16~31처럼 **겹치지 않는 두 발행**이 같은 달 항목을 각각 실어 이중청구가 된다. AI 크레딧(`ai_credit_transactions.billed_billing_id`)이 같은 부류를 이미 푼 계약이라 그대로 미러 — FK `ON DELETE SET NULL`이라 발행을 지우면 자동으로 미소비로 돌아온다 |
| 발행·반영·취소가 **같은 회사 advisory lock** | 잠금 밖에서 "발행이 있나" 조회만 하면 경합에서 진다. 취소 DELETE는 `WHERE billed_billing_id IS NULL` 원자 조건이라 져도 근거 행을 못 지운다 |
| 검산 결과의 서버 결속(HMAC) | 검산은 "전문 안에서의 일관성"만 본다 — 일관되게 조작한 전문은 통과한다. 세션 저장 없이 결속하는 최소 수단이 만료형 서명 |
| `toStrictInt`(숫자 타입 안전 정수만·반올림 금지) | `NaN → JSON null → Number(null)=0`으로 **"판독 불가"가 "0원"으로 살아나는** 3단 경로가 있었다. 671.6을 672로 살려주는 반올림도 같은 부류(손상 전문이 서명을 유지) |
| 총계·번호수 0을 불합격으로 | "안 보이면 0" 폴백이 검산을 여는 fail-open이었다 |

### 2-4. 원장 파생 (★2026-08-04 재설계 — 서수란 0803 접수 2건)

접수는 둘이었지만 뿌리는 하나다. **진실이 두 곳이었다.**

매핑 원장(`billing_080_numbers`)이 이용료·KT 부가서비스·통화료 청구 여부·귀속 계정의 진실인데, [반영]이 그 값을 `billing_extra_items`로 **복사해 굳혔다.** 발행은 복사본만 읽었고, 원장을 고쳐도 복사본은 그대로였다. 재반영도 UNIQUE 충돌로 막혔다.

| 접수 | 증상 | 원인 |
|---|---|---|
| 1 시세이도 | 이용료를 10만원·부가서비스 0·통화료 미청구로 고쳤는데 청구서에 9,000 / 4,000 / 7,096이 나갔다 | 금액 복사 (항목 생성 08-03 05:38 / 원장 수정 05:40~05:42) |
| 2 금강제화 | 귀속을 `kumkang` 계정으로 지정했는데 공통 장(₩24,185) 청구서가 생겼다 | 귀속 복사 (생성 시 `user_id` NULL / 원장 귀속 06:20) |
| 3 리스킨 | 매핑 회사를 인비토로 바꿨는데 계속 리스킨으로 청구된다 | **회사 축이 스냅샷 소유** — 매핑만 옮기면 옛 회사 청구서에 그대로 남는다 |
| 4 신성통상 | 무료 전환이라 비활성으로 바꿨는데 이용료가 계속 청구된다 | **활성 여부가 청구에 쓰이지 않았다** |

**처방 — 원장 상태가 곧 청구 상태다.** [반영]이 저장하는 것은 **명세서에서만 나오는 값 하나**(그 달 그 번호의 통화료)와 **회사 축**뿐이고, 금액·귀속·청구 여부는 발행 시점에 원장에서 읽는다.

| 원장 상태 | 청구 |
|---|---|
| 활성 + 그 회사 | 원장값 파생(이용료·KT 부가서비스·통화료) |
| **비활성** | **0줄.** 소비 마킹만 — 사람이 명시한 중단이라 발행을 막지 않는다(접수 4) |
| **매핑 없음**(삭제·타사 이관) | **0줄 + 발행 차단 422 `BILLING_080_MAPPING_MISSING`** |

| 결정 | 이유 |
|---|---|
| 스냅샷 = 통화료 1행(`080_call`), 통화료 0원도 저장 | "그 달 그 번호가 반영됐다"가 발행이 그 번호를 싣는 근거다. 0원 줄은 `buildInvoiceLines`가 항목표에서 빼므로 청구서에는 안 나온다 |
| 파생·귀속 판정을 CT 함수 하나로 (`buildExtraBillingItems`·`extraRowUserId`·`extraRowsBlockingIssue`) | 항목이 실린 장과 소비 마커가 걸리는 장이 갈라지면, 공통 장 하나를 지울 때 계정 장 항목까지 미청구로 풀려 이중청구가 된다(0731에 한 번 겪은 부류) |
| 조인 조각을 CT 상수로 (`EXTRA_ITEM_SOURCE_SELECT`·`_JOIN`) | 발행·최소과금 게이트·반영 현황 화면이 **같은 문**을 쓴다. 세 곳에 각각 적으면 한쪽만 고쳐졌을 때 화면 금액과 청구서 금액이 갈라진다 = 오청구 |
| 활성 여부는 **조인이 아니라 값**(`map_is_active`)으로 | "매핑 없음(근거 소멸 = 차단)"과 "비활성(청구 중단 = 0줄)"은 다른 상태다. 조인 조건에 섞으면 둘을 구분할 수 없다 |
| 매핑이 없으면 **아무것도 청구하지 않고 발행을 막는다** | 통화료만이라도 싣는 폴백이 **fail-open**이었다 — `charge_call_fee=false`로 등록해 통화료를 안 받던 번호도 매핑을 지우는 순간 **없던 통화료가 새로 청구된다**(Codex 적대검증 high) |
| **회사를 바꾸면 미소비 반영분도 함께 옮긴다**(양쪽 회사 잠금·발행 있으면 409) | 접수 3의 처방. 번호 표기를 고친 경우 `source_ref`도 함께 옮긴다 — 안 옮기면 그 반영분이 매핑을 잃어 그 회사 발행이 통째로 막힌다 |
| 옛 `080_fee`·`080_svc` 행은 **현행 스냅샷이 있을 때만** 건너뛴다 | 옛 반영기는 통화료 미청구·0원이면 `080_call`을 아예 안 만들었다. kind로 통째 거르면 그 고정료가 **영구 미청구**가 된다(Codex 적대검증 high) |
| 어느 장에도 안 실린 스냅샷 행도 발행이 소비 마킹 | 전액 무료 번호(리스킨)는 파생이 0줄이다. 안 마킹하면 달마다 다시 읽힌다 |
| 최소과금 게이트도 **같은 파생 함수로 양수 금액만** 차단 + 0줄 스냅샷은 그 청구서가 소비 | 행 존재만으로 거부하면, 일반 발행은 `BILLING_NOTHING_TO_ISSUE`로 막히고 최소과금은 게이트로 막혀 **어느 경로로도 발행 못 하는 교착**이 된다(Codex 적대검증 medium) |
| 반영 취소에 `kind` 범위 필수 + **화면에 실린 월**(`loadedMonth`)로 삭제 | 범위가 없으면 KT 재반영 때 수기 부가서비스까지 사라졌다(시세이도 25행·125만원). 월을 입력값으로 보내면 6월 목록을 보면서 7월이 지워진다(Codex 적대검증 high) |

| 발행에 실린 행은 화면에 **파생 금액을 보여주지 않는다** | 청구서는 `billing_items`에 굳어 있는데 원장을 고치면 화면 숫자만 바뀌어 "발행액이 바뀐 것처럼" 읽힌다 |
| 이관 가드는 **소비 여부를 가리지 않는다** | 미소비 행만 보면 이미 청구서에 실린 반영분이 옛 회사에 남는다. 그 청구서를 지우는 순간 FK가 그 행을 미소비로 되돌리는데 매핑은 옮겨져 있어 **옛 회사 발행이 영구히 막히고** 새 회사 재반영도 전역 UNIQUE에 걸린다(Codex 2R high) |

| 그 판정 기준은 **입력을 건드렸는가(dirty)**, 마지막 검색어가 비었는지가 아니다 | B를 쳤다가 전부 지우고 실행하면 사용자는 "비웠다"고 믿는데 A가 그대로 저장됐다(Codex 3R high) |
| 닫는 경로 넷(외부 클릭·포커스 이탈·Esc·Enter)을 **한 함수**로 모은다 | 외부 클릭만 처리하던 때는 form 안에서 Enter를 누르면 정리를 통째로 건너뛰고 옛 값이 제출됐다 — 사용자 추가·발신번호 등록이 다른 회사로 들어갈 수 있었다(Codex 3R high). 열림 상태를 ref로도 들어 mousedown·blur 중복 호출을 막고, 필터 결과가 하나면 Enter가 그것을 고른다(추가 클릭 없이) |
| 포커스 경계는 입력이 아니라 **wrapper** | 입력에만 걸면 Tab으로 목록 버튼을 거쳐 다음 필드로 나갈 때 정리가 **한 번도** 실행되지 않는다(버튼의 blur는 입력 핸들러에 안 온다). 그러면 키보드만 쓰는 사용자에게는 옛 값 제출이 그대로 남는다(Codex 4R high) |
| **한글 조합 확정 Enter는 가로채지 않는다**(`isComposing`·`keyCode 229`) | 한국어 회사명을 검색하는 도중 조합을 끝내는 Enter를 선택으로 처리하면, 미완성 검색 결과가 하나일 때 엉뚱한 회사가 골라진다. 소비처 넷이 전부 한글 이름을 검색한다(Codex 4R high) |
| 세션 시작값(`startValue`)과 지금 값이 같을 때만 비운다 · `latest` 스냅샷은 **커밋 후**(`useLayoutEffect`) 게시 | 편집 중에 부모가 값을 바꾸면 그쪽이 진실인데 내 편집 세션이 그것을 지웠다. 렌더 단계에서 공유 ref를 갱신하면 폐기될 수 있는 렌더의 값을 이미 화면에 있는 드롭다운의 핸들러가 읽는다(Codex 4R medium 2건) |
| 바깥 클릭은 **capture 단계**로 듣는다(해제도 같은 옵션) | bubble이면 바깥 요소의 `onMouseDown`이 부모 value를 먼저 예약해도 우리 close가 나중에 실행돼 빈 값으로 덮어쓴다. `startValue` 비교만으로는 **같은 native event 안의** 부모 변경을 못 막는다(Codex 5R high) |
| 옵션 버튼은 `onMouseDown`에서 포커스 이동을 막는다 | 버튼에 포커스를 주지 않는 브라우저(Safari/macOS)에서는 input이 body로 blur되면서 click 전에 목록이 사라져 **선택이 아예 안 되거나 기존 값만 비워진다.** 키보드 선택을 위해 `onClick`은 유지한다(Codex 5R high) |

**불수용(별도 과제)** — Codex가 권한 **effective-dated 매핑 원장**(번호별 대상월 버전 관리). 과거 달 재발행 시 금액이 달라지는 것을 근본적으로 막지만 공사가 크다. 지금은 매핑 없음 = 발행 차단으로 틀린 금액이 나가는 길만 닫는다.

## §3 축 A — 최소과금 (구현 완료)

## §4 축 A — 부가서비스 수기 항목 (구현 완료)

`billing_extra_items.kind='manual'`. 추가 청구 관리 모달의 "부가서비스 입력" 탭에서 회사·대상월·항목 내용·건당 공급가·수량을 넣으면 **수량만큼의 행**(행당 단가)이 생기고, 청구서 항목줄이 같은 단가를 합쳐 **"부가서비스 N건 × 단가"** 참 산식으로 인쇄한다.

시세이도 단축 URL(장당 5만)·제시뉴욕 대행 문안(건당 2만)이 이 경로다. **자동 집계하지 않는 이유** — "서비스 제외" 같은 판단이 사람 몫이라 자동으로 세면 틀린다(§7-5).

발행된 달은 추가 차단, 개별 삭제는 미소비 행만(소비된 행은 발행 삭제로만 복귀).

## §6 축 B — 발행 그룹 (미착수 · 설계 방향)

현행 발행 단위는 `combined`(회사 1장)·`by_user`(계정별)뿐이고 `by_agent`는 축만 잡힌 채 이월돼 있다(`billing-issue.ts`). 접수 3-4·3-6·3-7·3-8과 서 팀장 제안(4번)이 전부 이 공백이다.

**제안 = 발행 그룹.** 회사 밑에 그룹을 두고(이름·사업자·담당자), 구성원으로 **계정 N + 발송ID N + 대상ID N**을 묶는다. 유형 귀속 예외(에이스: 알림톡을 웹으로)도 그룹 속성으로 둔다.
- 기존 `by_user`는 "계정 1개짜리 그룹"의 특수형이라 흡수된다.
- 이월된 `by_agent`도 같은 구조로 열린다.
- 서 팀장 4번 제안("Agent 사용분도 계정별로 지정")의 일반형이 정확히 이것이다.

데이터는 이미 있다 — `billing_items`가 행마다 `user_id`·`agent_id`·`store_id`·`channel`을 적재 중이다. 없는 것은 **그룹 정의와 장 분할 규칙**뿐.

미시스템화 권장 2건: 최선어학원 27지점(분할 금액 기준 미확인 — §7-2), 이새 3장("모듈" 실체 미확인 — §7-3).
