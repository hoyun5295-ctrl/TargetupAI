## 1) 고객 360이란 — 제품 정의

고객 한 명을 누르면 **언제 무엇을 받았고 · 무엇을 보고 눌렀고 · 무엇을 샀고 · 어떤 동의·거부를 했고 · 어느 자동화에 들어가 있는지**가 시간순 한 화면에 나온다.

새로 수집하는 데이터는 없다. **이미 쌓인 12개 원천을 고객 기준으로 합쳐 읽는 뷰**다. AI CRM 축에서 일반 CRM 대비 빠져 있던 두 조각(고객 360 타임라인 · 인바운드 대화) 중 첫 번째다.

사용자는 마케팅 담당자다. "이 고객에게 뭘 했더라"를 답하는 화면이지, 데이터를 분석하는 화면이 아니다.

## 2) 불변 원칙 (어길 수 없는 것)

1. **⛔ 발송 사실은 MySQL 큐에서만 읽는다.** PG `messages`는 INSERT/SELECT 0건인 죽은 테이블이고 `campaigns.sent_count`로 고객별 발송을 만들어 내지 않는다. 캠페인 이름·출처는 PG `campaigns`가 **꾸밈**으로만 붙는다.
2. **⛔ MySQL 큐를 번호로 읽을 때는 회사(`app_etc2`)를 함께 본다.** 회사별 테이블 집합이 **전 bulk 라인 합집합**이라 라인이 회사 전용이라는 전제가 없다. 이 조건이 빠져 2026-08-22에 타사 발송이 고객 화면에 노출됐다(§5-2).
3. **⛔ 고객 식별 축은 `company_id + phone`이다.** `customers`는 UNIQUE(company_id, store_code, phone)라 같은 번호가 매장별로 여러 행일 수 있고, `customers_unified` 뷰는 그 행들을 **접는다**. 뷰로 읽으면 접힌 행의 구매·동의가 통째로 빠진다.
4. **⛔ MySQL 시각은 KST naive다.** 커서(UTC ISO)를 그대로 넘기면 9시간 어긋난다. 양방향 변환(`isoToKstSql` · `kstSqlToIso`)을 거치고, 꺼낼 때는 `DATE_FORMAT` 문자열로 받아 드라이버 타임존 해석에 기대지 않는다.
   **★0824 추가 — 값이 맞아도 화면은 틀릴 수 있다.** 서버는 UTC ISO를 주고, 그것을 **사람이 읽는 표기로 바꾸는 것은 화면의 몫**이다. 상세 카드가 모든 값을 `String(v)`로 찍어 `2026-08-23T23:02:32.000Z`가 그대로 나갔다(§5-5). 새 상세 키를 더할 때 그 값이 시각이면 `DETAIL_TIME_KEYS`에 함께 넣는다.
5. **⛔ 커서는 (시각, 종류, id) 세 짝이다.** 같은 초에 여러 사건이 있으면 시각만으로는 페이지 경계에서 행이 빠지거나 겹친다.
6. **⛔ 원천마다 상한을 걸고 잘렸음을 응답에 적는다.** 조용히 잘라서 "전부입니다"처럼 보이게 하지 않는다.
7. **⛔ 원천 하나가 죽어도 타임라인은 뜬다.** 그 종류만 오류로 표시하고 나머지를 그린다. 전체 500 금지.
8. **제목·부제·상태 문구는 서버가 한국어로 완성해서 보낸다.** 화면이 `status_code`를 다시 해석하면 라벨 표가 두 벌이 된다.
9. **⛔ 접기는 클라이언트가 한다.** 서버 커서가 원행 기준이라 서버에서 행을 접으면 커서가 깨진다. 그리고 **성공과 실패를 한 묶음으로 접지 않는다**(실패 1건이 "6건" 뒤에 숨는다).
10. **요약은 기간·검색·종류와 무관하게 최근 12개월 고정이다.** 타이핑마다 "이 고객이 누구인가"가 흔들리면 읽을 수 없고, 집계에 검색어를 얹으면 제한 시간에 늘 걸려 요약이 통째로 빈다.
11. **못 센 값은 0이 아니라 `null`이다.** 0으로 접으면 "안 보냈다"로 읽힌다.
12. **⛔ 자식 창의 톤은 그 창을 여는 부모 화면을 따른다.** 프로젝트 표준 토큰이 있어도 부모가 다른 언어면 그 자식만 이질적으로 뜬다.
13. **요금제 키는 `customer_db_view`(조회 전용)다.** 적재 키 `customer_db`와 분리한다 — 섞으면 2026-08-14 싱크 유실이 재발한다.

├ 좌 레일 320 (누구인가)          ┤ 우 779 (무슨 일이 있었나)

- 층: 부모 모달 z-50 → 360 z-[70] → 확인 다이얼로그 z-[2100].

### 3-2) 사건 카탈로그 12종

`send`(MySQL 큐) · `dm_view` · `dm_response` · `purchase` · `behavior` · `inapp` · `consent` · `unsubscribe` · `journey` · `inbound` · `email` · `profile`.

### 3-3) API

`GET /api/customers/:id/timeline` 하나. 쿼리 = `before`(커서) · `kinds` · `limit` · `q`(검색 1~40자) · `from`/`to`(YYYY-MM-DD, KST) · `summary=0`(요약 생략).
화면은 `months`를 보내지 않는다 — 서버가 `from`에서 MySQL log 개월 수를 역산한다. 24개월을 넘으면 `sources.send.rangeCapped`로 알린다.
계약 상세 = [v2 설계서 §3-2](2026-08-22-customer-360-v2-design.md).

### 5-5) 값은 맞았는데 화면이 원문을 찍었다 (2026-08-24 · 접수 `cmt6qw4kt00vcjnotd76wbut3` 남지현)

**증상**: 발송 상세 카드의 "요청"·"발송"이 `2026-08-23T23:02:32.000Z`로 보였다. 접수 제목은 "한국 기준으로 표시되지 않는다"였다.

**판정**: **값은 정확했다.** `kstSqlToIso`가 MySQL KST naive를 `+09:00`으로 붙여 올바른 UTC ISO를 만들고 있었고, 그 값은 KST 8월 24일 08:02로 같은 화면의 "마지막 활동 8월 24일 08:02"과 일치했다. 9시간 오차가 아니다.

**원인**: 상세 카드가 `detail` 전체를 `typeof v === 'number' ? v.toLocaleString() : String(v)`로 찍는다. 타임라인 본문은 `timeLabel`을 거치는데 이 카드만 안 거쳤다. **일반 렌더는 시각 키를 모른다.**

**수정**: `timeline-kinds.ts`에 `DETAIL_TIME_KEYS`(`requestedAt`·`sentAt`)와 `detailTimeLabel`을 두고 카드가 그것으로 그린다. 그 건의 날짜와 다른 날이면 날짜를 함께 보인다(예약 발송은 요청과 발송이 며칠 떨어진다). 시각이 아닌 값이 들어오면 원문을 그대로 둔다.

⚠ **별도 과제(안 건드렸다)**: 이 화면의 모든 표기는 `toLocaleTimeString('ko-KR')`을 **브라우저 시간대**로 쓴다(`dayLabel`의 오늘·어제 계산도 같다). 지금 사용자는 전원 국내라 결과가 같고, 이번 접수의 증상과도 인과가 없다. 국외 접속을 지원할 때 `timeZone: 'Asia/Seoul'` 고정을 4곳(`dayLabel`·`timeLabel`·`detailTimeLabel`·`Customer360Rail`)에 한 번에 건다.

### 5-1) 화면 축에서 네 번 왕복했다 (교훈)

목록 옆 패널 붙이기 → 고객 선택 시 목록 300px 접기 → **조회 모달을 콘솔 톤으로 재작성했다가 "예전이 낫다"로 원본 롤백** → 자식 창 톤 재작성.

- **쓰던 화면은 갈아엎기 전에 묻는다.** 옆 화면을 새 톤으로 올렸다고 이 화면도 올려야 하는 것이 아니다.
- **화면 재설계는 글이 아니라 버리는 목업으로 승인받는다.** 같은 날 오전 글로 가서 4회 왕복했고, 저녁에 목업으로 첫 시안 승인됐다.
- 관련 memory: `feedback_ask_before_replacing_a_screen_in_use` · `feedback_mock_before_approval_for_screen_redesign`.

### 5-2) 회사 격리 결함 — AI 기능이 타사 데이터를 노출했다 (⛔ 최중요)

**증상**: 테스트계정에서 법인폰 고객의 "받은 메시지"가 110건으로 보였다. 실제 그 회사가 그 번호로 보낸 것은 **4건**이었다.

**원인**: `fetchSends`·`countSends`가 `WHERE dest_no = ?`만 걸었다. 읽는 테이블이 회사 라인이 아니라 **전 bulk 라인 합집합**이라, 같은 라인을 쓰는 다른 회사(주식회사 인비토)의 발송과 한줄로 밖에서 적재된 행(`app_etc2` NULL 147건)이 전부 섞여 들어왔다.

**어떻게 드러났나**: tsc·vitest·빌드 전부 통과했다. 2차 개편 회의 중 "같은 LMS 6건이 live·log 중복인가"를 확인하려고 실행한 SQL에서 **우연히** 드러났다.

**처방**: 두 곳에 `AND app_etc2 = ?` + 소스 계약 테스트("`dest_no = ?` WHERE는 전부 `app_etc2 = ?`를 동반한다").

**일반화**: MySQL 큐를 번호로 읽는 코드는 회사 조건이 없으면 **다른 회사 데이터를 읽는 코드다.** 새 조회를 만들 때 `dest_no`·`app_etc1` 옆에 `app_etc2`를 기본값으로 둔다. → LESSONS_BACKEND 핵심 원칙 등재.

### 5-3) 내가 만들고 내가 잡은 결함 (Phase 0)

1. MySQL 시각을 UTC ISO로 넘겨 9시간 어긋남 → 양방향 변환 + 테스트 3건.
2. `num(true) = NaN`이라 예약 발송 판정이 항상 false.
3. 요약 COUNT가 인덱스 없이 20초씩 걸려 화면을 붙잡음 → 제한 시간 + `null` 반환.
4. (v2) 지역 변수가 모듈 헬퍼를 가려 tsc가 잡음 · 첫 로드 판정을 목록 길이가 아니라 요약 보유 여부로.

**교훈**: 다른 시각 축(MySQL KST naive ↔ PG timestamptz)을 잇는 코드는 **양방향 변환 테스트를 먼저 쓴다.**

### 5-4) 뒤집힌 판단

| 처음 생각 | 실제 | 왜 |
|---|---|---|
| PG `messages`로 고객별 발송을 읽는다 | MySQL 큐만이 진실 | `messages`에 쓰는 코드가 0건 |
| `customer_id` 하나로 묶는다 | `company_id + phone`으로 펼친다 | 같은 번호가 매장별 여러 행 |
| `/customers` 페이지를 신설한다 | 모달 안에 + `?customer=` 딥링크 | 이 앱은 "메뉴 = 모달" 규칙 |
| 읽기 폭 880px 중앙 정렬 | 폭을 다 쓰는 2열 | 1,100px 창에서 오른쪽이 빈다 |
| 서버가 접어서 내려준다 | 클라이언트가 접는다 | 커서가 원행 기준이라 깨진다 |
| 검색 시 서버가 기간을 강제로 좁힌다 | 좁히지 않는다 | 인덱스 적용 후 접근 경로가 `dest_no` ref 그대로 |
