## §8 Harold님이 정할 것(이 표 확인 뒤 · 설계 전)

1. **이 범위가 빠짐없는가** — 입구 15(§3) · 쓰는 자리 셋(§2 1 · 9 · 10) · 발송 적재(§2 11) · 정리 함수 세 벌(§4 나).
2. **대행 접수에 보낼 수 없는 글자가 있을 때 처리 방식**
   - (가) 접수 반려 · 메일 회신에 「n번째 줄 ○○ 뒤 · 글자 이름(코드)」 목록 · 고쳐서 다시 보내 달라(사람 문안 불변 원칙 그대로 · 한 번 더 왕복)
   - (나) 그 글자를 빼고 접수 · 회신 · 승인 요청 문자에 「이 글자를 빼고 보냅니다(n번째 줄 ○○)」를 적는다(왕복 0 · 고객 문안을 우리가 바꾼다 · 메모리 「고객 문안 불변」과 부딪힘 → 알리고 바꾸는 것이라 「몰래」는 아님)
   - (다) (나)인데 이모지 · 보이지 않는 글자 같은 **지워도 뜻이 안 바뀌는 글자만** 빼고, 그 밖(⭐ 같은 표 밖 기호)은 (가)로 반려
   - 추천 = (다) — 이모지 · 보이지 않는 글자는 문자에서 원래 나갈 수 없어 지워도 문장 뜻이 같고(여정 발송이 이미 같은 정리를 한다 · `sanitizeUnsendableForSms`), 접수 순간 알리면 「몰래 바꿈」이 아니다. 뜻이 담긴 기호는 사람이 고르게 반려한다.
3. **자동 마케팅 · 플래너 · 자동발송(AI 글)의 같은 반려** — AI 글은 고객 문안이 아니므로 생성 직후 같은 표로 정리(D6) · 사람 글(자동발송 고정 문안 · 리마인드 입력 · 플래너 편집)은 저장 때 막고 어느 글자인지 안내 — 이 둘을 같은 배포에 넣는가.
4. **명단 값(D5)** — 접수 때 명단 전체를 같은 판정으로 보고 「n행 ○○ 칸」을 알릴지(지금 = 첫 행만 검사 · 나머지 발송 때 9401).
5. 이미 나간 문자 확인 — 접수 0de4891d 의 3회째 담당자 문자(「문안 문제는 아닙니다」)가 실제로 나갔는지는 미확인(Harold 실행 · 읽기 SQL 은 확인 뒤 드림).
