# 여정(Journey) — 기능 상설 SoT

> **호출어: "여정"** — Harold님이 여정을 언급하면 이 문서를 먼저 연다.
> 이 문서는 **여정 기능의 현재 모습과 이력 색인**을 소유한다. 시점별 설계 근거·경위는 각 설계서가 소유하고 여기엔 링크만 둔다(doc_ownership).
> 상태·잔여는 STATUS §2 카드가 소유한다. 여기엔 **구조와 원칙**만 남긴다.

---

## 1) 여정이란 — 제품 정의

트리거가 발생한 **그 고객에게** 정해진 순서로 메시지를 보내는 자동화. 캠페인(한 번에 다수)과 다르다.
사용자는 마케팅 담당자다 — 직관 + 압도적 쉬움 + 완성 품질을 동시에 만족해야 한다.

**여정은 마케팅 자동화다** (2026-08-02 Harold 확정). 정보성 운영 알림은 `정보 알림` 축이 따로 가진다(`InfoAlertJourneyBuilder`).
**가르는 기준은 "트리거가 정보성이냐"가 아니라 "그 뒤에 마케팅 시퀀스가 붙느냐"다.**
- 배송 시작(정보성 사건) → 후기 요청·재구매 유도 = **여정**.
- 예약 접수·방문 리마인드 = 리마인드 자체가 목적, 뒤가 없다 = **정보 알림**.

## 2) 불변 원칙 (어길 수 없는 것)

| 원칙 | 뜻 | 어겼을 때 |
|---|---|---|
| **정답표를 갖지 않는다** | 무엇이 가능한지는 고객사가 준 데이터가 런타임에 정한다. 조건 하드코딩 금지, 없으면 정직하게 잠근다 | "켜 뒀는데 영원히 0건" — 이 재설계가 없애려는 병 자체 |
| **진실을 복사하지 않는다** | 같은 사실을 두 번째 테이블에 미러링하지 않는다. 원본을 읽는다 | 멱등키·대조워커·지표오염이 자동으로 따라온다 |
| **문은 회사마다 하나** | 같은 사실이 두 문(자사몰·싱크)으로 들어오면 한 문만 진실로 삼는다 | 같은 구매가 두 번 진입 = 중복 발송·중복 과금 |
| **커서를 DB 정밀도 밖으로 내보내지 않는다** | 커서 시각은 `::text` 원문으로 읽고 쓰고 비교한다 | µs 절사로 마지막 밀리초 묶음이 매 회차 재발송 |
| **게이트는 실제로 시작되는 길목에** | 발송이 시작되는 유일한 길목은 **활성화**다. 화면 잠금은 우회된다 | 자연어 생성·조회 실패로 게이트가 새고, 이미 활성인 여정은 아예 대상 밖 |
| **과거분 소급 금지** | 이관·전량 재적재가 과거 사실을 오늘 올려도 트리거로 인정하지 않는다(발생 시각 기준) | 3년 전 구매에 "구매 감사합니다"가 나간다 |
| **상한 없이 켜지지 않는다** | 전 트리거 수신자 상한 필수 | 대량 적재 한 번에 코호트 전체 발화 |
| **새 트리거 = 레지스트리 + DB CHECK 동시** | `TRIGGER_CONTRACTS`와 `journeys_trigger_event_registered`는 같은 집합 | 저장은 되는데 DB가 거부하거나 그 반대 |

## 4) 트리거 현황 (2026-08-02 — 마케팅 12종 + 상시로 확정)

**마케팅 12종** — 신규가입 · 첫 구매 · 재구매 · 휴면 · 휴면 복귀 · 구매 주기 이탈 · **등급 상승** · 생일 · 포인트 소멸 · 장바구니 이탈 · 배송 · 조회 후 미구매
**상시 1종** — 자유 세그먼트. 트리거가 없어 여정 정의에서 벗어나지만 남긴다(세그먼트 다단계 드립은 캠페인이 못 한다). **재진입이 구조적으로 안 되므로 화면이 "한 번만 나갑니다"를 명시해야 한다.**
**예약 3종은 여정에서 빠졌다** → 정보 알림 축([설계서 §3-3](2026-08-01-journey-redesign-design.md) · 설계 보존 = §12). 코드는 이미 잠김(`RESERVATION_REASON` · `implemented: false` 2종).

**등급은 상승만 발화한다** (2026-08-02 구현 완료) — 하락 통지는 마케팅이 아니다. 판정은 `customer_grade_ranks`(회사가 한 번 확인한 서열)로 하고, **양쪽 중 하나라도 표에 없거나 순서 없음이면 제외**한다. 서열 확인 전에는 트리거가 잠긴다. 하락도 원장 state 갱신은 계속한다. 근거·결정 전문 = 설계서 §3-1·§14.

**겹침 안내 의무** — 재구매와 휴면 복귀는 같은 구매 하나로 둘 다 발화한다. 둘을 같이 켜면 한 번의 구매에 두 통이 나간다. 여정끼리 밀어내지 않는 것이 설계 결정이므로(§5-3) 막지 않되 화면이 알린다.

정의 전문 = [여정 재설계 설계서 §3](2026-08-01-journey-redesign-design.md).

**구매는 문이 둘이다** — 자사몰(`cdp_events`) / 싱크에이전트(`purchases` 원장). 어느 문이든 같은 트리거가 물린다.
매장 구매는 **하루 모아 다음 날 오전(KST 09~12시)** 정책 — 고객사 동기화 주기가 우리 권한이 아니기 때문.
고객 공표 문구: "구매 여정을 쓰려면 그날 구매가 **밤 11시까지 한 번은 동기화**되어야 합니다."

| §13 | 1R 7 · 2R 4+별건1 · 3R 3 · 4R 6+승인1 · 5R 4 | **1R = 활성 여정에 스텝을 못 더한다**(지연 0 스텝은 사전 스팸검사 창이 없다 — 막으니 snapshot 코드가 함께 사라짐) · 2R = 확인과 반영을 같은 문장에(마커를 활성화 UPDATE WHERE로, 사전검사는 `updated_at::text` CAS) · **4R = 규약을 흩어 적으면 라운드마다 빠진 경로가 나온다** → `withJourneyValidationReset` 공용 문, 혜택 판정에서 비교를 없애고 근거를 원본 본문 하나로(3라운드 연속 지적의 원인이 "같은 혜택인가"가 열린 문제였다는 것) · 5R = 잠금은 status까지 읽어야 한다 |
| §14 | 6건 전량 | **하락이 새던 길 셋** — ①`DISTINCT ON`보다 WHERE가 먼저 걸려 오래된 중복행(옛 상위 등급)이 뽑힘 → 최신 행 CTE 선확정 ②화면이 "위=높은 등급"이라 안내하며 맨 위에 1을 줘 **방향 역전** ③순서 없음이 전역 토글이라 혼합·복원 불가 → 행별 + `configured`/`confirmed` 분리. 게이트는 `COUNT(DISTINCT rank_order)>=2` + 현재 고객 등급 조인 · 저장에 `pg_advisory_xact_lock` · 잠금 푸는 버튼이 도달 불가였던 것 |

⚠ Codex 런타임이 이 트랙에서 반복적으로 최종 보고 직전에 멈췄다. **살아있음 판정 = 작업 로그 파일 mtime**(`ps`는 Git Bash라 Windows 프로세스를 못 본다). 멈춰도 로그의 중간 판정에서 실결함 4건을 건졌다.

### 6-3) 뒤집힌 판단 — 같은 형태가 세 번 반복됐다

**셋 다 수정 후 코드가 줄었다. 구조를 고치면 덧댄 장치가 함께 사라진다.**

1. **진실을 복사했다** — 싱크 구매를 `cdp_events`에 미러하는 설계였다. 복사는 멱등키·대조워커·지표오염을 자동으로 데려온다. 원장 직독으로 넷이 동시에 사라졌다.
2. **고객사 권한 값에 동작을 걸었다** — 동기화 주기로 발송 창을 계산했다. 주기는 고객사가 정하고 우리는 모른다(DB `sync_agents` 값이 현장과 같다는 보장도 없다). **정책으로 못 박는 것**이 답이었다.
3. **커서를 DB 밖으로 내보냈다** — JS Date 왕복이 µs를 절사했다. 커서 여정이 전부 비활성이라 미발화였을 뿐 — **0건은 안전의 증거가 아니다.**

**물어볼 값이 아니었던 질문 2개**(설계서 §10) — "싱크 구매 적재 주기" · "어느 고객사가 예약 데이터를 가졌나". 묻는 것 자체가 정답표를 갖겠다는 뜻이었다. 판정 축은 사람의 답이 아니라 그 회사 원장의 런타임 관측이다.

### 6-4) DDL 실행 이력 (전량 배포 뒤 실행완료)

### 6-5) 운영 실측 (2026-08-01)

여정 전체 **19개** — active 1 · paused 3 · ended 2 · draft 13.
- **활성은 `custom`(상시) 1개뿐.** 장바구니·예약·배송·포인트 여정 0건. 쓰인 트리거 5종(구매 4 · custom 7 · 생일 3 · 휴면 2 · 신규가입 2).

### 6-6) 접은 것 (설계는 보존)
