## 0. 한 줄 요약

Harold가 영업 대상 업체 리스트만 넣으면, 백그라운드 워커가 업체 홈페이지를 분석해 한줄로 산출물(문안·이메일·모바일 DM·인앱 시안·스튜디오 이미지)을 그 브랜드 맞춤으로 제작하고, Harold가 승인 큐에서 미리보기·수신처 수정 후 **클릭 1회**로 이메일 또는 데모 문자를 발송하는 내부 영업 도구. "우리 서비스 좋습니다"가 아니라 **"귀사 브랜드로 이미 만들어 봤습니다"**를 들고 가는 구조.

- 영업 병목: 사람 손으로 업체별 샘플을 만들어 보내는 속도가 한계. 0722에 만든 영업용 테스트발송(수동 3채널)을 **리스트 단위 자동 제작 + 승인 발송**으로 확장한다.
- 사용자: Harold 1인 (ceo 전용 메뉴).
- 제품이 곧 데모: 받는 쪽이 여는 순간 한줄로의 실물 산출물을 본다. 문안·DM·이미지 전부 "한줄로AI로 만든 예시"임을 명시한다.

## 3. 전체 흐름 (파이프라인)

```
[0] 양식 학습 (1회 + 갱신)
    Harold 샘플 세트 → 스타일 가이드 저장 (구성 순서·톤·이미지 스타일·블록 패턴)
        ↓
[1] 리스트 등록 (Harold — 유일한 수동 입력)
    "업체명, 홈페이지 URL[, 이메일][, 전화번호]" 여러 줄 붙여넣기
        ↓
[2] 웹 분석 (워커)
    홈페이지 크롤 → 브랜드 프로필 추출(업종·톤·주력 상품·색·제휴/대표 이메일)
        ↓
[3] 샘플 제작 (워커)
    문안 → 스튜디오 이미지 → 모바일 DM(생성→저장→hlj.kr 발급) → 이메일 HTML → 인앱 시안(프레임 렌더 PNG)
        ↓
[4] 초안 조립 (워커)
    제안 메일(맞춤 서두+인라인 이미지+DM 링크) + 데모 문자 초안 → 상태 'ready'
        ↓
[5] 승인 큐 (Harold — 클릭 1회)
    카드 미리보기 → 수신 이메일 수정 / 채널 선택(이메일·문자·둘 다) → [보내기]
        ↓
[6] 발송·이력
    결과 기록 · 동일 업체 재발송 차단 · 회신 수동 표시
```

- 각 단계 실패는 그 단계에서 멈추고 카드에 사유를 표시한다. 단계별 개별 재시도 버튼. 자동 완화·대체 발송 없음(0건=차단 원칙과 동일 정신).
- [2]~[4]는 업체별 독립 진행 — 한 업체의 실패가 다른 업체를 막지 않는다.

## 4. 화면 설계 (신규 메뉴 = Journey Builder 동급 다크 퀄리티 의무)

메뉴: 슈퍼관리자 > **"AI 영업"** (가칭 — §13). 탭 3개.

### 4-1. 대상 보드
- 상단: 리스트 등록 영역 — 여러 줄 붙여넣기 1회(형식: `업체명, URL[, 이메일][, 전화]`), 등록 즉시 파이프라인 시작. 추가 입력 단계 없음.
- 본문: 업체 카드 그리드 — 상태 칩(등록→분석중→제작중→검토대기→발송됨→회신/실패/건너뜀), 진행 단계 표시, 실패 카드는 사유 + 재시도 버튼.

### 4-2. 승인 큐 (핵심 화면)
카드 1장 = 업체 1곳.
- 좌측(미리보기 탭): ①제안 메일 렌더 ②모바일 DM(단말 프레임, hlj.kr 실링크) ③문안 텍스트 ④인앱 시안(단말 프레임 PNG) ⑤스튜디오 이미지
- 우측(발송 패널):
  - 수신 이메일 — **수정 가능 입력칸** (크롤 추출값은 초안, 출처 표시: "홈페이지 하단에서 추출" / "미발견 — 입력 필요")
  - 전화번호 — 있으면 문자 채널 활성
  - 채널 선택: 이메일 / 문자 / 둘 다
  - 메일 제목·서두 인사말 — 수정 가능
  - 첨부 스위치(기본 OFF)
  - 버튼: [산출물별 재생성] [테스트(내게 보내기)] [보내기] [건너뛰기]
- [보내기]는 20크레딧+ 확인 모달 규칙과 동일 결의 사전 확인 모달(수신처·채널 최종 표시) 1회.
- 미리보기 = 실제 발송본과 **같은 조립 함수**로 렌더(미리보기용 별도 조립 금지 — 이중 진실 금지).

### 4-3. 발송 이력
- 발송 건 리스트: 업체·채널·수신처·발송 시각·결과·회신 표시(수동 토글)·재발송 차단 상태.

## 5. 데이터 모델 초안

> **초안이다.** 구현 착수 시 컬럼·타입을 확정하고, DDL 실행 전 `information_schema` 검증(db_column_verify_before_code) + 코드 배포 후 마이그레이션 순서(migration_after_deploy) + catch의 `DB_MIGRATION_PENDING` 503 분기(db_alter_safety_net)를 전부 적용한다. PG 신규 4테이블, 기존 테이블 변경 0.

| 테이블 | 역할 | 주요 컬럼 초안 |
|---|---|---|
| `sales_outreach_prospects` | 대상 업체 원장 | id, company_name, homepage_url, extracted_email, manual_email(승인 큐 수정값 — 발송은 manual 우선), phone, status, brand_profile(jsonb: 업종·톤·색·주력상품·근거 발췌), fail_stage, fail_reason, created_at |
| `sales_outreach_assets` | 업체별 산출물 | id, prospect_id, kind('copy'\|'email_html'\|'dm'\|'inapp_png'\|'studio_image'), payload(jsonb: 본문/경로/hlj.kr URL/원본 참조 id), regen_count, created_at |
| `sales_outreach_sends` | 발송 이력(멱등 원장) | id, prospect_id, channel('email'\|'sms'), recipient, subject, sent_at, result, provider_ref, **dedupe_key(홈페이지 도메인+채널 UNIQUE)** |
| `sales_outreach_style_guides` | 양식 학습 결과 | id, version, source_samples(jsonb: 샘플 세트 참조), guide(jsonb: 산출물별 구성 규칙·톤 규칙), active |

- 재발송 차단 = `dedupe_key` UNIQUE 제약으로 DB가 강제(화면 검사만으로 안 막는다). 기본 90일 — 기간 해제는 별도 확인 모달 경유로 키에 회차 부여.
- 발송 상태 전이는 서버가 강제: `ready` 상태가 아니면 발송 API 거부.

## 7. 웹 분석(크롤) 설계

- 서버측 fetch: 메인 페이지 + 회사소개/About + 푸터 우선. robots.txt 존중, 업체당 페이지 수 상한(기본 5), 타임아웃·요청 간격 두고 순차.
- 추출 항목: 업체명 대조, 업종, 톤·컬러, 주력 상품/진행 중 이벤트(문안 소재), 제휴/대표 이메일(mailto·푸터·contact 페이지 패턴), 전화번호(참고용 — 문자 발송은 Harold 입력·확인 번호만).
- 이메일 오추출 방어: 추출값은 항상 "초안+출처 발췌" 표시. 발송은 승인 큐에서 Harold가 눈으로 확인한 뒤에만. 미발견 시 '이메일 필요' 상태로 발송 비활성.
- 브랜드 프로필에는 **근거 발췌**(어느 페이지 어느 문장에서 업종·톤을 읽었는지)를 함께 저장 — 승인 큐에서 Harold가 맞춤화가 헛짚었는지 즉시 판별.
- 타사 로고·사진 원본을 산출물에 삽입하지 않는다 — 브랜드명 텍스트 + 스튜디오 생성 이미지 중심. (저작권·상표 방어)

## 8. 생성 규칙

- 양식 = `sales_outreach_style_guides` 활성 버전이 프롬프트 고정부. Harold 샘플 세트에서 학습(산출물별 구성 순서·블록 패턴·문단 톤·이미지 스타일). 샘플 세트 추가 시 버전 갱신.
- **혜택 수치(%·원·쿠폰·무료) 생성 금지** — 실존 브랜드에 가짜 혜택이 붙는 사고 차단. 중립 표현("신규 고객 혜택 안내" 수준)까지만, 필요 시 Harold가 큐에서 수정.
- 모든 산출물에 "예시(시안)" 표기 — 받는 쪽이 실제 진행 중 캠페인으로 오인하지 않게.
- 데모 문자 고정 구조:
  `[한줄로 소개 1줄] + AI 생성 문안(브랜드 맞춤) + 모바일 DM 링크(hlj.kr) + "본 문자는 한줄로AI가 생성한 문안과 한줄로AI로 제작된 모바일DM 예시입니다" + 수신거부 안내(§10 확정 후 문구)`
- 제안 메일 고정 구조:
  `맞춤 서두(그 업체 사이트에서 본 것 1~2가지 언급) + "한줄로AI로 귀사 브랜드 예시를 만들어 봤습니다" + 인라인 이미지(스튜디오·인앱 시안) + 모바일 DM 링크 + 서비스 소개 1문단 + 발신자 서명(회사·연락처) + 수신거부 링크 + (스위치 ON 시 첨부)`
- 사용자 노출 문구 규율 그대로: 모델명·내부 코드명 노출 금지, 고객 언어만.

2. ⛔ **그 업체 것 확정은 link 주소 대조뿐.** 검색 결과 `link`를 `new URL()`로 파싱해 hostname 완전 일치(`brand.naver.com` 또는 `smartstore.naver.com`) AND pathname 첫 조각(소문자 정규화)이 저장된 slug와 완전 일치할 때만 채택. 통합 카탈로그(`search.shopping.naver.com/catalog/...`) 탈락. 이름·mallName 유사도 폴백 금지. 0건 = `no_product` 정직 종결(재검색 루프·페이지네이션 금지).
3. ⛔ **lprice(가격)는 수집·저장 자체를 안 한다**(반환 타입에서 제거). 저장하지 않으면 샐 수 없다(불변 5 혜택 면허 체계 우회 차단).
4. ⛔ **아이템 한 묶음 원칙**: 채택 단위는 `{title·image·link}` 한 아이템. 아이템 사이 필드 혼합 금지(slug 게이트는 link에 걸리는데 image는 별개 필드라, 섞이면 게이트를 통과하고도 엉뚱한 이미지가 실린다).
5. ⛔ **스토어 이미지는 후보 풀 합류 + 사람이 고른 1장만 합성**(불변 11 유지). **자동·기본 선택 대상에서 제외**(기본값은 홈페이지 후보만 · 0716 "자동 삽입 금지"와 정합). 누끼·합성 파이프라인은 홈페이지 후보와 동일하게 사용 가능(§16-12 뒤집힌 판단 1·3 참조).
6. ⛔ **ENV 밸브 분리**: `OUTREACH_NAVER_CLIENT_ID/SECRET` 신설. 값은 기존 키와 같아도 된다(별도 앱 등록 강제 아님) · **기존 키로 폴백 금지**(fail-closed) · 목적 = 사고 시 값 하나 비워 이 축만 끄는 밸브(고객 DM 축과 자물쇠 분리). **G5(약관) 통과 전에는 이 키를 넣지 않는다** = 게이트가 문서가 아니라 코드 상태로 집행된다.
7. ⛔ **slug 컬럼에는 fetch 가능한 문자열이 못 들어간다**: `smartstore_slug` 저장 직전 정규화 = 영문·숫자·`_`·`-` 2~40자(소문자). 원본 URL은 `brand_profile`에 표시용만, fetch·대조 사용 금지(계약 테스트).
8. ⛔ **스토어 축은 어떤 실패로도 잡을 죽이지 않는다**: slug 미입력 = 현행 경로 100% 동일 / 실패 = `crawling_store: 'unavailable'` 기록 후 홈페이지 단독 진행 / **이미지 0·제품명 0은 발송을 잠그지 않는다.**
9. ⛔ **로고는 fail-closed**: vision 로고 판정에서 `logo` 확정과 `undetermined` 둘 다 제외. 인물(`person` 확정만 제외)과 기준이 다르다 = 불변 11의 "로고 픽셀은 어떤 경우에도 금지"는 무조건 금지라서다. 스토어 후보에는 URL 문자열 로고 필터(`jobs.ts:163`)가 구조적으로 안 걸려 vision이 유일 방어다.
10. ⛔ **제품명 최대 2개, 서버 고정 문형 verbatim.** AI가 문장에 녹이는 게 아니라 조립층이 intro 뒤에 문자열로 끼운다(문장이 다소 뻣뻣해지는 대신 오류가 구조적으로 0). 공개 샘플 페이지 진입 금지.

### 16-3) 사용자 흐름

1. **입력(① 단계)**: "스마트스토어 주소" 칸 추가(선택 · placeholder 예: smartstore.naver.com/브랜드아이디 · 시작 버튼 disabled 조건 무변경). 형식이 아니면 차단이 아니라 인라인 경고("이대로 진행하면 홈페이지만 읽습니다").
2. **자동 발견**: 크롤이 이미 받은 page.html의 a href 값에서 스토어 링크를 추출(신규 fetch 0)해 **후보 칩으로 제시**(최대 3 · 출처 URL 전문 표시) → **Harold가 클릭해야 칸에 채워진다**(자동 확정 0 · 홈페이지 푸터의 협력사·공동구매 스토어 오귀속 방지). 0건이어도 수동 입력으로 진행.
3. **분석**: 홈페이지 크롤(기존) + 스토어 API 조회(신규·병렬). 결과는 `stage_results.crawling_store` 3값.
4. **읽은 것 확인(③ 단계)**: 행사 카드(기존·공식몰 전용 유지) 아래 **"스마트스토어에서 가져온 제품" 전폭 카드**(제품명 목록·확인 전용 · 행사 라디오에 혼입 금지). 이미지 후보 그리드는 출처별 절 분리(홈페이지 N장 / 스토어 제품 N장 · 정직한 수) + 출처 배지 + 썸네일 밑 제품명 1줄.
5. **제작·메일**: 고른 1장(어느 출처든)으로 기존 파이프라인 그대로. 메일은 intro(AI) 다음에 제품명 문장 1개(최대 2개 나열) + 근거 패널에 출처 한 줄.

**A. 조회 함수(신규 · naver-shop-search.ts 안)**: `searchNaverShopStoreItems(slug, query)` → `{ outcome, items }`.

### 16-11) Harold 결재 항목 (착수 시점)

- **약관 수용 위험**: slug 완전 일치로 "그 업체 본인 스토어의 본인 상품"은 확정되지만, 네이버 CDN 경유 이미지의 가공·재호스팅이 오픈API 약관상 허용인지는 G5 원문 확인 + Harold 수용 판단 사안이다(0716 약관 판단의 전제는 "고객사 본인 상품"이었고 이 축은 영업 대상의 상품이다). 완화 자산 = 사람 1장 선택 · 고지 문구 · 만료 30일·파기(불변 14) · 밸브 ENV.
- `OUTREACH_NAVER_*` 값 결정: 기존 값 복사로 시작할지, 별도 앱 등록할지(별도 등록이면 쿼터도 분리된다).

### 16-12) 회의 이력 — 뒤집힌 판단 (같은 자리에서 다시 틀리지 않으려고)

1. **회의론자 "이미지 전면 제외·제품명 텍스트만" → 철회.** slug 완전 일치가 걸리면 판매처가 본인 스토어로 확정되어 권리 사슬이 홈페이지 이미지와 같고, 재호스팅·누끼·합성은 홈페이지 축이 이미 하는 처리라(0824 Harold 확정이 0731 금지를 대체) 신규 위험이 아니라 출처 차이뿐. 남은 것 = G5 약관 확인 + Harold 결재.
2. **기획 "기본 선택 스토어 우선" → 폐기.** 0716 §144("검색 API 썸네일 화질 한계 — 1·2순위 존재 시 항상 우선")가 반대 방향을 이미 확정. 기본 선택은 홈페이지 후보만.
3. **기획 "스토어 이미지는 합성 금지·메일 핫링크 1장" 절충 → 폐기.** 존재 이유(회의론자 1차 논거)가 철회됐고, 핫링크는 만료·파기(불변 14)가 안 걸리는 영구 제3자 참조라 오히려 나쁘다(회의론자 최종 검증). 프론트의 죽은 컨트롤 금지("보여주되 합성 불가" = 신뢰 파괴)와도 충돌.
4. **백엔드 "기존 NAVER_CLIENT_* 재사용" → 폐기.** 자기 1차 위험("429면 고객 기능이 먼저 죽는다")과의 자기모순을 인정. 밸브형 분리(§16-2-6)로.
5. **백엔드 "smartstore_url 전체 URL 컬럼" → smartstore_slug로.** fetch 가능한 문자열을 DB에 안 남기면 §16-1-1 위반이 구조적으로 불가능해진다(불변 13 논법).
6. **프론트 "후보를 객체 배열로 확장" → 철회.** 확정 검증(includes 문자열 방벽)을 다시 쓰게 되는 교환비 + 옛 이력 재방문 호환. string[] + 표시 전용 맵으로 표시 요구 전부 충족.
7. **프론트 "자동 발견 없으면 칸 추가 반대" → "후보 칩 + 클릭"으로 수렴.** 1클릭 원칙은 발견된 후보를 누르는 그 1클릭으로 충족. 자동 확정은 오귀속 방어를 없애므로 금지(백엔드·회의론자 일치).
8. **회의론자 "제품명 최대 5·서두 1곳 고정" → 최대 2·형태 제약만.** sort=sim 상위 2가 가장 확실하고, 나열은 영업 톤 손실이 재료 가치보다 크다(백엔드).
9. **엑셀 D열 "1차 포함 vs 제외" 논쟁 → 순서 문제로 해소.** 본체 배포·실측 1건 뒤 착수에 전원 동의하는 순간 "이 축을 하는 시점에 D열도 같이"가 된다.

### 16-13) 범위 밖 (이번 축에 넣지 않는다)

스토어 리뷰·판매량·순위 수집 = 금지. 가격 비교 = 금지(lprice 미수집이 그 방어다). 다중 이미지 합성 = 불변 11(1장) 유지. 스마트스토어 외 타 플랫폼(쿠팡·29cm 등) = 별도 안건. 자동 발견 정교화(다중 후보 검증) = 2차.
