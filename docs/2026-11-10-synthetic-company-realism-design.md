## 1. 불변식

1. **실제 고객사 영향 0** — 워커는 지금처럼 허용 목록(`SYNTHETIC_DATA_COMPANY_IDS`) · 시연 회사 키만 받는다(`syntheticTargetCompanyIdOfKey` 그대로). 자사몰 키도 같은 판정을 지난다.
2. **시연 회사(hanjulai) 동작 변화 0** — v3 는 「허용 목록 회사이면서 시연이 아닌 회사」만. 시연 회사는 v2 함수 그대로(시험 = 바꾸기 전 코드로 뽑은 v2 출력 지문과 대조).
3. **진짜 수집 경로만** — 매장 = `POST /api/sync/customers · /purchases`(지금과 같음) · 온라인 = `POST /api/cdp/identify · /event · /order`(자사몰 키). 결과 · 파생 표에 직접 쓰기 0.
4. **결정적 · 멱등** — 같은 날 다시 돌려도 같은 행(원장 키 · 몰 주문 번호 · 사건 키 고정). 끊겨도 다음 tick 이 빠진 것만 보낸다.
5. **번호 = 도달 불가 그대로** — 번호는 지금 함수 `demoPhone`(0100 + 7자리)만 쓴다. 이메일은 보내지 않는다. 몰 회원 번호 · 주문 번호 = 지어낸 글자. 실명 · 실번호 · 실주소 0.
6. **발송 경로 수정 0**(1층) — 발송 · 정산 · 결과 파일은 건드리지 않는다.

## 4. 생성 규칙 (v3)

- **매장 줄 = v2 줄 그대로 + 덧붙인 줄.** 그 방문(고객 · 날)의 v2 줄은 같은 원장 키(`demo-v2-…`)로 보내되 수량 1 · 행사 할인가로 값만 바뀐다(K8 = 같은 행 갱신). 목표 줄 수에서 v2 줄 수를 뺀 만큼 「함께 산 상품」을 새 키 `demo-v3x-번호-날-n` 으로 덧붙인다. 버전 전환 날짜가 없다 — 배포 당일 같은 날을 v2 로 한 번 · v3 로 한 번 보내도 v2 줄은 갱신 · 덧붙인 줄은 처음 한 번.
- 상품 = v2 20종 + 40종(스킨 · 선 · 메이크업 · 바디 · 헤어 · 세트 · 정가 9천 ~ 8만 · 가정) + 2026-11 부터 달마다 신상품 2종(코드 `NW-YYMM-1·2` · 출시 달 전에는 안 팔린다). v2 줄의 상품은 그대로 · 덧붙인 줄 · 몰 주문만 넓은 목록에서 고른다.
- 등급 · 포인트 = 매장 원장의 **고객 · 날짜별 합계**를 읽어 계산하는 순수 함수 `loyaltyAt(번호, 날짜별 합계, 끝 날)`. 몰 주문은 넣지 않는다(몰 포인트는 따로 운영하는 회사 모양 · 단순화).
  - **구매 전 고객 행**(고객과 구매를 잇는 단계) = 그 회차 대상(그날 신규 ∪ 구매 고객 ∪ 수신거부 따라잡기) 중 **DB 에 아직 없는 번호만** 만든다(번호로 조회 · is_active 무관). 이미 있는 고객은 이 단계에서 보내지 않는다 → 같은 날 다시 돌려도 · 구매 뒤 묶음이 일부 실패해 다시 돌려도 저장된 등급 · 포인트를 낮추는 쓰기가 없다(Codex 설계 2R #1). 새로 만드는 고객의 값 = 끝 날 그 전날까지(판매일 행 제외).
  - **구매 뒤 고객 행** = 판매일까지(그 회차 적재가 다 끝난 원장) · 대상 = 그날 구매한 신규 고객 ∪ 기존 구매 고객 ∪ 수신거부 따라잡기(Codex 1R #4).
  - 고객 행의 등급 · 포인트를 쓰는 단계 = 구매 뒤 하나(새 고객의 첫 행 제외). 원장 합계는 판매일보다 앞선 날 행이 다시 보내지지 않아 날마다 늘기만 한다 → 하루 구매 뒤 값 ≤ 다음 회차 구매 뒤 값 → 등급이 내려갔다 오르는 순간(가짜 등급 상승)이 없다. 등급 = max(지금 번호의 고정 등급 · 누적 기준 등급) ≥ v2 가 보내던 고정 등급.
  - 포인트 = 날짜순으로 방문마다 그날 합계 3% 적립 · 방문의 25%(번호 · 날로 결정) = 그 방문 전까지 쌓인 포인트를 다 씀 → 남은 값.
- 수신동의 = 고객마다 거부 날 하나(결정적) · 매일 회차가 **거부 날이 최근 7일 안인 고객**을 false 로 다시 보낸다(하루를 놓쳐도 따라잡음 · Codex 1R #5 · 이 고객들은 구매 뒤 고객 행 묶음에 넣어 누적 · 등급 · 포인트도 판매일까지 값으로 함께) · 다른 이유로 다시 보내는 행도 거부 날 뒤면 false.
- 이름 사전은 늘리지 않는다(늘리면 기존 고객 이름이 다시 보낼 때 바뀐다).
- 온라인 = 날짜 · 번호로 정해지는 방문 일정 · 사건 키 `ev-날짜-번호대-순번` · tick 마다 「그 시각까지 생긴 사건 − 이미 적힌 사건 키 · 주문 번호」만 **오래된 것부터** 보낸다. 범위 = 최근 7일(재기동 · 자정 걸침 · 장애 · 월 한도 회복 · Codex 1R #3) · 7일보다 오래된 미전송 = 보내지 않고 건수만 로그(합성 데이터 · 진행 위치 표 DDL 을 만들지 않는 상한).

## 5. 워커 변경 (자리)

- `utils/demo-data.ts` = v2 함수 그대로 두고 v3 함수를 더한다. 판정 `isRealismCompany` = 허용 목록 ∧ 시연 아님. 매장 회차는 회사 판정 → v2 · v3 갈래(같은 07:00 회차).
- 자사몰 키 = 새 ENV `SYNTHETIC_CDP_KEYS`(「hjl_키:sk_비밀」 쉼표) · 회사 = 키로 DB 에서 찾고 매장 키와 같은 허용 판정 · 없으면 온라인 갈래만 건너뛴다(매장 갈래는 돈다) · 시작 로그 한 줄(꺼짐도 로그).
- 온라인 갈래 = 10분 tick 마다(07:00 문 밖 · 밤에는 사건이 없어 빈 회차) · 루프백 `postCdp`(헤더 X-Hanjullo-Key · X-Hanjullo-Secret) · 쓰기 한도(10초 50) 아래로 초당 4 · 한 tick 상한 600건(남은 것은 다음 tick).
- 실패 = **그 tick 의 온라인 갈래를 바로 멈춘다**(같은 tick 안에서 다시 보내지 않음) · 그 키는 **실패 시각 + 10분** 전에는 보내지 않는다(tick 은 고정 주기라 실패 직후 tick 이 올 수 있다 · Codex 구현 1R) · 그 뒤 tick 이 적힌 키를 다시 읽고 이어간다 · 로그 한 줄. 요청은 응답을 끝까지 기다린다(클라이언트가 끊지 않음).
  - **상한(Codex 1R #2 일부 수용)**: 사건 중복은 「실패로 끝난 요청이 서버 안에서 다음 tick 의 키 읽기보다 늦게(10분 넘게) INSERT 를 끝내는」 경우에만 생긴다. 수집 서버에 유일 제약을 거는 처방은 받지 않는다 — 실제 고객사가 쓰는 수집 경로 · DB 를 바꾸는 것이라 불변식 1 에 어긋난다. 이 상한은 합성 데이터 회사 하나에만 걸린다.
- 매장 싱크 응답 = HTTP 200 이어도 본문 `data.failedCount` > 0 이면 실패로 던진다 → 그날 회차를 끝낸 것으로 적지 않는다(다음 tick 에 다시 · Codex 1R #5). v3 갈래만(시연 회사 v2 는 그대로 = 불변식 2 · v2 의 같은 틈은 §9 기록).

## 6. 시험 (계약)

- **시연 회사 변화 0** = 바꾸기 전 코드로 뽑은 v2 출력 지문(정해 둔 날짜 셋의 `buildDailyBatch` · `buildSeedData` 일부)을 상수로 두고 바꾼 뒤 같은지.
- v3 결정성(같은 날 두 번 = 같은 행 · 같은 사건 키) · 덧붙인 줄 키가 v2 키와 겹치지 않음.
- 분포: 한 방문 줄 수 평균 2.89 ± 0.15(충분한 표본) · 수량 1 · 등급 내려가지 않음 · 포인트 ≥ 0 · 같은 고객 같은 날 매장 · 몰 둘 다 0.
- **가상 번호 계약** = v3 가 내보내는 모든 행 · 사건 · 주문의 번호가 `SYNTHETIC_PHONE_PATTERN` 을 지나고 이메일 칸이 없음.
- **사건 이름 = 소비자에서 기계 추출**: `journey-target-extractor.ts` 의 `event_name = '…'` 를 읽어 v3 가 보내는 이름 집합이 장바구니 · 조회 조건 이름을 덮는지(손 등재 0).
- 멱등: 이미 적힌 사건 키 · 주문 번호는 다시 안 보냄(가짜 DB 응답으로) · 허용 목록 밖 키 · 시연 회사 키 → v3 갈래 0.
- 등급 · 포인트: 구매 전 단계 = 이미 있는 번호 0건 전송(가짜 DB 「있음」 응답) · 같은 날 회차를 두 번 돌린 전송 순서에서 한 고객에게 보낸 등급 서열이 내려가지 않음(구매 뒤 끝난 뒤 재실행 · 구매 뒤 묶음 실패 뒤 재실행 두 경우) · 가입 당일 구매 고객이 구매 뒤 대상에 듦 · 포인트 손 계산 예 1건(독립 기대값).
- 실패: 사건 전송 오류 → 그 tick 남은 사건 0건 전송 · 싱크 200 + failedCount 1 → 던짐(회차 미완) · 8일 전 미전송 사건 = 보내지 않고 건수 로그 · 오래된 것부터 상한 600.
