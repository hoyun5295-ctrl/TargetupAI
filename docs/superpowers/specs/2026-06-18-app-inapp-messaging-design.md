# 앱 네이티브 인앱 메시지 — 설계서 (Braze·Salesforce 상회 목표)

> **작성**: 2026-06-18 (Harold + 비토 brainstorming)
> **상태**: 설계 합의 — Harold 리뷰 대기
> **배경**: 2026-06-17 웹/앱 채널 분리(1단계)와 웹뷰 트랙(JS SDK `platform:'app'`)은 배포 완료. 그러나 순수 모바일 앱(React Native·Flutter·네이티브) 안에서 그려지는 "진짜 앱 인앱"은 아직 0. 웹 SDK는 브라우저 DOM 렌더러라 RN/네이티브 화면에는 뜨지 않음. 이번 단계는 앱 인앱을 **앱 사이즈에 맞는 네이티브 방식**으로, Braze·Salesforce Marketing Cloud가 쓰는 표준을 기준선으로 깔되 **그보다 앞서는 형태**로 만든다.
> **연속성**: `2026-06-17-onsite-app-message-redesign-design.md`의 2·3단계 방향을 본 문서가 구체화·대체한다(순수 네이티브 우선 → React Native 렌더러 우선으로 수정).

---

## 0. 타겟과 목표

- **타겟 사용자 = 장바구니·커머스를 갖춘 브랜드** — 의류·화장품·리테일 자사 앱. (딜 모음 앱이 아님)
- **팝폰(poppon-app)은 RN 렌더러를 띄워볼 테스트 기기**일 뿐, 설계 기준이 아니다.
- **목표**: 앱 인앱 메시징에서 Braze·Salesforce를 앞지른다. 기능 수 경쟁이 아니라 **압도적 쉬움 + AI 자동 운영 + 커머스 적합성**으로.

---

## 1. 기준선 vs 우리 업그레이드

### 두 업체 공통 (기준선 — 우리가 최소 갖출 것)
- 메시지 표면: 모달 / 전체화면 / 슬라이드 / 배너 / 커스텀 HTML + 상시 콘텐츠 카드
- 트리거: 이벤트·행동·세션 기반 실시간 트리거
- 타겟: 세그먼트·속성·행동
- 개인화: 토큰 치환(Liquid 류)
- 빈도 제한·우선순위·방해금지 시간
- 저니(크로스채널 오케스트레이션) / 분석(노출·클릭·전환)
- 전달: 네이티브 SDK(iOS·Android) + Web + RN·Flutter 래퍼

> 두 업체는 강력하지만 복잡하다. 마케터가 직접 세그먼트를 짜고 저니를 조립하고 카피를 쓰고 분석해야 한다.

### 우리가 앞서는 지점 (차별 — 슈퍼파워)
1. **AI 오퍼레이터가 마케터 대신 굴린다** — 콘솔을 쥐여주는 게 아니라, 브랜드 실데이터에서 시나리오를 제안·실행·보고. 1클릭 또는 자동.
2. **커머스 네이티브 기본 탑재** — 장바구니·찜·상품조회·구매·재입고·등급을 미리 모델링. 브랜드가 거의 설정 0으로 시작.
3. **시각 커머스용 네이티브 표면** — 풀이미지·바텀시트·햅틱·네이티브 애니메이션. 패션·뷰티에 맞춤(두 업체의 범용 HTML은 직접 만들어야 함).
4. **푸시↔인앱 연속을 1급 기능으로** — 저니 조립이 아니라 기본 흐름으로 제공.
5. **실데이터 개인화 + 임의 숫자 금지, 혜택은 브랜드가 작성(AI 창작 금지)** — 신뢰가 곧 업그레이드(거짓 광고·과장 점수 차단).

## 2. 앱 메시지 표면 (앱 사이즈 — 웹과 다른 메뉴)

| 표면 | 설명 | 주 용도 |
|---|---|---|
| 바텀시트(상품카드 내장) | 하단에서 올라오는 드래그 가능 시트, 상품 카드 포함 | 장바구니·찜·추천 |
| 전체화면 인터스티셜 | 풀블리드 히어로 이미지 | 드롭·룩북·시즌 |
| 중앙 모달 | 이미지+카피+CTA, 컴팩트 | 단발 오퍼·공지 |
| 상·하단 배너 | 세이프에어리어 도킹, 비차단 | 가벼운 넛지 |
| 인라인 콘텐츠 카드 | 피드에 상시 노출 | 상시 혜택·추천(Braze 콘텐츠 카드 대응) |

- 전부 스와이프 닫기·햅틱·네이티브 애니메이션·세이프에어리어(노치·홈바) 대응.
- 커스텀 HTML 표면은 후순위(두 업체 패리티용, 3단계).

## 3. 트리거

- **앱 생애주기**: 앱 실행(콜드/웜) · 포그라운드 복귀 · 특정 화면 진입 · 세션 수 · 미접속 경과일
- **커머스 이벤트**: 장바구니 담기·이탈 · 결제 이탈 · 상품 조회 · 찜 · 구매 완료 · 재입고 알림
- **푸시 탭 맥락**: 푸시 → 탭 → 진입 시 해당 맥락의 인앱 표시
- **제어**: 빈도 제한 · 우선순위 · 방해금지 시간

---

## 4. 커머스 시나리오 템플릿 (쉬움의 핵심)

각 시나리오 = 트리거 + 표면 + 카피 골격(혜택은 브랜드가 작성, AI 창작 금지)이 미리 묶여 제공.

- 장바구니·결제 이탈 되살리기 (담은 상품 그대로 표시)
- 재입고·신상·드롭 알림 (품절 잦은 의류·화장품 핵심, 푸시↔인앱 대표)
- 찜·최근 본 상품 리마인드
- 재구매 시점 (브랜드 실데이터 기반 주기, 임의 상수 금지)
- 등급·멤버십 혜택 노출
- 알림 권한 유도 (드롭·재입고를 받게)
- 웰컴·온보딩 / 휴면 깨우기

---

## 5. AI 오퍼레이터 연동 (핵심 차별)

- 브랜드 실데이터에서 **어떤 시나리오를 돌릴지 제안** → 카피 골격 작성 → 표면 선택 → 실세그먼트·등급 타겟 → 자동 또는 1클릭 실행.
- 타겟 0건이면 **차단**(자동 완화 금지, `no_target_auto_relax`).
- 추정(전환율·리프트)은 **그 브랜드 실데이터에서 도출**(등급별 실측 우선, 부족 시 정직하게 'insufficient_data'). 임의 상수 금지.
- 혜택(%·원·쿠폰·무료·적립) **AI 임의 생성 금지** — 브랜드 admin이 작성, AI는 구조·문구 골격만.

## 6. 전달 구조 (표면 공유 코어 + 채널별 렌더러)

```
[공유 백엔드 — 이미 존재]
 메시지 모델(cdp_inapp_messages, channel='app') · GET /cdp/inapp/active?channel=app
 · POST /cdp/inapp/track · 타겟 · AI 생성 · 과금 · 통계
        │
        ├─ JS SDK (웹 + 웹뷰 하이브리드)    ← 완료·배포됨 (sdk-js, platform:'app')
        ├─ React Native 렌더러             ← 이번 작업 (팝폰으로 검증)
        └─ 순수 네이티브 (Swift/Kotlin)     ← REST 가이드로 우선 대응, 향후 SDK(맥/CI 필요)
```

- **공유 코어는 그대로 재사용** (인라인 중복 금지). 채널마다 새로 만드는 건 "표면을 화면에 그리는 렌더러" 한 층뿐.
- **React Native 렌더러** 구성 요소:
  - active 조회: `GET /cdp/inapp/active?channel=app` 호출
  - 표면 렌더: RN 기본 컴포넌트(`Modal`/`View`/`Image`/`Pressable`) + 팝폰에 이미 있는 `expo-image`·`reanimated`·`nativewind`(추가 네이티브 모듈 0)
  - 추적: 노출·클릭 `POST /cdp/inapp/track`
  - **식별 브리지**: 앱 로그인 사용자(Supabase·카카오·네이버) → 한줄로 고객 식별자(external_id) 전달. 비로그인은 익명 디바이스 id.
  - 푸시 탭 맥락 처리(2단계부터)
- **순수 네이티브**는 같은 REST를 고객사 개발자가 자기 네이티브 UI로 호출하는 연동 가이드로 우선 대응.

## 7. 관리자 메뉴 / IA (웹과 분리)

- 진입은 기존대로 "인앱 메시지" → 웹/앱 선택(채널 분리 1단계에서 구현됨).
- **앱 쪽은 앱 전용**: 앱 표면 선택기(바텀시트·인터스티셜·배너 등) + 앱 트리거 + 푸시 연계 설정 + **기기 프레임 미리보기**(아이폰·안드로이드).
- 디자인 = 여정 빌더(`/ai-journeys`) 동급: 다크+바이올렛, ConfirmModal/useToast, 모바일 반응형, Source caption.

## 8. 분석

- 표면·시나리오별 노출·클릭·전환, 채널 필터(웹/앱), 실데이터 기준 리프트.
- impression 테이블에 channel 없으면 `message_id IN (SELECT id FROM cdp_inapp_messages WHERE channel=$)` 서브쿼리로 필터(1단계 패턴 재사용).

## 9. 데이터 모델 (구현 전 information_schema 선검증)

- `cdp_inapp_messages.channel`(web/app) — 존재(채널 분리 ALTER 완료).
- `companies.cdp_allowed_app_ids text[]` — **신규(1단계 ALTER)**. 앱 키 인증 허용 번들ID 목록. `cdp_allowed_origins`(존재, text[])의 앱 버전.
- 앱 표면 타입은 `template` 컬럼 값 확장(예: `bottom_sheet`, `interstitial`). **`template` varchar 길이·기존 값 information_schema로 선검증 후 추가**.
- 신규 컬럼이 필요하면(예: 앱 트리거 설정) ALTER는 Harold 직접 실행 + endpoint catch에 `column does not exist` → 503 분기.
- **tsc 통과 ≠ SQL 유효** — 새 컬럼·테이블·JOIN은 information_schema 검증 SQL을 Harold께 먼저 제공 후 코드 작성(`db_column_verify_before_code`).

## 10. 단계 분해

| 단계 | 내용 | 검증 |
|---|---|---|
| **1단계 (지금) — CDP 앱 등록 토대** | 자사몰 연동에 앱(번들ID) 등록 + 앱 키 인증(퍼블릭키+번들ID, 시크릿 없음) + 자사몰 연동 화면 앱 등록·앱 SDK 안내 | 등록한 번들ID로 `active?channel=app`·`track` 호출이 키만으로(도메인 없이) 200 통과 |
| **2단계 — 팝폰 RN 렌더러** | 팝폰에 RN 인앱 렌더러(바텀시트/모달) + `active?channel=app`/`track` + 신원 + 빈도 제한. 1단계 앱 키 인증 사용 | 팝폰 실기기에서 admin 생성 앱 메시지가 네이티브로 뜨고 노출·클릭 집계 |
| **3단계** | 커머스 이벤트 추적(RN) + 트리거 평가 + 시나리오(장바구니·재입고·찜) + 푸시↔인앱 + 표면 확장 | 이벤트로 시나리오 자동 발동 |
| **4단계** | AI 오퍼레이터 앱 인앱 자동 운영 + 분석 고도화 + (수요 시) 순수 네이티브 SDK | AI가 실데이터로 제안·실행·보고 |

> 본 문서는 1·2단계 중심. 3·4단계는 방향만 기록(각 단계 진입 시 별도 계획). 인증을 1단계로 분리한 이유 = 자사몰 연동이 웹 전용이라 앱 인앱이 인증을 못 한다(RN은 Origin 미전송 → 403). 토대 먼저.

### 1단계 상세 (CDP 앱 등록·인증 — 한줄로 본체)
- **DB**: `companies.cdp_allowed_app_ids text[]` ALTER(information_schema 선검증 → Harold 실행). `cdp_allowed_origins`의 앱 버전.
- **인증**: `requireCdpKeyOrBrowserOrigin`에 앱 분기 추가 — 시크릿 없고 `X-Hanjullo-App-Id`가 오면 퍼블릭키 + 등록 번들ID 검증(`requireCdpAppId`). 웹(키+도메인)·서버(키+시크릿) 경로 무손.
- **엔드포인트**: `GET/POST/DELETE /api/cdp/allowed-app-ids`(`allowed-origins` 미러 + 503 가드 + 번들ID 형식 검증).
- **화면**: 자사몰 연동(CdpSettingsPage)에 앱 등록 섹션(번들ID 추가/삭제) + 앱 SDK 안내(퍼블릭키 + 번들ID, 시크릿 없음).
- **운영 주의**: 라이브 CDP 인증을 건드림 — 기존 경로 무손 surgical + Codex 리뷰 의무.
- 계획서: `docs/superpowers/plans/2026-06-18-cdp-app-registration-foundation.md`

### 2단계 상세 (팝폰 RN 렌더러)
- 별도 계획서 `2026-06-18-app-inapp-rn-renderer-1.md`(작성됨). 단 인증을 Origin 스톱갭 → 1단계 앱 키 인증(`X-Hanjullo-App-Id`)으로 교체.
- 첫 표면 = 바텀시트 + 중앙 모달. 트리거 = 앱 실행/포그라운드 시 1건. 신원 = user.id/sessionId.

## 11. 영구 룰 준수 (구현 시 자가 검증)

- 모델명 UI 노출 0건 (Opus/Sonnet/GPT/Claude grep)
- native dialog 0건 (RN에서도 커스텀 다크 모달 — OS 기본 Alert 금지)
- AI 임의 혜택(%·원·쿠폰·무료) 0건 — `[직접 작성해주세요]` placeholder
- 타겟 0건 자동완화 금지
- 추정치 임의 상수 금지 — 실데이터 도출, 부족 시 insufficient_data
- 박-단어 0건 / 특수 표현 차용 0건
- DB ALTER 새 컬럼 endpoint catch → `column does not exist` 503 분기
- SQL 신규 컬럼/테이블/JOIN = information_schema 선검증
- 컨트롤타워 재사용(인라인 중복 금지)

## 12. 검증 (verification-before-completion)

- 팝폰(RN) tsc 0 + 한줄로 backend/frontend tsc 0 (해당 변경 시)
- 자가 grep 0 (모델명 / native dialog / 박-단어)
- 팝폰 실기기(dev client + `expo start`)에서 바텀시트 노출 + 닫기 + 클릭 → `/track` 집계 확인
- 한줄로 통계에서 앱 채널 노출·클릭 잡히는지 확인

---

## 13. 미정 / 리뷰 포인트

- 식별 브리지 — 팝폰 로그인 식별자를 한줄로 external_id로 어떻게 매핑할지(이메일 해시 vs supabase user id vs 별도 매핑)
- 1단계 노출 규칙 — 앱 실행 시 1건 vs 우선순위 큐
- RN 렌더러 배포 형태 — 팝폰 인라인 우선 후 재사용 패키지(`@hanjullo/react-native`)로 추출할지
- 표면 template 값 확장 vs 별도 컬럼
