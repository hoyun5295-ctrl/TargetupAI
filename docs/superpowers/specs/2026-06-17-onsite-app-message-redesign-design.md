# 인앱 메시지(웹/앱) 전면 재구성 — 설계서

> **작성**: 2026-06-17 (Harold + 비토 brainstorming)
> **상태**: 설계 합의 — Harold 리뷰 대기
> **배경**: 현 "인앱 메시지" 메뉴가 실제로는 웹 자사몰 온사이트 팝업만 구현(`sdk-js`, 브라우저 전용)되어 있고, 모바일 앱 네이티브 SDK는 전무. 이름("인앱")과 실체(웹 팝업)가 불일치. → 웹/앱을 진입부터 명확히 분리하고, 각 채널에 맞는 형태만 확실하게 제공한다. Braze를 쉬움 + AI 자동화 + 채널 적합성으로 압도하는 것이 목표.

---

## 0. 현황 (전수 조사 결과)

- **웹 온사이트**: `@hanjullo/sdk`(`packages/sdk-js`) — 8 templates 렌더러(`src/inapp.ts`) + 서빙 API(`GET /cdp/inapp/active`, `POST /cdp/inapp/track`) + AI 생성·개인화(Liquid)·A/B·트리거 자동감지·과금까지 완성·작동. **단 100% 브라우저(`document`) 전용.**
- **모바일 네이티브 SDK**: 전무. `packages`에 `sdk-js` 하나뿐 (`sdk-ios`/`sdk-android`/RN/Flutter 0).
- **설치**: `<script src="https://app.hanjul.ai/sdk/v0.3.5/hanjul.min.js" data-hjl-key="...">` — 웹 전용 스니펫 (CdpSettingsPage).
- **결론**: 메뉴 이름 "인앱 메시지"는 실제로는 "웹 자사몰 온사이트 팝업". 진짜 앱 인앱은 0.

---

## 1. 목표

- 웹/앱을 진입부터 명확히 분리(나눠서 클릭), 각 채널에 맞는 형태·기능만 제공.
- **확실한 것만 확실하게** — 레이아웃 충돌·고객사 협조 필요 등 애매한 형태는 과감히 배제.
- 전면 재구성 수용 (시간·공수 들여 제대로).

---

## 2. 단계 분해 (3단계)

| 단계 | 내용 | 비고 |
|---|---|---|
| **1단계** | 웹/앱 채널 분리 토대 — 메뉴·진입·편집·서버·통계의 채널 구분 | 웹 즉시 작동 / 앱은 화면·형태 준비(실동작은 2단계) |
| **2단계** | 앱 네이티브 SDK — iOS(Swift)+Android(Kotlin) 신규. 진짜 앱 인앱 렌더링 | 크로스플랫폼 래퍼는 그 위에 얇게 |
| **3단계** | 앱 전용 고도화 + 압도 — 푸시 연계 인앱, 전면 인터스티셜, AI 자동화 차별화 | |

**본 문서 = 1단계 중심.** 2·3단계는 방향만 기록(각 단계 진입 시 별도 spec).

### 1단계 완성 기준 (Harold 명시)

- 웹/앱을 나눠서 클릭, 각 채널 전용 편집 화면·형태를 다 갖춤
- **웹은 즉시 실제 작동** (기존 SDK 있음)
- **앱은 화면·기능이 다 준비된 채, 2단계 SDK가 들어오면 바로 켜지는 상태** — "만들었는데 앱엔 안 뜨네" 방지

---

## 3. 메뉴 / 이름 / 진입 구조 (1단계)

- **이름**: **"인앱 메시지" 유지** (메뉴 카드 길이 일관성 + 업계 통칭. 처음 우려한 "인앱=앱?" 혼란은 진입에서 웹/앱 분리로 해소 — 2026-06-17 Harold 확정. "온사이트/노출형"은 8자라 AI Operator 카드 줄바꿈 발생으로 기각)
- **진입 구조**:

```
[인앱 메시지] 메뉴 진입
   │
   ├─ 웹 (자사몰 팝업)   → 웹 전용 화면 (확실한 4종)
   └─ 앱 (모바일 인앱)   → 앱 전용 화면 (앱 고유 형태, SDK 준비되면 작동)
```

들어가면 먼저 웹/앱을 고르고, 각자 자기 형태·기능만 보인다.

---

## 4. 채널 모델

- **캠페인 단위 채널 선택**: 웹만 / 앱만 / 웹+앱
- 웹+앱 동시 선택 시 채널별 형태·문구를 **각각** 편집 (내용 같아도 형태는 채널 최적화)
- DB: `cdp_inapp_messages`에 `channel` 구분 추가(web/app). 기존 데이터(현 1건)는 `web` default.
- 메시지를 정하는 부분(편집)·서버 서빙·AI 생성·개인화·A/B는 **채널 무관 공통 — 이미 구현됨**. 채널별로 달라지는 것은 "형태(렌더러)"와 "노출 형태 선택지"뿐.

---

## 5. 웹 채널 — 확실한 4종

| 형태 | 방식 | 사유 |
|---|---|---|
| 중앙 모달 | 오버레이(백드롭) | 가장 강력·안전 |
| 슬라이드 인 | 우하단 오버레이 | 거슬리지 않는 알림 |
| 토스트 | 우상단 오버레이 | 가벼운 알림, 자동 사라짐 |
| 플로팅 버튼 | 우하단 오버레이 | 상시 CTA(쿠폰·장바구니) |

- 4종 전부 **사이트 위에 겹쳐 띄우는 오버레이** — 고객사 자사몰 레이아웃 불간섭.

### 배제 (애매/충돌)

- **상단 배너** — 고객사 고정 헤더와 시각 충돌
- **전체화면** — 웹에선 과해 이탈 유발 (앱에선 채택)
- **인라인 카드** — 고객사가 DOM selector로 자리 지정해야 작동(협조 필요)
- **하단 배너** — 일부 모바일 웹 하단 메뉴와 충돌

> 기존 `sdk-js`의 8종 렌더러 코드는 **보존**하되, 웹 채널 편집 UI에서는 위 4종만 노출. (배제 형태 렌더러를 삭제하지 않음 — 회귀 위험 차단)

---

## 6. 앱 채널 — 확실한 형태 (1단계는 정의/UI/미리보기, 실동작은 2단계 SDK)

| 형태 | 사유 |
|---|---|
| 모달 | 앱 중앙 팝업 — 앱 기본 |
| 전면 인앱(인터스티셜) | 화면 꽉 채우는 프로모션 — 앱에서 가장 자연스러운 핵심 |
| 인앱 배너(상단/하단) | 앱 화면 띠 배너 — 우리 SDK가 그려 헤더 충돌 없음 |
| 토스트/슬라이드 | 앱 내 가벼운 알림 |

### 앱 전용 강점 — Braze 압도 포인트 (2·3단계 본격)

- **푸시 연계 인앱** — 푸시 알림 탭 → 앱 열림 → 매칭 인앱 표시. 한줄로에 이미 푸시(웹 푸시·푸시 캠페인) 존재 → 앱 푸시와 인앱을 잇는 순간 강력한 무기.

> 1단계에서는 앱 채널 편집 화면 + 형태 정의 + 미리보기(목업)까지. 실제 렌더는 2단계 네이티브 SDK.

---

## 7. 1단계 작업 범위 (요약)

- **DB**: `channel` 컬럼 + 채널별 노출 형태 정리 (information_schema 선검증 후 ALTER, Harold 직접 실행)
- **편집 UI**: 진입 웹/앱 분기 + 채널별 형태 선택 + 미리보기(웹=실측 렌더, 앱=목업)
- **서버**: `/cdp/inapp/active`에 채널 필터 — 웹 SDK는 `web` 채널만 수신(앱 메시지가 웹에 새는 것 차단)
- **통계**: 채널 구분 집계 (웹/앱 분리 CTR·impression)
- **메뉴 이름 유지 + 진입 분기**: "인앱 메시지" 그대로, 진입 시 웹/앱 선택

---

## 8. 영구 룰 정합 (구현 시 자가 검증)

- 모델명 UI 노출 0건 (Opus/Sonnet/GPT/Claude grep)
- native dialog 0건 (ConfirmModal + useToast)
- AI 임의 혜택(%/원/쿠폰/무료) 0건 — `[직접 작성해주세요]` placeholder
- 0건 타겟 자동완화 X
- 모든 카드/차트 Source caption
- 박-단어 0건
- DB ALTER 새 컬럼 endpoint catch → `column does not exist` 503 분기
- SQL 신규 컬럼 = information_schema 선검증 (tsc 통과 ≠ SQL 유효)

---

## 9. 검증 (verification-before-completion)

- backend / frontend / sdk-js tsc 0 errors
- 자가 grep 0 (모델명 / native dialog / 박-단어)
- 웹 채널 = 기존 서빙(`/inapp/active`, `/track`) 유지로 실동작 확인
- 앱 채널 = 편집 + 목업 미리보기 동작 확인 (실 렌더는 2단계)

## 10. 미정 / 리뷰 포인트

- (확정) 이름 = "인앱 메시지" 유지
- 채널 구분 = `channel` 컬럼 vs 별도 테이블 (앱 형태가 웹과 크게 갈리면 분리 검토)
- 푸시 연계 인앱 = 2단계 포함 vs 3단계로 분리
- 기존 운영 중 인앱 메시지(현 1건) 마이그레이션 방식
