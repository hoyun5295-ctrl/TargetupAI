## 3. P2 설치 때 값 확인 · 설치별 값 분류

**목표**: 첫 전체 동기화 전에, 매핑된 수신동의(`sms_opt_in`) · 탈퇴 표시(`is_opt_out`) · 성별(`gender`) 컬럼의 실제 값 분포를 DB 에서 읽어 판정을 보여 주고, 낱말표가 모르는 값은 설치 담당이 그 자리에서 분류한다. 고객사에 묻지 않는다.

1. **어댑터** `countColumnValues(tableName, column, limit)` → `{ values: {value: string|null, count: number}[], truncated: boolean }` · 선택 메서드(`countKeyUniqueness` 와 같은 꼴). Oracle · MySQL 만 구현(두 등재 조합 · `countKeyUniqueness` 선례와 같음). SQL = `SELECT 컬럼, COUNT(*) GROUP BY 컬럼 ORDER BY COUNT(*) DESC` 상위 limit+1 행. 식별자는 어댑터의 기존 정리 · 따옴표 규칙(Oracle `tableRef` · `sanitizeIdentifier` / MySQL 백틱).
2. **판정 CT** `setup/value-check.ts` (순수 함수 + 대화 함수)
   - 값은 앞뒤 공백을 지운 글자로 합친다(정규화와 같은 기준) · 빈 값 · NULL = 「값 없음 · 그대로」(분류 대상 아님).
   - 서로 다른 값이 30 개를 넘으면 분류하지 않는다: 「이 컬럼은 값 종류가 너무 많습니다 · 매핑을 다시 확인하세요」 · 표 저장 안 함(지금 동작).
   - 낱말표가 아는 값은 판정만 보여 준다(바꿀 수 없다).
   - 모르는 값마다 고른다. 수신동의 = 수신동의 / 수신거부 / 모름(지금 규칙: 신규 고객 미동의) · 탈퇴 = 탈퇴(발송 제외) / 정상 / 모름(지금 규칙: 수신거부) · 성별 = 남 / 여 / 모름(비움). 「모름」은 표에 넣지 않는다.
   - 끝에 결과 요약(예: 「수신동의 935,291 · 수신거부 156,455 · 값 없음 0」) · 질의서 숫자와 대조할 수 있게.
   - 쿼리 실패 · 시간 초과 · 메서드 없는 어댑터 = 한 줄 안내 뒤 건너뜀(지금 동작 · 설치 계속).
3. **설정** 최상위 `valueMaps`(선택): 필드마다 `{ column, table, source, values }`(수신동의 · 탈퇴 = `{글자: boolean}` · 성별 = `{글자: 'M'|'F'}`). `table` = 고객 테이블 · `source` = `valueMapSourceOf(저장된 config.database)`(종류 · 호스트 · 포트 · DB · 계정 · 파일 · 비밀번호 없음). **최상위에 두는 이유** = 원격 매핑 갱신이 `mapping` 칸을 통째로 새로 써서 그 안에 두면 지워진다. 최상위는 모든 쓰기 자리가 펼침(`...`)으로 보존한다. 옛 판이 이 설정을 읽으면 Zod 가 모르는 칸을 버린다(되돌려도 안전). 칸이 잘못되면 그 칸만 버린다(`.catch` · 기동은 막지 않음).
4. **적용 판정 한 곳** `resolveValueMaps(valueMaps, customerMapping, { table, source })`: 표의 `table` · `source` 가 지금 설정과 같고, 그 필드에 매핑된 원본 컬럼이 **정확히 하나**이고 표의 `column` 과 같을 때만 그 표를 쓴다. DB · 테이블 · 매핑 중 하나라도 바뀌면 옛 표는 저절로 안 쓰인다(지금 동작으로 돌아감 + 배치 로그 `CONSENT_VALUE_UNKNOWN` · `OPT_OUT_VALUE_UNKNOWN` 그대로 · Codex 설계 1R high: 컬럼 이름만 묶으면 다른 원본의 같은 이름 컬럼에 옛 분류가 붙는다). 원본 식별을 어댑터 `getSourceId` 가 아니라 저장된 접속 설정으로 만드는 이유 = 마법사가 접속에 쓴 객체와 저장 객체의 기본값 채움이 달라 같은 DB 가 다른 글자가 될 수 있다.
5. **정규화** `normalizeCustomer(mapped, { dbType, valueMaps })`: 맨 앞에서, 그 필드 값이 비어 있지 않은 글자이고 **낱말표 판정이 null 일 때만** 표의 값으로 바꾼다(수신동의 · 탈퇴 = boolean · 성별 = 'M'/'F' · 표의 자기 키만 · prototype 키 무시). 그 뒤 기존 흐름(표 밖 표시 · 탈퇴 접기) 그대로. 낱말표가 아는 값은 표가 있어도 바뀌지 않는다.
6. **엔진** `effectiveValueMaps()` 한 곳 = `resolveValueMaps(config.valueMaps, 지금 고객 매핑, { 고객 테이블, config.valueMapsSource })`. 고객 정규화에 넘긴다(배치마다 · 원격 갱신 즉시 반영). **분류 변경 = 고객 전량**은 상태 파일 `appliedValueMapsDigest`(마지막 고객 전량에 적용한 분류표 지문) 한 곳으로 보장한다 — 고객 증분 맨 앞에서 지금 지문 ≠ 기록이면 전량(커서 · 증분 보류 · 시각 컬럼 없음 어느 경로든). **매핑 교체(`updateMapping` · 원격 update_config)는 엔진 실행 한 줄(inLane)에 줄 선다** — 실행 도중에는 매핑(과 그에 걸린 분류표)이 바뀔 수 없다(옛: 도는 전량의 배치 사이에 바로 바뀌어 한 실행 안에서 섞였다 · 구현 1R · 2R 같은 뿌리 세 번 → 실행당 고정 장치를 덧대는 대신 교체 자체를 실행 사이로). 고객 전량(`full` 감싸개 → `fullScan`)은 시작 지문이 기록과 다르면 **보내기 전에 「진행 중」(`!pending`)을 디스크에 기록**(못 쓰면 한 건도 안 보내고 `VALUE_MAPS_STATE_SAVE_FAILED` 잠금 결과 · 상태 저장 `setAppliedValueMapsDigest` 만 실패를 던진다 · 다른 상태 칸 save 는 그대로 삼킴) · 완결(스캔 끝 · 전송 실패 없음)됐을 때만 시작 지문을 기록. 그래서 일부만 보내고 실패하거나 그 뒤 분류가 옛 값으로 되돌아와도(A→B→A) 기록이 옛 값과 같아지지 않아 다음에 다시 전량(구현 2R). ⛔ 분류표 없는 설치 = 지금 '' · 옛 상태 파일 칸 없음 = '' → 업그레이드만으로 전량이 돌지 않는다. 커서 지문은 손대지 않는다(구현 1R: 커서 지문에 넣던 첫 구현은 증분 보류 경로 · 전량 도중 변경을 못 막아 걷어냄). `index.ts` 가 `config.valueMaps` · `valueMapSourceOf(config.database)` 를 엔진 설정에 싣는다.
7. **배선 자리**
   - CLI 마법사: Step 4 매핑 직후 같은 Step 안 「값 확인」(단계 번호 그대로) · 저장할 접속 설정 객체를 먼저 만들어 그 모양으로 `source` 를 찍고 같은 객체를 저장한다 · 저장 설정에 `valueMaps`.
   - 설정 편집: 메뉴 「[6] 수신동의 · 탈퇴 · 성별 값 확인」 = 저장된 접속 · 고객 표 · 고객 매핑으로 같은 CT 를 돌린 뒤 **최신 설정 파일을 다시 읽어 `valueMaps` 만 합쳐 바로 저장**(`updateConfigEncrypted`). 확인에 쓴 매핑 · 테이블 · 접속이 최신 파일과 다르면(그새 원격 매핑 갱신 · 이 편집기의 저장 안 한 수정) 저장하지 않고 다시 열라고 안내(Codex 설계 1R medium: 대화 중 원격 갱신을 옛 사본이 덮음). 설정 편집 「저장하고 종료」가 전체를 덮는 기존 경로는 그대로(BUGS 기록). 설정 보기에 표마다 「지금 매핑 · 테이블 · DB 와 달라 쓰이지 않음」.
   - 웹 마법사: 넣지 않는다(키 지정도 없는 기존 차이 · 설치 뒤 설정 편집 길로 닫힘) · 추가 과제 줄.
   - 원격 매핑 갱신: 손대지 않는다(최상위 `valueMaps` 보존 · 4번 판정이 옛 표를 거른다).

## 4. P3 고객 누계 보호

1. **에이전트**: 구매 배치 요청에 `customerSummaryFields` = 지금 고객 매핑의 대상 필드 중 요약 5칸(`total_purchase_amount` · `purchase_count` · `recent_purchase_date` · `recent_purchase_amount` · `recent_purchase_store`)에 든 것. 비면 싣지 않는다. 배치마다 지금 매핑으로 계산(원격 매핑 갱신 즉시 반영).
2. **서버** `customer-purchase-aggregates.ts` (CT):
   - `parseCustomerSummaryFields(raw)` = 배열 아니면 [] · 허용 5칸만 · 중복 제거.
   - `updateCustomerPurchaseAggregates(companyId, ids, { keepColumns })` = keep 칸은 **고객 적재(`customer-upsert.ts`)와 같은 합치기 규칙**으로만 쓴다 · 나머지 칸은 지금처럼 `칸 = 원장 식`(고정 조각만 · 요청 글자를 SQL 에 넣지 않음) · keep 비면 지금 SQL 과 같은 SET 5칸.

     | keep 칸 | 고객 적재 규칙(기존) | 원장 재계산 규칙 |
     |---|---|---|
     | 구매횟수 · 최근구매일 | GREATEST | `GREATEST(c.칸, 원장 식)` · 원본이 비어도 원장이 계속 채우고 굳지 않는다 |
     | 누적금액 · 최근구매금액 · 최근구매매장 | 원본 값이 있으면 덮음(환불로 줄 수 있어 큰 값 불가) | 쓰지 않는다 · 원본이 비운 칸 = 원본의 값 |
   - `routes/sync.ts` purchases 가 `req.body.customerSummaryFields` 를 파싱해 넘긴다.
3. 뜻: 고객 매핑으로 누계를 주는 회사는 고객 원본이 누계의 진실이다. 같은 칸을 쓰는 두 작성자(고객 적재 · 원장 재계산)가 같은 규칙을 쓰므로 번갈아 덮지도 굳지도 않는다(설계 1R medium 「원본이 비면 영영 빔」 · 구현 1R high 「원장이 채운 값이 굳음」 = 같은 뿌리 · 한 칸에 출처 표시 없이 두 진실을 합치려던 것). 매핑에 없는 칸은 지금처럼 원장으로 계산.
4. 이미 설치된 다른 업체 = 새 칸을 안 보내니 지금 그대로. **나중에 1.7.3 을 다른 업체에 낼 때** = 고객 매핑에 요약 칸이 있고 구매도 받는 회사는 동작이 바뀐다 → 그때 운영 `sync_agents.config.reported.appliedMapping` 대조가 출고 조건(배포 원장 줄).

## 8. 리뷰 이력

- 설계 1R(Codex · needs-attention 4건 전부 수용): high 분류표를 원본 · 테이블에 묶음 · high 분류 변경 = 고객 커서 폐기 · medium 값 확인 메뉴 = 최신 설정에 합쳐 저장 · medium P3 keep 칸 = 비었을 때만 원장으로.
- 구현 1R(Codex · needs-attention 5건 전부 수용 · 같은 뿌리 2건은 구조로): high 전량 도중 매핑 변경 + medium 증분 보류 중 분류 변경 미감지 = 설계 1R 「분류 변경 재처리」와 같은 뿌리 → 커서 지문 방식을 걷어내고 상태 파일 `appliedValueMapsDigest` 한 곳(§3-6) · high 원장이 채운 값이 굳음 = 설계 1R 「영영 빔」과 같은 뿌리 → 고객 적재와 같은 합치기 규칙(§4-2) · medium 값 세기 실행 상한(Oracle `conn.break()` · MySQL 쿼리 timeout · 5분 · 넘으면 건너뜀) · medium MySQL 분포 값도 고객 조회와 같은 한글 보정.
- 구현 2R 첫 실행(Codex 잡이 판정 전에 죽음 · 런처 exit 0 · 잡 pid 없음 · 런북 §3 · 레코드 cancelled 정리): 죽기 전 메시지의 두 지점을 코드로 확인해 수용 — 전량 도중 분류가 옛 값으로 돌아오는 경우(A→B→A · 일부 전송 뒤 실패) = 실행당 분류표 고정 + 시작 때 「진행 중」 기록 · Oracle 끊기 실패 시 상한 미보장 = 실행과 마감 타이머 경주(끊기 성공 여부 무관 · 남은 연결은 disconnect 의 pool.close(0) 이 끝냄).
- 구현 2R(재실행 · needs-attention 2건 전부 수용): high 전량 중 매핑도 함께 고정해야 함 = 「전량 도중 변경」 부류 세 번째 → 실행당 고정 장치(분류표 스냅숏)를 걷어내고 매핑 교체를 실행 한 줄에 줄 세움(scheduler 가 await) · high 「진행 중」 저장 실패 시 전송 중단 = 그 칸만 엄격 저장(실패 = 메모리 되돌림 + 던짐) · 엔진이 보내기 전에 잠금.
- 구현 3R(needs-attention 1건 수용): medium 「진행 중」 저장 실패 잠금이 경보 모듈에 성공으로 들어감 → 경보 운영 실패 = `API_SEND_FAILED` + `VALUE_MAPS_STATE_SAVE_FAILED`(보낸 건수 0 이어도 실패).
- **구현 4R approve**(지적 0 · 1028). 지적 흐름 = 설계 1R 4 → 구현 1R 5 → 2R(첫 실행 잡 사망 · 재실행) 2 → 3R 1 → 4R 0.
