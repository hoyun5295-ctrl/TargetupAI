## 1. 발행 단위(scope) — Harold 요구 (2026-07-26)

### 1-1. 요구 원문

- 온라인팀·오프라인팀을 따로 발행해 달라는 고객사가 있다
- 최선어학원(에이전트 사용, 발송ID 5개)은 **학원 지점별 발행**을 요구
- **"에이전트 ID가 다 나눠져 있는 경우 분산 발행 / 합산 발행을 선택하게 해달라"**
- **고객사 관리자 = 본사 개념.** 하위 아이디들이 하위 업체

### 1-2. 세 가지 발행 단위

| scope | 산출 | 축 | 이번 범위 |
|---|---|---|---|
| `combined` | 1장 | 회사 전체 (현행 기본) | **구현** |
| `by_user` | 하위 N장 + 공통 1장 | 웹 계정(`campaigns.created_by`) | **구현** |
| `by_agent` | 하위 N장 + 공통 1장 | 에이전트 발송ID(`company_agent_ids.agent_send_id`) | **D로 이월** |

> **`by_agent` 이월 (Harold 결정 2026-07-26)** — "지점별로까지 구현은 나중에. 지금도 충분히 너무 많다."
> `scope` 컬럼에 값만 나중에 추가하면 되도록 구조는 이번에 잡는다(ALTER 재실행 불필요).
> 그때까지 최선어학원은 `combined`로 발행한다.
>
> **웹 발송분 귀속 확정 (Harold 2026-07-26)** — "웹 발송은 본사에서 보내는 거니까 지점에 안 섞는다."
> `by_agent` 구현 시에도 웹 발송분은 공통 장에 남는다. §6-1 미결 해소.

### 1-3. 공통 장 — 회사 단위 항목은 별도 1장

요금제 구독료 · AI 크레딧 · 테스트 발송 · 스팸필터 · (`by_agent`의) 웹 발송분 · 계정 미상 발송분은 **공통 장 1장**에 담는다.

**대표 장에 몰지 않는 이유**: "대표"를 정할 규칙이 없다. 계정·발송ID가 추가·삭제되면 대표가 바뀌어 같은 항목이 달마다 다른 사람 청구서에 붙는다. 지점 회계 입장에서 "우리가 안 쓴 AI 크레딧이 왜 우리 청구서에"가 된다.

**안분하지 않는 이유**: 안분 기준 자체가 사실이 아니다. AI 크레딧 **충전**(`ai_credit_requests`)은 회사 행위라 계정으로 나눌 근거가 없다. 기준을 만드는 순간 그건 우리가 만든 숫자이고 분쟁 시 근거를 못 댄다. 게다가 VAT가 장마다 `Math.round`라 N번 반올림이 일어나 합계가 최대 N/2원 어긋난다(세금계산서 대조에서 걸린다). 한 장을 지우고 재발행하면 안분 분모가 바뀌어 나머지와 안 맞는다.

→ 별도 1장은 사실을 왜곡하지 않고, 합계가 **정수 덧셈**이라 정확히 성립한다.

### 1-4. 본사 판별 — 발행 시 선택

**`users.role`은 227명 전부 `admin` 한 값이다**(2026-07-26 실측). 금강제화 5계정도 전부 `admin`이고 `kumkang01`만 이름이 "금강제화 관리자"인데 그건 사람이 붙인 이름이지 데이터가 아니다. **role로는 본사/하위를 가를 수 없다.**

- `by_user`: 계정 목록에서 **본사 계정 1개를 발행 시 선택**. 그 계정 장에 공통 항목이 붙는다.
- `by_agent`: 발송ID에는 본사 개념이 없다. 공통 항목은 **회사 앞 별도 장**.

컬럼을 신설해 회사마다 본사를 미리 지정하는 방식은 227개 계정에 값을 채우는 운영 작업이 새로 생기고, 온라인팀·오프라인팀처럼 본사가 없는 구성을 담기 어렵다. 발행은 월 1회 슈퍼관리자 작업이라 그 자리에서 고르는 편이 싸다.

### 1-5. 묶음 발행 — 원자적으로

**한 번의 요청이 N+1장을 만들고, 실패하면 전부 롤백한다.** 장 단위 반복 발행은 "N장 중 3장까지 만들고 4장째에서 단가 미설정으로 막힌 상태"를 허용한다. 그러면 회사가 부분 청구 상태로 남고, 고객은 "이게 다인가"를 알 수 없다.

### 1-6. 중복 검사 — scope 값을 키에 더하는 것으로는 안 된다

축 값(`user_id`·`agent_id`)으로 키를 늘리면 `combined`(둘 다 NULL)와 `by_user`(user_id 있음)가 **키가 달라 둘 다 통과**한다. 지금 구멍이 셋으로 늘 뿐이다.

필요한 불변식은 하나다 — **한 회사·한 기간에는 하나의 scope만 존재한다.**

- 중복검사를 `company_id + 기간겹침`으로 좁히고, 기존 행의 scope와 요청 scope가 다르면 무조건 거부
- 같은 scope면 `combined`는 1장뿐이니 거부, `by_user`/`by_agent`는 같은 키면 거부·다른 키면 허용
- advisory lock 키를 **회사 단위로 되돌린다**(현행은 회사+사용자)

### 1-7. 필요한 ALTER 2건

```
ALTER TABLE billings ADD COLUMN scope varchar(20) NOT NULL DEFAULT 'combined';
ALTER TABLE billings ADD COLUMN batch_id uuid;
```

- `scope` = `combined` / `by_user` / `by_agent` / `common`(공통 장)
- `batch_id` = 묶음 식별. 부분 삭제 차단·"N+1장 중 k장" 표기의 근거
- 두 컬럼을 쓰는 endpoint catch에 `column does not exist` → 503 `DB_MIGRATION_PENDING` 분기 의무

`billings.agent_id`는 이미 존재하고 현재 항상 NULL이라(SCHEMA.md `billings` 절) `by_agent` 축으로 그대로 쓴다.

### 1-8. 합계 불변식

`Σ(하위 N장 subtotal) + 공통 장 subtotal === combined subtotal`

- 안분이 없으므로 정수 덧셈으로 정확히 성립한다
- **VAT에는 걸지 않는다.** 장별 `Math.round(subtotal × 0.1)`가 N+1번 일어나 최대 (N+1)/2원 어긋난다. VAT에 걸면 정상 발행이 막힌다
- 대가: 분산 발행 시 검증용 combined 집계를 한 번 더 돌려야 해 **집계가 2배**다. 포기하면 "분산 N장이 회사 총액을 다 담았는가"를 아무도 모르게 되고, 그건 이번에 발견한 `both` 17사 누락과 같은 클래스다

### ① 메일 발송

| 지적 | 처분 |
|---|---|
| 잠금을 든 채 SMTP를 하므로 **커넥션 풀(20) 고갈** 가능. `socketTimeout`은 **비활동** 상한이라 총 소요 시간을 못 막는다 | **수용** — ⓐ 트랜잭션 진입 직후 `SET LOCAL lock_timeout = '10s'`(대기자가 커넥션을 무한정 물지 않는다) ⓑ `Promise.race`로 **발송 총 시간 60초 상한**. 잠금 보유 시간에 상한이 생겼다 |

### ② 요금제 이력 게이트 — **판정 축을 바꿨다**

5차에서 넣은 `planAssigned`(지금 플랜이 있는가)를 "그 기간에 요금제를 썼는가"로 쓴 것이 틀렸다. 그래서 **7/15 최초 배정 회사**(7/1~14은 요금제 없음이 정상)와 **8/1 최초 배정 후 7월분 발행**(7월 이력 0)이 전부 차단됐다 — 정상 발행을 막는 결함을 내가 만들었다.

정답은 **공백의 종류**다. `findPlanCoverageGap`이 `kind`(`head`/`internal`/`trailing`)를 함께 돌려주고, 게이트는 **`internal`·`trailing`만** 막는다.

### 3-1. A-3 — 날짜 밀림과 기간 경계는 반드시 세트다

**두 버그가 정확히 서로를 상쇄하고 있다.**

- **날짜 밀림**: mysql2 풀에 `dateStrings`가 없어 `DATE()`가 로컬 자정 `Date`로 오고, `toDayKey`가 `toISOString().slice(0,10)`을 해서 하루 앞으로 간다. 서버 실측 — `DATE('2026-07-15 10:00:00')` → `Wed Jul 15 2026 00:00:00 GMT+0900` → **`2026-07-14`**. PG도 `date`(oid 1082) 파서를 안 덮어써서 같다. 에이전트는 `YYYYMMDD` 문자열 슬라이스라 안 밀린다.
- **기간 경계**: PG 세션 TZ가 `Etc/UTC`라 `>= $2::date` 경계가 UTC 자정 = **KST 09:00**이다. 실측 — 7/1 KST 00~09시 완료 직접발송 **6건**(7월 전체 4,670건 중).

| | run 집합 귀속 | `item_date`(현재) | 기간 안? |
|---|---|---|---|
| 7/1 00~09시 KST 발송 (6건) | 6월 | `06-30` | 예 |
| 8/1 00~09시 KST 발송 | 7월 | `07-31` | 예 |

- **밀림만 고치면**: 6월 청구서에 `07-01`, 7월 청구서에 `08-01` 행이 찍힌다. PDF 2페이지는 `slice(5,10)`이라 연도 없이 "08-01"만 나온다
- **경계만 고치면**: 7/1 00~09시가 7월로 들어오는데 `item_date`는 `06-30`

**처방**: `toDayKey`를 로컬 연·월·일 성분 포맷으로 교체(두 드라이버 모두 로컬 자정 `Date`를 주므로 TZ 무관 정답) + `>= ($2 || ' 00:00:00+09')::timestamptz` 형태로 경계를 KST 자정에 맞춘다(스팸 쿼리가 이미 쓰는 방식). `ecosystem.config.js`에 `TZ` 명시 + `toDayKey(new Date(2026,6,15)) === '2026-07-15'` 순수 테스트.

**지금이 무비용 시점**: `billings` 실행 이력이 금강제화 시험 1건뿐이고 그것도 구조 변경 후 삭제 예정이라, 경계를 바꿔도 재발행할 청구서가 없다.

### 3-2. A-4 — 트랜잭션 내 `count(*)` 대조는 장식이다

같은 트랜잭션 안에서 `SELECT count(*)`를 하면 자기 INSERT가 전부 보이고, PG는 부분 INSERT가 없다(에러면 전부 롤백). 실패할 경우가 구조적으로 없다. 잡고 싶은 건 청킹 루프 인덱스 버그이고 그건 **청크 분할 순수 테스트**로 잡는다. 런타임에 남기려면 `result.rowCount` 합이 더 싸고 정확하다.

### 3-3. A-7과 "계정 미상 차단"의 충돌 — 후자를 폐기한다

- A-7은 삭제된 사용자를 `null`로 만들고 차단하지 않는다
- "web 채널 `userId=null && success>0`이면 차단"을 함께 켜면, 퇴사자 계정 하나를 지웠을 때 A-7이 만든 null을 그 가드가 차단한다
- 두 종류의 null을 구분할 컬럼이 없다
- 금액 영향도 0이다(웹 단가는 회사 단가라 계정과 무관)
- **금액에 영향 없는 것으로 발행을 막지 않는다**는 원칙(§4-1에서 세운 것)을 스스로 깬다

→ 계정 미상 행은 차단하지 않고 **공통 장으로 귀속**한다. 경고 로그만 남긴다.

## 4. B — 하지 않기로 한 것

### 4-1. 음수 `ReadyCnt`를 0으로 자르지 않는다

청구 수량은 `success`(OkCnt)뿐이라 **금액 기여가 0**이다. 자르면 셋이 깨진다.

1. 발송통계 화면·엑셀은 음수를 그대로 둔다 → 같은 원천이 두 문서에서 다른 값
2. 청구서 한 줄 안에서 `전송 ≠ 성공+실패+대기`가 된다(`TotCnt`는 안 자르므로) — D150-2와 같은 모양
3. **음수는 게이트웨이가 뭔가를 되돌리고 있다는 신호인데, 그게 `OkCnt`에도 실렸는지 우리가 모른다.** 0으로 덮으면 다음 달에도 모른다 — LESSONS_DB 0629 "진단 기준을 버그 산식과 같게 잡으면 가려진다"와 같은 실수

→ 원본 보존 + `console.log('[정산][대기음수]')` 관측. 차단 없음. PDF 대기 컬럼 표시 여부는 C에서 판단.

### 4-2. 대조를 날짜×유형으로 승격하지 않는다

두 함수(`buildCompanyUsageByDay` / `buildBillingUsageRows`)는 같은 테이블 집합·같은 WHERE·같은 run 집합을 쓴다. 설계상 갈라지는 유일한 통로는 **사람이 한쪽만 고치는 것**이고, 그건 런타임 대조가 아니라 **소스 스캔 테스트**가 잡을 일이다.

런타임 대조가 실제로 잡는 건 두 스캔 사이의 LIVE→LOG 이동뿐이고 그건 오탐이다. 마감일에 오탐으로 발행을 막는 장치를 두려면 진탐이 하나는 있어야 하는데 없다.

→ A-8 금액 항등식으로 대체. **단 A-8도 같은 오탐 특성을 가지므로**(두 값이 각각 MySQL을 따로 스캔) 실패 시 1회 재계산 후 재검사한다.

## 9-5-A. ★절사 지점 정정 — 행 단위 → 항목줄 1회 (2026-07-30) · **★배포됨** (`b396e2a5`)

**현행 계약이다. 위 §9-5 표의 "행 단위" 서술은 폐기됐다.**

서수란 접수(0729 `cms5rl30e00ij6ueozwl3gcox`): 소수 단가 항목표가 `수량 × 단가`와 어긋난다. 실측 = SMS 1,733건 × 7.2원은 12,477.6원이어야 하는데 **12,456원**으로 표시. 정수 단가 행은 정확했다.

**원인** — 0726 지시("최종금액에 소숫점 그냥 버림")를 **일자별 행 단위 절사**로 구현한 것이 과대 해석이었다. 청구 상세는 일자 × 채널 × 유형 × 계정 축이라 한 항목줄이 수십 개 일자행으로 쪼개지고, 절사가 **일자 수만큼 누적**돼 항목줄이 정확값보다 수십 원 작아진다. Harold 정정: "계산서 발급할 때 소숫점 나오는 것만 버리라고 한 건데 단가 계산할 때도 버리면 어떻게 하냐."

**확정 계약 5줄**

| 축 | 계약 |
|---|---|
| 일자행 (`billing_items.amount`) | `성공 × 단가` **정확값**(소수 유지). `priceBillingRows`에서 절사하지 않는다 |
| 항목줄 (`buildInvoiceLines`) | **여기서 1회 절사**(`floorWon`). 같은 단가 그룹은 Σ(일자수량×단가) = 총수량×단가라 절사값이 정확히 `floor(수량×단가)`가 된다 |
| 헤더·장 공급가액 | 장별 `sumFlooredInvoiceLines`의 정수 합. 장 문서에 인쇄되는 항목표 세로합과 **정의상** 일치 |
| 최종 표시 금액 (2p 합계·상세 모달·미리보기) | 전부 그 절사 합에서 파생. **Σ소수를 따로 floor하지 않는다** — 항목표와 1원 갈린다 |
| 교차검증 (A-8·장합) | 정확값 축(`amountExact`·`subtotalExact`)끼리. 절사 축과 얽히면 검사가 사라진다 |

**계정별(`by_account`) 발행은 합산 발행과 1원 수준 차이가 난다 — 의도다.** 장이 늘면 절사 횟수도 늘기 때문인데, **장 = 독립 문서 = 세금계산서 단위**라 각 장의 공급가는 그 장 항목표의 절사 합이어야 한다. 전역 절사 후 장에 배분하면 장만 받아 본 고객의 검산(항목표 세로합 = 공급가)이 깨진다 — 서수란 문제의 장 단위 재발이다. 차이 방향은 항상 고객 유리(절사 횟수↑ = 금액↓). Codex 적대검증이 "합산↔계정별 불일치"를 HIGH로 지적했으나 이 근거로 **불수용**했고 논거 타당을 인정받았다(2R approve).

**호환** — 기존 발행분은 저장값이 이미 정수이고 절사는 멱등(정수의 절사 = 자기 자신)이라 검산·표시가 전부 그대로 통과한다. ⛔단 **미발행 draft 중 소수 단가 회사 것은 삭제 후 재생성**해야 새 산식이 반영된다(저장된 일자행이 옛 절사값).

### 실사고 — 마이그레이션을 배포 전에 실행

**증상**: 실패 0건인 패밀리투에 `발송 실패 환불 (sweep) (SMS 1건 × 7.5원)`이 반복 입금. 실측 **83건 622.50원**(22:30:27~28 한 사이클).

**원인**: 마이그레이션으로 SMS 단가가 8.25 → 7.50이 됐는데 운영 서버는 **옛 코드**였다. 옛 sweeper는
차감 건수를 `총차감액 ÷ 현재단가`로 역산한다 — 차감은 8.25원에 일어났으므로 `49.50 ÷ 7.50 = 6.6 → 7건`으로 읽고,
`7 − 성공 6 = 1건`을 "차감했는데 안 나간 건"으로 환불했다. 캠페인마다 반올림된 1~2건씩 나갔다.

**내가 틀린 곳**: "배포 뒤에 마이그레이션하라"고 안내해 놓고, 발송이 없다는 말에 그 판단을 뒤집었다.
**sweeper는 새 발송과 무관하게 최근 14일 캠페인을 30초마다 다시 계산한다** — 발송 창이 닫혀 있어도 노출은 열려 있다.

**회수**: 새 코드 배포 시 `deductedCount`가 기록된 건수(정확)로 잡혀 정당 한도가 0이 되고,

**진단 SQL 교훈** — 마이그레이션 시각을 `max(companies.updated_at)`로 잡으면 안 된다.
`prepaidRefund`가 환불할 때마다 `updated_at`을 갱신해 기준 시각이 앞으로 밀리고, 결과적으로 **마지막 1건만** 잡힌다.

## 9-8. 속도 1차 처방 — 병렬화·중복 조회 제거·계측 (2026-07-26 4세션)

§9-4 표의 ②③을 적용했다. ①(두 번째 스캔 폐기)은 금액 검증 장치(`diffBillingRowsVsDayData`)를 걷어내는 변경이라
**계측 로그를 보고 나서** 판단한다 — 추측으로 돈 검증을 떼지 않는다.

| 처방 | 내용 |
|---|---|
| ★ 정산 전용 MySQL 풀 분리 | **기간계 격리가 먼저다**(Harold 지시). 발송 풀에서 병렬로 돌리면 정산이 커넥션을 가져가 그동안 발송·환불 sweeper가 자리를 못 잡는다 — 월 1회 작업이 실발송을 밀어내면 안 된다. `mysqlBillingPool`(`connectionLimit` 8, env `MYSQL_BILLING_POOL_LIMIT`) + `mysqlBillingQuery` 신설. 발송 풀(10)은 정산과 무관하게 항상 10이다. 쿼리 1건 실행 상한도 함께(`max_execution_time` 60s — MariaDB엔 없는 변수라 미지원 서버에서는 조용히 건너뛴다) |
| ② 직렬 → 동시성 상한 병렬 | 세 집계 함수(`smsAggByDateType`·`smsAggByRunDateType`·`testSmsAggByUserDateType`)가 테이블을 `for await`로 하나씩 훑었다. 회사당 40~48개 × 두 집계 = **90~100회 순차 왕복**이 2분의 지배 요인이다. `utils/concurrency.ts` CT 신설(`mapWithConcurrency`) + 상한 = 정산 전용 풀 크기(8). 전용 풀이라 다 써도 기간계에 닿지 않는다. `concurrency.ts`는 순수 유틸로 두고 상한 값은 풀을 소유한 `config/database.ts`가 정한다 |
| ③ 테이블 목록 중복 조회 제거 | `getBillingLogTables()`(information_schema REGEXP)가 발행 1회에 **4번** 돌았다. 각 집계 함수가 시작할 때 한 번 읽어 넘긴다. **모듈 캐시로 두지 않는다** — 월 경계에 새로 생긴 LOG 테이블을 못 보면 그 달 첫 발행이 통째로 미청구가 된다 |
| 계측 | `/generate`에 `[정산][소요] 일자축 집계 Nms · 상세축 집계 Nms` 로그. 다음 개선은 이 숫자 위에서 판단한다 |

`mapWithConcurrency`는 **입력 순서를 보존**하고 **하나라도 실패하면 throw**한다 — 테이블 하나를 조용히 건너뛰면
그 라인 발송분이 미청구가 된다(IMC의 `queryImcOrSkipIfMissing`과 달리 SMSQ 라인 테이블은 반드시 터져야 한다).

**④ VIEW 혼입 — 실측으로 종결(2026-07-26).** `SMSQ_SEND`는 뷰가 맞지만(`information_schema` 확인),
`sms_line_groups.sms_tables`에는 **접미사 있는 실테이블만** 들어 있다:
`auth {SMSQ_SEND_11}` · `bito {13,14,15}` · `bulk {1,2,3}{4,5,6}{7,8,9}` · `test {SMSQ_SEND_10}`.

**검증 팁(기록)** — `SHOW CREATE VIEW`는 `SHOW VIEW` 권한이 필요해 `smsuser`로는 1142가 난다.
유형만 볼 때는 `information_schema.TABLES`의 `TABLE_TYPE`을 쓴다(권한 불필요).
참고로 `SHOW CREATE VIEW`가 1142를 낸 것 자체가 그 객체가 뷰라는 증거다 — 뷰가 아니면 1347(wrong object)이 난다.

§9-8의 병렬화·중복 조회 제거로는 닿지 않았다. 실제 원인은 옵티마이저의 선택률 오추정이었다.

**선행 실패 기록 (커밋 `a0b37bf8`)** — "IN 목록이 커서 옵티마이저가 인덱스를 버린다"고 추론해
`app_etc1 IN` 목록을 200개로 쪼개 배포했다. 결과는 **금강제화 44.3초 → 50.6초, 개선 0**.
스캔 대상 테이블은 그대로라 누락 위험은 없었지만 효과도 없었다.

**EXPLAIN 실측** — `type: ALL` · `key: NULL` · `filtered: 49.60`. **IN 값이 5개일 때도 풀스캔**이었다.
개수가 아니라 선택률 추정(49.6%)이 원인이라 청킹으로는 애초에 닿을 수 없었다.
단일 테이블 실측: 집계 **12.92초** = 테이블 전체 읽기 12.26초 → `FORCE INDEX` **1.17초**(11배).
(⚠ 함께 적혀 있던 "876MB"는 원 출력이 남아 있지 않다 — 0728 STATUS에서 옮겨온 값이고 재실측으로 확인한 것이 아니다. 판단 근거로 쓰지 말 것.)

**처방** — `app_etc1 IN` 집계 2곳에만 `FORCE INDEX(idx_app_etc1_sendreq)`.
테스트발송(단일값) 경로는 제외하고, 인덱스가 없는 서버에서 1176이 나면 힌트 없이 폴백한다.

**결과** — 금강제화 발행 전체 **50,643ms → 6,696ms (7.6배)**. 대조 기간은 오히려 3일 더 길다.
