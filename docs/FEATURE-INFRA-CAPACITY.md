## §2 산식과 한계

### §2-1 1명당 비용
- 고객 비례 표 합계 = customers 928 + purchases 647 + predictions 380 + identity_links 243 + customer_stores 147 = **2,345MB** ÷ 1,280,402명 = **약 1.9KB/명**.
- 그중 인덱스 = 564 + 397 + 225 + 161 + 86 = **1,433MB** ÷ 1,280,402명 = **약 1.15KB/명**.
- 발송 비례 표(staging 842 · unsubscribes 298 · fatigue 236 = 1.4GB)는 고객 수가 아니라 발송량과 함께 늘어나므로 산식에서 뺀다. 별도 관리 대상(§7).

### §2-2 "속도 지장 없음"의 기준 (이 문서 전체가 하나의 기준을 쓴다)
**고객 비례 데이터와 인덱스가 전부 메모리에 상주해 타겟 추출이 디스크를 읽지 않는 상태.** 인덱스만 상주하는 선을 넘으면 그때부터 느려지기 시작한다.

### §2-3 현재 서버(.62)의 수용
| 기준 | 산식 | 결과 |
|---|---|---|
| 메모리 상한 | 가용 44G ÷ 1.9KB | 약 2,400만 명 (MySQL·발송 표가 같은 캐시를 쓰므로 실제는 그 아래) |

### §2-4 구매를 실제로 당기는 신호 (고객 수가 아니라 지표)
하나라도 걸리면 그때가 착수 시점이다. 측정 SQL은 §8.
1. PG 캐시 적중률이 **99% 아래**로 유지
2. 평시(가져오기 없을 때) **1분 부하 4 이상** 유지(8스레드의 50%)
3. 가장 큰 회사(현재 아난티 50만)의 **타겟 추출 시간**이 체감되는 수준

### §2-5 고객 수와 무관한 다른 축 (이 문서의 산식이 답하지 않는 것)
- **앱 계층**: 백엔드는 4코어에서 **단일 프로세스(fork)**. 동시 접속자·동시 발송이 늘면 고객 수가 적어도 느려진다. cluster 전환은 fork_mode + ts-node 구조 때문에 별도 과제(`reference_deploy_downtime_fork_mode`). 이 축은 접속자 수로 판단하고, 한계에 닿으면 그때가 멀티노드 시점이다.
- **회사 하나의 크기**: 타겟 추출은 회사 단위 스캔이다. 아난티 50만에서의 추출 시간을 재지 않았으므로 "한 회사 몇 백만까지"는 **미측정**.
- **쿼리 계획**: 0921 이메일 조회가 26만 행을 통째로 읽던 사례처럼, 한계에 먼저 닿는 곳은 하드웨어가 아니라 인덱스 없는 쿼리다. 하드웨어 산식은 인덱스가 갖춰진 뒤의 이야기다.

### §3-3 `.62` 제자리 증설 검토 (0922 실측 · Harold "62번을 늘리는 방법도 있잖아")

**실측(0922 · Harold 실행)**
| 항목 | 값 |
|---|---|
| 기종 | **HPE ProLiant DL20 Gen11** · `systemd-detect-virt` = none(**실물**) · iLO 원격 관리가 있는 1U 엔트리 서버 |
| CPU | Intel Xeon **6325P** 4코어/8스레드 · 소켓 1 · Raptor Lake 계열(SATA 컨트롤러 = Raptor Lake AHCI) |
| 메모리 | 62G. DIMM 구성은 EDAC 노출 0건이라 미확인(**iLO → System Information → Memory** 에서 슬롯별 확인 가능) |
| 저장 컨트롤러 | 온보드 SATA AHCI만(`lspci` · NVMe·Smart Array 0건) · 위에 소비자용 TAMMUZ SATA SSD 1장 |

- 서버로 산 것은 맞다. HPE ProLiant = ECC 메모리 · iLO · 핫플러그 베이 · 이중 전원 옵션이 있는 진짜 서버 섀시다. 낮았던 것은 **안에 고른 부품**이다: 계열 최저 CPU(4코어) · 소비자용 SATA SSD 1장 · 메모리 62G.
- 그래서 **제자리 증설 여지가 있다**(HPE QuickSpecs 기준 · 구매 전 QuickSpecs·iLO로 재확인):
  - 메모리: DDR5 **ECC UDIMM** 4슬롯 · 최대 128G. 지금 62G가 32G×2면 32G×2 추가, 16G×4면 32G×4 교체. **§3-2의 DDR4 데스크탑 램은 이 서버에 꽂히지 않는다.**
  - CPU: 같은 6300P 계열 8코어(6349P·6369P·6373P)로 교체 가능. **선택 항목**(오늘 유휴 84% · 가격 보고 판단).
  - 디스크: PCIe 슬롯에 데이터센터용 NVMe 2장(AIC 또는 M.2 라이저) → 소프트웨어 미러 → PG 볼륨을 그 위로. MySQL은 SATA에 남겨 디스크를 나눈다. SFF 베이 NVMe(U.3) 지원 여부는 QuickSpecs로.
  - 타사 NVMe·메모리는 iLO가 경고를 띄울 수 있으나 동작은 막지 않는다(일반 사례 · 미검증).

**비교**
| 축 | `.62` 제자리 증설 | `.66` 재활용 + 경량 서버 |
|---|---|---|
| 사야 하는 것 | DDR5 ECC 32G × 2~4 · NVMe 2장 · (선택) CPU 8코어 | DDR4 32G × 4 · NVMe 2장 · 경량 서버 1대 |
| 옮기는 것 | **0**(PG 볼륨을 같은 서버 안 NVMe로 이동만) | PG 이전 + 그룹웨어 + 발송 콘솔 + Agent 4개 + `.65` 허용 목록 갱신 |
| 네트워크 변경 | 0 | WireGuard 터널 신설 · 앱↔DB 왕복 지연 추가 |
| 신뢰성 | ECC · iLO · 서버 전원 | 비ECC · 소비자 보드·전원 |
| CPU | 4코어 공유(교체하면 8코어 공유) | 8코어 PG 단독 |
| 수용(전부 상주 기준) | 128G에서 가용 약 110G → 상한 약 5,800만 · **계획선(43%) 약 2,500만**(지금 1,000만의 2.5배) · `shared_buffers` 32G면 인덱스 기준 2,800만 | 약 6,900만(단독) |
| 정지 | 부품 장착 + 볼륨 이동 1회(업무시간 밖) | PG 전환 1회 + 그룹웨어·콘솔 각각 |

**추천 = `.62` 제자리 증설**(메모리 128G + 데이터센터용 NVMe 2장 미러 · CPU 교체는 선택). 이유:
1. DB가 있어야 할 자리는 ECC·iLO가 있는 진짜 서버다. `.62`가 그 서버다.
2. 옮기는 것과 네트워크 변경이 0이다. 오늘 측정된 병목(디스크 공유·fsync·메모리 계획선)이 그 자리에서 풀린다.
3. `.66`은 그대로 두고 **다음 단계에서 PG 스트리밍 복제(대기 서버)**로 쓰는 것이 주 서버로 쓰는 것보다 가치가 크다. 디스크·서버 한 대 장애에서 DB가 살아남는 구조가 그때 생긴다.

계획선 2,500만이 `.66` 단독 6,900만보다 낮은 것은 사실이다. 그 차이는 앱·MySQL·에이전트와 메모리를 나눠 쓰기 때문이고, 2,500만이 보이면 그때가 멀티노드 시점이다(§2-5). **결정 대기(Harold).** 결정되면 D94를 "형태 = .62 제자리 증설"로 고치고 §6 절차를 이 형태로 다시 쓴다.

### §4-4 분리 뒤 속도 변화 (산술 추정 · 옮긴 뒤 실측으로 대체)
- 앱↔DB가 다른 서버가 되면 쿼리마다 왕복 지연 약 0.2ms. 가져오기는 1건에 쿼리 5개 안팎이라 건당 약 1ms, 0922 실측 12ms/건 기준 **약 8% 느려짐**. 화면 API는 체감 밖.
- 대신 PG가 디스크·메모리·CPU를 독점하므로 타겟 추출·가져오기 자체는 빨라지는 방향. 폭은 실측.

## §5 디스크 판독과 새 디스크 기준

- 현재 `.62` = **TAMMUZ SATA SSD 1.9T 한 장**(소비자용 · 미러 없음). HDD가 아니다.
- 그래서 IO 대기 11.5%는 HDD 탐색이 아니라 **커밋(fsync) 대기** 쪽이다. PG는 트랜잭션마다 디스크 확정 기록을 하고, 가져오기는 1건에 커밋이 여러 번, MySQL 발송 큐도 같은 패턴. `jbd2`(ext4 저널)가 top 상위에 있던 것이 그 표시.
- 소비자용 SSD는 전원 보호 캐패시터(PLP)가 없어 fsync 한 번의 지연이 데이터센터용 NVMe보다 수십 배 큰 것이 일반적이다(일반 지식 · **이 디스크의 실측값은 없다**).
- 실측 도구 `pg_test_fsync`는 부하 시험이라 **운영 중에는 돌리지 않는다**(진단이 운영을 건드리면 안 된다). 새 서버 입고 뒤 그 서버에서 먼저 돌려 기준값을 잡는다.
- 새 디스크를 고르는 기준 = 순차 속도가 아니라 **fsync 지연(PLP 유무)**.

## §8 측정 명령 모음 (전부 `.62` · 읽기만 · 운영 무접촉)

서버 상태(기준선 · 재측정은 `top -bn2 -d 2`의 두 번째 화면):
```bash
uptime; echo; free -g | head -2; echo; df -h / /var /home | tail -3; echo; top -bn2 -d 2 | grep "^%Cpu" | tail -1; echo; pm2 list; echo; docker stats --no-stream
```

PG 접속·크기·회사별 고객 수:
```bash
docker exec -i targetup-postgres psql -U targetup targetup -c "SELECT state, COUNT(*) FROM pg_stat_activity WHERE datname='targetup' GROUP BY state ORDER BY 2 DESC;" -c "SELECT pg_size_pretty(pg_database_size('targetup')) AS db_size;" -c "SELECT COALESCE(co.company_name, co.name) AS company, COUNT(*) AS customers FROM customers c JOIN companies co ON co.id = c.company_id GROUP BY 1 ORDER BY 2 DESC LIMIT 15;"
```

테이블 크기 · PG 설정 · 볼륨 위치:
```bash
docker inspect targetup-postgres --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'; docker exec -i targetup-postgres psql -U targetup targetup -c "SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS total, pg_size_pretty(pg_indexes_size(relid)) AS indexes, n_live_tup FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 12;" -c "SHOW shared_buffers;" -c "SHOW max_connections;"
```

캐시 적중률(§2-4 지표 1 · 통계 초기화 이후 누적값이라 두 시점을 비교해 읽는다):
```bash
docker exec -i targetup-postgres psql -U targetup targetup -c "SELECT round(100.0*sum(blks_hit)/NULLIF(sum(blks_hit)+sum(blks_read),0),2) AS hit_pct, sum(blks_read) AS blks_read FROM pg_stat_database WHERE datname='targetup';"
```

디스크 종류:
```bash
lsblk -d -o NAME,ROTA,SIZE,MODEL,TRAN
```

IO 귀속(10초 델타 · 표시 단위 0.1GB라 큰 쓰기만 보인다):
```bash
docker stats --no-stream --format "{{.Name}} CPU {{.CPUPerc}} IO {{.BlockIO}}" targetup-mysql targetup-postgres; sleep 10; docker stats --no-stream --format "{{.Name}} CPU {{.CPUPerc}} IO {{.BlockIO}}" targetup-mysql targetup-postgres
```
