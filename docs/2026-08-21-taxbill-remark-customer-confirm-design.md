# 계산서 비고(PO번호) — 고객이 컨펌 페이지에서 입력하면 자동 발행까지 (설계서)

> 2026-08-21 Harold 발안("거래내역서 메일에서 시세이도가 PO를 직접 넣게 하고 그걸로 자동 발행") · 착수 대기.
> 이 문서가 소유하는 것 = 이 자동화 축의 확정 사실·설계·영향표·단계·실측 게이트·⛔. 불변 원칙과 이력은

> 표기 규약: **[확정]** = 코드·실DB로 본 사실 / **[설계]** = 이 문서의 결정 / **[미검증]** = 구현·실측 전 가설.

## §0 한 줄

거래내역서 메일의 [컨펌하기]가 여는 **공개 컨펌 페이지**에 PO번호(필수)와 — 직접선택 회사면 — 희망 작성일자 칸을 두고,
고객의 [확인]이 **컨펌 + 비고 저장 + (직접선택이면) 발급 대기 진입**이 되게 한다. 운영자 개입 0. 0821(2) 배포분의
`taxbill_remark`·발행 패스 필수 게이트·워커 날짜 게이트를 그대로 재사용한다 — **DDL 0, 새 권한 축 0**.

## §1 왜 이 형태인가

- **[확정]** 이메일 본문 안의 입력폼은 메일 클라이언트가 제출을 보장하지 않는다 — 입력은 페이지에서 받는다.
- **[확정]** 공개 컨펌 페이지(`routes/invoice-public.ts`)는 이미 토큰으로 회사·장에 묶여 있고, 컨펌·이의신청을 받는다.
  컨펌 자체가 자동 정책 회사에서는 "발행 개시"를 뜻하므로, 이 페이지에 PO·작성일자를 받는 것은 **새 신뢰 축을 만들지 않는다**.
- **[확정]** 직접선택 건은 `POST /:token/confirm`이 컨펌 시각만 적고 `manual_wait`을 유지한다(§2-13 — "발급은 사람이 날짜를
  정한 뒤"). 시세이도는 **부서가 PO 때문에 발행일자까지 통보**하는 회사라, 그 "사람"은 곧 고객이다 — 고객이 페이지에서
  날짜를 고르면 운영자 전달 단계가 사라진다.
- **[확정]** 0821(2)로 비고 저장소(`invoice_confirmations.taxbill_remark`)·회사 플래그(`require_taxbill_remark`)·발행 패스의
  필수 게이트(채번 앞)·워커 작성일자 게이트가 있다. 이 설계는 **입력 창구를 하나 더 여는 것**이다.

## §3 설계

### 3-1. 페이지 (`GET /:token`) [설계]
- 회사 설정 `require_taxbill_remark = true`인 장에만 **"계산서 비고(PO번호)" 입력칸(필수)** 을 컨펌 버튼 위에 둔다.
  안내 = "세금계산서 비고란에 그대로 인쇄됩니다". 다른 회사 페이지는 **지금과 동일**(영향 0).
- 회사 정책이 `manual`(직접선택)이면 **"계산서 작성일자" 날짜칸**을 함께 둔다(기본값 = 컨펌 행의 미리 계산된 `taxbill_issue_date`).
  자동 정책(말일·익월 1일)이면 날짜칸 없음 — 날짜는 정책이 정한다.
- 이미 컨펌된 장(state=confirmed/issued)은 입력칸을 닫고 저장된 비고를 읽기 전용으로 보여준다(고치려면 담당자에게).

### 3-2. 컨펌 (`POST /:token/confirm`) [설계]
- 본문 `{ taxbill_remark?, issue_date? }`. 서버 검증:
  - 필수 회사인데 비고가 비면 **422 + 페이지 안내**(컨펌 자체를 받지 않는다 — 비고 없이 컨펌되면 발행 패스에서 멈춰 운영자 몫이 된다).
  - 비고 150자 상한(팝빌 비고 규격과 동일 — 0821(2)와 같은 상한).
  - 작성일자 허용 범위 = **`billing_start` ~ 공급월 익월 10일**(세금계산서 발행 기한) **[미검증 — 세무 규칙은 Harold 확인]**. 범위 밖 422.
- 전이:
  - 자동 정책 회사: 지금처럼 `confirmed`(+비고 저장) → 워커가 정책 날짜에 발행, 비고1에 PO.
  - 직접선택 회사 + 날짜 제공: **관리자 라우트의 트랜잭션을 CT로 추출해 공유**(`utils/taxbill-manual-queue.ts` [설계] —
    컨펌 관문·비고·`ready` 전이·`taxbill_issues` INSERT·취소 이력 관문을 한 함수로). 관리자 라우트와 공개 라우트가 **같은 함수**를
    부른다(두 벌 금지 — 발행 코어 추출과 같은 이유).
  - 직접선택 회사 + 날짜 미제공: 지금처럼 컨펌 시각만(운영자가 지정) — 날짜칸이 필수는 아니다(고객이 비워 두면 현행 경로).
- 멱등: 이미 `confirmed_at`이 있으면 200 + 현재 상태(두 번 눌러도 두 장 안 된다 — 기존 조건 `confirmed_at IS NULL` 유지).

### 3-3. 메일 (`utils/invoice-confirm.ts`) [설계]
- 필수 회사에만 한 줄 추가: "세금계산서 비고에 들어갈 **PO번호**를 확인 화면에서 입력해 주세요." 버튼은 그대로 하나.
- 두 발송 경로(일괄·개별)가 같은 조립 함수를 쓰므로 한 곳만 고친다(§2 사실 4).

### 3-4. 운영자 화면 [설계]
- 컨펌 현황 행: 0821(2)의 "비고 PO-xxxx" 표시가 그대로 고객 입력분을 보여준다. 추가 = "고객 입력" 표식(운영자 입력과 구분 — `confirm_note`와 같은 감각).
- 정정은 [작성일자 변경](채번 전 화이트리스트) 그대로.

## §4 안전장치 — 전부 기존 계약 재사용

| 위험 | 막는 것 |
|---|---|
| PO 없이 발행 | 발행 패스 게이트(§2-20) — 페이지 필수 검증은 앞단 |
| 엉뚱한 작성일자 | 서버 범위 검증 + 워커 날짜 게이트(미래면 그날) |
| 링크 유출로 임의 컨펌 | 기존 수준 그대로 — 컨펌은 이미 그 회사의 의사표시이고 발행을 개시한다(§2-13) |
| 두 번 눌러 두 장 | `confirmed_at IS NULL` 조건 + `taxbill_issues` NOT EXISTS 멱등(관리자 라우트와 같은 함수) |
| 컨펌 뒤 PO 정정 | 채번 전 = [작성일자 변경] 화이트리스트 ① |
| 이의신청과 충돌 | 이의신청이 `ready` 장부를 취소하는 기존 경로 그대로 |

## §6 단계

1. 0821(2) 배포분 실측 1건(시세이도 — 입력 → 비고1 인쇄) **선행** — 자동화는 그 위에 얹는다
2. CT 추출(관리자 라우트 동작 무변경) → 공개 페이지 입력·검증·전이 → 메일 문구 → 계약 테스트
3. Codex 적대(국세청 문서 경로) → 배포 → 시세이도 실측: 메일 수신 → PO·작성일자 입력 → 컨펌 → 그 날짜 자동 발행 → 비고1 확인

## §7 미확인 (착수 전 Harold 확인)

- 작성일자 허용 범위의 세무 기준(공급월 익월 10일까지가 맞는지 · 시세이도 부서가 통보하는 날짜가 이 범위 안인지)
- 시세이도가 한 달에 **계정(부서)별 장**을 여러 개 받는지(`by_user`) — 그러면 PO는 장마다 다르고 페이지도 장마다 열린다(현 구조로 자연 성립 — 확인만)
- 고객 입력 PO의 형식 제약이 필요한지(지금은 150자 자유 문자열)

## §8 ⛔

- 메일 본문에 입력폼을 넣지 않는다(제출 보장 없음). 페이지가 받는다.
- 공개 라우트에 직접선택 전이를 **따로 구현하지 않는다** — 관리자 라우트와 같은 CT를 부른다(두 벌 = 한쪽만 고쳐진다).
- 비고 필수 회사의 컨펌은 비고 없이는 받지 않는다 — 받아 두고 나중에 멈추면 자동화의 의미가 없다.
- 채번 후 정정 경로를 새로 만들지 않는다(§2-19 화이트리스트 그대로 — Codex 4R·5R 경위).
