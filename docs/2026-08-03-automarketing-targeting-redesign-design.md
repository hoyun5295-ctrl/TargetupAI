## §0 범위

**대상** — 자동마케팅(Continuous Operator)의 **대상 선정 축 전부**: 목표 자연어 해석 → 필터 생성 → 대상 수 검증 → 발송 시점 재추출 → 담당자 사전 통지에 실리는 수치까지.

**제외** — 문안 생성 품질·스팸 재생성·채널 판정·과금. 이번에 건드리지 않는다(타겟 축이 확정돼야 그 위가 의미 있다).

**왜 지금인가** — 여정은 2026-08-02에 트리거 축을 다 세웠고, 싱크에이전트는 2026-08-03에 데이터 유입을 고쳤다. **데이터가 들어오고 사건 축이 서는 지금이 조건 축을 세울 차례**다. 유료 요금제 업체가 없어 파괴적 변경을 할 수 있는 창도 아직 열려 있다.

## §1 현황 — 전수점검 실측 (2026-08-03)

### §1-1 타겟 선정 경로 (코드 실측)

```
목표 자연어(operator.objective)
  → [선택] targetHint 6종 지시 블록          autosend-policy.buildTargetHintPromptBlock
  → detectActiveFields(companyId)            services/ai.ts:1475
       · 이 회사에 값이 있는 컬럼만 추림(COUNT FILTER)
       · 문자열 컬럼은 DISTINCT 실측 값 200개까지 조회
       · 커스텀 필드 라벨(customer_field_definitions)
  → buildFilterFieldsPrompt                  services/ai.ts:1542
       · "이 고객사에 실제 데이터가 있는 필드만 표시"
       · "목록에 없는 값은 절대 사용 금지"
  → recommendTarget (Opus)                   services/ai.ts:1586
       → filters { 필드: {operator, value} }
  → countFilteredCustomers                   실제 DB count로 검증(AI 추정치 아님)
  → 0건이면 제안 미생성                       no_target_auto_relax
  → proposal_json.target.filters 저장
  → [발송 시점] buildSendableStagingInsertSql  operator-recipients.ts
       · 같은 filters를 CT-01로 재컴파일 + 안전필터 + 미클릭 + 피로도
```

### §1-2 이미 잘 되어 있는 것 (건드리지 않는다)

- **필드 축은 이미 런타임 판정이다.** `detectActiveFields`가 그 회사에 실제 값이 있는 컬럼만 AI에 노출하고, 문자열 값은 DISTINCT 실측 목록을 준다. 정답표를 안 갖는다는 원칙이 여기는 이미 지켜져 있다.
  ⛔ **앞선 세션 대화에서 "축 6종이 정답표"라고 한 진단은 부분적으로 틀렸다.** 필드·값 축은 데이터 기반이다. 틀린 것은 **사건 축**이지 필드 축이 아니다(§2).
- **AI 추정치를 안 믿는다** — `countFilteredCustomers`가 실제 DB count로 덮어쓴다.
- **0건 자동완화 없음** — 제안 자체를 안 만든다.
- **보여준 명단 = 나가는 명단** — 미리보기와 발송 추출이 같은 WHERE 합성(`operator-recipients.ts` 주석 계약).
- **안전필터 단일화** — `buildJourneySafetyFilter` 하나를 여정과 공유.

### §1-3 대상 축 어휘 (현재 가능한 전부)

| 축 | 소스 | 비고 |
|---|---|---|
| 인구 | `gender` `age` `birth_date` `region` `address` | `age`는 `birth_date` 폴백 있음 |
| 등급·매장 | `grade` `store_code` `store_name` | DISTINCT 실측 값으로 고정 |
| 구매 요약 | `purchase_count` `total_purchase_amount` `recent_purchase_date` `avg_order_value` | **`customers` 요약 컬럼** — 원장이 아니다 |
| 포인트 | `points` | |
| 커스텀 | `custom_1~15` | 라벨·값 실측 |
| 제외 축 | 미클릭(`excludeClickedSince`) · 피로도(`fatigueCap`) | 조건이 아니라 안전장치 |

**여기 없는 것** — `purchases` 원장 · `cdp_events`(장바구니·상품조회·배송) · `customer_grade_ranks` 서열 · 여정 진입 원장.

## §2 진단 — 정확히 무엇이 문제인가

### §2-1 사건 축이 없다 (핵심)

자동마케팅이 아는 세계는 **`customers` 한 장의 현재 스냅샷**이다. "무엇을 했는가"는 그 회사가 요약 컬럼(`recent_purchase_date` 등)을 채워 줄 때만 간접적으로 보인다.

- 원장(`purchases`)에 구매가 들어와도 **요약 컬럼이 갱신되지 않으면 자동마케팅은 그 구매를 모른다**(갱신은 `updateCustomerPurchaseAggregates`가 적재 시점에 하지만, 자사몰 경로·수기 업로드 경로가 다르다).
- "지난달 A 상품 산 사람"·"장바구니 담고 안 산 사람"·"등급 오른 사람" 같은 **행동 조건은 표현 자체가 불가능**하다.
- 여정은 이 축을 이미 갖고 있다(원장 커서·이벤트 커서·등급 서열). **같은 회사, 같은 데이터인데 여정은 보고 자동마케팅은 못 본다.**

### §2-2 축(targetHint)과 데이터 판정이 연결돼 있지 않다

`TARGET_HINTS` 6종은 **자연어 지시**로만 전달된다 — "휴면 = 최근 구매(또는 방문) 기록이 오래된 고객. 회사 스키마에서 최근 구매일/방문일 필드를 찾아 구성한다."

- 그 회사에 `recent_purchase_date`가 비어 있으면 `activeColumnFields`에 안 나오고, AI는 **다른 필드로 대체하거나 빈 필터를 만든다.** 무엇이 나올지 계약이 없다.
- 화면은 6종을 항상 다 보여준다 — **"이 회사에서 이 축이 되는가"를 판정하지 않는다.** 여정이 `journey-trigger-capability`로 푼 문제가 여기는 안 풀렸다.

### §2-3 결정성이 없다

같은 목표·같은 데이터인데 **회차마다 AI가 다시 해석**한다.

- 매일·매주·매월 실행 때마다 `recommendTarget`이 새로 돈다. 지난달과 같은 조건이라는 보장이 없다.
- `targetHint`는 축만 고정하고 **필터 형태는 고정하지 않는다.**
- 담당자가 "지난번이랑 왜 다르지"를 확인할 근거(직전 회차 filters와의 차이)가 화면에 없다.

### §2-4 0건이 조용하다

`shouldSkipProposalGeneration`/0건 미생성은 **오발송은 막지만 사유를 안 알린다.** 담당자는 "왜 이번 달은 아무것도 안 왔지"를 알 길이 없다. 여정이 "조용한 0건은 우리가 고치려는 병 자체"라고 못 박은 것과 같은 자리다.

### §2-5 사전 통지가 확정 수치를 말하는지 미확인

발송 2시간 전 담당자 통지(`notifyOperatorAdmins`)는 발송 일시·추출 타겟 수·예상 비용·정지 안내를 보낸다. 그런데 그 수치가 **제안 생성 시점 count**인지 **발송 시점 재추출 count**인지 코드로 확정하지 못했다. 둘은 다를 수 있다(그 사이 고객 유입·수신거부·피로도 제외).
→ 착수 1번에서 확정한다. 다르면 통지가 실제와 어긋나는 것이고, 그건 담당자가 판단을 잘못하게 만든다.

## §3 설계 원칙 (여정에서 가져오되 이 축에 맞게)

1. **정답표를 갖지 않는다** — 무엇이 가능한지는 그 회사 데이터가 런타임에 정한다. 필드 축은 이미 그렇다. **축(세그먼트) 축도 그렇게 만든다.**
2. **결정성** — 같은 조건 + 같은 데이터면 언제 돌려도 같은 명단. AI는 **조건을 만들 때 한 번만** 쓰고, 회차 실행은 저장된 조건을 **그대로 재사용**한다.
3. **근거성** — 조건에 쓰인 근거가 실제로 존재할 때만 그 축을 연다. 없으면 정직하게 잠그고 사유를 보여준다.
4. **동일성** — 화면이 보여준 수 = 사전 통지에 간 수 = 실제 나간 수. 셋이 다르면 하나는 거짓이다.
5. **조용한 0건 금지** — 대상이 0이면 사유와 함께 담당자에게 알린다.
6. **여정 축을 재사용한다** — 원장·이벤트·등급 서열 판정은 이미 CT가 있다. 복제하지 않고 공유한다.

## §4 목표 구조

### §4-1 세그먼트 축을 계약으로 (여정 `TRIGGER_CONTRACTS`의 자매)

`TARGET_HINTS` 6종(자연어 지시)을 **세그먼트 계약 레지스트리**로 승격한다.

```
utils/automarketing-segment.ts (신규 CT)
  SEGMENT_CONTRACTS: 각 축마다
    key            'dormant' | 'recent_buyers' | 'vip' | 'birthday' | 'new_customers' | 'all' | (확장)
    label          화면 표시명
    requires       판정에 필요한 근거(필드·원장·서열표)
    buildPredicate 그 축의 SQL 조각을 만드는 함수(파라미터화)
    params         담당자가 조절하는 값(휴면 N일·최근 N일 등)과 기본값
```

- **`requires`가 런타임 판정의 근거다.** 여정 `resolveTriggerAvailability`와 같은 형태로 회사별 facts를 조회해 열림/잠김을 정한다. 잠기면 사유를 그대로 화면에 노출한다("최근 구매일 데이터가 없어 휴면 축을 쓸 수 없습니다").
- **`buildPredicate`가 결정성을 만든다.** 축이 정해지면 SQL이 정해진다 — AI 해석이 개입하지 않는다.
- 화면·캘린더·제안 생성이 이 레지스트리 하나만 본다(인라인 금지).

### §4-2 어휘를 행동으로 넓힌다 — 여정 축 재사용

세그먼트 계약이 쓸 수 있는 근거를 넓힌다. **새로 만들지 않고 여정이 이미 세운 것을 공유한다.**

| 넓히는 축 | 근거 | 재사용할 것 |
|---|---|---|
| 구매 이력(기간·금액·횟수) | `purchases` 원장 + `cdp_events` 양 문 | `journey-target-extractor`의 양 문 합산 패턴 |
| 상품·매장 | `purchases.product_code/store_code` | — |
| 등급 상승 | `customer_grade_ranks` | `customer-grade-rank` CT 그대로 |
| 장바구니·상품조회 | `cdp_events` | 여정 추출 SQL 패턴 |
| 여정 미진입 | `journey_executions` | 자동마케팅과 여정이 같은 사람에게 겹치는 것을 담당자가 조절 |

⛔ **원장을 복사하지 않는다**(여정 §11-C-0의 재적용). 직독한다.
⛔ **`purchases.purchase_date`는 KST 날짜(시각 없음)**, `created_at`은 UTC 벽시계다. 기간 조건을 걸 때 축을 명시한다([싱크에이전트 §4](FEATURE-SYNC-AGENT.md)).

### §4-3 AI의 자리를 바꾼다 — 매 회차 해석 → 최초 1회 설계

| 지금 | 바꾼 뒤 |
|---|---|
| 매 회차 `recommendTarget`이 목표를 다시 해석해 filters 생성 | **등록 시 1회** — AI가 목표를 읽고 **세그먼트 축 + 파라미터**를 제안, 담당자가 확인하면 그것이 계약으로 저장 |
| 회차마다 filters가 달라질 수 있음 | 회차 실행은 저장된 계약을 `buildPredicate`로 컴파일 — **항상 같은 조건** |
| 담당자가 무엇이 뽑히는지 회차 전에 모름 | 등록 시점에 대상 수·표본 명단을 보고 확인 |

**AI는 여전히 쓴다** — 자연어를 축·파라미터로 옮기는 자리(1클릭 UX 유지)와 문안 생성. 다만 **대상 판정은 AI가 하지 않는다**(`feedback_prediction_never_selects_target`의 연장 — 예측만이 아니라 해석도 매 회차 반복하면 안 된다).

### §4-4 조용한 0건을 없앤다

회차 실행에서 대상이 0이면 제안을 안 만들되 **사유를 남기고 담당자에게 알린다** — "이번 회차 대상 0명(휴면 90일 조건에 해당하는 고객이 없습니다)". 여정이 트리거 정지에 사유를 남기는 것과 같은 형태.

### §4-5 사전 통지를 확정 수치로

발송 2시간 전 통지에 **발송 시점 재추출 기준 수**를 싣는다. 제안 생성 시점 수와 다르면 그 차이도 함께("등록 시 1,240명 → 발송 시점 1,198명, 수신거부·발송 피로도 제외"). 담당자가 정지 여부를 판단하는 유일한 화면이라 실제와 어긋나면 안 된다.

## §5-B 남은 착수 순서 — **2026-08-03 확정(다음 세션 이 순서로)**

> 아래 §5는 0803 착수 전에 세웠던 원안이고, 실측(실사용 오퍼레이터 0)으로 1~3을 한 조각으로 합쳐 끝냈다.
> 지금 남은 것은 이 순서다. **①이 원래 진단 1번(사건 축이 없다)이고, 이게 빠지면 재설계는 절반이다.**

**① 행동 축 확장** — 계약 어휘를 `customers` 스냅샷 밖으로 넓힌다(§4-2 표 그대로).
구매 원장 직독 · 상품·매장 · 등급 상승 · 장바구니·상품조회 · 여정 미진입.
축마다 `requires` 근거 판정과 `buildPredicate`를 붙인다. 여정이 세운 축을 재사용하고 복사하지 않는다.
⛔ `purchases.purchase_date`는 KST 날짜, `created_at`은 UTC — 기간 조건에 축을 명시한다.

**② 리마인드 되살리기** — 1차 수신자 코호트를 **발송결과에서** 얻는다(새 표 만들지 말 것 — 기능 문서 §5).
리마인드 = 1차 수신번호 ∩ 지금 안전필터 ∩ 미클릭 ∩ 피로도. 스팸 검증도 함께 붙인다.
착수 전 확인 5 = LIVE/LOG 분리 · `app_etc1` 축(campaigns.id vs campaign_runs.id) · `dest_no` 하이픈 정규화 ·
LOG 월 테이블 경계 · MySQL↔PG 직접 조인 불가.

**③ 신규 등록에 계약 필수화** — 자연어·시나리오·오늘의 추천 흐름에 축 선택을 배선한다.
지금은 세부설정 모달만 계약을 고를 수 있어 **기본 등록 경로에는 결정성이 적용되지 않는다.**

**④ DDL → 빌드 → 화면 실측 → 배포** — 컬럼 3개(`zero_target_notified_at`·`segment_key`·`segment_params`,
두 세그먼트 컬럼은 동시 추가). 실측 = 축 잠금·사유 표시·실측 대상 수·계약 저장 왕복·0건 통지.

**범위 밖(각각 별도 트랙)** — 일회성 발송 경로 통합(`preview-recipients` 축, 발송 파이프라인 보호 영역이라 영향표 선행) ·
`routes/manage-users.ts:216` 역할값 보안 건.

## §5 착수 순서 (0803 착수 전 원안 — 1~3은 한 조각으로 합쳐 완료)

1. **사전 통지 수치 축 확정**(§2-5) — 통지가 어느 시점 수를 말하는지 코드로 확정하고, 발송 시점 기준으로 통일. 가장 작고 즉시 사용자에게 보이는 정정.
2. **세그먼트 계약 레지스트리 신설**(§4-1) — 현행 6종을 계약으로 옮기고 `requires` 런타임 판정 + 화면 잠금·사유 노출. **동작 변화 없음**(같은 6종을 계약으로 표현만) — 여기서 회귀가 없어야 3번이 안전하다.
3. **결정성 전환**(§4-3) — 등록 시 축·파라미터 확정, 회차 실행은 재해석 없이 컴파일. 기존 운영 중 오퍼레이터는 저장된 filters를 그대로 쓰는 호환 경로 유지(마이그레이션 금지 — 옛 것은 옛 방식으로 계속 돈다).
4. **어휘 확장**(§4-2) — 구매 이력·상품·등급 상승·장바구니 축 추가. 축마다 `requires` 판정이 붙어 데이터 없는 회사에서는 자동으로 잠긴다.
5. **0건 통지**(§4-4) · 화면 정리(축 선택·파라미터·표본 명단).

1·2는 회귀 없는 정지작업이고 3이 축을 바꾼다. 4는 3이 끝나야 의미가 있다(계약이 있어야 축을 더한다).

## §6 착수 전 확인이 필요한 것

**Harold님 확인 2건** — 물어볼 값인 것만 남겼다(정답표가 되는 질문은 뺐다).

1. **자동마케팅과 여정이 같은 사람에게 겹치는 것을 어떻게 할지.** 지금은 서로 모른다. 겹침을 막을지(여정 진입자 제외 조건 제공), 알리기만 할지, 그대로 둘지는 상품 결정이다.
2. **기존 운영 중 오퍼레이터를 새 계약으로 옮길지.** 옮기지 않으면 옛 방식으로 계속 돌고(안전), 옮기면 대상이 달라질 수 있다(동작 변화). 기본은 **옮기지 않음**으로 설계했다.

**물어보지 않을 것** — "어느 고객사가 어떤 데이터를 가졌나". 런타임 판정이 답한다(여정 §10 미결 2와 같은 이유).

## §7 검증 방법

여정 전수점검에서 쓴 잣대를 그대로 적용한다 — **③까지만 하면 숫자가 나와도 맞는 숫자인지 모른다.**

| 단계 | 무엇 |
|---|---|
| ① | 그 축이 읽는 표·컬럼을 계약에서 그대로 나열 |
| ② | 대상 회사에 그 컬럼이 실재하는지(`information_schema`) + 값이 실제로 채워져 있는지 카운트 |
| ③ | 발송 없이 추출만 돌려 대상 수·표본 명단 확보 |
| ④ | **역검증** — 뽑힌 사람이 조건을 실제로 만족하는지 원본에서 되짚어 위반 0건 |
| ⑤ | **누락검증** — 조건을 만족하는데 안 뽑힌 사람이 있는지 조건을 뒤집어 교차 확인 |

**표본** — 싱크 연동은 이새 하나뿐이고 자사몰 연동은 없다. `cdp_events` 축(장바구니·상품조회)은 **미검증으로 남는다** — 0건이 나와도 통과가 아니라 표본 없음이다.

## §8 이 트랙이 절대 하지 말 것

- **예측으로 타겟을 고르지 않는다**(`feedback_prediction_never_selects_target`). 추천·개인화·send-time에만 예측을 쓴다.
- **0건 자동완화 금지**(`no_target_auto_relax`) — 어떤 경로에도 넣지 않는다.
- **AI가 구체 혜택(%·원·쿠폰·무료)을 만들지 않는다** — 타겟 축을 바꿔도 문안 규칙은 그대로.
- **원장 복사 금지** — 직독한다.
- **마이그레이션은 배포 뒤에** — 워커가 트래픽과 무관하게 돈다.
