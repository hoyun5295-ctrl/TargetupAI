> **호출어 = "자기 개선 루프" 또는 "AI 학습".** 이 문서가 학습 자산·환류 배선·루프 단계의 구조·불변 원칙·이력을 **전부 소유한다.**
> STATUS는 경로만 갖는다. 여기 있는 것을 다른 문서에 복사하지 않는다.
>
> 신설 = 2026-08-11(Harold 지시). 그전까지 이 축은 여러 파일 주석과 세션 기억에만 흩어져 있어,
> "무엇이 학습되고 있고 무엇이 안 되고 있는가"를 매번 코드에서 다시 찾아야 했다.

## §2 정체성 — 우리는 아직 모델을 학습시키지 않는다

**현재 상태 = 검색 자산(retrieval corpus)이지 학습 자료가 아니다.**

`ai_training_logs`는 비식별 문안 코퍼스를 쌓고, 실제 소비처는 `copy-rag-retriever.ts` **하나**다.
생성 직전에 과거 문안을 꺼내 프롬프트에 넣는 **검색(RAG)**이라 **모델 가중치는 바뀌지 않는다.**
`training-logger.ts` 주석의 "향후 인비토AI(메시징 특화 모델) 학습 데이터셋"은 **의도를 적어둔 것**이고 아직 그 단계가 아니다.

**LLM인가 SLM인가**(2026-08-11 Harold 질문) — **지금은 둘 다 아니다.** 학습 대상 모델 자체가 없다.
다만 언젠가 실제 학습을 한다면 **SLM이 맞는 판단**이다: 태스크가 하나(한국어 마케팅 단문 생성), 길이 제약이
강하고(SMS 45자·LMS), 도메인 어휘가 좁고, 호출당 원가가 손익 지렛대라 범용 대형 모델의 능력이 필요 없다.

**⛔ 그러나 순서를 뒤집지 마라.** 지금 코퍼스에는 **성과 라벨이 거의 없다.** 무엇이 잘 됐는지 표시가 없는
문장 뭉치로 학습하면 "그럴듯한 문장"밖에 안 나온다. **Phase 0~1이 그 라벨을 만드는 일**이고,
라벨이 쌓인 뒤에야 SLM 논의가 근거를 갖는다. 라벨 없는 코퍼스로 학습을 시작하는 것이 이 트랙의 가장 큰 함정이다.

## §3 불변 원칙 (어길 수 없는 것)

### 3-1. 루프가 조정하는 축은 **문안·시각 둘뿐**이다 — 타겟은 절대 아니다
예측으로 타겟을 고르지 않는다는 영구 원칙 그대로다. 루프는 "누구에게 보낼지"를 건드리지 않는다.
타겟 축에 걸리는 것은 기존 제외 게이트(발송 피로도·미클릭·수신거부)뿐이고, 그건 학습이 아니라 안전장치다.

### 3-2. 사람 승인 흐름을 없애지 않는다
Bandit이 이긴 변이를 고르고 루프가 다음 문안을 제안해도, **발송은 사람이 승인한 뒤에** 나간다.
"AI가 알아서 점점 잘하는 마케팅 직원"이지 "AI가 알아서 보내는" 것이 아니다.

### 3-3. 못 센 것을 0으로 만들지 않는다
클릭을 셀 수 없는 캠페인(단축 URL이 없는 문안)은 `null`이고 0이 아니다. 0으로 넘기면 "클릭 0회"로 학습돼
**링크 없는 문안이 영원히 하위로 밀린다.** `updateTrainingMetrics`는 `null`이면 클릭 열을 아예 안 건드린다(기존 값 보존).

### 3-4. 보상의 단일 진실은 **실측 count 컬럼**이다
α/β를 증분 갱신하지 않는다. `sent_count`/`click_count`만 적재하고 선택·통계 시점에 `deriveBanditArm`이 도출한다.
2026-06-26 이전 구조가 증분 갱신이었는데, 클릭 호출부가 `sent=0`으로 불러 가드에 막히면서 **α는 안 오르고 β만 쌓여
모든 변이가 동등 하락 = 학습 정지**했다(operator·journey 공통 버그). 같은 형태를 다시 만들지 않는다.

### 3-5. 환류 실패가 발송·워커를 막지 않는다
학습 적재·환류는 전부 fire-and-forget 격리다. 적재가 실패해도 발송은 나가고 워커는 돈다.

## §4 구조 — 신호가 어디서 나서 어디로 가는가

| 자산 | 소유 파일 | 무엇 |
|---|---|---|
| 문안 코퍼스 | `utils/training-logger.ts` | `ai_training_logs` 적재·성과 갱신. 키 = `source_ref = hmacHash(campaignRunId)` |
| 성과 문안 검색 | `utils/copy-rag-retriever.ts` | 생성 직전 고성과 문안 인출. **`click_count`가 있으면 클릭률 정렬**, 없으면 최신순 폴백 |
| 변이 보상 | `utils/bandit-arm.ts`(순수) · `utils/bandit-optimizer.ts`(CT-31) | Beta(α,β) 도출 + Thompson Sampling |
| 클릭 수신 | `routes/short-url.ts` · `utils/short-url.ts` | hlj.kr 클릭 → `message_short_urls.click_count` + 변이 테이블 보상 |
| 구매 전환 귀속 | `utils/operator-conversion-attribution.ts` | 발송 +7일 창이 닫힌 건만 1회 확정 귀속 |

### 4-1. `source_ref` 축 — 경로마다 다르다 (틀리면 조용히 0행 no-op)

| 경로 | 적재 시 넣는 값 | 성과 갱신 시 써야 하는 값 |
|---|---|---|
| AI 캠페인 | `campaignRun.id` (`campaigns.ts:1088`) | `getSourceRef(run.id)` |
| 직접발송 | **`campaignId`** (`campaigns.ts:2460` — run이 없어 캠페인 id를 그 자리에 넣는다) | `getSourceRef(campaign.id)` |
| 모바일 DM | `dm_id` | `getSourceRef(dm_id)` |

**축을 틀리면 에러가 안 난다** — `WHERE source_ref = $1`이 0행에 걸려 아무 일도 안 일어나고 로그도 정상으로 보인다.
새 채널을 환류에 붙일 때 **적재 호출부부터 찾아 같은 값을 쓴다.**

### 4-2. 채널별 환류 현황 (2026-08-11 Phase 0 이후)

| 채널 | 변이 테이블(Bandit) | 문안 학습 원장 |

| 이메일 | — | 흐름 (`updateTrainingEngagement`) |
| **SMS·LMS·MMS** | 흐름 (short-url → 변이 `click_count`) | **★2026-08-11 연결됨**(Phase 0) |

## §6 단계 (Phase) — 착수 원장

### Phase 0 — 문자 클릭을 학습 원장에 배선 ★2026-08-11 코드완료

**문제**: 문자 클릭이 `message_short_urls`와 변이 테이블에만 쌓이고 **문안 학습 원장에는 안 들어갔다.**
받는 쪽(`copy-rag-retriever`)은 `click_count`가 있으면 클릭률로 정렬하게 **이미 만들어져 있었는데** 값이 없어
최신순으로 떨어지고 있었다. 즉 "쓸수록 문안이 좋아진다"가 주력 채널에서만 멈춰 있었다.

**한 것**
- CT `getCampaignClickTotal(campaignId)` 신설(`utils/short-url.ts` — 그 테이블의 소유 파일).
  캠페인 1건의 단축 URL 클릭 **합계**(링크를 여럿 담을 수 있다). **단축 URL이 0개면 `null`**(§3-3).
- `campaign-lifecycle.ts` 결과 동기화 2경로에 `clickCount` 동반 — AI 캠페인(`run` → `runInfo.campaign_id` 기준) ·
  직접발송(`campaign.id` 기준). 두 경로 다 `updateTrainingMetrics` 호출은 **원래 있었고 클릭만 빠져 있었다.**
- `TrainingMetricsParams.clickCount`를 `number | null`로 넓혀 "못 셌다"를 계약에 명시.

**멱등** = 기존 성질 그대로. `updateTrainingMetrics`는 절대값 SET이라 동기화가 돌 때마다 최신 누적으로 덮어쓴다.
**DDL 0** — `ai_training_logs.click_count`·`conversion_count`는 2026-08-11 `information_schema` 실측으로 실존 확인
(SCHEMA.md의 "0704 ADD 대기" 표기가 낡은 기록이었다). `message_short_urls`도 같은 날 14컬럼 덤프로 확인.

**⚠ 남는 한계(설계상 인정)**: **동기화 대상에서 빠진 뒤 들어온 클릭은 반영되지 않는다.**
클릭은 발송이 끝난 뒤에도 며칠 이어지는데 결과 동기화는 캠페인이 완료되면 대상에서 빠진다.
늦게 온 클릭을 걷어 오는 별도 환류 스윕이 필요하고, 그건 아래 Phase 1에 붙인다.

### Phase 1 — 승자 환류 (미착수)

회차 마감 시 변이 성적(발송·클릭·전환)을 학습 원장에 확정 기록 → RAG 성과 정렬 가동 →
조립기 프롬프트에 **"직전 승자 변이 원문 + 성과 수치"**를 명시 투입.
지금은 Bandit이 **이번 제안 안에서** 이긴 변이를 고를 뿐, 다음 제안의 3안은 백지에서 새로 생성된다 —
이긴 문안이 **왜** 이겼는지(길이·훅·CTA형)가 다음 생성에 안 들어간다.
RAG(전사 검색)와 달리 **같은 오퍼레이터의 직전 회차**라는 가장 강한 신호를 쓰는 것이 이 단계의 핵심이다.
혜택 문구 복제 금지 원칙은 그대로 유지한다. Phase 0의 "늦은 클릭 스윕"도 여기서 함께 만든다.

### Phase 2 — 발송 시각 환류 (미착수)

회사별 클릭 시각 분포(실측)로 다음 회차 발송 시각 추천 + 사전 통지에 근거 1줄.
표본 미달이면 기존 시각 유지 + "학습 중" 표시(임의 상수·자동완화 금지).
send-time은 예측 허용 축이다(타겟 선정만 금지 — §3-1).

### Phase 3 — 학습 카드 (미착수)

자동마케팅·여정 상세에 "지난 회차 변이 성적표 + 이번 회차에 반영된 것 1줄".
**배운 것이 안 보이면 배운 적 없는 것과 같다** — 영업 시연의 한 방이 여기인데 지금 비어 있다.
아웃바운드 브리핑(별 축)에 그대로 실을 수 있는 단위로 만든다.

## §8 뒤집힌 판단 (다시 꺼내지 않기)

- **α/β 증분 갱신** — 클릭 호출부가 `sent=0`으로 부르면 가드에 막혀 α가 안 오른다. 실측 count에서 도출하는 방식으로 2026-06-26 확정(§3-4).
- **예측으로 타겟 선정** — 영구 금지. 루프의 조정 축은 문안·시각뿐이다(§3-1).
- **"라벨 없이 먼저 학습"** — 성과 표시가 없는 코퍼스로는 그럴듯한 문장만 나온다. Phase 0~1이 선행이다(§2).
