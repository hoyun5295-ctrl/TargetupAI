## §2 서버

### S1 적재 마감 CT(`utils/operator-recipients.ts sealServerStaging`)

`routes/ai.ts` 1185 ~ 1218 의 순서를 함수로 **옮긴다**(복사해 새로 쓰지 않는다 · 옮긴 뒤 그 자리는 호출 한 줄).

- 입력 = `{ stagingId, companyId, userId, userType, adEnabled, individualCallback, sendPlan: { scheduled, scheduledAt, splitEnabled?, splitCount?, splitIntervalMinutes? }, branch }`.
- 순서 = 중복 제거 → (개별 회신) 제외 → 광고 관문(`mode: 'load'`) → 서명 → 표본 100 · 기본 회신번호.
- **광고 관문의 기간 = 확정과 같은 함수** `directSendSpanOf(sendPlan, 관문 전 인원)`(`ad-send-gate.ts` 267 · 관문 전 인원 = 확정이 쓰는 `countStagingFiltered` 와 같은 세기). 나눔이 없으면 이 함수는 `sendSpanOf(예약이면 그 시각)` 을 그대로 돌려준다(같은 파일 273 줄) = **AI 한줄로가 지금 넘기는 값과 같다** → AI 한줄로는 `sendPlan` 에 예약 값만 넘긴다(동작 같음 · 순수 시험으로 고정).
- 출력 = `{ signature, total, excluded: { duplicates, callback, adGate? }, adGateNotice?, sample, defaultCallback }`. 광고 관문 장애(`AdGateUnavailableError`)는 지금처럼 밖으로 던진다(부른 주소의 공용 오류 처리).

### S2 한 줄로 묻기 적재(`POST /api/ai-line/ask/stage`)

- 입력 = `{ plan, message, individualCallback?, scheduled?, scheduledAt?, splitEnabled?, splitCount?, splitIntervalMinutes?, adEnabled }`(`plan` 에 문자 종류 포함 · S3 · `message` = 확정에 실을 본문).
- 순서: `lineGate` → `readAskPlan` → 나눔 값 검사(확정과 같은 `parseSplitSetting` · 틀리면 400) → **나가는 종류**(S4-b · `plan.channel` 과 `message` 로 다시 정한다) → 단가(`readAskPrice(회사, 나가는 종류)`) → 상한(`askLimit`) → **적재 한 문장**(`ask-segments.ts askStagingInsertSql` = 아래 S2-a 의 `picked` 에서 순서 · 상한 그대로 `INSERT INTO campaign_send_staging (staging_id, company_id, phone, name[, callback])` · 개별 회신이면 `callback` = 그 고객의 매장 번호) → `sealServerStaging`(나눔 값 포함) → 응답 `{ stagingId, signature, total, channel, unitPrice, amount, excluded, adGateNotice?, sample }`.
- **칼럼이 든 문안**(D12): 서버가 `message` 로 판정한다 = S4-b 의 본문 판정 `sendBodyVars(message, 그 회사 매핑 이름들).needsCustomer`(고객 원장을 찾아야 채워지는 변수가 있는가 · 화면이 주는 불리언을 믿지 않는다 · 생성용 칼럼 표 `aiLineVarTokensFor` 는 쓰지 않는다). 참이면 적재 문장이 「대표 행의 저장 번호 ≠ 숫자 꼴」 고객을 빼고 그 수를 `excluded.unfillable` 로 싣는다(없으면 그 칸 0).
- 0명 = 400 「보낼 수 있는 분이 없어요」(적재 줄을 지운다).
- 화면의 확인 창 인원 = `total`(서명이 센 수 = 중복 · 회신번호 · 광고 관문 · 수신거부 · 칼럼을 못 넣는 분을 뺀 실제 발송 수). `/direct-send/count` 를 더 부르지 않는다.
- 확정 = `POST /direct-send/commit { stagingId, signature, msgType = 적재 응답의 channel, 같은 예약 · 나눔 값, … }` · 화면은 적재 뒤 확인 창에서 예약 · 나눔 · 본문을 바꿀 수 없다(바꾸려면 창을 닫는다 = 다음 보내기가 새로 적재) · 명단이 달라졌으면 409 `RECIPIENTS_CHANGED` → C153 접수 판정 그대로(접수 상태 없음 + 서버 본문 거절 = 그 문구 + 준비분 놓음 → 다시 누르면 새로 적재).
- `POST /ask/audience` · `listAskAudience` = 이번에 지우지 않는다(D14 · 옛 화면 번들용 · 대상 문장은 S2-a 의 같은 것).

### S2-a 대상 한 문장(`ask-segments.ts askAudienceSql` 고침)

- 번호 = `regexp_replace(c.phone, '[^0-9]', '', 'g')`(숫자만) · 빈 값은 대상 아님 · 번호 하나 = 한 사람.
- 대표 행 = `ORDER BY 번호, (c.phone = 번호) DESC, <지금 순서 askOrderSql>, c.id`(저장된 번호가 숫자 꼴인 행이 있으면 그 행 = 일꾼이 `phone = 번호` 로 찾는 행 · 회사 안에서 `phone` 은 유일하므로 그런 행은 하나뿐이다).
- `picked` 의 칸 = id · phone(숫자만) · name · 순서 칸 · cell · `plain`(저장된 번호 = 숫자 꼴인가).
- 쓰는 곳 = 세기(`countAskCells` · `countAskPlan`) · 적재(`askStagingInsertSql`) · 표본(S5) · 옛 명단(`listAskAudience`) = **같은 CTE**(인원 · 사람 · 순서가 어긋나지 않는다).
- 달라지는 값: 꼴만 다른 같은 번호를 지금은 두 명으로 세던 것이 한 명이 된다(적재 뒤의 수와 같아진다).

### S3 문자 종류 · 단가

- `AskPlanInput.channel: 'SMS' | 'LMS' | 'MMS'`(없으면 `LMS` = 옛 요청 그대로) · `readAskPlan` 이 검사.
- `readAskPrice(companyId, channel)` = `resolveChargeUnitPriceDetailed(회사 행, channel)`(읽는 칸 = `MESSAGE_TYPE_PRICE_COLUMN` 의 세 칸 + `unit_price_basis`).

### S4 문안

- `/ask/compose` 입력 `channel`(S3 와 같은 검사 · 없으면 LMS) → `runLineCompose` 에 그대로. `vars` 는 지금처럼 빈 목록(칼럼은 카드의 꾸미기 · 손 편집으로 들어간다 · D5). 과금 키 입력에 `channel` 추가(LMS = 옛 키와 같은 값이 되게 기본값일 때는 키에 넣지 않는다).
- SMS = 90바이트 판정은 지금 있는 것 그대로(카드 칩 `too_long` · 확정 주소의 길이 검사).

### S4-b 나가는 문자 종류 — 최종 본문에서 정한다(판정 자리 하나 · 서버가 주인)

**규칙 함수 하나**: `services/ai-line.ts lineSendChannel(channel, hasVars, hasLink)` = 지금 601 ~ 602 줄의 식(칼럼 · 링크가 들면 SMS → LMS · 그 밖은 그대로)을 꺼낸 것. 생성기가 이 함수를 부른다(같은 값).

**본문으로 정하기**: `lineBodySendChannel(channel, 본문, 매핑 이름들)` = `lineSendChannel(channel, sendBodyVars(본문, 매핑 이름들).any, 본문에 주소가 있는가)`.

- **본문에 변수가 있는가 = 발송 치환이 실제로 바꾸는 것 전부**(판정 함수 한 곳 `utils/var-tokens.ts sendBodyVars(본문, 매핑 이름들)` → `{ any, needsCustomer }`). 치환(`messageUtils.replaceVariables`)의 단계마다:
  1. 0단계 = 주소록 칸 **글자 그대로**: `%기타1%` · `%기타2%` · `%기타3%` · `%회신번호%` · `%이름%` · `%고객명%` · `%성함%`(정규식 `/%이름%/g` 꼴 = 숫자 바로 뒤여도 바뀐다 · `messageUtils.ts` 233 ~ 256). 이 일곱 이름 = `var-tokens.ts STEP0_VAR_NAMES`.
  2. 2단계 = 그 회사 변수 매핑의 이름마다 `%이름%` **글자 그대로**(`result.split('%' + 이름 + '%')` · 같은 파일 302 ~ 322). 매핑 이름들 = `Object.keys(await prepareFieldMappings(회사))` = 직접발송 확정 · 일꾼이 쓰는 같은 함수(`routes/campaigns.ts` 2941 · `direct-send-worker.ts` 747).
  3. 3단계 = 남은 조각 지우기 = `findVarTokens(본문)`(숫자 바로 뒤의 `%` 는 퍼센트 기호로 본다).
  4. Liquid = `detectLiquidSyntax(본문)`.
  - `any` = 1 · 2 의 글자가 본문에 하나라도 **들어 있거나**(`includes` · 숫자 뒤 여부를 보지 않는다 = 치환과 같은 방식) 3 이 하나라도 있거나 4 가 참.
  - `needsCustomer`(D12) = 2 의 이름 가운데 0단계 이름이 아닌 것이 들어 있거나 4 가 참(= 고객 원장의 그 행을 찾아야 채워진다 · 이름은 적재 줄의 이름 칸으로 채워지므로 여기 들지 않는다).
  - **계약 시험이 치환 코드에서 기계로 뽑아 묶는다**: `replaceVariables` 소스의 0단계에서 `/%…%/g` 리터럴을 전부 뽑아 `STEP0_VAR_NAMES` 와 같은 집합인지 · 2단계가 매핑 이름의 `%이름%` 글자 그대로를 바꾸는지(치환에 리터럴이 더해지면 시험이 빨개진다 = 판정 사전과 실제 치환이 어긋날 수 없다 · 설계 Codex 3R · 4R 같은 부류).
- 본문에 주소가 있는가 = `listUrlsForTracking(본문).length > 0`(`utils/short-url.ts` · 추적 링크로 바꿀 때 쓰는 같은 주소 찾기). 생성기는 링크를 받으면 LMS 로 만든다 → 그 문안에는 주소가 들어 있으므로 본문 판정도 LMS 다(생성 · 세기 · 적재가 같은 종류 · 3R).
- 「10% 할인 + 5% 적립」처럼 퍼센트 기호만 있는 글은 1 ~ 4 어디에도 걸리지 않는다 = SMS 그대로.

**서버(주인)** — `/ask/stage` 가 받은 `plan.channel`(사람이 고른 종류)과 `message`(최종 본문)로 `send = lineBodySendChannel(plan.channel, message, 그 회사 매핑 이름들)` 를 다시 정하고:
- 단가 · 예산 인원(상한) · 적재를 **`send` 종류로** 한다(고른 종류로 세지 않는다).
- 응답에 `channel: send` · `unitPrice` · `amount`(= `total` × 단가)를 싣는다.
- 화면은 확정 본문의 `msgType` 을 **이 응답 값으로** 채운다(화면이 계산한 값을 쓰지 않는다) · 확인 창의 종류 · 금액 · 인원도 이 응답 값.
- 본문이 어떤 길로 바뀌었든(생성 · 꾸미기 · 편집 칸에 직접 붙여 넣기) 적재가 보는 것은 최종 본문 하나다 → **적재 시점의 매핑으로 보아** 변수 조각 · 주소가 든 본문은 SMS 로 적재되지 않는다.
- D12(칼럼 값을 넣을 수 없는 분 빼기)의 「칼럼이 든 문안」도 같은 함수의 값이다(`needsCustomer`).

**이 판정이 보장하는 범위(적재 시점까지)** — 매핑 이름들은 적재 때 한 번 읽는다. 발송 일꾼은 그때의 매핑을 다시 읽어 치환한다(`routes/campaigns.ts` 2941 · `direct-send-worker.ts` 747 = 직접발송 · AI 한줄로 · 자동 마케팅 · 대행발송이 전부 쓰는 공용 길의 **지금 동작**). 그래서 적재와 발송 사이에 회사가 칼럼 이름을 바꾸면(그 이름이 마침 본문의 `숫자%글자%` 자리와 같아지는 경우 등) 종류 · D12 판정과 실제 치환이 달라질 수 있다 — 한 줄로 묻기에만 있는 틈이 아니라 발송 길 전체의 성질이다.
- 그 경우의 받침 = 공용 길의 기존 안전망 그대로: 치환 뒤 90바이트를 넘는 SMS 줄은 적재 CT 가 싣지 않고(`sms-queue.ts bulkInsertSmsQueue` 의 마지막 문 · C143) 그 건은 미적재 환불 · 제외 기록으로 남는다(조용히 잘려 나가지 않는다). 고객 행을 찾지 못한 줄의 남은 조각은 `cleanLeftoverVars` 가 지운다.
- 매핑을 발송 자료에 고정해 확정 · 일꾼이 같은 매핑을 쓰게 하는 것 = 확정 주소 · 일꾼 · 적재 표(공용 발송 길)를 고치는 일이다 → 이번 범위 밖(§0-1 「발송 일꾼 · 적재 표 0줄」) · §8-6 ③ 에 추가 과제로 기록한다.

**화면(거울 · 상태 아님)** — `utils/ai-ask.ts askSendChannel(고른 종류, 본문, 매핑 이름들)` = 같은 규칙의 순수 함수. 매핑 이름들 = `GET /ask/segments` 응답 `varNames`(서버가 위 2 와 같은 함수로 낸 이름들) · 0단계 이름 일곱 = 화면 상수(서버 상수와 같은 값인지 시험이 대조) · 3 · 4 = 화면의 `findVarTokens`(`utils/formatDate.ts`) · `detectLiquidSyntax`(`utils/liquid-templating.ts`) = 서버 것과 짝인 기존 함수 · 주소 = 서버 정규식과 같은 식. **같은 본문 표로 서버 함수와 결과를 줄마다 대조하는 시험**으로 묶는다. 화면은 이 값을 **저장하지 않고 본문에서 매번 계산**한다(생성 · 꾸미기 응답을 기다렸다가 바꾸는 상태가 없다 = 응답의 순서 · 늦음과 무관):
- 2단계 세기(`/ask/count` 의 `plan.channel`) · 3단계 카드에 넘기는 종류(검사 지문 `spamFp` 에 종류가 들어 있다 = 종류가 달라지면 옛 검사 결과는 버려지고 다시 검사) · 요약 글이 모두 이 값을 쓴다.
- 고른 종류와 다르면 알림 줄 「칼럼이 들어 있어 LMS 로 보내요. 1통 값과 인원을 LMS 로 다시 셌어요.」
- 만든 문안의 입력 지문(`askInputFp`)에는 **사람이 고른 종류**만 들어간다(본문 때문에 달라진 종류는 입력이 바뀐 것이 아니다 = 카드가 낡은 것으로 바뀌지 않는다 · 사람이 종류를 바꾸면 「다시 만들기」).
- 화면 값과 서버 값이 다를 수 있는 틈은 서버 응답이 이긴다(확인 창 · 확정은 응답 값).

**보내기 앞의 잠금 · 확정 건의 묶음**(늦게 온 응답이 열린 확인 창 · 준비분과 엇갈리지 않게):
1. 꾸미기 요청이 떠 있는 동안 = 「다음」 · 「보내기」 · 「이전」 잠금 **+ 본문 · 제목 편집 칸 잠금**(그 사이 손으로 고친 글을 늦은 응답이 덮는 길 0 · 3R). 페이지가 카드 부품에 넘기는 `onDecorate` 를 감싸 「꾸미는 중」을 쥔다(부품의 내부 상태에 기대지 않는다 · 부품 무변경). 세기가 도는 동안(`countBusy`)도 지금처럼 잠긴다.
2. 꾸미기 응답은 **보낸 때의 실행(run) · 카드 · 본문**이 지금도 같을 때만 본문에 쓴다(그 사이 다시 만들었거나 글이 달라졌으면 버린다 · 크레딧은 서버가 이미 한 번만 걷는다 · 1번의 잠금이 놓친 길의 둘째 문).
3. 확정 건(`SendJob`)에 **적재 때의 발송 지문**을 묶는다 = `askSendFp(본문 · 제목 · 고른 종류 · plan · 발신번호 · 개별 회신 · 예약 · 나눔 · 이미지)`. 확인 창의 「보내기」는 지금 화면의 지문이 그 값과 같을 때만 확정한다. 다르면 확정하지 않고 준비분을 놓은 뒤 「문안이나 조건이 바뀌었어요. 다시 눌러 주세요.」(= 바뀐 문안이 옛 적재로 나가는 길 0). 확인 창이 떠 있는 동안 뒤 화면은 지금처럼 막힌다(`inert`) — 이 지문 대조는 그 막이 놓친 길(늦은 응답)을 닫는 둘째 문이다.

제목: 나가는 종류가 LMS · MMS 면 제목 칸이 보인다(비워 둘 수 있다 = 직접발송 확정이 제목 없는 LMS 를 받는다 — 구현 때 확인해 §9 에 · 받지 않으면 제목을 적어야 넘어가게 잠근다).

- **2단계**: 인원 · 예산 아래 「문자 종류」 칩 셋(이름 + 1통 단가) · 바꾸면 인원 · 금액 다시 셈(지금 `count` 요청에 `channel`). MMS = 「이미지를 붙여 보내요」 한 줄.
- **3단계**: MMS 면 폼에 「이미지」 줄(`MmsUploadModal` 재사용 · 없으면 「문안 만들기」 잠금 글) · 카드에 「칼럼 더 넣기」가 살아난다(부품 그대로) · 본문에 칼럼이 들어 나가는 종류가 달라지면(S4-b) 알림 줄 + 금액 갱신 · 꾸미는 동안 · 세는 동안 「다음」 잠금.
- **4단계**: 발신번호 = 지금 선택 + (조건이 되면) 「고객별 매장 번호」 · 「나눠 보내기」 줄(끔 / 한 번에 n건 · m분 간격 · 입력 조각은 직접발송 창의 것을 꺼내 쓸 수 있으면 그대로 · 구현 때 §9 에) · 요약에 문자 종류 · 이미지 수.
  - 「N명에게 보내기」 = `POST /ask/stage` 한 번(본문 · 예약 · 나눔 값을 실어) → 확인 창(서버가 정한 종류 · 금액 + 「중복 · 회신번호 · 광고 제한 · 칼럼을 넣을 수 없는 분 n명을 빼고 m명에게」 + 광고 관문 안내 · 뺀 것이 0 인 갈래는 적지 않는다) → 확정(적재 응답의 종류 · 같은 값 · 발송 지문이 같을 때만). 받는 분 수가 바뀌었으면(409) 그 문구 + 다시 누르기.
  - 칼럼을 넣을 수 없는 분의 글 = 「번호에 숫자가 아닌 글자가 있어 칼럼 값을 넣을 수 없는 n명은 뺐어요」.
  - C153 의 소유 · 접수 판정(`hold` · `settle` · 뒤 화면 막기) 그대로 · 확정 건에 `signature` 가 더해질 뿐.
- 폭 320 ~ 1920 넘침 0 · 디자인 최소 기준은 구현 직전에 열어 맞춘다.

## §6 직원 지시문

1. 한 줄로 묻기 2단계에서 「문자 종류」를 SMS 로 바꾸면 1통 값과 예상 금액이 줄어듭니다.
2. 3단계에서 문안을 만들고, 카드의 「칼럼 더 넣기」로 이름을 넣습니다. 문안에 이름 자리가 들어가고(크레딧 1), SMS 였다면 「LMS 로 바꿨어요」 줄이 보이고 금액이 다시 계산됩니다.
3. MMS 를 고르면 3단계에 이미지 줄이 보이고, 이미지를 붙이기 전에는 「문안 만들기」가 눌리지 않습니다.
4. 4단계 발신번호에서 「고객별 매장 번호」를 고르고 보내기를 누르면 확인 창에 매장 번호가 없어 빠지는 인원이 보입니다.
5. 「나눠 보내기」를 켜고 1,000건 · 10분으로 예약하면 예약 내역에 나뉜 시각이 보입니다. 확인 뒤 취소합니다.
6. (합성 번호 회사에서만) 이름을 넣은 문안을 지금 보내고, 발송 결과의 문자 내용에 받는 분 이름이 들어가 있는지 봅니다.
