## §1 실행 순서 — 이대로만

1. **이전 백그라운드 작업부터 정리한다.** 폴러·앞선 리뷰가 남아 있으면 결과가 섞이고 화면이 어지러워진다(0804 실측 — 폴러를 안 내린 채 재실행해 둘이 겹쳤다). `TaskStop`으로 내린 뒤 시작한다.
2. **전용 커맨드 두 개만 쓴다.** `review`(표준) / `adversarial-review`(**돈·환불·DB 마이그레이션·정산·큰 영구 룰**). `task`(rescue 서브에이전트)로 리뷰를 돌리지 않는다 — 자율 조사로 새다가 멈춘다(0728에 30분 손실).
   ★**1.0.6부터 `review`는 커스텀 요청문을 받지 않는다**(내장 리뷰어 직결 · 요청문을 붙이면 exit 1로 즉시 반환). §2 규격 요청문이 필요한 리뷰는 등급과 무관하게 `adversarial-review`로 띄운다(도구 자체가 그렇게 안내한다).
3. **요청문은 §2 규격 4항을 채운다.** 하나라도 빠지면 멈추거나 헛돈다.
4. **`--background`로 띄우되 런처를 죽이지 않는다 — 이 항목으로 두 번 잃었다(0805·0814).** `--background`는 잡을 런처에서 떼어내지 않는다 —
   **런처가 죽으면 잡도 죽는다.** `timeout`으로 감싸지 말고 Bash `run_in_background`로 띄운다(★0814 실측 = §4).
5. **결과는 `result`로 따로 받는다.** `codex-companion.mjs result [job-id]`.

⚠ **런처 태스크가 "completed (exit 0)"이어도 리뷰가 끝난 것이 아니다.** 0804 실측 — 런처는 exit 0으로 끝났는데 잡은 그 뒤로도 40분 넘게 `running`이었다. 완료 판정은 `result`가 본문을 돌려줄 때뿐이다.

| # | 항목 | 왜 |
|---|---|---|
| ① | **[검사 재실행 금지]** `tsc`·`vitest`·`npm`·`psql`을 실행하지 말라고 명시하고, **이미 통과한 수치를 값으로 준다**(예: backend tsc 0 / frontend tsc 0 / vitest 136파일 1,973건) | **오늘까지 확인된 최다 멈춤 원인.** 리뷰가 장시간 명령을 띄운 뒤 그 결과를 영영 못 받고 선다(§3) |
| ② | **[범위]** 대상 파일을 경로로 나열 + "그 밖의 변경 파일은 대상이 아니다 — 발견해도 `[범위 밖] 파일:라인 — 한 줄 요약`만 남겨라" | 작업 트리에 다른 트랙 변경이 섞여 있으면 그것까지 리뷰해 헛돈다. `codex_review_scope_incremental`의 실행 형태다 |

| ④ | **[함께 볼 지점]** 내가 의심하는 곳을 번호로 | 리뷰가 스스로 기각하면 그것도 소득이다(0804: targetless `ON CONFLICT` 건을 "삼킬 별도 UNIQUE 없음"으로 기각) |

## §3 살아 있는가 — 잡 로그의 성장으로 판정한다

주근거는 하나다. **`state/<ws>/jobs/<job-id>.log`의 mtime·크기가 자라는가.**

| 신호 | 판정 |
|---|---|
| 잡 로그 mtime·크기 **성장** | **주근거.** 살아 있으면 수십 초 단위로 줄이 늘고 실제 명령이 찍힌다 |
| 자식 프로세스(`codex-command-runner*`·`pwsh`·`node`) 존재 | 보조. ⚠ 셸 명령마다 떴다 사라지므로 **순간 부재는 죽음이 아니다.** 프로세스명에 버전 접미사가 붙는다(`codex-command-runner-0.146.0-...`) — 와일드카드로 본다 |
| `status`의 `running` / `Elapsed` 증가 | **근거 아님.** 죽은 잡도 계속 `running`으로 남고 경과 시간은 계속 는다(0804: 프로세스 0개인데 42분으로 표시) |
| 런처 태스크 `exit 0` | **근거 아님**(§1) |
| 잡 로그 파일의 *존재* | 근거 아님 — *성장*이 근거다 |
| 경과 시간 | 근거 아님. 정상 1라운드 7~15분 |
| **`state.json`의 그 잡 `pid`가 프로세스 목록에 있는가** | **가장 빠른 확정 수단**(★0804 2차 추가). 이름 와일드카드(`codex*`)로 세면 공유 브로커·호스트가 섞여 "2개 살아 있음"으로 오판한다 — **잡 레코드의 pid 하나를 직접 대조한다.** 그 pid가 없으면 죽음 확정 |

⚠ **완료도 "로그 정지"로 보인다.** 리뷰가 끝나면 당연히 로그가 안 자란다 — 정지 카운터만 보는 감시는 **성공을 멈춤으로 오판한다**(0804 2차 실측: 정상 완료를 `STALLED`로 보고). 정지를 판정하기 전에 **결과 유무부터 확인한다.**
⚠ **`result <job-id>`는 완료 직후 잠깐 `No job found`를 낸다.** 그 시점에 잡은 `status`의 `Active jobs`에서 빠지고 아직 조회 인덱스에 안 올라온 상태다. 조금 뒤 같은 명령이 본문을 돌려준다. **가장 빨리 확인되는 경로는 런처 태스크의 출력 파일** — `result` 본문과 같은 내용(Verdict·Findings·Next steps)이 거기 그대로 찍힌다.

**멈춤 확정** = 잡 로그가 5분 넘게 그대로 + **결과 없음** + 잡 레코드 pid 부재.
판정할 때 **`date`를 함께 찍어** 로그 mtime과 현재 시각을 같은 출력에서 비교한다(0804에 13분 정지를 이렇게 확정했다).

## §4 멈추면

멈춤 지점이 로그 마지막 줄에 남는다. 그 줄로 원인을 가른다.

| 로그 마지막 줄 | 원인 | 처방 |
|---|---|---|
| `Starting collaboration tool: wait` | **직전에 띄운 장시간 명령의 결과를 못 받고 선다.** 0804 실측 — `tsc`·`vitest`·`git`을 동시에 띄웠는데 `vitest`만 종료 기록이 없고 프로세스는 이미 사라져 있었다 | 잡을 버리고 §2 ①(검사 재실행 금지)을 넣어 재실행 |
| `Starting Codex task thread.` | **브로커 좀비** — 브로커가 살아 있어도 app-server 연결을 잃으면 그 뒤 모든 잡이 여기서 영구히 선다(0729: 잡 4개 전멸) | 컴패니언·브로커 `Stop-Process` → `state/<ws>/broker.json` 삭제 → 재실행 |
| 파이프 `ENOENT` | 인증 만료(`auth.loggedIn=false`) | **Harold님이 `codex login`.** 인증이라 본 AI가 대행하지 않는다 |
| 마지막 줄이 **정상 명령 완료**인데 잡 pid만 사라짐 | **런처 사망 = 잡 사망**(0805·0814 2회). 0814는 **런처를 `timeout`으로 감쌌다.** `--background`는 잡을 런처에서 떼어내지 않아 **런처가 죽으면 잡도 죽는다.** Bash 도구 타임아웃을 피하려고 `timeout 100 node ... > /dev/null` 로 띄웠더니 100초마다 리뷰가 통째로 죽었다(3회 반복 · 로그가 시작 후 약 91초에 멈춘 것이 지문). 55초에 끝난 회차만 살아남아 "도구가 불안정하다"로 오판했다 | **런처를 절대 `timeout`으로 감싸지 않는다.** Bash `run_in_background`로 띄워 런처를 살려 둔다(그 태스크의 출력 파일에 결과 본문이 그대로 찍힌다) |
| `Running command: ... Get-ChildItem -LiteralPath ...` (디렉터리 스캔) | **대상 파일을 경로로 줬는데도 리뷰가 스스로 레포를 훑다가 선다.** 0804 2차 실측 — 6개 파일을 다 읽고 마지막에 파일 목록 조회를 띄운 뒤 32분간 로그가 한 줄도 안 늘었고 잡 pid는 이미 사라져 있었다 | 잡을 버리고 §2 ①과 **함께** "디렉터리 재귀 탐색·파일 목록 조회 금지 — 아래 경로만 읽어라"를 요청문에 넣어 재실행 |

**`cancel <job-id>`는 프로세스만 죽인다 — 레코드는 그대로 남는다.** Git Bash가 `taskkill /PID`의 `/PID`를 경로로 바꿔 인자 오류가 나므로 PowerShell로 실행한다. 그런데 **PID가 이미 없으면 `exit 128`로 끝나고 잡은 `running`으로 남는다**(0804 실측 — 좀비 6개에 `cancel`을 돌렸는데 6건 다 "프로세스를 찾을 수 없습니다"였고 목록은 그대로였다).

**좀비 잡 정리 = 상태 파일을 직접 내린다.** `state/<ws>/state.json`의 `jobs` 배열에서 해당 `id`의 `status`·`phase`를 `cancelled`로 바꾸고 저장한다(백업 먼저). 레코드를 지우지 않고 상태만 내리면 이력이 남는다. **실행 중인 잡이 있으면 그 잡이 같은 파일에 쓰므로, 정리 후 `status`로 되살아나지 않았는지 확인한다.**
