## 핵심 원칙
- **★ 기존 배관에 두 번째 입구를 내면, 리뷰는 기능이 아니라 그 배관을 판다 — 경계는 "이 지적이 내 변경 없이도 성립하는가" (2026-08-29 충전 승인 문자 링크 · Codex 3라운드)** — 슈퍼관리자 충전 실행 화면에 문자 링크 입구를 하나 더 냈다. 리뷰 지적이 1R 6건 → 2R 5건 → 3R 6건으로 **줄지 않았고**, 3R부터는 대상이 전부 기존 충전 배관이었다(운영자 둘 동시 제출·재전송 응답의 실상태 은폐·해소 시 SeqNo 미저장). 나는 그것을 출하 조건으로 착각해 배관을 계속 덧댔다. **판정 한 줄 = 그 지적이 내 변경 없이도 성립하면 지금 운영 중인 화면의 성질이다**(매일 돌고 있다는 사실이 실발생률의 증거) — BUGS 등재하고 넘어간다. **새 입구의 출하 기준 = 기존 화면과 같은 문(같은 코어·같은 검증)을 지나고, 그 입구 고유의 위험(재클릭 멱등·토큰 유출)만 막았으면 끝.** 기존 배관 개선을 기다리면 그 기능은 영원히 안 나간다.
- **★ 1라운드 지적을 입구에만 붙이면 2라운드에 같은 것이 온다 — 게이트는 효과가 만들어지는 함수 안이다 (2026-08-29 · 같은 축)** — "충전 전에 주문을 선점하라"는 1R 지적을 **링크 라우트에만** 넣고 실행 코어는 두었다. 화면 입구는 선점 없이 그대로라 2R에 같은 critical이 다시 왔다(서로 다른 멱등키로 같은 주문 이중 충전). 코어의 예약 트랜잭션 안, **외부 호출 전으로** 옮기니 두 입구가 같은 문을 지나고 **링크 쪽 선점·연결·원복 코드가 통째로 사라졌다** — 구조를 고치면 덧댄 장치가 줄어든다는 신호 그대로다. 부수로 얻은 것: 선점과 예약이 한 트랜잭션이라 그 사이 프로세스가 죽어도 함께 롤백된다(고착 경로 소멸). 판정 = 지적을 받으면 "이 게이트가 **모든** 입구를 덮는가"를 먼저 묻는다.
- **★ 승인권이 든 링크는 범용 단축·추적 배관에 태우지 마라 — 클릭 기록이 그 값을 고객사에게 돌려준다 (2026-08-29 · Codex 1R critical)** — 단축 CT(CT-40)의 클릭 라우트는 `full_url` **전체**를 그 회사 `cdp_events.properties`에 적고, 고객사는 자기 이벤트 조회로 그것을 읽는다. 승인 토큰이 fragment에 실린 주소를 단축하면 **담당자가 링크를 열기만 해도 고객사가 승인권을 회수**한다(대행발송 승인 링크도 같은 구조였다 = B-0828-7). **처방 = 뿌리를 끊는다** — 클릭 라우트에 승인류 경로 비추적 가드(cdp 기록 생략·클릭 수만 집계). 그 가드를 전제로 단축을 다시 쓴다(만료 = 토큰 만료 동치 · 실패 = 원본 폴백). 일반화: **링크에 실린 값이 그 자체로 권한이면, 그 링크가 지나는 모든 관측·기록 지점을 먼저 세어 본다.**


- **★ UNIQUE 제약은 우리 판정이 편한 모양이 아니라 실무의 관계를 적어야 한다 — 카디널리티를 한 번 잘못 굳히면 그 기능을 쓸 수 없는 고객이 생긴다 (2026-08-27 대행발송 청구 계정, 서수란 접수)** — 이메일 접수 설계가 "허용 주소 1개 = 귀속 1개"를 전제로 **활성 부분 UNIQUE `(email_norm)`**(전역 1행)을 걸고, 판정 코드도 "2행 이상 = fail-closed"로 그 전제를 복제했다. 그런데 대행 실무는 **담당자 1명이 청구 계정 여러 개를 대신 요청**한다(금강제화 4계정 1담당 등 4사례). 결과는 버그가 아니라 **"그 업체는 이 기능을 이용할 수 없음"**이었고, 귀속 = `created_by` = 정산 계정이므로 편의가 아니라 **청구 정확성** 문제였다. **처방 = ①제약은 실무 관계로 다시 쓴다**(`(email_norm, user_id)`) **②그래서 판정이 모호해지는 부분은 제약이 아니라 "지정 입력"으로 푼다** — 요청서에 "청구 계정" 칸(선택)을 만들고 **표시명·로그인 ID 정확 일치**로 하나를 고른다. ⛔ **돈 귀속에 자동 선택·기본값·유사 일치를 두지 마라** — 지정이 없으면 반려가 정답이다(기본 계정을 두면 지정을 깜빡한 건이 조용히 엉뚱한 계정으로 청구된다). 반려 회신에 **그 주소로 요청 가능한 계정 목록**을 실으면 사용자가 스스로 고친다. **일반화: 원장 테이블에 UNIQUE를 얹기 전에 "이 관계가 실제로 1:1인가"를 업무 쪽 사례로 확인한다** — 코드는 제약을 따라 굳고, 나중에 푸는 비용은 인덱스 교체 + 판정·게이트 재배열 + 화면·양식까지다.
  ★같은 축 Codex 1R 지적 두 개도 같은 뿌리 = **"활성 집합의 불변은 그 집합을 바꾸는 경로 전부가 같은 판정을 지나야 한다"** — 지정 이름 유일성을 **등록(POST)에서만** 검사하고 **재활성(PATCH)은 무검사**로 두니 "등록 → 비활성 → 교차 키로 다른 계정 등록 → 재활성"이라는 **정상 관리자 조작만으로** 모든 지정값이 모호한 집합이 만들어져 그 주소의 접수가 전부 반려된다. 게다가 검사와 쓰기가 갈라져 있으면 **동시 요청 둘이 서로를 못 보고** 같은 키로 함께 들어간다. 처방 = 판정을 함수 한 벌로 뽑고(`senderKeyClash` — 교차 겹침 = 내 표시명 ↔ 남의 로그인 ID까지 본다), **자원 단위 `pg_advisory_xact_lock` 한 트랜잭션 안에서 현재 집합을 다시 읽어** 그 함수를 지난다. 집합을 **줄이는** 방향(비활성)은 검사 대상이 아니다. 부수 둘 — ⓐ**커넥션 획득(`pool.connect()`)을 `try` 밖에 두면 풀 고갈·failover가 그 API의 JSON 오류 계약 밖으로 샌다**(획득을 try 안으로, client는 nullable로, 연결된 경우에만 ROLLBACK·release) ⓑ`pg`의 `pool.connect`는 오버로드라 `Awaited<ReturnType<typeof pool.connect>>`가 `void`로 잡힌다 — `import type { PoolClient } from 'pg'`를 쓴다. 경위·판정표 = [대행발송 설계서 §20](../../docs/2026-08-22-agency-send-design.md).
- **★ 외부 시스템의 능력을 실측 없이 설계 전제로 삼지 마라 — 대신 착수 게이트와 조건부 분기를 설계서에 박아 둔다 (2026-08-26 대행발송 이메일 접수)** — "하이웍스는 IMAP이 된다"는 전제로 브레인스토밍·설계서를 다 썼는데, 착수 게이트 실측에서 **POP3S만 지원**(가비아 문서 + 설정 화면 + 실접속)이 나왔다. 같은 실측에서 두 번째 전제도 뒤집혔다 — **수신 인증 헤더(Authentication-Results)를 안 붙인다**(gmail 외부 메일 헤더 실측). 이건 위조 방어의 기둥이라 신원 게이트가 통째로 바뀌었다(3값 fail-closed → allowlist_only + 일일 상한 절반). **손실이 작았던 이유는 설계서에 "이 실측 전 코드 착수 없음"과 "헤더 부재로 판명되면 그때 이 모드"를 미리 적어 둬서 재설계가 아니라 분기 선택으로 끝났기 때문이다.** 처방 = ①외부 시스템 위 설계는 능력 표(프로토콜·명령·헤더 + 근거 URL·화면·출력)를 먼저 만들고 근거가 "일반적으로 그렇다"뿐이면 **미검증으로 표기** ②착수 게이트를 절로 만들고 그 전에 코드 금지 ③전제가 깨졌을 때의 대안을 설계서에 조건부로 함께 적는다. ⛔ **접속 실패 메시지를 액면대로 읽지 마라** — `-ERR [AUTH] Access denied`라 비밀번호 문제로 보였지만 실제로는 CAPA 미구현 → 클라이언트가 APOP으로 붙음 → 서버가 그 방식을 거부한 것이었다(USER/PASS로 바꾸니 즉시 통과). **인증 실패는 자격 증명 문제와 방식 문제 둘 다일 수 있다.** memory `feedback_verify_external_capability_before_designing_on_it`.
- **★ 폴링 워커가 "처리 전에 죽는 메일"을 만나면 원장 행이 없어 무한 재시도한다 — 실패 행을 만들어 백오프에 태운다 (2026-08-26 자체 적대 검토 1R)** — 이메일 워커는 헤더 수신·신원 판정을 **선점 INSERT보다 먼저** 한다(무인증 첨부를 안 받으려고). 그런데 그 앞 구간에서 예외가 나면 원장에 행이 없어 **다음 틱이 같은 메일을 또 집는다** — 백오프 없이 매 틱, 틱당 처리 상한 10통 중 1칸을 영구 점유한다(독약 메시지). 처방 = 실패 경로에서 원장 행이 없으면 **파생 해시로 `failed` 행을 만들어** 같은 백오프 계단(1·5·30·120분, 4회 후 종결)에 태운다. **일반화: "선점 전에 하는 일"이 있는 워커는 그 구간의 실패도 원장에 남겨야 한다** — 선점 실패는 조용한 무한 루프가 된다.
- **★ 읽기가 우선하는 컬럼과 쓰기가 갱신하는 컬럼이 다르면, 쓰기는 성공하는데 화면은 안 바뀐다 (2026-08-25 DM 버전 복원 재오픈)** — 같은 데이터에 폴백 축이 둘이면(`pages`가 있으면 그것을, 없으면 `sections`를 읽는다) **쓰기는 읽기가 보는 쪽을 갱신해야 한다.** 복원이 `sections`만 되돌려서 UPDATE는 1행 성공하고 오류도 없는데 화면은 그대로였다. 운영 실측하니 DM이 **전부** `pages`를 갖고 있어(scroll 모드도 1페이지) 복원은 특정 건이 아니라 **전 건 무효**였다. 더 나쁜 것은 전날 1차 수정에서 **오류(`invalid input syntax for type json`)만 고치고 효과를 확인하지 않아** 고쳐진 것으로 닫았다는 점이다(6원칙 ② 위반 → 다음 날 재오픈). **처방 = ①상태를 바꾸는 기능은 "오류가 없어졌다"가 아니라 "의도한 변화가 실제로 일어났다"를 확인한 뒤 성공이라고 쓴다 ②고치기 전에 그 데이터를 **읽는** 경로가 어느 컬럼을 우선하는지 먼저 본다 ③되돌릴 대상 목록을 상수로 못박고(`DM_SNAPSHOT_KEYS`) 화면에 영향을 주는 컬럼이 늘면 거기 등재한다 — 부분만 늘리면 다음에 "헤더는 왜 안 돌아오냐"가 온다.** 부수 = **재오픈 건은 배포 누락부터 의심하되 점검을 명령으로 확정한다**(소스 → 프로세스 기동 시각·실행 대상 → 번들 → 로그). 이번엔 넷 다 최신이라 배포가 아니었고, 거기서부터가 진짜 디버깅이었다. 그리고 **에러 로그 0건은 해소의 증거가 아니다** — 옛 코드가 오류를 화면으로만 보내고 로그를 안 남기면 당연히 0건이다. 경위 = [BUGS B-0824-1](../BUGS.md).
- **★ 게이트를 건너뛰는 근거는 "마지막 시도"가 아니라 "마지막 통과"다 (2026-08-23 대행발송 · 배포 전 발견)** — 시도 스탬프(`last_*_at` 류)는 **실패한 회차에도 갱신된다.** 그것으로 "이미 통과했으니 건너뛴다"를 판정하면, 실패 뒤 후처리에서 예외가 나 상태가 되돌아간 건이 다음 순회에 게이트를 그냥 지난다(대행발송에서는 **차단된 문안이 스팸 검사 없이 예약**되는 경로였다). 두 값이 이름도 타입도 닮아 코드만 보면 옳아 보이고, tsc·테스트 둘 다 못 잡는다. **처방 = 성공 분기 안에서만 쓰이는 컬럼을 근거로 쓴다.** 없으면 성공 전용 스탬프를 두고, 그 값을 **찍는 자리를 전부 성공 분기 안으로** 옮긴 뒤 실패·소유권 상실·catch 분기에서 실행될 수 있는지 자리마다 자문한다. **지우는 자리도 함께 센다**(전제가 바뀌면 스탬프는 무효다). 경위 = [대행발송 설계서 §14](../../docs/2026-08-22-agency-send-design.md).
- **★ 새 발송 경로는 큐를 스스로 만들지 말고, 새 축도 만들지 마라 (2026-08-23 대행발송 · 배포 전 발견)** — 새 축이 `campaigns` INSERT + `bulkInsertSmsQueue`를 손으로 쓰자 그 자리에서 **선불 차감 0 · 수신거부 제외 0 · 부분 적재 롤백 0 · 재시도 멱등 0**이 한꺼번에 빠졌다. tsc·vitest·자가 리뷰 셋 다 통과했다(빠진 것을 검사하는 테스트가 없으니 당연하다). **처방 = `campaign_send_staging` 적재 → `createDirectSendCampaign` 위임.** 차감·정제·적재·미적재분 환불·`sentTables` 기록·적재 중 취소 감지가 전부 딸려 온다.

- **★ 진단 목록의 판정 기준은 실제 게이트의 기준과 같아야 한다 — 갈리면 목록이 소음이 되어 진짜 문제를 묻는다 (2026-08-14 에이전트 단가 공백)** — `GET /billing/agent-price-gaps`는 "마감일에 어느 단가가 비었는지 하나씩 발행해 보며 찾는" 일을 없애려고 만든 진단 API인데, **"단가 NULL"만 보고** 목록을 만들었다. 발행 게이트(`priceBillingRows`)는 **`success > 0`일 때만** 막는데 목록은 실적을 안 봤다. 그래서 유형이 하나 늘 때마다(0729 브랜드 `G` 신설) **그 유형을 쓰지도 않는 발송ID가 전부 목록에 올라왔고**, 0814 실측 190행 중 대부분이 그 소음이라 정작 급한 "전 유형 미설정 20행"(SMS조차 비어 발송만 있으면 즉시 발행 차단)이 묻혔다. **처방 = 목록의 좁힘 규칙을 게이트와 같은 식으로 맞춘다**(실적 있는 유형만) — 축 파생은 `BILLING_TYPES`, MsgType→유형키 변환은 `agentUsageKey` CT 재사용(매핑 두 벌 금지). **다만 좁히는 방향은 fail-open이어야 한다** — 실적을 못 읽으면(수집 DB 미설정·조회 실패) 전부 보여주고 `usage_known:false`를 함께 돌려준다. 공백을 숨기면 "채울 것 없음"으로 읽히고 마감일에 이유 없이 막힌 발행을 찾아다니게 된다(가장 위험한 방향). 부수 — 실적은 있는데 **단가 컬럼 자체가 없는** 유형(`KS`·`KL` 대체발송)은 입력으로 못 고치고 발행은 똑같이 막히므로 `unpriceable`로 따로 표시한다. 일반화: **"무엇이 나를 막는가"를 답하는 화면·API는 막는 쪽 코드와 같은 판정을 써야 한다.**
- **★ upsert에서 "미제공 기본값"을 INSERT 값으로 채우면 UPDATE가 기존 진실을 덮는다 — 특히 수신동의 (2026-08-14 Codex 적대 1R)** — sync·upload·manual 세 경로가 `sms_opt_in` 미제공을 `?? true`로 채워 보냈고, ON CONFLICT UPDATE의 `COALESCE(EXCLUDED...)`는 그 true를 "명시값"으로 받아 **기존 false(수신거부)를 true로 되돌렸다**(광고 발송 동의 = 법 축). arbiter가 (company_id, phone)이 되면서 다른 매장 행까지 흡수하므로 노출 폭이 커진 상태였다. **처방 = 미제공은 null로 보내고(UPDATE COALESCE가 기존 값 보존), 신규 기본값은 업서트 직후 `sms_opt_in IS NULL` 행만 백필한다**(`buildSmsOptInBackfill` CT — 기존 행은 COALESCE 보존이라 null이 될 수 없어 신규만 잡힌다. 전제 = 컬럼 nullable, information_schema 실측). **함정 2개** — ①VALUES에 `COALESCE($n, true)`를 넣는 방식은 **EXCLUDED가 표현식 결과를 보므로** UPDATE까지 true가 전파되어 답이 아니다(자가 반증 후 철회) ②명시 null INSERT는 컬럼 DEFAULT를 타지 않는다 — "DEFAULT true가 있으니 null 넣으면 true"는 착각. 일반화: upsert 경로에서 "없으면 기본값"은 INSERT에만 참인 문장이다 — UPDATE 의미론과 분리해서 설계하라.
- **★ 검사를 분기마다 복붙하면 반드시 빠진 분기가 생긴다 — 조립은 여러 갈래여도 출구는 하나여야 한다 (2026-08-14 아난티 날짜 거절)** — `normalizeDate`는 입력 형식별로 7개 분기가 각자 `YYYY-MM-DD`를 조립했는데, 범위 검사는 **한국식·YYMMDD 둘에만** 복붙돼 있었다. 나머지 5개(ISO 접두·YYYYMMDD·`/`·`.`·미국식)는 무검사라 8자리 쓰레기값 `20144850`이 `2014-48-50`으로 통과했고 PG가 `date/time field value out of range`로 행을 거절했다. **처방 = 분기에 검사를 되살리는 게 아니라 `toValidDate(y,m,d)` 단일 출구를 만들어 전 분기를 통과시킨다** — 새 형식을 추가해도 검사를 빠뜨릴 수 없고, 기존 인라인 검사 2벌은 그 함수로 흡수돼 사라진다(코드가 늘면 또 땜질한 것이다). 범위(1~12월·1~31일)만으로는 부족하다 — 2월 30일·4월 31일도 PG가 거절하므로 `Date.UTC` 왕복 대조로 달력 실재까지 본다. **함께 드러난 같은 뿌리 4곳** — ⓐ**정규화 실패를 "값 없음"이 아니라 "원본 유지"로 구현**했다(`sync.ts`·`upload.ts`가 `if (normalized) { 대입 }`이라 실패 시 원본이 그대로 PG로 갔다. 정규화를 아무리 엄격하게 해도 소용없는 구조 — 무조건 대입으로 바꾸면 분기가 줄어든다) ⓑ**FIELD_MAP이 `normalizeFunction`을 지정하는데 `sync.ts` 동적 루프가 그걸 무시**하고 `birth_date`만 특수 처리해 `recent_purchase_date`는 원본 그대로 갔다(`upload.ts`는 `normalizeByFieldKey`로 이미 태우고 있었다 — **같은 CT를 한쪽만 쓰는 비대칭**) ⓒ`cdp-identity.ts`가 자사몰이 준 생일을 정규화 없이 SQL 파라미터로 넘겼다 ⓓ조회 쪽 `safeDateValue`·`isDateLikeValue`가 **모양만** 보고 통과시켜, 목적이 "쿼리가 터지지 않게 방어"인 함수에 같은 구멍이 있었다(`::date` 캐스팅이 붙어 쿼리째 실패). **불변식은 테스트로 고정한다** — `normalize-date.verify.ts`가 실측 거절값 6종을 그대로 담고 있어, 단일 출구를 우회하는 분기가 생기면 빨간불이 된다. 부수 진단 요령 — **실패 로그에 원본 값을 안 남기면 원인을 못 가른다**(`sync_logs.failures`는 `{phone, reason}`뿐이라 원본이 `20144850`인지 `2014-48-50`인지 끝내 확정 못 했다). 그리고 **UPSERT는 중복을 조용히 흡수하므로 원본 중복은 실패 행에서만 드러난다**(같은 번호가 한 배치에서 4회 실패 = 그 배치에 그 행이 4개 — 단건 재시도는 행당 1회만 기록한다).

- **★ 우리 편의를 위한 부가 작업을 고객 확정 트랜잭션 안에 넣지 마라 — 격리 장치를 덧대는 순간 그 장치가 새 실패 축이 된다 (2026-08-08 발행 메일 아카이브 참조, Codex 적대검증이 형태를 뒤집음)** — 세금계산서 발행 확정 트랜잭션 안에서 아카이브 주소(우리 보관용 참조)를 큐에 넣으면서 "고객 참조와 갈라 아카이브 때문에는 확정을 미루지 않는다"를 `SAVEPOINT` 격리로 지키려 했다. 적대검증이 그 격리 자체를 깼다 — ①`ROLLBACK TO SAVEPOINT`가 실패하면 세션이 aborted라 이후 `COMMIT`이 조용히 롤백으로 끝나 **팝빌엔 발행됐는데 `issued` 갱신과 고객 참조 기록이 통째로 사라진다**(호출부는 command tag를 안 본다) ②아카이브 전용 `information_schema` 조회 한 번이 거절·풀 타임아웃만 나도 그 임계 경로가 확정을 롤백시킨다. **처방 = 트랜잭션 밖(COMMIT 뒤) 자기 연결로 best-effort 실행.** SAVEPOINT·임계 경로 카탈로그 조회가 통째로 사라져 코드가 줄었다(구조를 고쳤는데 코드가 늘면 또 땜질이다). 대신 실패는 **던지지 않고 식별자와 함께 로그로 남긴다**(`issue`·`mgtKey`·주소 — "대상 N건"만 남기면 누가 빠졌는지 재구성이 안 된다), 실패는 **수신자별로 격리**해 한 주소가 막혀도 뒤가 계속 간다. 남는 창(COMMIT과 후처리 사이 프로세스 중단)은 **위험 수용**이 정답이다 — 잃는 것이 우리 사본뿐이고 고객 영향이 0이면, 내구화(outbox+대조 워커)는 별건으로 미루는 것이 맞다. **판정 기준 = "이 작업이 실패했을 때 고객이 무엇을 잃는가."** 아무것도 안 잃으면 확정 경로에 둘 이유가 없다.
- **★ 증분 커서를 DB 정밀도 밖(JS Date)으로 내보내지 마라 — 마지막 밀리초 묶음이 매 회차 재발송된다 (2026-08-02 여정 §11-4 F1)** — PG 시각은 마이크로초, JS Date는 밀리초다. 커서 값이 드라이버를 거쳐 저장·재조회되면 실제 마지막 행보다 최대 999µs 이르게 잘리고, 행 비교 `(t,id) > (커서,id)`는 첫 항이 이기면 끝이라 **마지막 밀리초의 행 전부가 매 회차 다시 잡힌다.** 벌크 INSERT는 한 문장의 전 행이 같은 시각이라(트랜잭션 NOW) 500행 통째로 반복된다 — 재진입 허용·쿨다운 0·UNIQUE 없음이면 그대로 중복 발송·과금. 처방 = ①커서는 `::text` **원문 문자열**로 읽고 쓰고 비교한다(파라미터로 나가면 PG가 풀 정밀도 캐스팅) ②쓰기에 **후진 금지 가드**(`WHERE (신규 t,id) >= (기존 t,id)`) — 절사된 값이 커서를 뒤로 물리는 잔여 경로까지 닫는다 ③Date는 창 계산 같은 JS 산술에만. **이 결함은 §11-3 배포분에 이미 잠복해 있었고 커서 여정이 전부 비활성이라 미발화였다** — "0건이라 안 터졌다"는 안전의 증거가 아니다.

## 직접발송 대량 504 사고 (D231+ 추가)

### D231+ (2026-06-04) — 톤28 8~30만 발송 504 + 중복 발송 (응답 전 동기 정제 self-join 폭발)

**사고**: 톤28(toun28) 8~30만 직접발송 시 빨간 알럿(504) 반복 → 오류로 알고 재시도 → 중복 64만건 처리(취소·예약도 send_phase='sent'로 게이트웨이 송출).

**Root cause**: commit endpoint가 정제(수신거부 DELETE + **중복제거 self-join** `a.phone=b.phone AND a.id>b.id`)를 **응답 전 동기로** 수행. `(staging_id,phone)` 인덱스가 있어도 **같은 테이블 자기조인**이라 10만에 59초(\timing 실측 239,674ms) → commit 60초 초과 → **nginx 504(upstream timeout)**. 백엔드는 완주 → 발송 + status='scheduled' 잔존 → 재시도 중복.
- 진단: 백엔드 out.log 완료만, error.log에 commit 에러 0 → **백엔드 안 죽음, nginx가 응답 못 받아 504**. nginx access.log `POST /direct-send/commit 504`, error.log `upstream timed out`.

**정정** (`routes/campaigns.ts` + `utils/direct-send-worker.ts` + `DirectSendPanel.tsx`/`Dashboard.tsx`):
1. commit 정제 제거 → 발송 건수만 COUNT(헬퍼 `countStagingFiltered`) → 즉시 202.
2. 정제(중복 ctid+ROW_NUMBER O(N log N) + 수신거부 인덱스 JOIN)를 worker 발송 직전(processed===0)으로 이동.
3. 모달 카운트도 phones 통째 POST·프론트 계산 폐기 → stage 적재 후 count endpoint(같은 헬퍼). count=commit=worker 동일 기준이라 모달=차감=발송 일치.

**교훈**:
- **응답 전 동기로 대량 정제(DELETE/JOIN) 금지** — 타임아웃은 백엔드 에러 안 남고 nginx 504. commit/모달은 즉시 응답, 무거운 작업은 worker 청크.
- **self-join(자기조인 `a.id>b.id`)은 인덱스로도 폭발** — 중복제거는 ctid+ROW_NUMBER 한 패스(O(N log N)).
- **진단은 백엔드 error.log + nginx access/error 둘 다** — 백엔드 완주 시 백엔드 로그엔 안 남는다.
- 대량 정제 카운트(모달)는 프론트 메모리/phones 통째 POST 금지 → staging 서버 COUNT.

## 발송 시각 기준 통일 (D233+ 추가)

### D233+ (2026-06-09) — 발송통계 성공→실패 오분류 + 미도래 예약 대기집계 (등록시각 vs 발송시각)

**사고**: shiseido4·라프레리 발송통계에서 정상 성공 건이 실패로 집계(목록=실패/상세=성공), 미발송 예약이 '대기'로 집계. P1 돈/정산.

- `campaign-lifecycle.ts` 120분 타임아웃이 `sent_at || scheduled_at`(등록 우선) → 예약은 scheduled_at에 발송되는 순간 이미 "120분 초과" → 통신사 결과 몇 초만 늦어도 `pending→실패`로 굳음. 굳으면 `success+fail=target`이라 재sync(`target > success+fail`)에서 **영구 제외**(session6 markFinalized와 같은 뿌리). 상세=MySQL 실시간(성공)·목록·통계=PG 캐시(실패) 불일치.
- 발송통계가 STAT_DATE_EXPR로 묶기만 하고 "발송 시작됨" 가드가 없어 미도래 예약도 집계.

**정정** (backend ~25곳):
- 발송시각 = `COALESCE(scheduled_at, sent_at)`로 타임아웃·markFinalized·sync 윈도우·성과집계 전수 통일(`campaign-lifecycle`·`campaign-sync-worker`·`mysql-refund-sweeper`·`stats-aggregation`). AI/직접 sync에 예약 발송전 제외 가드(`scheduled_at <= NOW`).

**교훈**:

## 타겟 건수 "조회 vs 추출" 불일치 = 데이터 불일치부터 의심 (2026-07-09 추가)

**진짜 근본 (실데이터 확정)**: 차이 4~5명은 `customers.sms_opt_in=true`(동의)인데 `unsubscribes.source='sync'`가 **잔존**한 고객. `source='sync'`는 080/수동 거부가 아니라 **sms_opt_in 파생**이다 — `sync.ts reconcileSyncUnsubscribes`: sms_opt_in=false→sync 등록 / sms_opt_in=true 전환→sync 해제(DELETE, 288-301행 2026-06-15 fix). 인비토는 가상데이터라 sms_opt_in을 sync 밖에서 true로 바꿔 reconcile이 안 돌아 해제 누락 5명. **전 회사 스캔 = 인비토만 5명, 운영 회사 전원 0 = 코드·발송 로직 정상.** 발송(회사+전화 수신거부 제외)이 이 잔존 5명을 빼 660, 조회(user_id)는 664. 즉 **조회 664(동의)가 맞고, 발송이 "해제됐어야 할 sync 수신거부"로 동의 고객을 잘못 제외** — 단 인비토 데이터 한정. 진짜 해결 = 인비토 재sync로 reconcile 자동 해제(둘 다 664).

- **광범위 기준 변경(B17-01 역행 등) 전 = "실제 원인이 이 코드가 맞나"를 데이터로 확정.** 사용자("왜 수정하려 했냐")의 의심이 오판을 차단 — 추측 단정 금지(no_guess) 재확인.

- **현상**: 발송 2h 전 담당자에게 가는 사전 알림 문자의 발신번호가 대표번호(1800-8125)가 아니라 담당자 본인 번호(수신자와 동일). 번호도용차단서비스 가입 담당자는 자기→자기 발송으로 인식돼 아예 미수신(임은지 실측).
- **근본**: `notifyOperatorAdmins`(continuous-operator.ts)가 SMS 큐 row의 call_back을 dest_no와 같은 수신자 phone으로 넣음. 안내는 단방향(회신 불필요)인데 발신=수신이 되어 도용/스팸 차단에 걸림. 동일 패턴이 `journey-pretest-notifier`(여정 2h전)에도 있었음.
- **fix**: `getPlatformNoticeCallback()`(sms-queue CT 신설, `SYSTEM_SMS_CALLBACK||18008125` = internal-alert와 동일 소스) → operator·journey 안내 call_back을 플랫폼 대표번호로. 인비토=특수유형 부가통신사업자라 대표번호는 회신번호 등록 없이 발신 가능. system-alert(슈퍼관리자=우리 내부, "회신 안전" 의도)은 별개로 유지.
- **교훈**: **시스템이 사용자/담당자에게 보내는 단방향 안내 문자의 call_back은 플랫폼 대표번호를 쓴다 — 수신자 번호를 넣으면 발신=수신이 되어 번호도용차단 가입자에게 통째 미수신.** 새 안내/알림 발송 코드 = call_back 소스부터 확인, `getPlatformNoticeCallback` 재사용.
