### 1-3. 교차검증 프로토콜 (Closed 조건)

버그가 "해결됨"이 되려면 반드시 아래 **2단계를 모두 통과**해야 한다.

**1단계 — 코드 검증 (Claude):**
- 수정 코드가 관련 경로 **전부**에 일관 적용되었는지 확인
- 발송 관련이면 5개 경로 전수 점검 매트릭스 필수
- AI 관련이면 한줄로 + 맞춤한줄 양쪽 확인
- TypeScript 타입 체크 통과 근거 제시

**2단계 — 실동작 검증 (Harold님):**
- 실서비스(app.hanjul.ai)에서 점검 방법대로 실행
- 기대 결과와 실제 결과 일치 확인
- 스크린샷/로그 등 증거 확보 (가능한 경우)

**판정:**
- 2단계 모두 통과 → ✅ Closed
- 하나라도 실패 → 🔄 Reopened + 실패 원인 분석 → 재수정

### 1-4. 에러 대응 프로토콜 (신규 버그 발생 시)

1. **증상 기록:** 기대 결과 / 실제 결과 / 재현 절차 / 환경
2. **원인 특정:** 3줄 이내로 근본 원인 요약
3. **해결 옵션:** 2가지 이상 제시 (장단점/리스크/소요) → Harold님 선택
4. **최소 수정:** 선택된 옵션으로 수정 + 관련 경로 전수 점검
5. **교차검증:** 1-3의 2단계 프로토콜 실행

### 🟢 B-0805-1 정산 잠금 규약이 경로마다 갈려 있었다 (🟢 배포완료) — 2026-08-05 (Codex 1R critical + 2R high → 같은 세션 정정)
> **수정 (2026-08-05)**: 뿌리는 **같은 잠금이 7벌로 복제돼 있던 것**이었다 — 발행에만 회사 행 잠금을 더했더니 수동완료·080 두 경로가 옛 축에 남아 "발행은 막았는데 수동완료는 통과"가 성립했다(Codex 재지적). `utils/billing-lock.ts` CT 하나로 합치고 7자리를 전부 그 CT로 바꿨다(인라인 잔존 0 — 불변식 테스트가 감시).
> 잠금은 **두 겹**이다. ①advisory(옛 키 그대로 — 바꾸면 배포 순간 옛 코드가 든 잠금과 키가 달라져 그 창에 진짜 경합이 생긴다) ②회사 행 `FOR NO KEY UPDATE`(`$1::uuid` 캐스트가 표기를 정규화 + 요금제 변경 경로의 `UPDATE companies SET plan_id`와 충돌해 **비로소 직렬화**). `FOR UPDATE`가 아닌 이유 = 자식 INSERT의 `KEY SHARE`까지 막아, 집계를 트랜잭션 안에서 도는 경로(최소과금)의 몇 초가 무관한 쓰기로 전파된다.
> **다건 잠금 순서 — 같은 부류가 세 번 났다.** 교착을 막으려 넣은 정렬을 **내가 손으로 정규화**하고 있었다: 대소문자로 한 번, 중괄호·하이픈 생략으로 또 한 번(Codex가 매 라운드 다음 표기를 냈다). 규칙이 모자란 게 아니라 **PG의 uuid 파서를 흉내내는 접근 자체가 틀렸다** — 규칙을 늘리는 한 다음 표기가 또 나온다. ⇒ 파싱·정규화·정렬을 **전부 PG에 맡긴다**(`JOIN companies c ON c.id = x.raw::uuid ORDER BY c.id`). JS 정렬은 0줄이 됐고 그 부류가 통째로 사라졌다. 실재하지 않는 회사는 조용히 빼지 않고 던진다(잠근 줄 알았는데 안 잠긴 상태가 제일 나쁘다).
> **불수용 1건 기록** — "집계를 트랜잭션 밖으로 빼라"(Codex medium). 그 배치는 Codex 1R에서 수용해 들어간 것이고 되돌리면 그때 닫은 구멍(잠금 밖 판정)이 다시 열린다. 잠금 강도를 낮추는 쪽으로 처리했다.
> **검증**: backend tsc 0 · vitest 140파일 2,050건(`billing-lock.test.ts` 8건 신설 + 불변식) · **신규 SQL `PREPARE` 실검증** · **운영 DB 순서 실측** — 같은 두 회사를 `[소문자, {중괄호}]`와 `[대문자, 역순]`으로 넣어도 잠금 순서가 `01da…→fe9c…`로 동일(교착 축 닫힘 확정). **잔여 = 운영 실측**(발행 중 요금제 변경 시도가 실제로 대기하는지).
>
> #### (원문 — 발견 당시 기록)
> **한 줄**: 두 지적이 **같은 뿌리**다 — 회사 단위 직렬화의 키가 하나가 아니다.
> **(가) 표기 축**: 발행 잠금이 `pg_advisory_xact_lock(hashtext($1::text), hashtext('billing'))`로 **원문 문자열**을 해시한다([billing-issue.ts](../packages/backend/src/utils/billing-issue.ts) 발행 코어·최소과금 공통). 같은 UUID라도 대소문자 표기가 다르면 잠금이 갈려 두 요청이 기간 충돌 검사를 함께 통과할 수 있다.
> **(나) 키 축**: 요금제 이력 쓰기는 `hashtext('plan_change')`([plan-change-log.ts:107](../packages/backend/src/utils/plan-change-log.ts:107)), 발행은 `hashtext('billing')`이라 **서로 직렬화되지 않는다.** 그래서 발행이 요금제 이력 지문을 재대조해도 재조회~COMMIT 사이에 커밋되는 소급 변경은 못 잡는다. 발행 코어(`issueBilling`)도 같은 계약이다 — 최소과금만의 문제가 아니다.
> **불수용 근거 (2026-08-05)**: ①두 줄 다 이번 변경이 만든 것이 아니라 **발행 코어가 공유하는 규약**이다. 최소과금에서만 고치면 두 경로의 키가 갈려 직렬화가 오히려 깨진다. ②최소과금 경로의 `company_id`는 `company_billing_settings` 조회 결과라 **PG가 준 정규 소문자**이고 사용자 입력이 아니다 — (가)의 실현 경로가 없다. ③(나)의 창은 소급(backdated) 이력 변경이 재조회~COMMIT 수 ms 안에 커밋돼야 하고, 최소과금은 **끝난 달만** 발행하며 대상 회사는 사람이 등록한 소수다. ④키를 바꾸면 **배포 순간 진행 중인 트랜잭션과 새 트랜잭션의 잠금 키가 달라진다** — 이론적 결함을 고치려다 배포 창에 실제 경합을 만든다.
> **착수 시**: 잠금 키를 하나로 통일한다(`hashtext(($1::uuid)::text)` + 발행이 `plan_change` 축도 함께 잡거나 축을 합침). `hashtext($1::text)` 전수 grep으로 한 번에, 무발행 시간대 배포. 최종 방어는 `billings`에 회사×기간 exclusion constraint. **plan_id 쓰기 9곳이 딸려오는 별도 과제다.**
